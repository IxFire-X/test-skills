# Быстрый старт

Пайплайн — переносимый набор навыков и инструментов для тестирования проекта. Он читает требования и код, готовит тест-кейсы с действиями и ожидаемыми результатами, затем передаёт их проверяющему в отдельном контексте. По вашему запросу он также создаёт функциональные автотесты, проводит их ревью и запускает средствами проекта.

Работа начинается с обычного запроса в вашей CLI — программе, через которую вы работаете с моделью. Вы указываете, что проверить и какой результат получить; последовательность этапов и технические команды выполняет оркестратор. На выходе — читаемые кейсы, отчёты ревью и, если вы запросили выполнение, результаты тестов. Неоднозначные требования или недостающие условия он выносит на уточнение.

Для первого запуска достаточно этой страницы. [Посмотреть готовый результат: 64 тест-кейса Spring Petclinic](docs/examples/petclinic-owner-lifecycle/cases.md).

## 1. Что подготовить

- **Рабочую папку проекта** с исходниками и требованиями в одном или нескольких документах, например `docs/feature.md`, либо в спецификациях OpenSpec. Можно запросить проверку всей актуальной спецификации или выбранного изменения вместе с поведением, которое оно затрагивает.
- **Совместимую CLI с настроенной моделью**, которая умеет читать и создавать файлы, выполнять команды и вызывать проверяющего в отдельном контексте. Откройте в ней рабочую папку проекта; провайдер и модель выбираются в настройках CLI.
- **Python 3.11, 3.12 или 3.13** для инструментов пакета. Он нужен и для работы с Java-проектом.
- **Для запуска автотестов** — уже подготовленную тестовую среду проекта: Java/JUnit 5 с Maven Wrapper, системным Maven или Gradle Wrapper либо Python с pytest. Системный Maven должен быть доступен как `mvn` в PATH. Зависимости проекта и доступ к нужным тестовым ресурсам должны быть настроены заранее.

## 2. Один раз подключить пакет

Установите пакет из ветки **`main`**. Откройте терминал **в корне рабочего проекта** и выполните:

```text
git clone --branch main --single-branch https://github.com/IxFire-X/test-skills.git .tools/test-skills
python -m venv .tools/test-skills/.venv
```

Вместо Git можно скачать [ZIP ветки main](https://github.com/IxFire-X/test-skills/archive/refs/heads/main.zip) и распаковать содержимое папки пакета в `.tools/test-skills`. После распаковки должен существовать файл `.tools/test-skills/skills/orchestrate/SKILL.md`; затем выполните команду создания `.venv` выше. Если `python` не находится, используйте путь к установленному Python 3.11–3.13.

Установите зависимости пакета в созданное окружение. Выберите команду для своей ОС; терминал по-прежнему должен быть в корне проекта.

**Windows / PowerShell:**

```powershell
.\.tools\test-skills\.venv\Scripts\python.exe -m pip install -r .tools\test-skills\requirements.txt
```

**Linux:**

```bash
.tools/test-skills/.venv/bin/python -m pip install -r .tools/test-skills/requirements.txt
```

В рабочей сети используйте разрешённый в компании источник Python-пакетов. Это окружение обслуживает инструменты пайплайна; автотесты используют среду самого проекта.

## 3. Дать модели один из двух запросов

Вставьте выбранный запрос в CLI, где открыт проект. Замените `<область требований>` на пути к документам, всю актуальную спецификацию OpenSpec либо имя выбранного change со связанной регрессией. Профиль и команды запуска Python указывать не нужно: контроллер определит их по запросу и проекту. Если пакет находится в другой папке, укажите фактический путь к его `skills/orchestrate/SKILL.md`.

### Вариант А: получить тест-кейсы

```text
Выполни .tools/test-skills/skills/orchestrate/SKILL.md.
Подготовь и независимо проверь тест-кейсы для <область требований> в этом проекте. Не создавай и не запускай автотесты.
```

Этот режим создаёт и проверяет кейсы. Автотесты не создаются, код проекта не запускается.

### Вариант Б: получить кейсы и запустить автотесты

```text
Выполни .tools/test-skills/skills/orchestrate/SKILL.md.
Подготовь и независимо проверь тест-кейсы для <область требований> в этом проекте. Создай функциональные автотесты, проведи их ревью и запусти прошедшие ревью тесты средствами проекта. Разрешаю такое выполнение только в рамках этого запуска.
```

Первый запуск определит настройки проекта и при необходимости создаст `.skillsrc`. Если в проекте несколько модулей или настройки неоднозначны, модель попросит уточнение. Для одного запуска выбирается один модуль.

### Что происходит после запроса

Оркестратор ведёт запуск через драйвер `tools.pipeline_driver`. Драйвер сам выполняет все шаги, где не нужна модель, и выдаёт ей по одной задаче: подготовить контекст, написать кейсы, проверить часть ревью, написать автотесты. Модель отвечает на задачу и возвращает ответ драйверу; так повторяется до итогового результата или до вопроса к вам. Вводить эти команды вручную не нужно. Для справки, первый вызов выглядит так (из папки пакета; `$project` — абсолютный путь проекта):

```powershell
python -m tools.pipeline_driver next --project "$project" --profile cases-only-v1 `
  --docs docs/feature.md --subject "Название документа"
```

Драйвер может задать вам два вопроса. Первый — умеет ли ваша CLI выполнять каждую часть ревью в отдельном свежем контексте; если нет, запуск останавливается, а кейсы остаются непроверенными (`UNREVIEWED`). Второй — в варианте Б, если созданные тесты не прошли компиляцию или сбор: создать одну новую попытку или завершить.

Драйвер покрыт тестами пакета, но пока не проверен на Windows и на живой модели.

## 4. Открыть результат

Начните с **HTML или Markdown выбранной проверяющим редакции**. Там находятся цель, предусловия, шаги, данные и ожидаемые результаты каждого кейса.

Материалы сохраняются в папке `.pilot-runs/<run_id>/` внутри проекта. `run_id` — идентификатор запуска; полный путь должен быть в ответе модели. Файлы появляются по мере прохождения этапов: при ранней остановке часть из них ещё не создана.

| Что получаем | Для чего открывать |
| --- | --- |
| `<document_id>.r<revision>.html` | Читать кейсы в браузере в виде таблиц |
| `<document_id>.r<revision>.md` | Читать и обсуждать те же кейсы в редакторе или на GitHub |
| `<document_id>.r<revision>.json` | Сохранить исходный документ со связями с требованиями и данными для автоматизации |
| `<document_id>.r<revision>.zephyr-scale.csv` | Использовать выгрузку кейсов для Zephyr при совместимых настройках импорта |
| Отчёт ревью | Понять, приняты ли кейсы и что проверяющий потребовал исправить |
| Код автотестов и отчёт исполнения | В варианте Б — увидеть реальные проверки и их результаты, если эти этапы выполнены |
| `terminal-results/<attempt_id>.json` внутри папки запуска | Посмотреть окончательный статус завершённой попытки |

При успешном полном запуске принятые автотесты сохраняются в тестовой папке проекта. При `FAIL` или `NOT_RUNNABLE` пайплайн убирает свои неизменённые созданные файлы из проекта, сохраняя свидетельства и исходный код проверки в материалах запуска. Пустые каталоги, созданные под эти файлы, и отчёт `test-results/pytest.xml` могут остаться. При `UNKNOWN` созданные файлы сохраняются. Их фактическую судьбу смотрите в итоговом ответе.

## 5. Понять, чем всё закончилось

**Для варианта А сначала читайте вердикт ревью кейсов.** Значения `verification=NOT_APPLICABLE`, `accepted=false` и код завершения `1` ожидаемы для этого режима: они означают, что полного подтверждения через исполнение автотестов нет. Сами по себе они не означают, что ревью отвергло кейсы.

**Для варианта Б полный принятый результат имеет `accepted=true` и `verification=PASS`.** Другие результаты требуют внимания:

| Что видим | Как понимать |
| --- | --- |
| `FAIL` | Проверки завершились с неуспехом. Откройте причину и отчёт: нужно установить, проблема в приложении, тесте или сборке |
| `UNKNOWN` | Надёжного результата исполнения нет. Сначала выясните причину и состояние предыдущего процесса |
| `NOT_RUNNABLE` | Выполнение невозможно при текущих условиях; в отчёте должна быть причина. `GENERATED_TEST_INVALID` — созданный тест не компилируется или не импортируется: его можно один раз сгенерировать заново в новой попытке. `LAUNCH_FAILED` — тестовый процесс не запустился. `TESTS_DESELECTED` — настройки pytest проекта исключили выбранные тесты; файлы тестов при этом остаются |
| `AUTOMATION_REVIEW_REJECTED`, `AUTOMATION_REVISION_BUDGET`, `AUTOMATION_REVIEW_CONTEXT_LIMIT`, `AUTOMATION_REVIEW_TRANSPORT_FAILED`, `AUTOMATION_REVIEW_INCOMPLETE` | Статическое ревью не приняло автотесты. Файлы тестов в проект не записаны, запуска не было |
| `REVIEW_INCOMPLETE` | Ревью кейсов прервано: часть областей осталась непроверенной. Кейсы не приняты, запуска не было |
| `REVIEWER_ISOLATION_UNAVAILABLE` | У CLI нет отдельного свежего контекста для ревью. Запуск остановлен, кейсы остались непроверенными |
| `WAITING_FOR_INPUT` | Нужен ваш ответ на конкретное уточнение |
| `WAITING_FOR_MODEL` | Нужно продолжить работу через программу с моделью; это ещё не завершённый результат |

`COMPLETE` означает завершение процесса и может стоять рядом с `FAIL`. `FULL` относится к покрытию выбранного набора кейсов, а не к проверке всего приложения.

Если после перерыва непонятно, где остановилась работа, дайте модели путь к папке запуска и попросите:

```text
Прочитай сохранённое состояние этого запуска. Покажи, какие этапы
завершены, какой следующий шаг требуется и где лежат готовые файлы.
Пока ничего не запускай повторно.
```

Чтобы продолжить прерванный запуск, попросите модель вызвать `next` драйвера с `--run <run_id>`: драйвер вернёт ту же незакрытую задачу или продолжит с последнего подтверждённого шага.

Для изменения кейсов передайте модели замечания и попросите подготовить новую попытку. Сохранённые файлы прошлой попытки оставьте как историю результата.

Подробности для настройки и разбора нестандартных ситуаций: [USAGE.md](USAGE.md). Устройство пакета и назначение файлов: [справочник](docs/pipeline-file-guide-ru.md).
