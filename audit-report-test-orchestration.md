## 1. Краткое введение

Задача понята: провести строгий аудит 4 скиллов тестового пайплайна (`tc-generator`, `tc-reviewer`, `tc-to-autotest`, `autotest-reviewer`) и Оркестратора (`orchestrate`) **без внесения изменений**. Аудит охватывает:

- Общий анализ (мусор, нехватки, архитектурная целостность) — только в этих компонентах.
- Детальную оценку каждого по 5 параметрам (10-балльная шкала) с явными CoT-рассуждениями.
- Сравнение с мировыми практиками: **Anthropic Agent Skills** (progressive disclosure), **OpenAI** (single-task skills, чёткие входы/выходы, оркестрация через рутины), **DeepSeek/Qwen** (JSON Schema для параметров, управление контекстом), **Google Gemini Agent Designer** (достаточный контекст, границы возможностей, уточняющие вопросы), **Z.ai** (Plan Before Execution, агент как настраиваемый коллега).
- Сводную таблицу оценок и итоговые рекомендации.

**Контекст проекта:** мультиагентная система «Скиллы для работы» — набор AI-скиллов для генерации тест-кейсов и документации из аналитики/кода, управляемых Оркестратором. Целевой проект — `subscription-renewal-service` (Java, Spring Boot, Maven, JUnit 5). Все 5 пайплайнов описаны в `PIPELINE.md`.

### 2.2 Чего не хватает

**Рассуждение (CoT):** Проверяю каждый компонент на наличие критических элементов: обработчики ошибок, логирование, валидация входных данных, тесты (на сами скиллы), документация.

**Ключевые нехватки (только в указанных компонентах):**

1. **Отсутствие тестов на сами скиллы:** Ни один из 4 скиллов и Оркестратор не имеет unit-тестов или интеграционных тестов, проверяющих корректность их собственной логики. Это **критический пробел** для системы, которая сама генерирует тесты. Сравнивая с практикой **OpenAI** («каждый скилл должен иметь чётко определённые входные и выходные данные»), отсутствие тестов означает, что контракты входа/выхода не верифицируются автоматически.

2. **Отсутствие версионирования API между скиллами в рантайме:** Версионирование описано декларативно (версии в заголовках SKILL.md, таблица в PIPELINE.md), но Оркестратор не проверяет совместимость версий при диспетчеризации. Согласно **Anthropic Agent Skills**, метаданные должны включать версию для предотвращения несовместимости.

3. **Отсутствие timeout-конфигурации на уровне скиллов:** `CONTRACTS.md` §6 упоминает `step_timeout` как «рекомендацию хосту», но ни один SKILL.md не определяет конкретные таймауты. Это противоречит практике **Google Gemini Agent Designer** — «устанавливай границы того, что скилл может и не может делать».

4. **Отсутствие circuit breaker / retry с экспоненциальной задержкой:** В `CONTRACTS.md` §6 retry описан как «рекомендация LLM перезапустить шаг; 1–2 попытки». Это недостаточно для production-системы. Нет упоминания exponential backoff, jitter, max retry limit с метриками.

5. **Отсутствие наблюдаемости (observability) на уровне оркестрации:** Оркестратор пишет отчёт (`orchestration-report-<TS>.md`), но не имеет:
   - Сбора метрик (длительность шагов, количество retry, процент успешных/неуспешных запусков).
   - Трассировки (trace ID, связывающий все шаги одного запуска).
   - Алертинга при критических сбоях.
   Это расходится с практикой **Z.ai** («планируй перед выполнением, измеряй после») и общим принципом observability-first в распределённых системах.

6. **Отсутствие валидации JSON Schema на входе в рантайме (для всех скиллов кроме v3.0+ с `<output_format>json</output_format>`):** JSON-схемы созданы (`schemas/*.json`), но валидация через `schema-validator.md` описана только для **выходного** JSON при флаге `<output_format>json</output_format>`. **Входные** данные (Markdown в CDATA) не валидируются структурно. Это противоречит подходу **DeepSeek/Qwen** («чёткая структура инструментов с JSON Schema для определения параметров»).

7. **Отсутствие документации по деплою и конфигурации скиллов:** `Instruction.md` описывает ручную загрузку `SKILL.md` в AI-ассистент. Нет описания автоматического деплоя, CI/CD-интеграции, версионирования в реестре скиллов.

### 2.3 Архитектурная целостность

**Рассуждение (CoT):** Проверяю связность между 5 компонентами: согласованность протоколов обмена (XML-теги), единообразие стиля SKILL.md, корректность цепочки вызовов.

**Сильные стороны:**

1. **Единый канон контрактов (`CONTRACTS.md`):** Это сильное архитектурное решение. Все скиллы ссылаются на единый источник истины для имён тегов и статус-маркеров. Соответствует практике **Anthropic** — «единый источник метаданных».

2. **Согласованная структура SKILL.md:** Все 5 SKILL.md следуют единому шаблону: YAML-заголовок → «Когда применять» → «Место в пайплайне» → «Контракт входа/выхода» → «Определение режима работы» → «Роль» → «Алгоритм» → «Формат вывода» → «Финальная проверка». Это делает систему предсказуемой для LLM.

3. **Чёткая цепочка контрактов в тестовом пайплайне:**
   ```
   tc-generator → <generated_test_cases> → tc-reviewer → <corrected_test_cases> / <test_cases> → tc-to-autotest → <automation_matrix> + код → autotest-reviewer → <autotest_review>
   ```
   Каждый переход документирован, имена тегов не пересекаются.

4. **Progressive Disclosure в `.skillsrc`:** Реестр `skills_registry` с полями `name`, `description`, `tags`, `input_contract`, `output_contract` — прямая реализация подхода **Anthropic Agent Skills** (L1-метаданные для первичного отбора).

**Проблемы архитектурной целостности:**

1. **Дублирование между `CONTRACTS.md` и `tag-registry.md`:** Оба файла описывают реестр тегов и статус-маркеров. `tag-registry.md` позиционируется как «Central source of truth», но `CONTRACTS.md` также заявляет себя «единственным источником истины». Это архитектурный конфликт: два источника правды для одной и той же информации.
   - **Пример:** `CONTRACTS.md` §2 определяет 13 выходных блоков; `tag-registry.md` §2–4 определяет те же блоки, но с другой группировкой.
   - **Риск:** при изменении тега в одном файле, но не в другом — рассинхрон.

2. **Расхождение в версиях между SKILL.md заголовками и PIPELINE.md:**
   - `tc-generator`: SKILL.md говорит `version: 2.3`, PIPELINE.md говорит `v2.4`.
   - `tc-reviewer`: SKILL.md говорит `version: 2.1`, PIPELINE.md говорит `v2.2`.
   - `tc-to-autotest`: SKILL.md говорит `version: 3.2`, PIPELINE.md говорит `v3.1`.
   - `autotest-reviewer`: SKILL.md говорит `version: 1.3` (предположительно, нужно проверить), PIPELINE.md говорит `v1.2`.
   - **Риск:** Оркестратор, полагающийся на версии из метаданных, может принять неверное решение о совместимости.

3. **Несогласованность имён папок в `Instruction.md` vs реальной структуре:**
   - `Instruction.md` показывает структуру `Скиллы для работы/`, но реальный проект находится в `test-orchestration-skills/`. Это не критично для функциональности, но сбивает с толку при настройке.

4. **Отсутствие формального контракта на уровне Оркестратор ↔ Скилл:**
   - Оркестратор описан как диспетчер Sub-Agent'ов, но протокол вызова скилла (REST? gRPC? прямая передача контекста?) не специфицирован. Согласно **OpenAI** («оркестрация через рутины и передачу управления»), протокол должен быть явным.
   - В `Оркестратор/SKILL.md` есть упоминание «Sub-Agent диспетчеризация» и «изоляция контекста», но нет деталей: как именно Оркестратор «вызывает» скилл (передаёт ли он `SKILL.md` как system prompt? отправляет ли REST-запрос?).

**Вердикт по архитектурной целостности:** ⭐ **7/10** — сильный канон контрактов и единообразие SKILL.md компенсируются дублированием источников правды и расхождением версий.

## 3. Детальный разбор каждого компонента с CoT и сравнением с мировыми практиками

### 3.1 Скилл: tc-generator (Ручные тест-кейсы)

**Файл:** `test-orchestration-skills/Ручные тест-кейсы/SKILL.md` (380 строк, v2.3)

#### 3.1.1 Отсутствие багов и косяков

**CoT-рассуждение:** Проверяю логику определения режима, pre-validation, алгоритм анализа, формат вывода, финальный чеклист.

**Наблюдения:**
- ✅ **Строка 62–71 (определение режима):** Чёткая логика: если `<analytics_documentation>` заполнен → Режим B, иначе → Режим A. Запрет галлюцинаций при пустых тегах явный.
- ✅ **Строка 85–123 (Pre-validation):** Алгоритм сверки с фактическим кодом детально проработан. Таблица «Правила разрешения конфликтов» (стр. 127–133) логична: endpoint'ы/статусы → код, бизнес-правила → аналитика.
- ⚠️ **Строка 231 (лимит ТК):** «Целевое количество ТК на одну фичу/endpoint: до 25… допускается расширение до 35 ТК». Логика расширения описана, но **нет явного MAX-лимита для случая «сложный процесс с 4 состояниями и 4 ролями»**. Потенциально 4 состояния × 4 роли = 16 комбинаций только на ролевую модель. Если добавить Happy Path (1), валидацию (~5), негатив (~3), observability (~3) = 28. Это в пределах 35, но близко к пределу.
- ✅ **Строка 350–361 (финальная проверка):** Чеклист из 12 пунктов покрывает ключевые аспекты.
- ⚠️ **Баг в нумерации чеклиста:** Строка 362 говорит «Количество ТК на observability ≤ 3», но это дублирует пункт 10 (стр. 360). Не критично, но несогласованность.

**Оценка:** ⭐ **8/10**

#### 3.1.2 Логическая полнота

**CoT-рассуждение:** Проверяю, все ли сценарии покрыты: что если код содержит endpoint'ы, не описанные в аналитике? что если аналитика противоречит сама себе?

**Наблюдения:**
- ✅ **Pre-validation (стр. 75–123):** Покрывает случай расхождения аналитики и кода. Решение «код > аналитика для endpoint'ов, аналитика > код для бизнес-правил» — зрелое.
- ✅ **Обработка отсутствующих источников (стр. 156–160):** Если источник недоступен — генерация продолжается с маркером `⚠`.
- ⚠️ **Пропущен сценарий:** Что если `<analytics_documentation>` содержит **противоречивые** требования (например, AC-1 требует `amount ∈ [1, 1000]`, а AC-2 в том же документе говорит `amount ∈ [1, 500]`)? Скилл не описывает, как разрешать внутренние противоречия аналитики.
- ✅ **Режим A (стр. 137–177):** Детально проработан: запрос → блокировка → сбор → фиксация → генерация.
- ⚠️ **Пропущен сценарий частичного предоставления кода:** Если в `<source_code_and_diff>` передан только один класс из нескольких, затронутых фичей — скилл должен предупредить, что сверка неполная. Сейчас просто «если код есть — сверяем».

**Оценка:** ⭐ **8/10**

#### 3.1.3 Функциональность

**CoT-рассуждение:** Соответствует ли скилл заявленным требованиям? Генерирует ли он детерминированные ТК высокого уровня технической точности? Правильно ли интегрируется с `tc-reviewer`?

**Наблюдения:**
- ✅ **Заявленная цель (стр. 4–5):** «Генератор детерминированных ручных тест-кейсов высокого уровня технической точности». Скилл полностью этому соответствует: требует технические имена из кода, запрещает фразы-заглушки, обеспечивает детерминированность ожидаемых результатов.
- ✅ **Интеграция с tc-reviewer (стр. 27–34):** Контракт выхода чётко определён: `<generated_test_cases>` в Zephyr Markdown внутри CDATA. Это именно то, что ожидает `tc-reviewer` на входе.
- ✅ **Интеграция с Оркестратором (стр. 40–42):** Поддержка `<output_format>json</output_format>` для машиночитаемого вывода — продвинутая функциональность.
- ✅ **Иерархия источников (стр. 184–192):** Чёткое разделение: аналитика = источник сценариев, код = технический справочник.

**Оценка:** ⭐ **9/10**

#### 3.1.4 Использование передовых технологий

**CoT-рассуждение:** Проверяю: асинхронность, стриминг, кеширование, observability, паттерны мультиагентных систем.

**Наблюдения:**
- ✅ **Машиночитаемый вывод (JSON Schema, v3.0+):** Опциональный JSON-выход по JSON Schema — сильное решение. Соответствует подходу **DeepSeek/Qwen** (JSON Schema для чёткой структуры параметров).
- ✅ **Pre-validation с Super-Conflicts:** Алгоритм сверки аналитики и кода с таблицей приоритетов — это паттерн «источник правды с разрешением конфликтов», соответствующий принципу **Google Gemini** («предоставляй достаточно контекста для устранения неоднозначности»).
- ⚠️ **Отсутствие стриминга:** Скилл не поддерживает потоковую генерацию ТК (все ТК генерируются за один проход). Для больших фич это может привести к таймаутам LLM. **OpenAI** рекомендует разбивать большие задачи на чанки.
- ⚠️ **Отсутствие кеширования:** При повторном запуске с теми же входными данными скилл перегенерирует ТК заново. Нет механизма детерминированного кеша (хотя `tc-to-autotest` имеет `<automation_matrix>` для инкрементальной генерации).
- ✅ **Изоляция контекста (стр. 34):** «Этот скилл не знает о результатах последующих скиллов» — правильный принцип для микросервисной архитектуры агентов.

**Оценка:** ⭐ **7/10**

#### 3.1.5 Качество межскиллового взаимодействия

**CoT-рассуждение:** Проверяю корректность вызовов, обработку таймаутов, версионирование API, обработку ошибок при взаимодействии с `tc-reviewer` и Оркестратором.

**Наблюдения:**
- ✅ **Контракт выхода (стр. 27–34):** Чётко определён: `<generated_test_cases>` + `<analytics_documentation>` + `<source_code_and_diff>` → `tc-reviewer`.
- ✅ **Запрет переименования тегов (стр. 374):** «Никогда не переименовывай `<generated_test_cases>` в `<test_cases>` или `<corrected_test_cases>` внутри этого скилла». Это предотвращает контрактные ошибки в пайплайне.
- ⚠️ **Нет обработки таймаутов:** Скилл не определяет, что делать, если LLM не успевает сгенерировать все ТК за один вызов.
- ⚠️ **Нет версионирования контракта в рантайме:** Версия скилла (`2.3`) указана в YAML-заголовке, но не включена в выходные теги. `tc-reviewer` не может проверить, что принимает ТК от совместимой версии `tc-generator`.

**Оценка:** ⭐ **7/10**
