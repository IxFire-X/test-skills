# Использование portable pilot

Для первого запуска откройте **[QUICKSTART.md](QUICKSTART.md)**: там есть подготовка окружения, готовые запросы и список результатов. Ниже — подробные правила настройки и выполнения.

## 1. Подключите пакет

Поместите папку пакета в обычный рабочий проект, сохранив `contracts/`, `schemas/`,
`skills/`, `tools/`, `release/` и `ts.py`. Проект уже должен иметь рабочие JDK/Maven,
Gradle или Python/pytest environment. Пакет сам не ставит ни Python-пакеты, ни JDK, ни
сборщики. Сборку и тесты проекта по командам драйвера запускает человек (раздел 8); она
может скачивать зависимости и плагины в `~/.m2` / кэш Gradle, а с `--mutation` Maven
скачивает PIT — см. раздел «Права, сеть и исполнение».

Пакет поставляется хост-сборкой: список её файлов печатает
`python -m tools.release_manifest --list host --commit <коммит>` (комплект делает
`git archive` этого списка), `python -m tools.doctor --root <пакет>` сообщает профиль копии
(`delivery_profile: host`). В ней нет запуска сборки и тестов пакетом и запуска CLI модели
драйвером; универсальная сборка (репозиторий пакета) с ними описана в `docs/process-mode.md`
этого репозитория.

Удобное место — `<project>/.tools/test-skills/` (или каталог навыков CLI, например
`<project>/.gigacode/skills/test-skills/`: каталоги агентов CLI пакет не считает кодом
проекта). Все пути пакета разрешаются от этой папки. Команды драйвера запускайте
пускателем `<python> <пакет>/ts.py next|submit|status|answer|doctor …` из любого каталога,
с абсолютным `--project`; остальные `python -m tools...` — с cwd пакета, так модуль `tools`
целевого проекта не подменит инструменты пакета. Сами автотесты запускаются из выбранного
module root.

Копия внутри дерева проекта попадает под проверки его сборки: Petclinic проверяет
`nohttp` на фазе `validate` и находил `http://` в фикстурах `tests/` пакета и в
`docs/*.pptx` (живой прогон 2026-10-08). Поэтому ставьте копию без них —
sparse checkout — или вне дерева проекта (тогда `--project` указывает на проект, а
пакет запускается из своего каталога):

```bash
git clone --no-checkout <url пакета> .tools/test-skills
cd .tools/test-skills
printf '%s\n' '/*' '!/tests/' '!/docs/*.pptx' '!/CLAUDE.md' '!/.github/' '!/.claude/' | MSYS_NO_PATHCONV=1 git sparse-checkout set --no-cone --stdin
git checkout <коммит>
```

В Git Bash на Windows шаблоны передаются только через `--stdin` и с
`MSYS_NO_PATHCONV=1`: аргумент `/tests/` в командной строке MSYS превращает в путь
Windows, и шаблон молча перестаёт исключать каталог. Проверка: `git sparse-checkout list`
показывает шесть шаблонов как есть, а каталога `tests/` в копии нет (`git ls-files` его
по-прежнему перечисляет — файлы лишь не выложены в рабочее дерево). `CLAUDE.md`, `.github/`
и `.claude/` — файлы разработки самого пакета (инструкция агенту, CI репозитория пакета):
в дереве проекта агент мог бы принять их за инструкции проекта, поэтому в копию они не
попадают.

Нормативная точка входа — явный запрос model-enabled CLI выполнить
`skills/orchestrate/SKILL.md`. Ход запуска ведёт драйвер `tools.pipeline_driver`
(раздел 4): он выполняет детерминированные шаги и выдаёт модели по одной задаче. Задачи
решает сессия CLI, которая ведёт запуск (каждую — свежим субагентом); пакет CLI модели не
запускает. Учётных данных модели пакет не хранит и не читает: CLI пользуется своей
конфигурацией.

Пример запроса CLI:

```text
Выполни .tools/test-skills/skills/orchestrate/SKILL.md. Подготовь и независимо проверь тест-кейсы
для <область требований> в этом проекте. Создай функциональные автотесты, проведи их ревью и
запусти прошедшие ревью тесты средствами проекта. Разрешаю такое выполнение
только в рамках этого запуска.
```

В примере пакет находится в `.tools/test-skills`; при другом расположении замените
путь. Для тест-кейсов достаточно попросить подготовить и проверить кейсы: такой запрос
не разрешает запуск кода. Профили — внутренняя деталь; controller выводит применимый
профиль из запроса и состояния проекта.

## Права, сеть и исполнение

Манифест прав пакета: что он делает на машине при обычном запуске и при каких флагах
появляется остальное. Пути — относительно проекта, если не сказано иное.

**Читает.** Файлы модуля проекта по inventory (`git ls-files`, раздел 2), выбранные
документы требований, `.skillsrc`; переменную `JAVA_HOME` (для PIT); jar-файлы PIT в
`~/.m2` по путям, которые сообщил Maven (только с `--mutation`, для сверки SHA-256).

**Пишет.** `.pilot-runs/` (журнал, квитанции, отчёты), сгенерированные тесты — только в
тестовый корень выбранного модуля и только файлы с именем теста (`*Test.java`,
`*Tests.java`, `*IT.java`, `test_*.py`, `*_test.py`), `test-cases/` (проекции и манифест
набора), `.skillsrc` (создаётся при первом запуске, если его нет; замена существующего —
только с подтверждением). Сборка проекта, которую запускает человек, пишет туда же, куда
обычно: `target/`/`build/`, `~/.m2`, кэш Gradle.

**Запускает.** Только локальный `git` (`ls-files`, `status`, `diff` диапазона
`suite impact --git-range`; проверка владельца репозитория `safe.directory` не отключается),
списком аргументов, без оболочки. Сборку, компиляцию, гейт и прогон тестов, мутации и прогон
живого набора пакет не запускает (`execution.mode: human`, раздел 8): драйвер печатает
закрытые команды — обёртку сборки проекта (`mvnw`/`gradlew`), системный `mvn` или Python
модуля с pytest; с Gradle — init-скрипт пакета `tools/gradle/selected-symbols.init.gradle`
(отключает только проверку покрытия JaCoCo для выбранного подмножества); с `--mutation` —
Maven (резолвер classpath) и `java` с PIT, — а выполняет их человек в своём окружении. CLI
модели пакет не запускает: модель вызывает ведущая сессия CLI по команде человека.
Драйвер запускает агент этой сессии командой `<python> <пакет>/ts.py …`, которую человек
подтверждает в CLI.

**Сеть.** В коде пакета нет сетевых вызовов, и пакет не запускает процессов, которые ходят в
сеть (только локальный git). Сеть возможна только в действиях человека и ведущей сессии CLI:

- сборка проекта — её запускает человек по командам драйвера; Maven/Gradle разрешают
  зависимости и плагины из репозиториев `~/.m2/settings.xml` / настроек Gradle, если их нет в
  локальном кэше; с `test.offline: true` модуля (раздел 3) — только из локального кэша
  (`-o` / `--offline`), сеть не используется;
- `--mutation` — команды резолвера и PIT запускает человек; Maven скачивает PIT и его
  зависимости (SHA-256 закреплены в `tools/mutation_tools.json`, пакет сверяет их после
  разрешения); плагин-резолвер
  `maven-dependency-plugin` и `junit-platform-launcher` версии проекта должны уже лежать в
  `~/.m2/repository` (плагин сверяется по закреплённому SHA-256) — иначе этап
  останавливается до запуска Maven; с `test.offline: true` и PIT разрешается offline.
  Путь к локальному репозиторию из `settings.xml` (`localRepository`) пакет не читает: проверяется
  только `~/.m2/repository`;
- установка зависимостей пакета — только командой человека
  `pip install --require-hashes -r requirements.txt` (хеши всех файлов в `requirements.txt`);
- ведущая сессия CLI — её агент читает входы задач (подтверждённые человеком файлы:
  `confirm-context`, раздел 4) и обращается к модели из конфигурации CLI; пакет ничего не
  отправляет. В модель уходят выбранные файлы проекта, требования, кейсы и тесты
  (маскирование секретов — раздел 2, по шаблонам, не гарантия);
- сгенерированные тесты запускает человек; они исполняют то, что в них написано, в
  окружении сборки проекта.

Экспорт в Zephyr и OpenSpec — локальные файлы и stdout; переносит их человек.

## 2. Что указать

Обязательно:

- область требований: один или несколько документов, все актуальные OpenSpec specs
  либо выбранный change со связанной регрессией;
- открытый рабочий проект в совместимой model-enabled CLI.

Controller определяет project root, требования, модуль, Python для инструментов и
проектные настройки по доступным данным. При реальной неоднозначности или недостающем
обязательном входе он задаёт уточняющий вопрос и переходит в `WAITING_FOR_INPUT`.
Факты, которые можно прочитать из проекта, controller устанавливает сам.

`--target` или allowlist могут сузить read-only inventory. `.git`, dependencies,
build outputs, binaries, generated artifacts и потенциальные secrets не передаются
модели. Inventory учитывает `.gitignore` (`git ls-files -co --exclude-standard`; если
git недоступен — обычный обход файлов). По умолчанию также исключены `.gradle`,
`.kotlin`, `.idea`, `.vscode`, отчёты `coverage*` и `*.log`; каталоги `build`,
`generated` и `coverage` с исходным кодом остаются.

По имени как секреты исключаются только `.env*`, `*.pem`, `*.key`, `*.p12`, `*.pfx`,
`*.kdbx`, `id_*` и каталоги `secrets/`, `credentials/`; а также хранилища учётных данных
CLI, где бы они ни лежали в проекте: каталоги `.ssh`, `.aws`, `.kube`, `.gnupg`, `.docker`,
`.azure`, `.gcloud`, `.config/gh`, `.config/gcloud`, `.config/hub` и файлы `.netrc`,
`_netrc`, `.pgpass`, `.git-credentials`, `.npmrc`, `.pypirc`, `.dockercfg`, `kubeconfig`
(`credential-directory-v1`, `credential-file-v1`). Это исключение из inventory — значит из
контекста модели; на диске файлы остаются, и сборка их видит как обычно; хранилища
учётных данных не считаются входом исполнения и не делают прогон `NOT_RUNNABLE`.
Бинарные файлы (в том числе `*.jks`, `*.keystore` тестовых ресурсов) в контекст не
попадают как `BINARY_OR_GENERATED` и тоже остаются входом сборки. Все пути, исключённые как
секреты, с правилом перечислены в листинге подтверждения отправки (`context-files.txt`,
строки `исключено`). По содержимому — сигнатуры
токенов, PEM-блок приватного ключа, присваивание строкового литерала от 16 символов и
`aws_secret_access_key` с 40-символьным значением без кавычек.
Файл кода или настроек с совпадением исключается целиком; если он необходим, дайте
sanitized source, safe fixture или opaque runtime handle. В документах и спецификациях
совпавшие строки заменяются на `[REDACTED:<rule>]`, файл остаётся входом, а номера
замаскированных строк записываются в inventory в поле `redactions`. Документы требований
(`--docs`) так же замаскированы для всех ролей — разметки, генератора и ревьюеров; дайджест
источника в снимке ревью остаётся дайджестом исходного файла, а у замаскированного источника
есть `redactions`, и журнал проверяет маску по исходнику. Файл с именем секрета (`.env*`,
`*.pem`, `*.key`, `.netrc`, хранилища учётных данных) документом требований быть не может:
`scan` отказывает `SNAPSHOT_DOCS`.

Файл, который не помещается в бюджет контекста, пропускается явно: он попадает в `gaps`
квитанции выбора контекста и в `context_gaps` ответа `scan`.

## 3. `.skillsrc`

Linux и Windows используют один пайплайн и project-native адаптеры:

| Runtime | Имя в `.skillsrc` | Linux | Windows |
|---|---|---|---|
| Python / pytest | `python` | `.venv/bin/python` | `.venv/Scripts/python.exe` |
| Maven Wrapper / JUnit 5 | `mvnw` | `mvnw` | `mvnw.cmd` |
| Системный Maven / JUnit 5 | `mvn` | `mvn` в PATH | `mvn.cmd` в PATH |
| Gradle / JUnit 5 | `gradlew` | `gradlew` | `gradlew.bat` |

`.skillsrc` хранит логическое имя, а путь под текущую ОС разрешается при запуске; для
`python` сначала проверяется `.venv`, затем `venv` модуля. Старые файлы с путями
конкретной ОС читаются как раньше. Необязательные поля раздела `test`:
`timeout_seconds` — таймаут тестового процесса от 1 до 86400 секунд (по умолчанию 600);
`build_root` — корень сборки многомодульного Maven/Gradle-проекта относительно проекта
(по умолчанию module root); `offline: true` (Maven и Gradle) — все команды сборки модуля,
гейта, прогона набора и этапа мутаций идут с `-o` / `--offline`: зависимости берутся только из
локального репозитория, а отсутствующий артефакт останавливает прогон с
`BUILD_FAILED_BEFORE_TESTS` («offline: артефакт не найден в локальном репозитории», перегенерация
тестов не нужна) или `MUTATION_TOOL_MISSING`; что сборка шла offline, видно по argv в квитанции
исполнения и по `execution_launch.build_offline` в `driver-log.jsonl`.
`build_profile: "default"` означает, что профиль не объявлен.
Необязательный раздел `limits` задаёт лимиты в байтах: `context_batch_bytes`,
`docs_file_bytes`, `docs_total_bytes`, `task_input_bytes` (бюджет входа задачи, раздел 4). В контекст модели не попадают обёртки сборки
(`mvnw`, `mvnw.cmd`, `gradlew`, `gradlew.bat`, `.mvn/wrapper/`, `gradle/wrapper/`),
`.gitattributes`, `.gitignore`, сам `.skillsrc` (конфигурация пакета: модели она не нужна, и
её правка не меняет подтверждённый список отправки) и скрипты запуска в корне проекта (`*.ps1`, `*.sh`,
`*.bat`, `*.cmd`); в инвентаре и baseline запуска они остаются. Если для модели не осталось
ни одного файла кода, манифеста сборки или документа, `scan` останавливается с `CONTEXT_EMPTY`
(проверьте `paths` модуля и `--target`). Файлы, которые называет
provenance capability, драйвер добавляет в срез ревью (`contexts`) в пределах четверти
бюджета части. Linux venv может содержать
стандартный interpreter symlink: baseline связывает `pyvenv.cfg`, целевой interpreter
и его bytes. Произвольные symlink wrappers и выходы пути за module запрещены. На Linux
interpreter/wrapper должен уже иметь executable permission; пайплайн её не изменяет.
После переноса проекта на другую ОС создайте её venv и подтвердите изменение runtime
в существующем `.skillsrc`; старый attempt с прежним baseline не переиспользуется.

При создании `.skillsrc` для Maven сначала выбирается пригодный wrapper, затем
системный `mvn` из PATH. Для системного варианта используется
`maven:selected-symbols-v1` и поле `executable`; разрешённый абсолютный путь и bytes
launcher связываются с baseline. Существующая явная конфигурация не переключается
молча. Оба Maven-адаптера запускают фазу `test` и читают Surefire; маршрут
Failsafe/`verify` ими не реализован.

Пакет переносится в проект целиком, но автоматическое выполнение ограничено этими
адаптерами и имеющимся project setup. Для другого языка/framework сохраняйте явный
manual/blocker gap; наличие Python tools в пакете само по себе не делает такой проект
исполняемым. `coverage=FULL` означает покрытие автоматизацией выбранного canonical
документа, а не доказательство исчерпывающего покрытия произвольной функциональности.
Для полноты reviewer сравнивает исходные требования, сценарии и наблюдаемые проверки;
нерешённые пробелы и manual-проверки должны оставаться видны в результате.

Если `.skillsrc` отсутствует, scanner предлагает и атомарно создаёт его. Существующий
valid файл — authoritative user configuration и молча не перезаписывается. Значимый
drift требует `WAITING_FOR_INPUT`; подтверждённая замена сохраняет прежние bytes как
evidence.

Каждый attempt выбирает ровно один exact module, включая nested module. Module cwd,
test root, wrapper/interpreter/executable, adapter ID, build profile и typed adapter parameters
принадлежат этому attempt. Cross-module orchestration в pilot отсутствует.

## 4. Ход запуска: драйвер

Основной путь — детерминированный драйвер `tools.pipeline_driver`. Он выполняет все
шаги, где не нужна модель (scan, inventory, baseline, attempt, батчи, сборку,
публикацию, ведение ревью, выбор редакции, материализацию, закрытие), и останавливается,
только когда должен ответить человек или модель. Задачу модели выполняет ведущая сессия
CLI по `skills/orchestrate/SKILL.md` — свежим субагентом на каждую задачу.

Цикл: `next` → выполнить задачу по её Skill → `submit` → повторять до `done`,
`ask_user` или `human_exec`. Ответ `submit` — уже следующая задача, отдельный `next`
между ними не нужен.

Команды (пускатель `ts.py` пакета из любого каталога, `--project` — абсолютный путь
проекта, `<python>` — интерпретатор с зависимостями пакета):

```powershell
# первый вызов: создаёт run (внутри вызывает scan) и доходит до первой задачи
<python> <пакет>/ts.py next --project "$project" --profile cases-only-v1 `
  --docs docs/feature.md --subject "Название документа" --compact

# ответ на задачу
<python> <пакет>/ts.py submit --project "$project" --run "$runId" --task-id "$taskId" --compact

# ответ человека на гейт (confirm-context, approve-generated-tests*)
<python> <пакет>/ts.py answer --project "$project" --run "$runId" --task-id "$taskId" --value <дайджест>

# продолжение после перерыва и чтение состояния (у завершённого run — и result)
<python> <пакет>/ts.py next --project "$project" --run "$runId" --compact
<python> <пакет>/ts.py status --project "$project" --run "$runId"
```

`--compact` печатает только то, что нужно ведущей сессии: у `llm` — `task_id`, `stage`,
`task_path` (полная задача в файле), `output_path`, `input_bytes`,
`requires_fresh_context`; у отклонённого ответа — первые пять ошибок и `errors_total`; у
гейта — `summary` (документы, файлы, байты), `listing_path` и готовая `answer_command`; у
`done` — главное из `result` и `result_path`.

Первый `next` требует `--profile cases-only-v1|local-pilot-v1|suite-update-v1` и для первых двух хотя бы
один `--docs` (путь внутри проекта, флаг можно повторять; `suite-update-v1` берёт документы набора, если
`--docs` не задан — раздел 13). Необязательные флаги: `--subject`,
`--module <ID>`, `--target`, `--document-id`, `--model-id`, `--host-cli`,
`--host-cli-version`, `--host-settings`, `--reviewer-isolation fresh|none`,
`--review-input-bytes N`, `--review-reserve-bytes N`, `--review-context-bytes N` (одно окно
контекста модели в байтах, по умолчанию 500000), `--task-input-bytes N` (бюджет входа задачи, ниже),
`--execution-review human|none` (одобрение сгенерированных тестов перед запуском, раздел 8),
`--confirm-context yes|no` (подтверждение отправки файлов в модель, ниже),
`--execution-mode auto|human` (исполнение человеком, раздел 8; продолжение — `next --run <id> --junit <отчёт>`
с `--exit-code`/`--gate-exit-code`),
`--accept-self-review`, `--review-mode pairs|compact-v1` (формат ревью, по умолчанию `compact-v1`), `--max-tasks K`
(сколько независимых задач — частей ревью `compact-v1` или батчей разметки контекста — выдать сразу). Опции волн 2–3 — `--mutation`,
`--analyst-report`, `--suite`, `--disposition-policy cleanup|quarantine` — разделы 11–13. Миграцию набора без записи показывает
`python -m tools.suite migrate --project "$project"` (запись — только с `--write`). `run_id` берётся
из первого ответа.

Каждый вызов печатает один JSON-объект:

| `action` | Основные поля | Что делать |
|---|---|---|
| `llm` | `task_id`, `stage`, `skill_path`, `inputs`, `output_path`, `schema_path`, `instructions` | Прочитать `skill_path` и все файлы из `inputs`, записать ответ в `output_path` по `schema_path`, вызвать `submit` |
| `ask_user` | `task_id`, `question`, `options` (`value`, `label`) | Задать вопрос пользователю; гейт — `answer ... --value <value>` после его явного решения, прочие вопросы — `submit ... --answer <value>` |
| `batch` | `tasks` (каждая — как `llm`) | Только `compact-v1` с `--max-tasks K`: выполнить каждую задачу отдельным свежим вызовом (параллельно), затем `submit` по каждой |
| `human_exec` | `commands`, `report_path`, `continue` | Показать команды человеку; он выполняет их сам и называет отчёт; продолжить `next --run ... --junit <отчёт>` (раздел 8) |
| `done` | `result` | Остановиться и передать результат пользователю |
| `error` | `code`, `message` | Прочитать причину; не обходить ошибку ручными вызовами |

Что делает `submit`:

- проверяет ответ по схеме задачи и правилам роли. Сам вычисляет все digests, порядок
  массивов, `display_order` и служебные поля, публикует артефакт и возвращает следующую
  задачу. Модель не считает SHA-256, не сортирует массивы и не переносит пути между
  шагами;
- невалидный ответ не публикует: возвращает ту же задачу со `"status": "rejected"` и
  списком `errors` (`path`, `code`, `message`). Исправьте файл ответа и вызовите
  `submit` снова;
- повторный `submit` уже принятой задачи безопасен: он возвращает текущую задачу;
- `--output <path>` задаёт другой файл ответа; по умолчанию читается `output_path`;
- для задач ревью `--failed TRANSPORT|CONTENT --reason "..."` фиксирует, что пригодной
  оценки нет (вызов не дошёл или ответ непригоден). Драйвер выдаёт ту же часть ревью
  новой задачей — не более трёх вызовов на часть.

Задачи ревью (`tc-reviewer:*`, `autotest-reviewer:*`) имеют
`requires_fresh_context=true`: каждую выполняет отдельный вызов в свежем контексте без
истории генерации.

Вопросы `ask_user`:

- `skillsrc.<вопрос>` — в проекте нет `.skillsrc`, и обнаружение не может выбрать
  значение само (например, `module:root:test.framework`). Прогон уже создан; после
  ответа драйвер пишет `.skillsrc` и продолжает тот же `run_id`. Если `free_text: true`
  (вопрос о каталоге исходников), ответом может быть путь каталога внутри модуля;
- `reviewer-isolation` — может ли хост выполнить каждую часть ревью в отдельном вызове
  без истории генерации (свежим субагентом). При ответе `none` ревью не останавливается: части проверяются тем же порядком и в
  том же формате в текущей сессии, результат получает `review_independence: SELF` и
  `accepted=false` с `reason_code: REVIEW_NOT_INDEPENDENT` (кейсы публикуются, в
  `local-pilot-v1` автотесты проходят ревью и запускаются). Флаг `--accept-self-review`
  разрешает принятие; пометка `SELF` остаётся. Если
  сумма входов частей ревью больше `--review-context-bytes`, задачи ревью и сводка несут
  предупреждение `SELF_REVIEW_CONTEXT_OVERFLOW`. Вопрос не задаётся, если ответ передан
  флагом `--reviewer-isolation` при создании run;
- `regenerate-after-gate` — после `NOT_RUNNABLE/GENERATED_TEST_INVALID`: `regenerate`
  создаёт одну дочернюю попытку, `stop` завершает с текущим результатом. Вопрос
  задаётся один раз.

Коды завершения команды: `3` — драйвер ждёт модель или человека (`llm`, `ask_user`, `human_exec`);
при `done` — код результата (`0`, `1` или `2`, см. раздел 10); `2` — ошибка (`error`).
`status` только читает состояние и завершается с кодом `0`.

Рабочие файлы драйвера лежат рядом с run, в `<project>/.pilot-runs/<run_id>.driver/`:

```text
config.json        параметры первого вызова и ответы на вопросы
tasks/             выданные задачи и их схемы
inputs/            входы задач (уже маскированные байты)
outputs/           ответы модели
artifacts/         копии собранного кандидата, квитанций и вывода exec
carriers/          входные файлы для exec (только local-pilot-v1)
candidate-bundle/  опубликованный набор кейсов; у дочерней попытки —
                   candidate-bundle-<начало attempt_id>/
driver-log.jsonl   служебный лог: каждый next/submit/status с длительностью,
                   выдача задачи и её повторная выдача (со временем с первой выдачи),
                   submit --failed с причиной, любое исключение с traceback
```

`driver-log.jsonl` отличает ожидание от работы: у `submit` есть `task_age_seconds` —
сколько прошло с первой выдачи задачи, у `task_reissued` — `since_first_issue_seconds`.
Лог не входит ни в журнал, ни в дайджесты.

**Подтверждение отправки в модель (`context.confirm`).** По умолчанию драйвер после `scan` и
до первого вызова модели возвращает `ask_user` с меткой `confirm-context`: в вопросе —
документы требований (`--docs`) и число файлов проекта с общим размером в байтах; в полях
`documents` и `files` и в файле `<run>.driver/context-files.txt` — каждый файл с размером;
в `confirmation_digest` — дайджест списка. Проверьте, что в нём нет персональных данных,
секретов и лишнего кода, и ответьте `answer ... --value <confirmation_digest>` (`submit
--answer` гейт в хост-сборке не принимает: `GATE_ANSWER_COMMAND`). Ответ пишется в
журнал событием `CONTEXT_CONFIRMED`; журнал не примет ни одного `MODEL_REQUESTED` без
подтверждения именно этого списка (требование фиксируется в квитанции авторизации,
`context_confirm_required`). Подтверждение — одно на run: доработка или регенерация с тем
же списком не спрашивает снова, другой список — спросит. Лишнее исключается в `.skillsrc`
(`paths`/`exclusions` модуля) или `--target` с новым запуском. Выключение — явно:
`.skillsrc` `context: {confirm: false}` или `--confirm-context no` (флаг сильнее
`.skillsrc`). В `suite-update-v1` — то же перед первой задачей модели со списком её входных
файлов (подтверждение — в состоянии run и `driver-log.jsonl`). Ручной `run_pipeline scan`
решает так же (флаг, иначе `.skillsrc`, иначе включено); снимает `--confirm-context no`.

**Тест-дизайн (`design`).** По умолчанию между разметкой требований и генератором кейсов
идёт стадия `test-design`: модель по одним текстам требований (без кода проекта) строит
параметры (`P-`), классы эквивалентности (`EQ-`), граничные значения (`BV-`) и правила
решений, состояний и ошибок (`DR-`), а требование без разбиения называет в `not_designed`
с причиной. Стадия добавляет один вызов модели; выключение — `.skillsrc`
`design: {enabled: false}` (без флага запуска), прогон тогда идёт как раньше. Решение
фиксируется в квитанции авторизации (`design_required`). Генератор получает срез дизайна
своего пакета: каждый кейс называет в `design_refs` элементы, которые проверяет, элемент
без кейса попадает в `design_uncovered` с причиной, невалидный класс покрывается
негативным кейсом, иначе ответ отклоняется. Приоритет кейса ставит код по дизайну, а не
модель: правило `error` или невалидный класс — HIGH, граница за пределом — HIGH, другая
граница — MEDIUM, первый кейс на ещё не покрытый валидный класс или правило — MEDIUM,
повтор — LOW; CRITICAL не назначается (признака критичности у требований нет). Итог
(`result`, версия 1.3.0) несёт `design_coverage`: доли покрытых классов, границ, правил и
невалидных классов негативными кейсами, непокрытое с причинами и распределение
приоритетов; если кейсов не меньше 10 и один уровень больше 70 % — предупреждение `PRIORITY_DEGENERATE`.
С `--analyst-report` то же покрытие — в отчёте для аналитиков.
Комбинации (`CB-`) строит код, а не модель: параметры с общим требованием комбинируются по
валидным классам (невалидные проверяются по одному); группа не больше
`design.full_factorial_max` вариантов (по умолчанию 16) — полностью, больше — попарно
(каждая пара значений двух параметров встречается хотя бы в одной комбинации). Порог
фиксируется в квитанции авторизации (`design_full_factorial_max`); каждую комбинацию
покрывает кейс или `design_uncovered` с причиной, доля — `design_coverage.combinations`.
Ревью кейсов (`compact-v1`) получает дизайн в снимке: часть показывает элементы дизайна своих
кейсов с якорями; ревьюер полноту заново не выводит (её считает код), а проверяет смысл —
ссылки кейса (`DESIGN_REF_WRONG`), ожидаемый результат правила (`DESIGN_EXPECTED_MISMATCH`) и
негативность проверки невалидного класса (`DESIGN_NEGATIVE_WRONG`). Журнал сверяет дизайн в
снимке с артефактом попытки. Без стадии дизайна текст частей ревью прежний.
Живой набор хранит дизайн прогона в `test-design.json` по ключам требований (номера SREQ при
обновлении меняются), в манифесте — `suite_files.design` и `design_coverage`. `suite-update-v1`
при `design.enabled` между IMPACT и UPDATE проектирует заново только изменённые и добавленные
требования (набор без дизайна — все): элементы неизменённых требований сохраняют ID, новые
нумеруются после максимального, элементы удалённых требований уходят, комбинации того же набора
классов сохраняют ID; кейсы со ссылками на удалённые или пересобранные элементы обновляются вместе
с затронутыми. Генератор покрывает срез изменённых требований, приоритеты обновлённых кейсов
ставит код, ревью видит дизайн, покрытие пересчитывается по всему набору. С `enabled: false`
шаг пропускается, хранимый дизайн остаётся, покрытие пересчитывается.

Источник истины остаётся в `.pilot-runs/<run_id>/` (журнал и квитанции). Не запускайте
параллельно две команды драйвера для одного run и не удаляйте `.lock` вручную.

Ограничения:

- драйвер продолжает только run, созданный его же `next`; run, начатый ручными
  командами, он не подхватывает;
- один модуль на run;
- context-marker читает контекст батчами: если `scan` разбил выбранный контекст на
  несколько частей (`limits.context_batch_bytes`, по умолчанию 256 КБ), драйвер выдаёт по
  задаче `context-marker:batch-NNN` на часть (черновик требований + файлы только этой части,
  до `--max-tasks` сразу) и сам детерминированно сливает ответы в `context-marker:baseline`:
  порядок частей, повторы `sources`/`warnings`/`requirement_gaps` убираются, слитый артефакт
  привязан в журнале к ответам всех частей. При одной части задача одна, как раньше.
  Генератор кейсов и генератор автотестов по-прежнему получают весь выбранный контекст
  одним входом;
- бюджет входа задачи: для разметки, генератора кейсов и генератора автотестов драйвер
  сравнивает `input_bytes` с порогом (`--task-input-bytes`, иначе `limits.task_input_bytes`
  в `.skillsrc`, иначе 1 000 000 Б) до вызова модели. Если вход больше, модель не
  вызывается и в журнал ничего не пишется: команда возвращает ошибку
  `TASK_INPUT_TOO_LARGE` с `input_bytes`, `threshold` и подсказкой — сузить контекст
  (`--target`, `paths`/`exclusions` модуля в `.skillsrc`) или уменьшить
  `limits.context_batch_bytes`. Вход не обрезается. Ориентир для порога — 0,24 токена на
  байт (замер на DeepSeek-V4.1-Flash через gigacode): окно 239 тыс. токенов ≈ 1 МБ входа;
  для другой модели порог считайте от её окна с запасом на ответ;
- автоматизация частями: если вход единой задачи генератора автотестов больше порога или
  кейсов больше `limits.automation_cases_per_part` (по умолчанию 12; `0` — без лимита по
  кейсам), драйвер делит кейсы на части в порядке документа — поровну по числу и каждая в
  пределах порога по байтам — и выдаёт задачи `tc-to-autotest:rN:part-NNN` (до `--max-tasks`
  сразу): у части бриф, документ только с её кейсами и весь контекст. Каждая часть пишет
  свои файлы: `file_id` с префиксом `FILE-PNNN-`, имя файла и класса содержит `PartNNN`,
  вспомогательный код — внутри своего класса. Ответы частей драйвер сливает сам в
  `tc-to-autotest:rN` (журнал привязывает слитую ревизию к плану и к ответам всех частей и
  пересчитывает слияние при записи и чтении); ревью, одобрение S3 (одно, по всем файлам),
  материализация и исполнение идут по слитой ревизии как раньше. В ревизии r2 к модели идут
  только части, которых касаются corrections ревью r1; остальные переносятся без вызова
  модели. Цена разбиения — в `driver-log.jsonl` (`automation_parts`: число частей,
  суммарный вход против входа единой задачи): контекст и шапка документа идут в каждую
  часть. Если контекст, бриф и шапка документа сами не влезают в порог — `TASK_INPUT_TOO_LARGE`
  с подсказкой сузить контекст (`--target`, `paths`). При одной части — одна задача, как раньше;
- драйвер не проверяет, что ревью действительно выполнено в свежем контексте: это
  сообщает хост;
- драйвер покрыт тестами пакета, но не проверен на Windows и на живой модели.
  Состояние релиза остаётся `implemented_unverified`, ready tuple — `null`.

Внутренние шаги драйвера — `tools.run_pipeline` (`scan`, `status`, `exec`),
`tools.orchestrate_test_case_revision`, `tools.review_budget`; в разделах ниже они
упоминаются как шаги, которые вызывает драйвер. Ручной ход ими — только в универсальной
сборке.

## 5. Durable run

Первый `next` драйвера вызывает прежнюю команду `run_pipeline scan`. Она сама создаёт
новый run (флага `--run` у неё нет) до inventory и первого model call:

```text
<project>/.pilot-runs/<run_id>/
  run-authorization-receipt.json
  run-manifest.json
  events/
  attempts/
  .lock
```

Рядом драйвер создаёт каталог рабочих файлов `<project>/.pilot-runs/<run_id>.driver/`.

`.lock` — межпроцессная блокировка run: писатели и читатели одного run выполняются по
очереди. Чтение (`status`) ничего не восстанавливает и не удаляет; незавершённую запись
после сбоя доводит следующий писатель. Если блокировка занята дольше 120 секунд,
команда завершается ошибкой `run is locked by another process`.

Все JSON artifacts публикуются атомарно, читаются обратно и связываются digest.
Один run получает одну project/module identity и последовательную append-only lineage
child attempts. Одновременно разрешён максимум один nonterminal attempt.

`WAITING_FOR_INPUT`, `WAITING_FOR_MODEL` и interruption между model stages можно
продолжить из новой CLI session после snapshot/config validation: вызовите
`<python> <пакет>/ts.py next --project <abs> --run <run_id>`. Драйвер вернёт
ту же незакрытую задачу или продолжит с последнего подтверждённого шага. Изменение
requirements, module или policy создаёт child attempt. Terminal attempt не меняется.
После `WAITING_FOR_INPUT`/`WAITING_FOR_MODEL` attempt снова становится `ACTIVE`, как
только записан следующий шаг работы.

Если процесс был запущен, но authoritative framework result отсутствует, результат —
`UNKNOWN`; автоматический повтор запрещён. Новый execution retry возможен только в
explicit child attempt после доказанной остановки прежнего process scope. Доказательство
выдаётся при остановке по таймауту: на Windows процесс запускается в Job Object, и
proof `WINDOWS_JOB_TERMINATED` означает завершение всего Job; на Linux proof
`POSIX_PROCESS_GROUP` выдаётся, только когда живых процессов нет ни в группе, ни среди
ушедших из неё через `setsid`. Если остановку доказать не удалось, retry запрещён.

Для чувствительных параметров pytest задавайте безопасные явные `ids`: значения
параметров могут попасть в имена тестов в JUnit. Отчёт с обнаруженной сигнатурой
токена в имени, классе или пути не сохраняется; runner завершает такой execution
как `UNKNOWN` с причиной `JUNIT_INVALID` и очищает чувствительный вывод.

## 6. Canonical и reviewer

Requirements детерминированно разбиваются на batches из разрешённых source roots.
Каждый source requirement получает provenance и digest, затем many-to-many mapping к
canonical requirements, cases, steps, assertions, symbols и execution evidence.

Candidate revision 1 немедленно публикуется как `UNREVIEWED` и читается обратно.
После этого выполняется одно логическое ревью по частям: controller замораживает
исходные требования, контекст и candidate в одном snapshot и делит проверку на части.
Каждую часть проверяет отдельный fresh role-isolated вызов reviewer со своим host
evidence; событий `EVIDENCE_REQUESTED`/`EVIDENCE_PROVIDED` нет. Правила:

- итог собирает controller: одно ревью даёт ровно один authoritative verdict;
- terminal pre-verdict abort, включая `REVIEW_CONTEXT_LIMIT`,
  `REVIEW_TRANSPORT_FAILED` и `REVIEW_INCOMPLETE`, содержит ноль;
- часть без пригодной оценки можно открыть заново новым вызовом — не более трёх
  вызовов на часть; сбой вызова фиксирует `submit --failed TRANSPORT|CONTENT --reason`
  драйвера (при ручном ходе — команда `fail-part` с
  `--failure-class TRANSPORT|CONTENT`);
- содержимое, которое повторяется внутри одной части, передаётся один раз; у повтора
  вместо `content` стоит ссылка `content_ref` на первое вхождение;
- generator dialogue/reasoning reviewer не получает;
- без host isolation evidence каждой части записывается `independence_unverified`,
  acceptance запрещён. Драйвер при ответе `none` на вопрос `reviewer-isolation` ревью
  не останавливает: части проверяет та же сессия, результат получает
  `review_independence: SELF` и `REVIEW_NOT_INDEPENDENT` (без `--accept-self-review`).

При `AUTO_FIX_APPLIED` revision 2 строит controller из механических исправлений,
предложенных в частях ревью; reviewer её не пишет.

Если ревью кейсов вынесло вердикт REJECTED, попытка завершается с `REWORK`, и драйвер
сам начинает одну доработку — дочернюю попытку `CANONICAL_REWORK`. Её context-marker
получает прошлый ответ как готовый черновик, а генератор — документ r1, находки ревью
уровня BLOCKING и WARNING (без INFO) и список затронутых кейсов; он возвращает только
изменённые кейсы. Драйвер собирает из них canonical r2 (`revision: 2`, `parent_sha256` от
r1) и проводит новую сессию ревью. Она инкрементальная: области, входы которых
совпадают с проверенными областями r1 и которых не касается находка BLOCKING, не
отправляются заново, и агрегат перечисляет их в `carried`. Доработка одна: отклонённый
r2 даёт окончательный `REWORK`. Непроверенные области (UNCHECKED, `REVIEW_INCOMPLETE`)
генератору не отдаются: это не вердикт REJECTED.
Механическую правку ревьюера к r2 доработки применить нельзя (r3 не бывает): такое
ревью отклоняется.

В режиме `--review-mode compact-v1` вход части — текст проекции канона с якорями `[ID]`
(файл `.input.md`), кейсы приходят целиком, ответ — короткие строки покрытия с проверяемыми
ссылками, находки, правки по `target_id`/полю, решения по подозрениям линтера. Ревью
автотестов идёт по срезам методов с общим кодом файла и таблицей общего состояния. Части
независимы: `next --max-tasks K` выдаёт их пачкой. Подробно — `HOW-IT-WORKS.md`, раздел 5.

Лимит части ревью задаётся при создании run флагами драйвера `--review-input-bytes`
и `--review-reserve-bytes` (по умолчанию 200000 и 20000 байт). Значения можно получить
из лимита модели в токенах:
`python -m tools.review_budget --context-tokens N --response-tokens M --sample <файл>`
печатает `input_byte_budget` и `response_reserve_bytes`. При ручном ходе те же значения
передаются в `prepare-review`.

Canonical human fields пишутся по-русски. JSON остаётся единственным semantic source;
HTML, Markdown и CSV — derived exports. Профиль CSV по умолчанию —
`zephyr-scale-step-row-24-v5` (только человеческие поля шага); прежний v4 включается
явным `--csv-profile zephyr-scale-step-row-24-v4`.

## 7. `cases-only-v1`

Профиль даёт draft/artifact-only canonical cases: verification=NOT_APPLICABLE, accepted=false, полный pipeline exit не 0: валидное завершение даёт exit 1, а FATAL, `FINALIZATION_INVALID`, невалидный trace или ненадёжное закрытие — exit 2. Live PASS и accepted=true только у local-pilot-v1. Для него:

```text
materialization = NOT_APPLICABLE
execution       = NOT_APPLICABLE
dispositions    = NOT_APPLICABLE
verification    = NOT_APPLICABLE
```

Запрос этого профиля не запускает project code, plugins или lifecycle hooks.

## 8. `local-pilot-v1`

После accepted canonical pipeline:

1. создаёт automation revision 1;
2. выполняет отдельный static review;
3. при correction допускает ровно одну полную revision 2 и второй review;
4. формирует complete generated file set;
5. материализует каждый pipeline-owned file и пишет receipt;
5a. останавливается на одобрении человеком (по умолчанию, см. ниже);
6. выполняет шлюз компиляции/сбора и запускает exact reviewed targets закрытым adapter;
7. строит execution trace и disposition всего generated delta;
8. выполняет finalization и terminal transition.

**Одобрение сгенерированных тестов перед запуском (`execution.review`).** По умолчанию
(`human`) драйвер после записи сгенерированных тестов в проект и до любого запуска сборки,
тестов и мутаций возвращает `ask_user` с меткой `approve-generated-tests`: в вопросе и в
поле `files` — каждый записанный файл с дайджестом содержимого, в `approval_digest` —
дайджест этого списка. Прочитайте файлы и ответьте
`answer ... --value <approval_digest>`; другой ответ отклоняется. Ответ
пишется в журнал событием `EXECUTION_APPROVED`, и журнал не даст начать исполнение
(`EXECUTION_STARTED`) без одобрения именно этих файлов; пока ответа нет, ничего не
запускается (код выхода 3). Требование фиксируется при создании run в квитанции
авторизации (`execution_review_required`). Выключение — явно: `.skillsrc`
`execution: {review: none}` или флаг `next --execution-review none` (флаг сильнее
`.skillsrc`), например для повторных прогонов на известном проекте. Если предохранитель
выключил сам `.skillsrc` (не флаг запуска), результат (`result`, `suite-update-result.json`)
несёт `gates_disabled_by: skillsrc` и список `gates_disabled` (`context.confirm`,
`execution.review`), а `driver-log.jsonl` — событие `gates_disabled`. В `suite-update-v1`
то же перед прогоном набора, если run записал обновлённые или новые методы
(`approve-generated-tests-apply`), и перед повторным прогоном после починки
(`approve-generated-tests-repair`); одобрение хранится в состоянии run и в
`driver-log.jsonl`. Ручной `run_pipeline scan` решает так же (флаг, иначе `.skillsrc`,
иначе `human`): ручной `exec` без одобрения не начнётся; снимает `--execution-review none`.
`execution.mode` из `.skillsrc` ручной `scan` тоже учитывает.

**Исполнение человеком (`execution.mode: human`).** В хост-сборке это единственный режим и
умолчание: `auto` (флагом или в `.skillsrc`) — ошибка `EXECUTION_MODE_UNAVAILABLE` до начала
работы. Режим фиксируется в квитанции авторизации (`execution_mode_human`): пакет не
запускает ни сборку, ни тесты, ни мутации: после записи
сгенерированных тестов (и одобрения, если включено `execution.review`) драйвер отвечает
`{"action": "human_exec"}` (код выхода 3) с полями `commands` — шлюз компиляции/сбора
(`gate`) и тесты (`tests`), у каждой команды `argv` списком, `cwd`, готовые строки `bash` и
`powershell` с экранированием, — `selectors` (проверяемые тесты), `report_path`/`report_dir`
(куда команда пишет JUnit-отчёт) и `continue`. В терминах протокола это команды
generated-for-human-review, а их запуск — действие человека. Выполните команды по порядку
сами и передайте отчёт: `next --run <id> --junit <отчёт> [--junit …] [--exit-code N]
[--gate-exit-code N]`. Отчёт должен быть файлом закрытого места отчётов и новым относительно
снимка, сделанного при выдаче команд; иное — ошибка `HUMAN_REPORT_INVALID`, прогон
продолжает ждать. Без `--exit-code` код берётся из отчётов. Результат решают те же правила,
что при запуске пакетом (сопоставление с проверенными тестами, нулевой сбор, изменение
файлов, durable-копии отчётов); в квитанции исполнения — `executor: human`. Если человек
прогнал больше, чем `selectors` (весь класс или модуль), лишние кейсы не мешают: они
считаются в `extra_testcases`, а итог берётся по проверенным тестам. Событие
`EXECUTION_STARTED` пишется, когда драйвер принимает отчёты в обработку (повторная выдача
команд до этого ничего не начинает). Сборка в этом режиме идёт в окружении человека:
фильтр секретоподобных переменных S1d к ней не применяется, это его ответственность.
Мутации (`--mutation`) в этом режиме тоже запускает человек, в три шага, потому что каждая
команда зависит от вывода предыдущей: classpath проекта (`step: resolve-project`), пиннованные
jar'ы PIT под версию JUnit Platform проекта (`resolve-tool`) и сам PIT (`pit`). На каждом шаге
драйвер отвечает `{"action": "human_exec", "kind": "mutation"}` с одной командой, её
`expected_output`, `step_index`/`steps_total`; перед выдачей драйвер удаляет ожидаемый файл, а
продолжение требует, чтобы он существовал и был непустым (иначе `HUMAN_STEP_INCOMPLETE`):
`next --run <id> --mutation-step-done` после резолверов и `next --run <id> --pit-report
<expected_output>` после PIT (ровно этот путь). Jar'ы сверяет с пинами сам драйвер, ничего не
запуская; квитанция мутаций — `executor: human` и `commands_digest`, проверка «проект не
изменился за стадию» остаётся. В `suite-update-v1` режим тот же (`.skillsrc` `execution.mode` или
`next --profile suite-update-v1 --execution-mode human`): прогон набора и повторный прогон после
ремонта запускает человек — драйвер отвечает `{"action": "human_exec", "kind": "suite"}` с
одной командой (`step: suite-run` или `repair-run`, `expected_output` — каталог или файл
отчётов адаптера, только он удаляется перед выдачей команды), продолжение —
`next --run <id> --junit <отчёт в expected_output> [--exit-code N]`; если сборка упала до
отчёта (ошибка компиляции), — `next --run <id> --exit-code N --build-log <вывод сборки>`, по
которому пакет, как и в своём прогоне, находит упавший файл. Без отчёта и с нулевым кодом —
`HUMAN_STEP_INCOMPLETE`. Повторы упавших методов в этом режиме не выполняются, поэтому метка
FLAKY не присваивается: упавший метод считается стабильно упавшим и проходит triage как
таковой; в итоге run — `executor: human`, `repeats: 0`, в описании PR — та же пометка.

Все эти шаги ведёт драйвер. Модель получает задачи `tc-to-autotest:r1` (и `r2` при
`AUTO_FIX_APPLIED`) и части статического ревью `autotest-reviewer:*`. Если ревью не
приняло автотесты, попытка завершается без записи файлов в проект, с причиной:

- `AUTOMATION_REVIEW_REJECTED` — ревью отклонило автотесты;
- `AUTOMATION_REVISION_BUDGET` — исправления потребовались и после revision 2;
- `AUTOMATION_REVIEW_CONTEXT_LIMIT` — часть ревью не поместилась в лимит;
- `AUTOMATION_REVIEW_TRANSPORT_FAILED` — части ревью не удалось доставить reviewer;
- `AUTOMATION_REVIEW_INCOMPLETE` — часть областей осталась непроверенной.

Execution работает в доверенном обычном проекте: pytest plugins, conftest, Maven/Gradle
plugins и lifecycle hooks могут выполнять код. Run-scoped authorization относится
только к текущему явному запросу. Никакого постоянного trust store, clone или sandbox
нет.

Pipeline не принимает shell strings или `argv_template`. Команду строит только один из
closed adapters:

- `pytest:selected-symbols-v1`;
- `maven-wrapper:selected-symbols-v1`;
- `maven:selected-symbols-v1`;
- `gradle-wrapper:selected-symbols-v1`.

pytest запускается из module root. Maven запускается из корня реактора с
`-Dtest=… -B -ntp test`; для модуля внутри реактора добавляются `-pl <module> -am` и
`-Dsurefire.failIfNoSpecifiedTests=false`, а `-P<profile>` — только для объявленного
профиля. Gradle запускается из корня сборки:
`:<path>:cleanTest :<path>:test --tests <FQN> --no-daemon`.

Перед основным запуском выполняется шлюз компиляции/сбора: pytest `--collect-only` по
выбранным nodeid, Maven `test-compile`, Gradle `:<path>:testClasses`. Провал шлюза, а
также ошибка компиляции или импорта в основном запуске дают `NOT_RUNNABLE` с причиной
`GENERATED_TEST_INVALID`: сгенерированные файлы убираются, вывод сохраняется в run root.
Исправленная ревизия автоматизации допускается один раз, в child attempt с
`retry_reason=GENERATED_TEST_INVALID`, если прежний attempt не потратил revision 2 в
статическом ревью и сам не был таким child attempt. Вывод `exec` в этом случае содержит
`reason`, `automation_revision`, `automation_revision_allowed` и `regeneration`.
Когда регенерация разрешена, драйвер задаёт вопрос `regenerate-after-gate`; при ответе
`regenerate` он сам создаёт child attempt, в котором кейсы, ревью и автоматизация
проходят заново.
Падение продуктовой проверки — `FAIL`; регенерации после него нет.

Другие причины `NOT_RUNNABLE` после старта: `LAUNCH_FAILED` — процесс не запустился;
`TESTS_DESELECTED` — pytest собрал 0 тестов по явно выбранным nodeid из-за `addopts`,
`-m` или `PYTEST_ADDOPTS` (файлы тестов остаются `RETAINED`);
`BUILD_FAILED_BEFORE_TESTS` — сборка проекта (Maven/Gradle) упала до компиляции тестов:
плагин фазы `validate`, основной код и т. п.; тесты ни при чём, перегенерации нет, итог
драйвера несёт `build_failure` — шаг сборки и хвост runner-output.

После запуска с замороженным baseline сравниваются только его входы: изменённый или
удалённый файл — drift, новые файлы (coverage, `.gradle`, логи) drift не считаются.
Execution receipt записывает в `execution.environment_inputs` имена и SHA-256 значений
`PYTEST_ADDOPTS`, `PYTEST_PLUGINS`, `MAVEN_OPTS`, `MAVEN_ARGS`, `JAVA_TOOL_OPTIONS`,
`_JAVA_OPTIONS`, `GRADLE_OPTS` и `JAVA_HOME`; сами значения не сохраняются.

## 9. Disposition и finalization

Физический порядок неизменяем:

```text
materialization -> execution -> execution trace -> retain/cleanup decision
-> disposition receipts -> pre-finalization trace -> finalization verification
-> finalization receipt readback -> terminal result -> derived terminal trace
-> terminal event
```

Для всего generated file set:

- `PASS` + valid trace/path/digests: `RETAINED` до finalization;
- `FAIL` в `local-pilot-v1` (по умолчанию с 2026-10-08, политика `quarantine`): файл без упавших
  методов — `RETAINED`, файл с упавшими — `QUARANTINED` (методы помечены `@Disabled`/`xfail`); `FAIL` без
  исходов по методам и `--disposition-policy cleanup` — `CLEANED`;
- `NOT_RUNNABLE`: byte-identical pipeline-owned files получают `CLEANED`
  (кроме `NOT_RUNNABLE/TESTS_DESELECTED`: файлы остаются `RETAINED`);
- `UNKNOWN`: unchanged file получает `PRESERVED_EXECUTION_UNKNOWN`, изменённый —
  `PRESERVED_CONTENT_CONFLICT`; cleanup запрещён;
- partial materialization: execution не начинается, неизменённые созданные файлы
  очищаются, остальные получают `NOT_MATERIALIZED`.

Для `FAIL` cleanup следует только после readback execution receipt, где остаются
exact generated bytes, native report, bounded scrubbed output, exit и structured result.
Для Maven/Gradle valid process-bound report с `tests=0` даёт `NO_TESTS_COLLECTED`,
`FAIL`, exit `1`; для pytest ноль собранных выбранных тестов — `NOT_RUNNABLE`
(`TESTS_DESELECTED` или `GENERATED_TEST_INVALID`). Missing/corrupt/unbound report
(`JUNIT_MISSING`, `JUNIT_INVALID`), ненулевой exit при зелёном отчёте
(`NONZERO_EXIT_GREEN_REPORT`), timeout и сбой сохранения артефактов
(`ARTIFACT_PERSISTENCE_FAILED`) дают `UNKNOWN`, exit `2`. Процесс, который не удалось
запустить, — `NOT_RUNNABLE/LAUNCH_FAILED`.

Если безопасный cleanup невозможен, файл сохраняется с точной причиной и
`accepted=false`. Terminal transition требует completed/read-back finalization receipt,
но receipt может иметь `valid=false`; тогда terminal reason — `FINALIZATION_INVALID`.

## 10. Как читать результат

Не сводите результат к одному слову. Проверяйте вместе:

```text
attempt_state  completion  verification  coverage  reason_code  accepted
```

Поля completion/verification/coverage могут отсутствовать, пока факт не установлен.
`COMPLETE + FAIL` допустим. `EXECUTION_UNKNOWN` означает
`TERMINAL + PARTIAL + UNKNOWN + accepted=false`.

Exit projection:

- `0` — accepted terminal;
- `1` — trustworthy terminal, но unaccepted (включая валидное завершение
  `cases-only-v1`);
- `2` — controller error, unreliable closure, UNKNOWN, NOT_RUNNABLE, FATAL,
  `FINALIZATION_INVALID` или невалидный trace;
- `3` — waiting for input/model.

Команды драйвера используют те же значения: `3` — выдана задача `llm` или `ask_user`;
при `done` — код результата; `2` — ошибка драйвера (`action: "error"`). Остановка без
terminal result тоже даёт `2`. Если scan при создании run ждёт уточнения `.skillsrc`,
драйвер выдаёт вопрос `ask_user` (код `3`) и после ответа продолжает тот же run.
Результат без изоляции ревью (`review_independence: SELF`) без `--accept-self-review`
не принимается: в `local-pilot-v1` это код `1`.

`COMPLETE + PASS + accepted=false` с `reason_code: UNRESOLVED_AUTOMATION_BLOCKER`
(`local-pilot-v1`): тесты прошли, но в принятом canonical остались блокеры
автоматизации (`automation_blockers`, `evidence.blocker_count > 0`) — эти кейсы не
автоматизированы, предикат `no_unresolved_blocker` не выполнен; код завершения `1`.
Код ставится, только если более ранней причины нет (`REVIEW_NOT_INDEPENDENT` и
`REVIEW_ISOLATION_UNVERIFIED` важнее); при `FAIL` и `NOT_RUNNABLE` причину объясняет
`verification`, и кода нет. Terminal result, записанный до появления кода, остаётся
валидным: блокеры видны только в `evidence.blocker_count`, `reason_code` отсутствует.

## 11. Проверка и release identity

```powershell
python -m tools.contract_check --root . --full
python -m tools.render_contract_docs --root . --check
python -m pytest -q
python -m tools.doctor --root .
python -m tools.ci_gate --root .
```

`tools.ci_gate` завершается с кодом `2`, если pytest не установлен или проверка не
уложилась в таймаут: `--check-timeout` (по умолчанию 900 секунд на каждую проверку
контрактов) и `--pytest-timeout` (по умолчанию 4 часа).

Это maintainer/release-команды, а не шаги обычного production run. Runtime не запускает
полный repository test suite, `ci_gate` или release eval автоматически.

`release/manifest.json` — persisted machine authority для package version, exact runtime
registry/digest, pipeline contract, profiles, adapters и release-eval suite. Он исключён
из собственного runtime digest, чтобы не создавать self-cycle.

Текущий package state — `implemented_unverified`. Claim
`core-pilot-ready for <exact verified tuple>` разрешён только после одного smoke и
трёх fresh runs каждого critical scenario. Instability или protocol violation навсегда
блокирует readiness текущей campaign; evaluator сохраняет append-only receipt в
`.pilot-runs/release-eval-ledger`, и следующая clean campaign автоматически требует
пять fresh runs каждого critical scenario. `--predecessor-evaluation` нужен только для
импорта валидного внешнего predecessor; отсутствие флага не сбрасывает уже записанную
эскалацию.
Эта adaptive campaign запускается отдельно для release qualification; production run
не вызывает её и не повторяет model stages ради квалификации.
В обычном run каждое `MODEL_RESPONSE_RECEIVED` записывает `transport_attempts` от 1 до
3 — число транспортных попыток получить этот ответ; его передаёт
`submit --transport-attempts` драйвера (при ручном ходе для части ревью —
`submit-part --transport-attempts`). Число вызовов reviewer читается из частей ревью и
их boundary (повторный вызов части имеет stage с суффиксом `-try2` или `-try3`), а не
из evidence pairs: таких событий нет.

## 13. Живой набор (волна 3)

Всё включается явно, кроме одного: с гейта волны 3 карантин (A4) — политика `local-pilot-v1` по
умолчанию (`--disposition-policy cleanup` возвращает прежнюю очистку). Остальное без флагов прежнее.

**Шаблон ID требований** (`.skillsrc` 5.2.0). Строка, начинающаяся с ID, открывает
требование так же, как встроенные `REQ-…`/`AC-…`; без шаблона разбиение прежнее:

```yaml
requirements:
  id_pattern: '[OPVX]\d\d\.'   # Petclinic: O01. … X02. — 29 требований вместо 7
suite:
  path: test-cases/            # каталог набора (по умолчанию test-cases/)
```

**Первый набор** — обычный `local-pilot-v1` с `--suite`: после терминального результата
драйвер пишет в `test-cases/` канонический JSON, Markdown, HTML, CSV и
`suite-manifest.json` (ключи и хеши требований, кейсы, методы и дайджесты их срезов,
статусы, доли мутантов, снимок эндпоинтов). Сводка — версия 1.2.0 с полем `suite`.

```powershell
<python> <пакет>/ts.py next --project "$project" --profile local-pilot-v1 --docs docs/feature.md --suite --compact
```

**Карантин вместо очистки** (`local-pilot-v1`; по умолчанию с гейта волны 3, прежняя очистка —
`--disposition-policy cleanup`): после `FAIL` прошедшие тесты остаются, упавшие методы получают одну строку
`@org.junit.jupiter.api.Disabled("test-skills quarantine: …")` (pytest —
`@pytest.mark.xfail(strict=True, reason=…)`); диспозиция файла — `QUARANTINED`. `FAIL`
по-прежнему не принимается.

**Без модели** — что изменилось и нужна ли модель вообще (для CI проекта):

```powershell
python -m tools.suite status  --project "$project"
python -m tools.suite impact  --project "$project" --junit target/surefire-reports/TEST-My.xml --git-range origin/main..HEAD
python -m tools.suite migrate --project "$project"           # набор прошлого формата → 1.0.0: предпросмотр
python -m tools.suite migrate --project "$project" --write   # запись (согласие человека, квитанция в .pilot-runs/suite-migrations/)
```

`impact` — требования по ключам (добавлены, изменены, удалены, переименованы),
затронутые кейсы, упавшие и сломанные тесты отчёта, новые эндпоинты без требования (вопрос
аналитикам), `needs_model`.

**Обновление набора** — профиль `suite-update-v1`:

```powershell
<python> <пакет>/ts.py next --project "$project" --profile suite-update-v1 --reviewer-isolation fresh [--mutation] [--junit report.xml] --compact
```

Шаги: миграция → анализ влияния → обновление затронутых кейсов (задача
`tc-generator:update`) → ревью только изменённых кейсов → автоматизация изменённых
(`tc-to-autotest:update`, методы заменяются по срезам) → статическое ревью изменённых
методов → прогон всего набора (карантинные — явно, упавшие — с повторами) → разбор
падений: карантин с вопросом и черновиком баг-репорта, нестабильность, один ремонт
(`tc-to-autotest:repair`, ожидания не меняются) → мутации (`--mutation`) → манифест → итог.
Кейс или метод, который правил человек, не перезаписывается — изменение уходит
предложением. Итог — изменения в рабочем дереве, `pr-description.md`, `suite.patch` и
`suite-update-result.json` в каталоге драйвера; `accepted` у профиля нет, коммит и PR
делает человек.
