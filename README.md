# Камертон

**От требования до теста — в одном ключе.**

Камертон — набор инструкций для модели и Python-инструментов к ним. По документу требований к одной функции он
готовит тест-кейсы и отдаёт их на ревью. Код проекта, его сборку и тесты агент не запускает; если в поставке есть автотесты, их запускает человек.

Для кого: тестировщики и разработчики, которые работают в программе с доступом к модели (CLI компании или
похожей).

**Как начать — [QUICKSTART.md](QUICKSTART.md)**: подключить пакет, проверить его и дать первый запрос.
Подробно — [HOW-TO-USE.md](HOW-TO-USE.md): когда какой запрос давать, результаты, продолжение после перерыва и частые остановки.
Что нужно от команды проекта и когда запускать — [FOR-PROJECT-TEAM.md](FOR-PROJECT-TEAM.md).

**Начните с кейсов.** Первый прогон — тест-кейсы и их ревью, без автотестов: так работает любая поставка. Автотесты (режим Б) есть только в поставке с файлом `HOW-TO-USE-MODE-B.md`; к ним переходите, когда кейсы уже есть.

## Что вы получаете

- **Тест-кейсы** — в HTML и Markdown для чтения и в JSON как исходный документ. Каждый кейс связан
  с требованием, из которого он вырос.
- **CSV для Zephyr Scale** — файл `<документ>.r<ревизия>.zephyr-scale.csv`, только у набора, принятого ревью. Пользовательские поля
  Zephyr (АС, Команда…) у новых кейсов в нём пустые: заполните их перед импортом или один раз задайте шаблон выгрузки вашего
  проекта — тогда Камертон заполнит и CSV для импорта без ручных правок (HOW-TO-USE.md, раздел 6). Отклонённый набор — файлы
  `*.REJECTED.*` с замечаниями в шапке, без CSV.
- **Отчёт ревью** — приняты ли кейсы и что проверяющий потребовал исправить.
- **Отчёт прогона** — шаги, время, размеры входа модели, коды остановок; без кода проекта и текстов кейсов.
- **Вопросы аналитику** — `questions-for-analyst.md`: пробелы и неясности требований, найденные по дороге.
- **Автотесты** — позже и только в поставке с режимом автотестов: файлы тестов в проекте и команда запуска, которую выполняете вы.

## Что происходит

Камертон читает документы и код проекта, пишет кейсы и проводит их ревью. Пишет он в проект только своё:
папку прогонов `.pilot-runs/`, файл настроек `.skillsrc` и каталог публикации `published/` с готовыми кейсами —
`.pilot-runs/<run_id>/published`; в режиме автотестов — ещё сгенерированные тесты в тестовый корень модуля. Сам ничего не устанавливает, не обращается к сети и не запускает сборку, тесты и git: где в поставке есть автотесты, команду запуска печатает пакет, а выполняете её вы.

- **Изменение OpenSpec** — по умолчанию кейсы только по его требованиям. Требования базы, которые оно может задеть, названы строкой «Проверьте регресс:»; полную регрессию области даёт её `spec.md` в запросе (HOW-TO-USE.md, раздел 3).
- **Общая среда.** Кейсы считают, что в среде есть чужие записи: создают свои с меткой прогона и удаляют их шагом «Уборка» (что удалить нельзя без риска для чужих данных — называют словами), чужие не трогают. Среда только ваша — впишите у модуля в `.skillsrc` `"shared_data": false`.
- **Модуль только с тестами.** Первый запуск спросит, в какой папке код приложения, или ответ «кода приложения нет». В поставке с автотестами он сначала спросит имя переменной окружения с адресом стенда.

Режим автотестов (режим Б) входит в поставку профиля `mode-b`; в поставку `cases-only` он не входит. Профиль называет `doctor`.

## Что лучше иметь для гладкого запуска

- **Программу с доступом к модели**, которая умеет читать и писать файлы и выполнять команды. Лучше, если
  она умеет запускать проверяющего в отдельном контексте; если нет — ревью идёт в той же сессии.
- **Python 3.11–3.13.** Больше ничего ставить не нужно: сторонние пакеты и виртуальное окружение пакету не требуются.
- **Документы требований в UTF-8.**
- **Для импорта кейсов** — CSV-выгрузка Zephyr Scale (разделитель «,» или «;», UTF-8) или CSV Камертона
  профиля v5. CSV без единого кейса пакет не примет: остановит запрос до прогона.

Если ваш CLI ругается на шапку файлов `SKILL.md` (блок `permissions` в начале), напишите разработчикам.

## Ревью без отдельной сессии

Ревью идёт в одной из двух веток. `INDEPENDENT` — отдельная чистая сессия (или субагент), свежий контекст обязателен. `SELF` — если
в вашем CLI её не открыть: ревью в той же сессии, новую открывать не нужно, результат не называется независимым. Это нормальный режим,
а не сбой: отчёт показывает пометку, а принимается такой результат только по вашему согласию (флаг `--accept-self-review` на шаге ревью или в `scan`).

## Чем всё закончилось

Главное — вердикт ревью кейсов. В прогоне только кейсов `verification=NOT_APPLICABLE` и `accepted=false` ожидаемы: запуска
автотестов нет, ревью кейсы при этом не отвергло. В прогоне с автотестами итог другой: см. `accepted` в словаре ниже.

## Если команду оборвали

Прогон восстанавливается после обрыва процесса: следующая команда доводит или откатывает незаконченную запись журнала. Крах
операционной системы и отключение питания не обещаются: после них журнал мог остаться неполным, тогда команда назовёт
`JOURNAL_CORRUPT` и поможет начать новый прогон. Команды одного прогона не запускайте параллельно — вторая подождёт первую, а если
та идёт слишком долго, ответит `CONCURRENT_WRITER`.

## Что принести после прогона

Короткие ответы, без текстов требований и кейсов, без путей и названий систем:

1. Сколько минут прошло до первого шага модели и сколько занял весь прогон (`report.md`)?
2. Какая первая строка итога в `report.md` — дословно?
3. Где прогон останавливался: коды остановок, помог ли совет рядом с ними, сколько раз агент спрашивал вас?
4. Сколько кейсов в CSV и прошёл ли импорт в Zephyr?
5. Три главные помехи — что мешало больше всего?

## Словарь терминов

| Слово | Что значит |
| --- | --- |
| прогон (run) | одна папка `.pilot-runs/<run_id>` в проекте: всё, что Камертон записал по вашему запросу |
| попытка (attempt) | один заход внутри прогона: кейсы и ревью; закрывается итогом |
| ревизия (revision) | версия документа: `r1` — первая, `r2` — после правок по ревью, `r3` — после доработки отвергнутых ревью кейсов (она одна; остальные кейсы те же, что в `r2`); дальше версий нет |
| ревью принято (accepted) | в прогоне только кейсов `false` по определению; в режиме автотестов `true` — только если запуск, сделанный вами, прошёл по всем автотестам и ручных кейсов нет; главное — вердикт ревью |
| проверка (verification) | в прогоне только кейсов запуска нет: `NOT_APPLICABLE`; в режиме автотестов — результат запуска, сделанного человеком |
| покрытие (coverage) | автотесты создаются только в режиме автотестов; значение (`FULL`, `MIXED`, `MANUAL_ONLY`) справочное, на вердикт ревью не влияет |
| завершённость (completion) | `COMPLETE`, `PARTIAL` или `FATAL` (прогон не довели) |

## Для разработчиков пакета

В поставке — машинный контракт `contracts/pipeline.json` и его проекции `CONTRACTS.md` и `PIPELINE.md`. Справочник
разработчика, тесты и гейт пакета — только в репозитории разработчика.
