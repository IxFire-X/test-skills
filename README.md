# Трасса v0.1

**От требования до теста — по одной трассе.**

Трасса — набор инструкций для модели и Python-инструментов к ним. По документу требований к одной
функции она готовит тест-кейсы, отдаёт их на ревью и, если вы попросите, пишет автотесты,
проверяет их и запускает средствами вашего проекта.

Для кого: тестировщики и разработчики Java- и Python-проектов, которые работают в программе с доступом
к модели (CLI компании или похожей).

**Как начать — [HOW-TO-USE.md](HOW-TO-USE.md)**: подключение, проверка готовности, запросы для модели,
результаты, продолжение после перерыва и частые остановки.

## Что вы получаете

- **Тест-кейсы** — в HTML и Markdown для чтения и в JSON как исходный документ. Каждый кейс связан
  с требованием, из которого он вырос.
- **CSV для Zephyr Scale** — файл `<документ>.r<ревизия>.zephyr-scale.csv`; по шаблону выгрузки вашего
  проекта Трасса заполнит и CSV для импорта без ручных правок.
- **Отчёт ревью** — приняты ли кейсы и что проверяющий потребовал исправить.
- **Автотесты** (режим Б) — код тестов в тестовой папке проекта и отчёт их запуска.
- **Отчёт прогона** — шаги, время, размеры входа модели, коды остановок; без кода проекта и текстов кейсов.
- **Вопросы аналитику** — `questions-for-analyst.md`: пробелы и неясности требований, найденные по дороге.

## Два режима

| | А — только кейсы | Б — кейсы и автотесты |
| --- | --- | --- |
| Профиль | `cases-only-v1` | `local-pilot-v1` |
| Что делает | пишет кейсы и проводит их ревью | то же, затем пишет автотесты, проводит их ревью и запускает |
| Код проекта | не запускается | запускается сборкой проекта |
| Что нужно | Python 3.11+ и документ требований | плюс готовая тестовая среда проекта |

Профиль называете вы — в запросе модели и в команде проверки готовности. Режим Б работает только по вашему
явному разрешению и только в пределах текущего прогона. Если сборка проекта не готова, прогон Б честно
понижается до кейсов и говорит, что исправить.

## Что происходит в каждом режиме

**Режим А.** Трасса читает документы и код проекта, пишет кейсы и проводит их ревью. Код проекта, его сборка
и тесты не запускаются.

**Режим Б.** То же, а после принятых кейсов — автотесты: модель пишет их, отдельное ревью проверяет, затем
сборка проекта (Maven Wrapper, системный Maven, Gradle Wrapper или pytest) их запускает. Если тесты ходят
на стенд, его адрес берётся из переменной окружения, имя которой указано в `.skillsrc`.

В обоих режимах Трасса пишет в проект только своё: папку прогонов `.pilot-runs/`, файл настроек `.skillsrc`
и — в режиме Б — новые файлы тестов в тестовой папке модуля. Упавшие автотесты помечаются в карантин
(`@Disabled` / `xfail`), прошедшие остаются в проекте.

## Что лучше иметь для гладкого запуска

- **Программу с доступом к модели**, которая умеет читать и писать файлы и выполнять команды. Лучше, если
  она умеет запускать проверяющего в отдельном контексте; если нет — ревью идёт в той же сессии.
- **Python 3.11–3.13.** Больше ничего ставить не нужно: сторонние пакеты и виртуальное окружение пакету не требуются.
- **Документы требований в UTF-8.**
- **git**, если проект в git.
- **Для режима Б** — JDK и Maven или Gradle проекта (Maven Wrapper, `mvn` в PATH или Gradle Wrapper) либо
  Python с pytest; зависимости проекта настроены заранее; **тестовый стенд**, если тесты ходят на сервис.
- **Для импорта кейсов** — CSV-выгрузка Zephyr Scale (разделитель «,» или «;», UTF-8) или CSV Трассы
  профиля v5.

## Какие это автотесты

Это функциональные тесты приложения: запрос идёт через его HTTP-интерфейс, а за ним работают настоящие
компоненты и база проекта. Тест гоняется в самом процессе приложения (`@SpringBootTest` с MockMvc и базой проекта —
в Petclinic это H2) или, если модуль проекта объявляет стенд (`paths.context` и `service_url_env` в `.skillsrc`), —
по внешнему API поднятого стенда. Один запрос годится, если он проходит кейс и наблюдает его результат.

Чего Трасса не пишет: юнит-тесты отдельных классов и методов, UI-тесты (Selenium, Playwright). Сквозных
UI-тестов в этих версиях нет.

Ревью без отдельной сессии. Если в вашем CLI нельзя открыть для ревью отдельную чистую сессию, ревью идёт в
той же сессии и честно помечается `SELF`. Это нормальный режим, а не сбой: отчёт показывает пометку, а
принимается такой результат только по вашему согласию (флаг `--accept-self-review` в `scan`).

## Чем всё закончилось

В режиме А главное — вердикт ревью кейсов. `verification=NOT_APPLICABLE` и `accepted=false` здесь
ожидаемы: запуска автотестов в этом режиме нет, ревью кейсы при этом не отвергло.

В режиме Б полный принятый результат — `accepted=true` и `verification=PASS`. Иначе:

| Что видим | Как понимать |
| --- | --- |
| `FAIL` | Тесты упали: разберите отчёт — проблема в приложении, тесте или сборке |
| `UNKNOWN` | Надёжного результата нет: сначала выясните причину |
| `NOT_RUNNABLE` | Запустить нельзя при текущих условиях; причина — в отчёте |

## Словарь терминов

| Слово | Что значит |
| --- | --- |
| прогон (run) | одна папка `.pilot-runs/<run_id>` в проекте: всё, что Трасса записала по вашему запросу |
| попытка (attempt) | один заход внутри прогона: кейсы, ревью, при необходимости автотесты; закрывается итогом |
| ревизия (revision) | версия документа или автотестов: `r1` — первая, `r2` — после правок по ревью; третьей нет |
| ревью принято (accepted) | итог попытки: `accepted=true` — результат принят целиком; в режиме А он `false` по определению, главное там — вердикт ревью |
| проверка (verification) | как прошёл запуск автотестов: `PASS`, `FAIL`, `UNKNOWN`, `NOT_RUNNABLE`; без запуска — `NOT_APPLICABLE` |
| покрытие (coverage) | какая часть шагов автоматизирована: `FULL` — все, `MIXED` — часть осталась ручной, `MANUAL_ONLY` — ни одного |
| завершённость (completion) | `COMPLETE`, `PARTIAL` (часть кейсов без автотестов) или `FATAL` (прогон не довели) |
