# tc-to-autotest — Генератор автотестов

## Что это

AI-скилл, который превращает ручные тест-кейсы в готовый Java-код автотестов. Берёт тест-кейсы в формате Zephyr Markdown и генерирует DTO-классы, тест-классы с использованием JUnit 5, RestAssured, AssertJ и других enterprise-инструментов.

## Зачем нужен

Ручное написание автотестов — это много шаблонного кода: DTO, маппинг полей, assertions, настройка HTTP-клиента. Скилл автоматизирует эту рутину, сохраняя при этом трассировку: каждый тест-кейс превращается в метод с понятным названием и полным покрытием ожидаемых результатов.

## Как работает

Получает на вход утверждённые тест-кейсы (после валидации `tc-reviewer` или напрямую от `tc-generator`). Анализирует их, группирует для параметризации и генерирует:

- **DTO** — классы запросов и ответов с Lombok Builder
- **Тест-класс** — JUnit 5 тесты с RestAssured для HTTP и AssertJ для проверок
- **Матрицу трассировки** — таблица соответствия тест-кейсов и сгенерированных методов

Если в тест-кейсе есть шаги, которые нельзя автоматизировать без доступа к базе или логам — помечает их как `// TODO` с пояснением.

## Что генерирует

- `pom.xml` — зависимости (только для нового проекта)
- `ApiConfig.java` — конфигурация базовых URL и таймаутов
- `BaseApiTest.java` — базовый класс с настройкой RestAssured
- `*Request.java` / `*Response.java` — DTO для запросов и ответов
- `*Test.java` — тест-класс с `@Test` и `@ParameterizedTest` методами

## Ключевые принципы

- **Один тест-кейс = один тест-метод** (или участие в параметризованном тесте)
- **Data-Driven** — валидация одного поля через `@ParameterizedTest`, а не десяток отдельных `@Test`
- **Soft Assertions** — множественные проверки через `assertSoftly()`, чтобы видеть все падения сразу
- **Изоляция** — каждый тест использует уникальные данные, нет общего состояния между тестами

## Место в пайплайне

Третий этап. Получает тест-кейсы от `tc-reviewer` (или `tc-generator`), передаёт Java-код и матрицу в `autotest-reviewer`.
