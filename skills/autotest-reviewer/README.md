# autotest-reviewer — Валидатор автотестов

## Что это

AI-скилл, который проверяет сгенерированный Java-код автотестов на качество. Финальный этап пайплайна — убеждается, что все тест-кейсы покрыты кодом, нет анти-паттернов, все TODO обоснованы, технический стек соблюдён.

## Зачем нужен

Сгенерированный код не всегда идеален. Скилл ловит типичные проблемы: забытые тест-кейсы, `Thread.sleep` вместо нормальных асинхронных проверок, хардкод URL, общее состояние между тестами. Указывает на ошибки — но не исправляет сам, доработка идёт через повторную генерацию в `tc-to-autotest`.

## Как работает

Получает на вход три вещи: исходные тест-кейсы, матрицу трассировки (какой ТК → какой метод) и сам Java-код. Проверяет по пяти категориям:

1. **Traceability** — каждый тест-кейс из входа имеет соответствующий `@Test` или `@ParameterizedTest` метод в коде, и каждый шаг с ожидаемым результатом отражён в assertions
2. **Анти-паттерны** — сканирует код на `Thread.sleep`, хардкод URL, shared mutable state, пустые catch-блоки
3. **TODO-корректность** — все `// TODO` помечены обоснованно (нет доступа к БД, нужен лог-агрегатор и т.п.)
4. **WireMock** — если используются моки смежных сервисов, проверяет корректность настроек
5. **Стек** — используются ли заявленные инструменты (JUnit 5, RestAssured, AssertJ) без запрещённых замен

## Что выдаёт

- **Вердикт** — `ПРИНЯТО` (код готов к CI/CD) или `ТРЕБУЕТ ДОРАБОТКИ` (есть критические ошибки)
- **Отчёт** — список ошибок по каждой категории с пояснениями, что и где не так

## Что НЕ делает

- Не исправляет код автоматически (в отличие от `tc-reviewer`)
- Не проверяет компиляцию и синтаксис — это делает `javac` и линтер
- Не проверяет стиль кода — это делает Checkstyle

## Место в пайплайне

Четвёртый (финальный) этап. Получает код от `tc-to-autotest`. Если вердикт `ПРИНЯТО` — код готов к запуску. Если `ТРЕБУЕТ ДОРАБОТКИ` — замечания передаются обратно в `tc-to-autotest` для повторной генерации.
