# Скилл: Валидатор автотестов (Traceability + Анти-паттерны) — autotest-reviewer v1.3

**Когда применять:**
- "проверь сгенерированные автотесты"
- "отвалидируй Java-код автотестов"
- следующий шаг пайплайна после `tc-to-autotest`

**Место в пайплайне:**
`tc-generator` → `tc-reviewer` → `tc-to-autotest` → **`autotest-reviewer`**

**Примеры:** полный разбор Java-кода → вердикт — [examples.md](examples.md)

### СВЯЗЬ С PIPELINE: ЕДИНЫЙ СЛОВАРЬ ТЕГОВ

См. [`CONTRACTS.md`](../CONTRACTS.md) — **единственный источник истины** для имён XML-тегов и статус-маркеров. Этот скилл использует:

- **Вход:** `<test_cases>` / `<corrected_test_cases>` + `<automation_matrix>` + `<autotest_code>` (CONTRACTS.md §2 п.4-6, 8)
- **Выход:** `<autotest_review version="1.3">` (CONTRACTS.md §2 п.9) + `<review_verdict version="1.3">` (CONTRACTS.md §2 п.10) + опц. `<review_comments>` (CONTRACTS.md §2 п.11) + опц. `<corrected_autotest_code version="1.3">` (CONTRACTS.md §2 п.12)
- **Статус-маркеры:** `ПРИНЯТО`, `AUTO_FIX_APPLIED`, `ТРЕБУЕТ ДОРАБОТКИ` (CONTRACTS.md §3.2)
- **Атрибут `version`:** все корневые выходные блоки содержат атрибут `version="1.3"` для runtime-проверки совместимости Оркестратором.
- **Правило непереименования тегов:** `<autotest_review>` НИКОГДА не переименовывается в плоский `<review>`. Это имя зарезервировано каноном CONTRACTS.md.

## ГРАНИЦЫ ОТВЕТСТВЕННОСТИ

### Что проверяет autotest-reviewer (LLM-зона)

| Проверка | Описание |
|---|---|
| **Traceability** | Каждый `ТК-N` из входа имеет `@DisplayName("ТК-N: ...")` и запись в `<automation_matrix>` |
| **Анти-паттерны** | `Thread.sleep()`, хардкод URL/токенов, shared mutable state, пустые `catch` |
| **TODO-корректность** | Все `⚠` из исходных ТК отражены как `// TODO`, без выдуманной реализации |
| **WireMock-покрытие** | Для каждой внешней зависимости из ТК есть стаб (или явный `// TODO`) |
| **Стек** | Только инструменты из разрешённого стека (JUnit 5, RestAssured, AssertJ, WireMock, Allure, Awaitility) |
| **DRY (stub-методы)** | Stub-методы для внешних зависимостей не дублируются между тестовыми классами (см. [`../shared/stub-helper.md`](../shared/stub-helper.md)) |

### Что НЕ проверяет autotest-reviewer (зона компилятора / линтера / рантайма)

| Проверка | Почему не делаем |
|---|---|
| Компиляция / синтаксис Java | Задача `javac`, не LLM |
| Корректность импортов | Задача IDE / Checkstyle |
| Стиль кода (отступы, naming) | Задача Checkstyle |
| Рантайм-ошибки (гонки, таймауты) | Видны только при запуске |
| Логическая корректность assert'ов | Доверяем `tc-to-autotest` |

**ЗАПРЕЩЕНО:**
- Галлюцинировать ошибки там, где их нет
- Проверять то, что не входит в границы ответственности

### MACHINE-READABLE OUTPUT (v3.0+)

Помимо основного Markdown-вывода `<autotest_review>` + `<review_verdict>` + `<review_comments>`, скилл может формировать **структурированный JSON** по схеме:

- **Схема:** [`../schemas/autotest-reviewer-output.schema.json`](../schemas/autotest-reviewer-output.schema.json)
- **Флаг-триггер:** если Оркестратор передаёт тег `<output_format>json</output_format>` — вывод JSON **обязателен** в дополнение к Markdown.
- **Валидация:** перед отправкой JSON проверяется через [`../shared/schema-validator.md`](../shared/schema-validator.md) → `schema-validator validate --schema schemas/autotest-reviewer-output.schema.json --input <json>`.

**Структура JSON (ключевые поля):**

| Поле | Тип | Описание |
|------|-----|----------|
| `meta` | object | Метаданные: версия схемы, дата валидации, источник данных |
| `source` | object | Источники: `test_cases_type` (test_cases / corrected_test_cases), `automation_matrix_version`, `autotest_code_files[]` |
| `verdict` | string | `PASS` / `AUTO_FIX_APPLIED` / `NEEDS_REWORK` |
| `summary` | object | `total_critical`, `total_warnings`, `total_checked_tc_ids` |
| `traceability` | array | По каждому `tc_id`: `found_in_code` (true/false), `found_in_matrix` (true/false), `method_name`, `display_name`, `missing_assertions[]`, `conflicts_with_analytics[]` |
| `anti_patterns` | array | По каждому найденному анти-паттерну: `type` (thread_sleep/hardcoded_url/shared_state/empty_catch/...), `severity` (CRITICAL/WARNING), `location` (file:line), `suggestion` |
| `todo_correctness` | array | По каждому `⚠`-маркеру: `tc_id`, `marker_text`, `reflected_in_code` (true/false), `todo_location` |
| `wiremock_coverage` | array | По каждой внешней зависимости: `dependency_name`, `has_stub` (true/false), `stub_location`, `has_todo` (true/false) |
| `stack_compliance` | object | `violations[]` с полями `tool_name`, `severity`, `location` |
| `autofix_applied` | array | (Только при AUTO_FIX_APPLIED) список применённых автофиксов: `type`, `location`, `before`, `after` |

**Правило:** JSON не заменяет Markdown — он дополняет его для автоматической обработки Оркестратором и CI/CD-пайплайном.

## РЕЖИМ A: РУЧНОЙ СБОР КОНТЕКСТА
*Выполняй только в Режиме A.*

### A.1 Первичный опрос и БЛОКИРОВКА ВАЛИДАЦИИ
Если контекст не предоставлен, задай пользователю ОДИН уточняющий запрос:
> «Чтобы провести валидацию автотестов, предоставь:
> 1. Исходные тест-кейсы (в формате Zephyr Markdown, `ТК-N`).
> 2. Сгенерированный Java-код автотестов (DTO + тест-класс) и `<automation_matrix>` (если есть).»

**КРИТИЧЕСКИ ВАЖНО:** После вопроса — СТОП. ЗАПРЕЩЕНО выводить `<autotest_review>` до ответа пользователя.

### A.2 Явная фиксация контекста
Перед валидацией выведи **только те теги, данные которых были получены от пользователя в текстовом виде** (не обёрнуты в XML-теги на входе). Если пользователь передал данные уже в тегах — не дублируй их, а подтверди получение:

```
✅ Контекст получен:
- <test_cases>: [краткое описание, например "3 ТК: ТК-1, ТК-2, ТК-4"]
- <automation_matrix>: [например "6 записей"] или "отсутствует"
- <autotest_code>: [например "DTO + тест-класс, ~140 строк"] или "отсутствует"
```

Если данные были в свободной форме (без тегов) — оберни их в теги фиксации:

```xml
<test_cases>
[Исходные ТК в Zephyr Markdown]
</test_cases>

<automation_matrix>
[Матрица ТК-N → методы — или "отсутствует"]
</automation_matrix>

<autotest_code>
[Полный Java-код автотестов: DTO + тест-класс]
</autotest_code>
```

Только после фиксации переходи к секции РОЛЬ.

## КРИТИЧЕСКИЕ ПРАВИЛА

1. **Приоритет аналитики.** Если автотест реализует проверку, противоречащую `<analytics_documentation>`, это всегда критическая ошибка, независимо от соответствия ТК.
2. **Traceability.** Каждый `ТК-N` из `<test_cases>` / `<corrected_test_cases>` должен иметь:
   - запись в `<automation_matrix>`;
   - `@DisplayName("ТК-N: ...")` в коде;
   - хотя бы один assertion, `.body()`, `verify()` или явный `// TODO: ⚠`, отражающий ожидаемый результат каждого шага.
3. **Анти-паттерны.** Любое наличие `Thread.sleep()`, хардкода URL/порта в теле теста, shared mutable state, пустого `catch`, запрещённых инструментов — критическая ошибка.
4. **TODO-корректность.** Каждый `⚠` из исходных ТК должен быть отражён как `// TODO` без выдуманной реализации.
5. **Без Автофикса критических ошибок.** Все критические ошибки требуют возврата в `tc-to-autotest`. Автофикс разрешён только для предупреждений.

## АЛГОРИТМ ВАЛИДАЦИИ

**Главный принцип:** твоя задача — найти смысловые расхождения между исходными ТК и Java-кодом. Синтаксис и компиляция — не твоя забота. **ЗАПРЕЩЕНО** менять логику теста, если она соответствует ТК и аналитике.

---

Перед выводом вердикта заполни `<autotest_review>`:

### 1. Traceability: ТК-N → @DisplayName → Шаги
- Выпиши все `ТК-N` из `<test_cases>` / `<corrected_test_cases>`.
- Для каждого `ТК-N` найди соответствующий метод с `@DisplayName("ТК-N: ...")` в коде.
- Проверь, что каждый `ТК-N` есть в `<automation_matrix>` (если матрица предоставлена).
- **Проверка покрытия шагов:** для каждого шага ТК с ожидаемым результатом (HTTP-код, тело ответа, запись в БД, лог) проверь наличие соответствующего `assertThat`, `.body()`, `verify()` или явного `// TODO: ⚠` в коде.
- **Ошибка (КРИТИЧЕСКИ):** `ТК-N` из входа отсутствует в коде или в матрице.
- **Ошибка (КРИТИЧЕСКИ):** шаг ТК с ожидаемым результатом не отражён в коде (нет assertion, нет TODO).
- **Ошибка (КРИТИЧЕСКИ):** Код или ТК противоречат аналитике (при наличии `<analytics_documentation>`). Приоритет всегда у аналитики.
- **Замечание к входу (не к коду):** если `<automation_matrix>` содержит `ТК-N`, отсутствующие во входных `<test_cases>` / `<corrected_test_cases>` — выведи замечание, но не считай это ошибкой кода.

### 2. Анти-паттерны (скан кода)
Просканируй Java-код на наличие:

| Анти-паттерн | Маркер | Severity |
|---|---|---|
| `Thread.sleep()` вместо Awaitility | `Thread.sleep(` | КРИТИЧЕСКИ |
| Хардкод URL/порта | `"http://`, `"https://` в теле тестового метода (не в конфигурационных классах, константах класса или ApiConfig) | КРИТИЧЕСКИ |
| Shared mutable state | `static` не-final поле в тест-классе | КРИТИЧЕСКИ |
| Жёсткие assert'ы без SoftAssertions | `assertThat(...).isEqualTo(...)` подряд 2+ раз на **одно и то же поле** DTO без `.as("...")` | ПРЕДУПРЕЖДЕНИЕ |
| Пустой catch | `catch (Exception e) { }` | КРИТИЧЕСКИ |
| Отсутствие `.as("...")` | `assertThat(...)` без цепочки `.as(...)` в сложных проверках | ПРЕДУПРЕЖДЕНИЕ |
| `@Test` вместо `@ParameterizedTest` | Несколько методов с похожими названиями, проверяющих одно поле (рекомендация — не автоматическое правило) | ПРЕДУПРЕЖДЕНИЕ |

**Примечание про Hamcrest:** матчеры Hamcrest (`org.hamcrest.Matchers.*`), используемые внутри RestAssured `.body(...)` — **допустимая практика**, т.к. это часть API RestAssured для проверки JSON-тела, а не отдельный assertion-фреймворк. Это НЕ нарушение стека.

### 3. TODO-корректность
- Найди все `⚠` в исходных ТК.
- Проверь, что каждому `⚠` соответствует `// TODO: ...` в коде с текстом маркера.
- **Ошибка (КРИТИЧЕСКИ):** `⚠`-маркер не отражён в коде, или вместо `// TODO` написана выдуманная реализация.

### 4. WireMock-покрытие
- Выпиши все внешние зависимости из ТК (смежные сервисы).
- Проверь наличие `WireMock.stubFor(...)` или `// TODO: WireMock` для каждой.
- **Ошибка (ПРЕДУПРЕЖДЕНИЕ):** внешняя зависимость без стаба и без `// TODO`.

### 5. Соответствие стеку
- Проверь, что используются только инструменты из разрешённого стека:
  - ✅ JUnit 5 (`@Test`, `@ParameterizedTest`, `@BeforeEach`)
  - ✅ RestAssured (`given()`, `when()`, `then()`)
  - ✅ AssertJ (`assertThat()`, `SoftAssertions`)
  - ✅ WireMock (`stubFor()`)
  - ✅ Allure (`@Step`, `@Feature`)
  - ✅ Awaitility (`await()`)
  - ✅ Lombok (`@Data`, `@Builder`, `@NoArgsConstructor`, `@AllArgsConstructor`)
  - ✅ Jackson (`@JsonInclude`, `@JsonProperty`) — для DTO
  - ✅ Hamcrest-матчеры **только внутри RestAssured `.body()`** (не как основной assertion-фреймворк)
- **Ошибка (ПРЕДУПРЕЖДЕНИЕ):** использование инструмента вне стека (например, TestNG, Hamcrest `assertThat()` вместо AssertJ `assertThat()`).

### 6. DRY (дублирование stub-методов)
> См. [`../shared/stub-helper.md`](../shared/stub-helper.md) — контракт для этой проверки.
- Найди в `<autotest_code>` методы, мокирующие внешние зависимости через WireMock (паттерн имени `stub*Success`/`stub*Declined`/`stub*Failed` и аналогичные).
- Проверь, определены ли идентичные (или почти идентичные) stub-методы в НЕСКОЛЬКИХ тестовых классах вместо единственного определения в `BaseApiTest`.
- **Ошибка (ПРЕДУПРЕЖДЕНИЕ):** stub-метод дублируется в 2+ тестовых классах — нарушение DRY. Рекомендация: перенести в `BaseApiTest`, вызывать через `this.stubXxx(...)`.
- **Не является ошибкой:** тестовый класс вызывает stub-метод, унаследованный от `BaseApiTest` (`this.stubXxx(...)` или `stubXxx(...)` без переопределения).

## ВЕРДИКТЫ


| Вердикт | Условие |
|---|---|
| **ПРИНЯТО** | 0 критических ошибок и ≤ 2 предупреждений |
| **AUTO_FIX_APPLIED** | 0 критических ошибок, 3+ предупреждений, все предупреждения исправимы автофиксом |
| **ТРЕБУЕТ ДОРАБОТКИ** | 1+ критических ошибок, либо предупреждения не исправимы автофиксом |

**Пороги принятия:**
- **ПРИНЯТО:** 0 критических ошибок + не более 2 предупреждений (предупреждения можно игнорировать или исправить вручную)
- **AUTO_FIX_APPLIED:** 0 критических ошибок + 3+ предупреждений, все из которых исправимы автоматически (например: добавление `.as("...")`, замена `@Test` на `@ParameterizedTest`, добавление `SoftAssertions`)
- **ТРЕБУЕТ ДОРАБОТКИ:** 1+ критических ошибок (Thread.sleep, хардкод URL, пропущенный ТК-N, отсутствующий TODO) ИЛИ предупреждения, требующие ручной доработки

**Автофикс (новое в v1.1):**
В отличие от предыдущей версии, autotest-reviewer теперь может применять автофикс для **предупреждений** (не критических ошибок). Автофикс применяется только к предупреждениям, которые можно исправить безопасно:
- ✅ Добавление `.as("описание")` к `assertThat` без описания
- ✅ Объединение нескольких `assertThat` в `SoftAssertions`
- ✅ Замена `@Test` на `@ParameterizedTest` для похожих тестов
- ❌ НЕ исправляются критические ошибки (Thread.sleep, хардкод URL, пропущенные ТК-N, расхождение с аналитикой) — это требует возврата в `tc-to-autotest` или в `tc-generator`/`tc-reviewer`.

При `AUTO_FIX_APPLIED` выводится `<corrected_autotest_code>` с исправленным кодом.

**Действие при ТРЕБУЕТ ДОРАБОТКИ:**
- Вывести `<autotest_review>` с `VERDICT: ТРЕБУЕТ ДОРАБОТКИ`.
- Перечислить критические ошибки и неисправимые предупреждения.
- **Пайплайн приостанавливается.** Оркестратор не передаёт `<corrected_autotest_code>` дальше автоматически. Возврат в `tc-to-autotest` возможен только после подтверждения пользователя или повторной валидации с вердиктом `ПРИНЯТО`/`AUTO_FIX_APPLIED`.
