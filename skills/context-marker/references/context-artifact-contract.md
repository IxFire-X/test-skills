# Контракт артефакта контекста

Машинным источником истины является схема
[context-marker-output.schema.json](../../../schemas/context-marker-output.schema.json).

Названия полей и правила валидации бери из схемы. Этот документ определяет
порядок создания артефакта.

- Установи `schema_version` в `2.1.0`, а `stage` — в `context-marker`. Заполни обе обязательные ветви `artifacts` подтверждёнными непустыми данными.
- Для каждого подтверждённого требования сохрани точный смысл текста и точную ссылку на источник в `provenance`: JSON Pointer для JSON либо `path#anchor` / `path:line` для текста. Каждый элемент `requirements[].provenance` содержит только ссылку: без цитаты, описания, разделителя ` — ` и любого суффикса. Если структурированная запись содержит отдельные поля исходного идентификатора и текста утверждения, `provenance` обязательно содержит ссылки на оба поля в таком порядке: сначала идентификатор, затем текст. Исходный идентификатор не является ID вида `REQ-*`. Наблюдения по исходному коду и предупреждения сохраняй строками со встроенной ссылкой на источник: `<ссылка> — <точное наблюдение или пробел в данных>`. Для `requirements[].provenance` этот формат не применяется.
- Самостоятельные контекстные метаданные — метод, маршрут, путь, модуль или символ — сохраняй как наблюдения по источнику. Не превращай их в требования без явного описания поведения или критерия приёмки. Не удаляй подтверждённые метаданные.
- Для каждого требования к поведению или критерия приёмки проверь наличие в разрешённых источниках действия либо условия и внешне наблюдаемого результата: статуса, поля ответа, кода ошибки, состояния или события. Сохрани в тексте требования достаточно подтверждённых сведений, чтобы его можно было однозначно проверить. Одного маршрута или метода недостаточно. Подтверждения могут находиться в нескольких разрешённых источниках: объединяй только точные факты и добавляй `provenance` каждого из них в детерминированном порядке. Не копируй секретные значения или учётные данные, но сохраняй несекретные наблюдаемые результаты — например HTTP-статус, наличие или отсутствие поля ответа, событие либо состояние. Если наблюдаемый результат в разрешённых источниках отсутствует, сохрани частичное описание поведения и добавь предупреждение о пробеле вместо выдуманного ожидаемого результата.
- Назначай канонические ID детерминированно. Только для сортировки нормализуй каждую ссылку и точный текст утверждения: примени Unicode NFC, удали пробелы по краям, замени `\` на `/` и сверни каждую последовательность пробельных символов в один ASCII-пробел. Представляй ссылку парой `(нормализованная_ссылка, исходная_ссылка)` и сортируй пары по порядковому значению сначала нормализованной, затем исходной ссылки. Исключение: пара ссылок «идентификатор — текст утверждения» всегда сохраняет именно этот порядок. Требования сортируй по упорядоченному кортежу нормализованных ссылок, кортежу исходных ссылок, нормализованному точному тексту и исходному точному тексту — во всех случаях по порядковому значению кодовых точек. После этого назначь `REQ-0001`, `REQ-0002` и далее.
- Если источник содержит собственный идентификатор, сохрани его происхождение в `provenance`, но всё равно сопоставь требованию канонический ID вида `REQ-####`. Не переноси автоматически некорректный идентификатор или идентификатор другого формата.
- По возможности сохраняй исходные формулировки. Любое неподтверждённое утверждение, включая утверждение заказчика, которого нет в разрешённых источниках, может быть только предупреждением о пробеле. Оно не становится требованием или фактом об исходном коде.
