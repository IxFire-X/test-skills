# Запуск test-skills на внутреннем проекте (Linux, свой CLI и модели)

Комплект — папка `kit/` ветки `demo-kit-20261015`, без архивов: `test-skills/` (пакет, коммит 54eb8b9 ветки `main`; без `tests/`,
`docs/*.pptx`, `CLAUDE.md`, `.github/`), `test-skills-54eb8b9.files.sha256` (суммы его файлов), `wrap/`, `bench/`,
`preflight.py`, `operate.py`, этот файл. Ниже `~/ts` — каталог комплекта; он может лежать и внутри проекта (раздел
«Размещение внутри проекта»). Из проекта сюда не возвращается ничего — только тексты ошибок и служебные логи (п. 7).

## Запуск: три команды

```bash
mkdir -p ~/ts && cp -r <комплект>/. ~/ts/ && cd ~/ts
python3 operate.py init --project <проект> --docs <спека в проекте> --model <модель> \
  --cli-command '/opt/llm/bin/cli chat --model {model}'
```

1. **`init`** проверяет комплект, находит модуль и сборку, подбирает форму вызова CLI (первый ответ модели), решает про
   `--target`, записывает `.skillsrc` (покажет diff), показывает список файлов, которые уйдут в модель, и спрашивает
   подтверждение, замеряет первую задачу без модели и печатает **одну готовую команду** — строку «Запуск (шаги 0–2 и 4
   init уже сделал): …» — и что ещё спросит прогон (подробно — «Шаги operate.py подробно» → «init»).
2. **Команда из вывода `init`** (`… --only 5a`) — пробный прогон: разметка, кейсы и их ревью за 30–60 минут; отправку
   этого же списка файлов он второй раз не спрашивает. Итог `completion: COMPLETE` — можно идти дальше.
3. **Полный прогон** — та же команда с `--only 1,5,7,8` вместо `--only 5a`: preflight проекта, автотесты (перед их
   запуском — одобрение файлов), прогон
   сборкой, отчёт `~/ts/report/` и CSV для Zephyr. Бенчмарк моделей по ролям (шаг 3) — по желанию, `--only 3`.

**Если остановился** — любой шаг печатает «СТОП на шаге N: …» и строку «Что делать» или «Продолжить после
исправления» с **готовой командой**: исправить сказанное и выполнить её. Вопросы драйвера (`ask_user`) задаются в
терминале; без терминала — та же готовая команда с `--answer метка=значение` или флагом подтверждения. Что прислать
после прогона — п. 7.

Ниже — справочник: поставка и интерпретатор, права и сеть, размещение, все шаги `operate.py` и ручные команды пакета
(пп. 0–8).

## Поставка, раскладка, интерпретатор

Для ревью безопасности поставка — папка `kit/` целиком: происхождение, сверка (`sha256sum -c` по
`test-skills-*.files.sha256` и `kit-files.sha256`), что в поставке (в том числе `test-skills/evals/` и почему) и чего
нет (`tests/` пакета, `docs/*.pptx`, `CLAUDE.md`, `.github/`), откат — `PROVENANCE.md`; описание в формате протокола
ревью — `SKILL.md`.

Раскладка «всё из `kit/` в `~/ts/`» — рекомендация, а не требование: `operate.py` берёт `preflight.py`, `wrap/` и
`bench/` рядом с собой, а `--home` — только место пакета (`test-skills/` и `test-skills-*.files.sha256`), каталога
раннера, состояния и отчёта. Например, `~/ts/kit/operate.py --home ~/ts` работает так же, как `~/ts/operate.py --home ~/ts`.

**Интерпретатор.** Пакет запускается Python'ом из `~/ts/test-skills/.venv` (`bin/python`, на Windows
`Scripts\python.exe`), если такой venv есть, иначе тем, которым запущен `operate.py`; у него должны быть `jsonschema` и
`pyyaml` — иначе шаг 0 останавливается с командой установки. **Ни один скрипт комплекта не запускается по shebang**:
обёртка CLI всегда идёт как `[python, wrap.py, exec, …]` (в некоторых окружениях `execve` скрипта по `#!` запрещён —
код 126 / `Operation not permitted`), поэтому `chmod +x` для `wrap.py`, `preflight.py`, `bench.py` не нужен.

## Права и сеть

Что пакет читает, пишет, какие процессы запускает и куда при этом может ходить сеть — раздел USAGE.md «Права, сеть и
исполнение» (манифест прав пакета). Коротко, для этого комплекта:

- **Модель.** Задачи — части спеки и кода проекта — уходят модели через ваш CLI (`wrap/wrap.py` → команда из
  `wrap.json`) на тот адрес, который настроен в самом CLI. Сам `wrap.py` в сеть не ходит. Секреты в `extra_env` обёртка
  не принимает: учётные данные модели — в конфиге CLI. Если у CLI есть режим «без инструментов / read-only», его флаги —
  в `sandbox_args` (`--sandbox-args` у `operate.py`), иначе модель внутри CLI может сама читать и менять файлы.
  Окружение CLI — белый список (S6): `PATH`, `HOME`, `JAVA_HOME`, `LANG`, `LANGUAGE`, `LC_*`, `TMP*`, `TEMP`,
  `PYTHONUTF8`, `PYTHONIOENCODING` (вывод UTF-8 у CLI на Python) и системный минимум Windows; всё остальное (токены, прокси, переменные самого CLI) — только явно, через `env_passthrough` в
  `wrap.json` (`--env-passthrough 'GIGACODE_*,HTTPS_PROXY'` у `operate.py`; имя или префикс со `*` в конце). Какие
  имена дошли до CLI — `wrap/wrap.py exec --verbose …` (только имена, без значений).
- **Сборка и тесты.** Пакет запускает сборку проекта (Maven/Gradle), сгенерированные моделью тесты и PIT. Шаг 4
  `operate.py` пишет в `.skillsrc` `modules[].test.offline: true`: все сборки модуля и этапа мутаций идут с `-o` /
  `--offline`, только из `~/.m2` (кэша Gradle), без сети; нет артефакта — прогон останавливается
  (`BUILD_FAILED_BEFORE_TESTS` с «offline: артефакт не найден…» или `MUTATION_TOOL_MISSING`), а не скачивает его.
  `--online` — не включать offline: тогда сборка может ходить в репозитории из `~/.m2/settings.xml`.
- **Пины мутаций.** Jar'ы PIT и плагина-резолвера `maven-dependency-plugin` 3.8.1 закреплены по SHA-256
  (`test-skills/tools/mutation_tools.json`); резолвер и `junit-platform-launcher` версии проекта должны заранее лежать
  в `~/.m2` — preflight проверяет оба (резолвер — по SHA-256), пакет проверяет их до запуска Maven.
- **pip.** `operate.py` ничего не ставит: если нет `jsonschema`/`pyyaml`, он печатает команду
  `pip install --require-hashes -r test-skills/requirements.txt` (хеши всех файлов — в `requirements.txt`) и
  останавливается.
- **`operate.py` и `preflight.py`** сами в сеть не ходят; пишут только в каталог комплекта, а в проект — `.skillsrc`
  (шаг 4, после показа diff и подтверждения) и `chmod +x mvnw/gradlew` (шаг 1, с подтверждением). `--yes` эти два
  подтверждения не снимает — для них отдельные `--yes-skillsrc` и `--yes-chmod`.

## Размещение внутри проекта

Если писать вне проекта нельзя, комплект кладётся в проект, например в `<проект>/.ts`, и `operate.py` получает
`--home <проект>/.ts`. Тогда всё остаётся внутри:

- каталог процессов модели — `<home>/.runner` (вместо `<home>/runner`), временные файлы обёртки — `<home>/.tmp`
  (ключ `tmp_dir` в `wrap.json`); прогон пакета — как всегда, в `<проект>/.pilot-runs`;
- preflight печатает строку excludes линтера (nohttp, checkstyle, spotless …) сразу для `.pilot-runs` и `<home>` — её
  нужно вставить на ветке прогона, иначе линтер прочтёт файлы пакета и раннера и сборка упадёт. Исключается весь
  `<home>`, а не только `.runner` и `.tmp`: в нём лежит и сам пакет, а в его документации есть `http://` (nohttp);
- `<home>` добавить в `.gitignore` ветки прогона (или `.git/info/exclude`), чтобы комплект не попал в коммит.

Каталог раннера внутри проекта пакет принимает: в `driver-log.jsonl` пишется предупреждение
`RUNNER_DIR_INSIDE_PROJECT` — это ожидаемо, линтеры от него защищает строка excludes выше. Корень проекта, `.pilot-runs`
и `.git` как каталог раннера не принимаются.

## Шаги operate.py подробно

### init

Одна команда от распаковки до готовой команды прогона (цель — первый ответ модели за 15 минут и не больше 5 решений):

```bash
mkdir -p ~/ts && cp -r <комплект>/. ~/ts/ && cd ~/ts
python3 operate.py init --project <проект> --docs <спека в проекте> --model <модель> \
  --cli-command '/opt/llm/bin/cli chat --model {model}'
```

`init` по очереди: проверяет комплект и интерпретатор (шаг 0); находит модуль (из `.skillsrc` пакетным парсером, а
без `.skillsrc` — по разбору пакета без записи; при нескольких модулях — тот, где лежит спека) и сборку; пробует CLI
модели через `[python, wrap.py]` в формах stdin → stdout и «задача последним аргументом» (если в команде есть
`{prompt_file}`/`{answer_file}` — только файловая форма) и пишет удачную в `wrap/wrap.json` — это первый вызов модели;
решает про `--target` (модуль влезает в окно — не нужен; не влезает — угадывает каталог по словам спеки или
показывает до 5 каталогов-кандидатов); выполняет шаг 4 — запись `.skillsrc` с diff и подтверждением (без терминала —
`--yes-skillsrc`) — до замера, чтобы прогон шёл уже с итоговым `.skillsrc`; замеряет
первую задачу модели командой драйвера `next` без вызова модели — с пакетом S5 перед этим показывает документы и файлы
с размерами (копия списка — `~/ts/context-files.txt`) и спрашивает подтверждение отправки (y/n, `--yes-send`), «нет» —
стоп с подсказкой сузить вход; удаляет замерный прогон (git status проекта остаётся как был, кроме записанного
`.skillsrc`); запускает preflight «тихо» — до первого прогона показывает только файлы с ПДн/секретами, остальное —
списком «до полного прогона». В конце печатает одну готовую команду (`… --only 5a`, с `--answer
confirm-context=<дайджест>` после подтверждения), что ещё спросит прогон, и сводку: время до первого вызова модели,
остановок до него, решений впереди. Тема прогона — первый заголовок спеки (`--subject` — своя). Каждая проблема — одна
строка «Что делать» с готовой командой. В проект `init` пишет только `.skillsrc` (шаг 4, после diff и подтверждения); в
комплект — `wrap/wrap.json` (прежний — в `wrap.json.orig`), `init.json`, `context-files.txt`, `operate.log`. Время до первого вызова модели и число остановок до него попадают и в
`report/summary.md` (шаг 7).

### Шаги 0–8 одним скриптом

`operate.py` выполняет пункты 0–8 ниже по порядку: Python 3.11+, только stdlib; сам в сеть не ходит и ничего не
ставит, а что делают запущенные им процессы — в разделе «Права и сеть». Шаги: 0, 1, 2, 3, 4, 5a, 5, 7, 8.
Каждый шаг печатает свои команды, коды выхода и главные строки, а весь вывод пишет в `~/ts/operate.log`.
Подтверждения y/n снимает `--yes` (кроме правки `.skillsrc` и `chmod +x` файлов проекта — см. выше). Если шаг упал,
скрипт печатает подсказку и останавливается; после исправления продолжить с того же шага — `--from-step N`.
`--dry-run` только печатает команды, ничего не запускает.

```bash
mkdir -p ~/ts && cp -r <комплект>/. ~/ts/ && cd ~/ts
python3 operate.py --home ~/ts --project <проект> --docs <спека в проекте> --subject "<тема по-русски>" \
  --models glm-5.3,deepseek-0731-flash,qwen3.6-27b,qwen3.8-27b \
  --cli-command '/opt/llm/bin/cli chat --model {model}' --prompt-via stdin --answer-from stdout --cli-version '<cli> <версия>' \
  --module <id модуля из .skillsrc> --target <каталог фичи>
```

- **`--module` и `--target`.** Если в `.skillsrc` несколько модулей, `--module <id>` обязателен: без него (или с
  неизвестным id) шаги 4 и 5a останавливаются с перечнем id и корней модулей из `.skillsrc`. `--target <каталог фичи>`
  обязателен для проектов больше одного модуля или 1 МБ кода: без него разметка контекста получает весь модуль и не
  влезает в окно модели (см. «Арифметика контекста»).
- **Шаг 0.** Сверяет папку `test-skills/` с `test-skills-*.files.sha256` (лишние `.py` — тоже стоп), проверяет, что
  `preflight.py`, `wrap/`, `bench/` лежат рядом с `operate.py`, что у интерпретатора пакета есть `jsonschema`/`pyyaml`
  (нет — одна строка «запустите через интерпретатор пакета или поставьте: `… -m pip install --require-hashes -r …`» и стоп;
  `--no-pip` — ставить пакетами ОС), запускает doctor.
- **Шаг 1.** Preflight; файлы с секретами/ПДн печатаются всегда (до 20 на вид) с подсказкой, как их исключить, — они
  уходят в модель вместе с кодом модуля.
- **Шаг 2.** Записывает `wrap/wrap.json` из `--cli-command`/`--prompt-via`/`--answer-from`/`--answer-file`/`--sandbox-args`
  (плейсхолдеры — как в п. 2; `extra_env` прежнего `wrap.json` сохраняется), прогоняет селфтест и делает один живой вызов
  первой модели с показом ответа — той же командой, которую потом получит драйвер (`--review-runner-command`: аргументы
  пресета `codex` пакета, впереди `[python, wrap.py]`).
- **Шаг 3.** После бенчмарка предлагает модели по ролям. Для ревью кейсов и автотестов — по правилу п. 3, для
  остальных ролей — первая из `--models` (или `--default-model`). Свои назначения — `--role-model роль=модель`.
- **Шаг 4.** Пишет в `.skillsrc`:
  - `review_runner` и `requirements.id_pattern` (шаблон выводится из спеки или задаётся `--id-pattern`);
  - `mutation.enabled`, если мутации включены;
  - `test.offline: true` в каждом модуле (`--online` — не писать; если ключ уже есть — `false`);
  - если у модуля `adapter_id: maven-wrapper:selected-symbols-v1`, а `mvnw` нет и `mvn` есть в PATH (preflight: «mvnw нет,
    есть mvn в PATH») — `adapter_id: maven:selected-symbols-v1` и `executable: mvn` вместо `wrapper` (системный Maven).

  Перед записью показывает diff и спрашивает (`--yes` не отвечает, без терминала — `--yes-skillsrc`). Прежний
  `.skillsrc` копирует в `~/ts/skillsrc.bak-*`.
- **Мутации.** `--mutation` ставится, если preflight нашёл PIT в `~/.m2`; выключить — `--no-mutation`.
- **Шаги 5a и 5: размер первой задачи.** Прогон заводится командой `next` (драйвер сканирует проект и выдаёт первую
  задачу, модель не вызывается); `operate.py` печатает её вход в байтах и оценку в токенах (`--tokens-per-byte`, по
  умолчанию 0,24) против окна модели (`--model-context`, по умолчанию 239 144). Больше окна — стоп с подсказкой
  `--target`, модель не вызывалась; иначе тот же прогон продолжается `run --run <run_id>`.
- **Подтверждение отправки в модель (пакет с S5).** До первой задачи модели драйвер останавливается на
  `confirm-context`: `operate.py` показывает документы требований и файлы проекта строками «путь  байты» (первые 30),
  итог в байтах и путь к полному списку `listing_path` (`<run>.driver/context-files.txt`: «требования|контекст, байты,
  путь»). Проверить, что в списке нет ПДн, секретов и лишнего кода, и ответить дайджестом в терминале; без терминала —
  готовая команда с `--yes-send`: флаг отвечает только `confirmation_digest` показанного списка (`--yes` не отвечает).
  Лишнее — исключить (`--target`, `paths` модуля, `.gitignore`) и начать новый прогон. Для повторов на учебном проекте —
  `--confirm-context no` (или `.skillsrc` `context: {confirm: false}`). `init` показывает тот же список (копия —
  `~/ts/context-files.txt`) и спрашивает подтверждение сам (y/n, `--yes-send` отвечает): «да» — дайджест уходит в его
  замерный прогон и в готовую команду как `--answer confirm-context=<дайджест>`, и настоящий прогон с тем же набором
  файлов второй раз не спросит (с другим — спросит: дайджест не совпадёт); «нет» — стоп с подсказкой сузить вход.
  `.skillsrc` в список не входит (пакет с `54eb8b9`): пакет его читает, но модели не передаёт, и его правка дайджест не
  меняет; если для модели не осталось ни одного файла кода или документа — `scan` останавливается с `CONTEXT_EMPTY`
  (проверить `paths` модуля и `--target`).
- **Порог входа задачи (пакет с P1).** `operate.py` передаёт драйверу `--task-input-bytes` = 0,8 окна модели в байтах
  (`--model-context` / `--tokens-per-byte`; свой порог — `--task-input-bytes`): задача больше — `TASK_INPUT_TOO_LARGE` до
  вызова модели и стоп с готовой командой нового прогона с `--target`.
- **Автоматизация частями (пакет с P2).** Если кейсов больше `limits.automation_cases_per_part` в `.skillsrc` (по
  умолчанию 12; `0` — без лимита по кейсам) или вход генератора автотестов больше порога, драйвер делит кейсы на части и
  выдаёт задачи `tc-to-autotest:rN:part-NNN`; каждая часть пишет свои классы с маркером `PartNNN` в имени, ответы
  частей драйвер сливает сам. Ревью, одобрение тестов (одно, по всем файлам) и исполнение идут по слитой ревизии.
- **Одобрение сгенерированных тестов (пакет с S3).** После записи тестов в проект и до любой сборки драйвер
  останавливается на `approve-generated-tests`: `operate.py` показывает файлы строками «путь  дайджест» (первые 30,
  полный список — в `operate.log`) и `approval_digest`. Прочитать файлы и ответить в терминале дайджестом; без
  терминала — готовая команда с `--yes-exec`: флаг отвечает только `approval_digest` показанных файлов (`--yes` не
  отвечает). Правка файла меняет дайджест — нужно новое одобрение. Для повторов на учебном проекте —
  `--execution-review none` (или `.skillsrc` `execution: {review: none}`). Пробный прогон (`--only 5a`) тестов не
  исполняет и этой остановки не даёт.
- **Исполнение человеком (пакет с S9).** С `--execution-mode human` (или `.skillsrc` `execution: {mode: human}`) пакет
  сам не запускает ни сборку, ни тесты, ни мутации. После записи тестов (и одобрения, если оно включено) драйвер отвечает
  `human_exec`, и `operate.py` печатает команды по порядку — шлюз компиляции (`gate`) и тесты (`tests`): у каждой `cwd`
  и готовая строка для своей оболочки (PowerShell на Windows, bash на Linux; другая — в `operate.log`), список
  проверяемых тестов и куда команда пишет JUnit-отчёт. Выполнить команды самому, в своём окружении, и продолжить
  готовой командой из вывода: `… --from-step 5 --run <run_id> --junit <отчёт>` (отчётов может быть несколько; код
  выхода тестов — `--exit-code N`, шлюза — `--gate-exit-code N`, иначе — из отчёта). Отчёт должен быть новым файлом из
  указанного каталога, иначе драйвер ответит `HUMAN_REPORT_INVALID` и будет ждать дальше. Сборка идёт в окружении
  человека: фильтр секретоподобных переменных пакета к ней не применяется.
  **Мутации человеком (пакет с S9b).** С `--mutation` после тестов идут три остановки подряд — «мутации, шаг N из 3»:
  classpath проекта (`resolve-project`), jar'ы PIT (`resolve-tool`) и сам PIT (`pit`); каждая следующая команда зависит
  от вывода предыдущей. У команды напечатано, какой файл она должна записать. Продолжение — готовая команда из вывода:
  `… --from-step 5 --run <run_id> --mutation-step-done` после резолверов и `… --pit-report <этот путь>` после PIT
  (ровно напечатанный путь). Если файла нет или он пуст, `operate.py` останавливается сам, драйвер не вызывается.
  Пакет без S9b мутации в этом режиме не запускает (`NOT_APPLICABLE`, `HUMAN_EXECUTION_MODE`).
- **Шаг 5.** На `ask_user` показывает вопрос и ждёт ответа. На `regenerate-after-gate` и `BUILD_FAILED_BEFORE_TESTS`
  печатает хвост `runner-output.txt` и останавливается. Прерванный прогон продолжается так:
  `--from-step 5 --run <run_id> [--answer метка=значение]`. Если в проекте несколько целей — `--target <цель>`
  (передаётся драйверу).
- **Шаги 7–8.** Шаг 7 собирает `~/ts/report/`: файлы п. 7 и `summary.md` с цифрами прогона. Шаг 8 показывает путь
  к CSV для Zephyr.
- **Шаг 9 — обновление живого набора (`suite-update-v1`).** Только по запросу: `--only 9`; в обычную цепочку не входит.
  Нужен набор, записанный полным прогоном с `--suite` (иначе `SUITE_MISSING`). В режиме human (пакет с S9b) прогон
  набора и повторный прогон после ремонта запускает человек: остановка «живой набор, прогон набора (`suite-run`)» или
  «прогон после ремонта (`repair-run`)» с одной командой и местом её отчёта. Продолжение —
  `… --from-step 9 --run <run_id> --junit <отчёт или каталог отчётов> [--exit-code N]`; если сборка упала до отчёта —
  `--exit-code N --build-log <файл с выводом сборки>` вместо `--junit`. Повторы упавших методов в этом режиме не
  выполняются и метка FLAKY не ставится: упавший метод считается упавшим. Между прогонами возможно одобрение
  отремонтированного метода (`approve-generated-tests-repair`, `--yes-exec`). Перед шагом 9 убедиться, что
  excludes линтера из preflight (nohttp, checkstyle …) применены к `.pilot-runs`, `.runner` и `.tmp`: иначе `suite-run`
  или `repair-run` упадёт на линтере, прочитав записи прогонов — в том числе текущего (вывод упавшей сборки, переданный
  `--build-log`, сохраняется в `.pilot-runs`).

## 2. Обёртка CLI

Отредактировать `wrap/wrap.json` под свой CLI — одна из трёх форм (полные файлы — `wrap/examples/`; режим `arg` для
частей ревью не годится: задача 126–552 КБ, а Linux ограничивает один аргумент 128 КиБ):

```json
{"command": ["/opt/llm/bin/cli", "chat", "--model", "{model}"], "prompt_via": "stdin", "answer_from": "stdout"}
{"command": ["/opt/llm/bin/cli", "run", "-m", "{model}", "-i", "{prompt_file}", "-o", "{answer_file}"], "prompt_via": "file", "answer_from": "file", "answer_file": "{tmp}/answer.txt"}
{"command": ["/opt/llm/bin/cli", "ask", "--model", "{model}", "{prompt}"], "prompt_via": "arg", "answer_from": "stdout"}
```

Плюс по желанию `"timeout_seconds": 1700`, `"extra_env": {"LLM_ENDPOINT": "…"}` (имена с TOKEN, SECRET, PASSWORD,
API_KEY, `AWS_*`, `AZURE_*` обёртка отвергает — секреты в конфиг CLI), `"version": "<cli> <версия>"`, `"tmp_dir": "…"`
(где создавать временный каталог вызова; относительный — от `wrap.json`), `"sandbox_args": ["…"]` (флаги CLI «без
инструментов / read-only»: встают на место элемента `"{sandbox_args}"` в `command`, иначе в конец),
`"env_passthrough": ["GIGACODE_*", "HTTPS_PROXY"]` (переменные окружения, которые нужны CLI сверх белого списка — см.
«Права и сеть»; без них CLI их не получит). Если CLI
печатает JSON-конверт (`result`/`text`/`content`/`choices[0].message.content` и `usage`) — обёртка возьмёт текст и токены
сама. Проверка до бенчмарка:

```bash
python3 wrap/wrap.py --selftest --pack ~/ts/test-skills            # фальшивым CLI: «Итог: ок»
echo '{"x":1}' | python3 wrap/wrap.py exec --json --model <модель> --output-last-message /tmp/w.txt - && cat /tmp/w.txt   # живой CLI
```

## 4. `.skillsrc` проекта

```yaml
review_runner:
  preset: codex
  models: {context-marker: <м>, tc-generator: <м>, tc-reviewer: <м по бенчу>, tc-to-autotest: <м>, autotest-reviewer: <м по бенчу>, mutation-triage: <м>}
  max_parallel: 2          # локальные модели на одной машине: 1–2 одновременных вызова, иначе тайм-ауты
  timeout_seconds: 3600     # часть ревью у бюджета на локальной модели генерируется минутами
requirements: {id_pattern: '<шаблон ID требований спеки>'}
mutation: {enabled: true, threads: 2, timeout_seconds: 3600}   # для --mutation (без этого test_strength = NOT_APPLICABLE)
```

И в блоке `test` каждого модуля (`modules: - id: … test: …`) — `offline: true`: сборка и мутации только из `~/.m2`.

Бюджет части ревью: `--review-input-bytes` ≈ окно модели (токены) × «Б на токен» × 0,4; при окне 262k и ~3,5 Б/токен —
порядка 100 000 (меньше, если модель слабеет после 64–128k).

### Арифметика контекста

Задачи разметки, генератора и автоматизации получают полный контекст (код модуля + черновик требований) и не режутся.
Замер внутреннего прогона 2026-10-15 (DeepSeek-V4.1-Flash через gigacode): 0,24 токена на байт входа (≈ 4,2 Б/токен),
жёсткий лимит 239 144 токена → бюджет одной задачи ≈ 239 144 / 0,24 ≈ 1 000 000 Б. Задача разметки модуля `main` (377
файлов, 3 МБ инвентаря) дала 1 352 513 Б ≈ 323 000 токенов — в 1,32 раза больше лимита; код — 95,6 % входа, поэтому
резать спеку бесполезно. Отсюда:

- `--target <каталог фичи>` — обязателен для проектов больше одного модуля или 1 МБ кода; `--module` — при нескольких
  модулях;
- перед первой задачей модели `operate.py` печатает её `input_bytes` и оценку в токенах и останавливается, если она
  больше окна; для другой модели — `--tokens-per-byte` (по `bench-*.md`: 1 / «Б на токен») и `--model-context`.

## 5a. Пробный прогон (сначала)

Ранний сигнал по схеме и качеству за 30–60 мин: только разметка, генератор и ревью кейсов.

```bash
cd ~/ts/test-skills
python3 -m tools.pipeline_driver run --project <проект> --runner process --profile cases-only-v1 \
  --docs <спека> --subject "<тема>" --model-id <модель> --host-cli <имя CLI> --host-cli-version <версия> \
  --reviewer-isolation fresh --module <id> --target <каталог фичи> --review-runner-preset codex \
  --review-runner-command "[\"$HOME/ts/test-skills/.venv/bin/python\", \"$HOME/ts/wrap/wrap.py\", \"exec\", \"--skip-git-repo-check\", \"--sandbox\", \"read-only\", \"--ephemeral\", \"--json\", \"--model\", \"{model}\", \"--output-last-message\", \"{last_message}\", \"-\"]" \
  --runner-dir ~/ts/runner --review-input-bytes 100000 --max-tasks 2
```

`--review-runner-command` — JSON-массив: интерпретатор пакета, `wrap.py` и аргументы пресета `codex` пакета без `{cli}`
(`--review-runner-cli wrap.py` запускал бы обёртку по shebang). `operate.py` строит его сам из пресета пакета.

Итог `completion: COMPLETE` и кейсы в `test-cases`-проекциях — можно идти в полный прогон (п. 5). Код выхода 1 у
`cases-only-v1` — норма (черновик).

## 5. Прогон

```bash
cd ~/ts/test-skills
python3 -m tools.pipeline_driver run --project <проект> --runner process \
  --profile local-pilot-v1 --docs <спека> --subject "<тема по-русски>" --model-id <модель по умолчанию> \
  --host-cli <имя CLI> --host-cli-version <версия> --reviewer-isolation fresh \
  --module <id> --target <каталог фичи> --review-runner-preset codex --review-runner-command "<тот же JSON-массив, что в п. 5a>" \
  --runner-dir ~/ts/runner --review-input-bytes 100000 --max-tasks 2 \
  --mutation --analyst-report --suite
```

- `--runner-dir` — долговечный каталог (не `/tmp`): там входы и выходы процессов модели. По умолчанию — вне
  проекта; внутри проекта (`<home>/.runner`) — с предупреждением в журнале (раздел «Размещение внутри проекта»).
- Прервался (Ctrl+C, обрыв)? Продолжить тот же прогон: `… run --project <проект> --runner process --run <run_id>`. Каталог
  процессов прогон помнит сам (`config.json`), флаг повторять не нужно — но `~/ts/runner/<run_id>` не удалять и не
  переносить: уже запущенные вызовы модели собираются оттуда.
- Без PIT в `~/.m2` — убрать `--mutation`.

## 6. Если остановился

| Что в выводе | Что делать |
| --- | --- |
| `"action": "ask_user"`, код 3 | прочитать `question`; ответить повтором с `--answer <метка>=<значение>` (метка — хвост `task_id` после `.ask.`) |
| `ask.confirm-context` (пакет с S5) | открыть список `listing_path`; отправить — ответ `confirm-context=<confirmation_digest>` (в `operate.py` — ввод дайджеста или `--yes-send`); лишнее — исключить и начать новый прогон |
| `human_exec` (пакет с S9, `--execution-mode human`) | выполнить напечатанные команды по порядку в указанных `cwd`; продолжить готовой командой из вывода: тесты — `--junit <отчёт>`, мутации — `--mutation-step-done` / `--pit-report <путь>`, набор (шаг 9) — `--junit <отчёт>` или `--exit-code N --build-log <файл>`; `HUMAN_REPORT_INVALID` — отчёт не тот (не новый или не из указанного каталога); `HUMAN_STEP_INCOMPLETE` — команда шага не записала свой вывод |
| `ask.approve-generated-tests` (пакет с S3) | прочитать перечисленные файлы; одобрить — ответ `approve-generated-tests=<approval_digest>` (в `operate.py` — ввод дайджеста или `--yes-exec`); не одобрять — остановиться и поправить или удалить файлы |
| `ask.regenerate-after-gate` / `GENERATED_TEST_INVALID` | **не перегенерировать сразу**: открыть `.pilot-runs/<run>/artifacts/<attempt>/runner-output.txt` — если там линтер/сборка проекта, а не ошибки тестов, исправить окружение (п. 1) и начать новый прогон; перегенерация — только при ошибках компиляции самих тестов |
| `"action": "error"`, `code` | код и `message` — сюда (п. 7); `DRIVER_FAILURE` — дефект пакета |
| `RUNNER_*` в журнале (`RUNNER_TIMEOUT`, `RUNNER_EXIT_n`, `RUNNER_ANSWER_NOT_JSON`) | смотреть `~/ts/runner/<run>/runner/<задача>/stderr.txt` и `last-message.txt`; модель не держит схему → другая модель для роли или меньший `--review-input-bytes` |
| `completion: PARTIAL`, `reason_code` | `reason_code` — сюда |
| verification `FAIL` | ожидаемо при дефекте продукта: `quarantine.md` (вопрос аналитику и черновик баг-репорта) |

## 7. Что принести

Из `<проект>/.pilot-runs/<run>.driver/`: `driver-log.jsonl`, `config.json` (без секретов), итоговый JSON прогона (вывод
`run`), коды и тексты ошибок, хвост `runner-output.txt` (только строки ошибок Maven, без кода проекта), сводки
`candidate-bundle/test-strength.md` и число вопросов `analyst-report.md`. Не приносить: код, спеку, кейсы, ответы
моделей, `stdin.txt`.
