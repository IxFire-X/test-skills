# Проверка ревью по частям — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` to implement this plan task-by-task. Пользователь выбрал минимальное последовательное выполнение; не запускайте по агенту на каждый этап, не добавляйте тесты и не делайте коммиты автоматически по шаблону навыка. Ограничения пользователя имеют приоритет.

**Goal:** Сделать ревью кейсов и автотестов воспроизводимым и способным проверять одну задачу, целиком не помещающуюся в контекст, сохранив один общий проверяемый результат.

**Architecture:** Одна неизменная проверяемая версия, ограниченные пакеты, последовательные изолированные вызовы ревьюера, отдельные содержательные проверки полноты и связей, затем один итог из сохранённых свидетельств. Маленькая задача использует тот же механизм с одним пакетом. Контроллер отвечает за состав, привязки и сборку; модель — за смысл проверяемого материала.

**Tech Stack:** Существующие Python tools, JSON Schema, файловые receipts, append-only journal, совместимая рабочая CLI и выбранная пользователем модель. Новых зависимостей и сервиса вызова LLM нет.

**Spec:** Согласованные требования в разделе 1 этого документа. Это самостоятельная передача контекста, а не ссылка на недоступную переписку.

**Статус на 2026-10-05:** требования и общая схема подтверждены пользователем; реализация Tasks 0–5 выполнена, итоговая проверка Task 6 продолжается. Промпт запуска: [2026-10-05-bounded-review-prompt.md](2026-10-05-bounded-review-prompt.md).

## 1. Согласованные требования и границы

### Global Constraints

1. Приоритеты: воспроизводимость; масштаб одной задачи; затем размер репозитория. Стоимость и скорость пока не определяют выбор.
2. Воспроизводимость проверяется на одинаковых входах, версии пакета, CLI, модели и настройках: без ручного ремонта JSON/служебных полей, одинаковое решение о принятии/доработке, обнаружение подтверждённых существенных дефектов, явные пробелы при недостающих доказательствах. Формулировки и необязательные рекомендации могут различаться. Это критерий эксперимента, не математическая гарантия LLM.
3. Проверка по частям нужна в первой реализации. Пользователь ожидает задачи больше контекста около 260k токенов. Это ориентир объёма, НЕ новая константа, требование к модели или равенство токенов байтам.
4. Каждый вызов имеет свежий изолированный контекст, точные входы и собственное подтверждение изоляции от генератора. Последовательное добавление файлов в один растущий диалог не решает задачу.
5. После содержательного дефекта продолжать остальные проверяемые части. При повреждении/недостоверности входов блокировать затронутую область; при повреждении общего снимка дальнейшая проверка не считается достоверной. Всё непроверенное явно отражается в результате.
6. Нельзя принимать весь результат по частичному успеху, одним пересказам, числу ID или корректным хешам. Проверка исходных требований и смысловых связей между частями обязательна и тоже ограничена по контексту.
7. Сохранить точные digest/readback, ownership, append-only историю, изоляцию, закрытые схемы, запрет выдуманных API/ожиданий. Проверяющий сопоставляет оригинальные требования с кейсами, а автотесты — с реальным поведением приложения.
8. Сохранить существующие пределы исправлений: canonical r1 и максимум один полный механический r2; automation максимум r1/r2 с полным повторным ревью новой версии. Части не расходуют бюджет исправлений. Никакой регенерации после runtime FAIL.
9. Продукт остаётся copied skills + working CLI/LLM + проектные инструменты. DeepSeek был примером доступного уровня моделей, обязательной модели/провайдера нет.
10. Не менять смысл `cases-only-v1`, разрешения на исполнение и терминальные критерии `local-pilot-v1`. Статическое ревью не доказывает runtime PASS. `implemented_unverified` / `ready_tuple=null` сохраняются без отдельной квалификации.
11. Работать последовательно; сначала читать действительные вызовы, затем менять общую границу. Существующие адресные тесты в приоритете. Новое покрытие — только отсутствующие проверки текущего изменения, без новой инфраструктуры/широких матриц.
12. Не выполнять commit/push/merge/PR и необратимые операции в рамках этого плана. Для них требуется отдельное разрешение пользователя по его правилам подтверждения. Не сбрасывать, не чистить и не прятать прежний WIP.

### Не-цели и неизменяемая область

- Параллелизация ревью, деревья агентов, универсальный граф зависимостей, новый LLM runner, модельные адаптеры и второй legacy-путь для малых задач.
- Переписывание генераторов, поддержка новых стеков, новая система тестирования, оптимизация всего репозитория.
- Сокращение самой глубины проверки ради вместимости или перенос всего материала в последний «сводный» вызов.
- Перепроектирование выполнения, materialization, cleanup, retained rerun и финализации. Менять их потребителей лишь там, где новая общая граница требует этого.
- QUICKSTART остаётся человеческим объяснением продукта; предыдущие правки про запуск обычным промптом через CLI и отсутствие обязательной модели сохраняются.

**Предел обещания:** этот план масштабирует две стадии ревью. Он не доказывает, что предшествующая генерация произвольного объёма уже масштабируется. Блокер до ревью фиксируется отдельно, а не превращается в незапрошенный рефакторинг генерации.

## 3. Минимальный технический договор

Эти решения направляют реализацию. Имена новых функций ниже — планируемые, пока их в коде нет. При уточнении интерфейса обновить этот план и всех его потребителей; отдельного разрешения на обычное техническое уточнение не требуется.

### Состав и роли

- **Review plan:** тип ревью, snapshot/revision digest, упорядоченный состав обязательных единиц проверки, привязки к оригинальным источникам, назначение единиц пакетам и бюджет входа. Идентичные данные и настройки дают одинаковое начальное разбиение и ID.
- **Part:** собственный ID, состав проверок (`source`, `local`, `cross`), точная область, входные digest/ссылки, выделенный бюджет и actual invocation/isolation evidence. Один небольшой пакет может включать все применимые проверки; тип проверки не требует отдельного вызова. Область проверки и приложенный справочный контекст различаются: чтение зависимости не означает, что она целиком проверена.
- **Part result:** привязка к plan/snapshot/part, фактически проверенная область, findings, явные непроверенные участки и необходимые дополнительные проверки. Завершённое содержательное ревью с найденным дефектом отличается от технически непроверенной части. `manual_only` или продуктовый blocker сам по себе не означает, что их обоснование невозможно проверить.
- **Aggregate:** одно общее решение по exact набору сохранённых результатов. Полный успех требует закрытого состава исходных, локальных и межчастных проверок. Контроллер может вычислить состав/хеши/формальную допустимость и объединить findings; он не выводит смысловое покрытие из наличия ID.

Использовать существующие IDs, исходные receipts и публикацию артефактов. Для небольших общих детерминированных операций двух ревьюеров допустим один модуль `tools/review_parts.py`; это не исполнитель моделей и не scheduler. Публичные pure-функции для обоих потребителей:

```python
build_review_plan(snapshot: Mapping[str, Any], scopes: Sequence[Mapping[str, Any]], *, input_byte_budget: int) -> dict[str, Any]
validate_review_part(plan: Mapping[str, Any], part: Mapping[str, Any], result: Mapping[str, Any]) -> list[dict[str, str]]
aggregate_review_parts(plan: Mapping[str, Any], results: Sequence[Mapping[str, Any]]) -> dict[str, Any]
```

`scopes` содержит уже выбранные, привязанные к источникам единицы и зависимости; `build_review_plan` не придумывает смысловую независимость. `validate_review_part` проверяет структуру и точное покрытие назначенной области. `aggregate_review_parts` возвращает состав, findings и признаки complete/blocked/eligible, а не самопровозглашённый runtime PASS. Проверка durable provenance остаётся в `pilot_state` и вызывается до использования этих pure-результатов.

### Вместимость и смысловая полнота

- Исходный набор требований проверяется независимо от нормализованного списка генератора. Условие, потерянное при нормализации, должно обнаруживаться в `source`-пакете, даже если на него нет CREQ/case.
- Начальная единица локального canonical review — кейс с относящимися требованиями, полными необходимыми шагами/связями и определениями используемых операций. У automation — проверяемые case/relation targets с фактическими символами, setup, helpers и границей приложения.
- Распределять в стабильном порядке с учётом реально передаваемых bytes, повторных зависимостей, инструкций и резерва ответа. Если CLI предоставляет надёжный token accounting — фиксировать его; не вводить универсальное «N байт = токен» и не считать 260k доступным полезным входом.
- Полные canonical/automation документы хранятся и валидируются инструментами. В каждый модельный вход попадает только точная нужная часть, а не полный документ плюс те же генераторные фрагменты. Все исходные доказательства происхождения сохраняются.
- Большой JSON обрабатывается структурно инструментом. Для чрезмерно большого исходного файла/единицы нужны явные диапазоны, привязанные к digest полного файла, и проверка их полноты/зависимостей. Развивать текущий отбор контекста только насколько нужно для этого сценария; не добавлять универсальный parser framework и не обрезать текст молча. Неразделимая область, которую невозможно достоверно проверить в бюджете, остаётся явным пробелом.
- Обязательные межчастные проверки выводятся из оригинальных условий, общих операций/состояния и находок локального ревью. Проверять именно связанные исходные фрагменты: например, согласованность Expected одной операции в двух пакетах. Сводка без исходных привязок не заменяет эту работу.
- Новую обнаруженную зависимость не терять: зарегистрировать дополнительную ограниченную проверку в append-only учёте до её вызова. Начальный plan сохраняется неизменным; дополнения связываются с его digest и тем же snapshot в существующем ledger. Перед агрегацией контроллер получает из readback исходного plan и этих дополнений финальный обязательный состав. Прежний result остаётся допустим только для неизменных part ID/scope/input bytes, а не автоматически для расширенной области. Итог связывает digest исходного plan и exact набора дополнений; незакрытый запрос исключает принятие. Не создавать отдельную систему версий планов, рекурсивное дерево ревьюеров или цикл «пересматривать до PASS».

### Lifecycle, итог и исправления

- Один logical review имеет несколько свежих invocations и один итог. Не изображать агрегат фиктивным model response и не назначать ему вымышленный invocation ID. В итоговых схемах должна быть явная ссылка на состав частей/ledger; фактические identity остаются у частей.
- Предпочтительная схема IDs вызовов: `tc-reviewer:canonical:part-000001`, `autotest-reviewer:r1:part-000001` и далее по порядку. Состав проверок `source/local/cross` задаётся данными части. Обновить закрытые stage patterns, role policy/version bindings и всех читателей согласованно.
- Сохранить один authoritative canonical verdict после полного ревью; части не являются дополнительными authoritative verdicts. При технически неполном ревью сохранить неполноту и findings без принятия; не называть его завершённым только потому, что все доступные части обработаны.
- При resumе использовать результаты только той же версии, точных scopes/inputs и подтверждённых invocations. Смена snapshot исключает перенос прежнего acceptance; опубликованные bytes и терминальная история не переписываются. Старый неподдерживаемый активный протокол диагностируется явно, без скрытой миграции/второго исполнительного пути.
- Ревью не меняет проверяемую версию на ходу. Механические исправления собираются после проверок из точных, привязанных к полям предложений, инструментом формируется полный r2 и проходят существующие whole-document/lineage/identity validators. Не заставлять модель перепечатывать неизменённый полный JSON. Конфликт исправлений, неоднозначность или изменение машинного поведения требуют доработки, а не merge наугад. Межчастные проверки учитывают относящиеся к ним предложения; частичный patch сам по себе не выбирается effective.
- Automation r2 ссылается на полный r1 и его общий correction review; все части новой версии проверяются заново. Общий accepted review остаётся единственным основанием для materialization/execution.
