# Масштабируемое ревью: диагноз, эксперимент, решение (2026-10-06)

## 1. Диагноз по данным

Источники: журналы и ответы ревьюеров прогонов step5-java-demo (`2c10d733`, `3e852e76`, `d1834358`, `9340016c`), канонический документ Petclinic из `docs/examples/petclinic-owner-lifecycle`, отчёты сентябрьских пилотов.

**Входы дублируются в 5–12 раз.**

| Ревью в `9340016c` | Уникальное содержимое | Отправлено ревьюерам | Кратность |
| --- | --- | --- | --- |
| Кейсы, 2 части | 66 КБ | 340 КБ | 5× |
| Автотесты, 6 частей | 90 КБ | 1,06 МБ | 12× |

Причины:

- Единица упаковки — «область». Пара кейсов несёт оба кейса, их требования и описание возможности.
- В ревью автотестов каждая область несёт весь Java-файл: это 52% входа.
- Внутри части повторы заменены ссылками `content_ref`, но каждая ссылка — около 230 байт дайджестов и указателей. В части `r1-1` 250 таких ссылок занимают 57 КБ, треть конверта.
- Содержимое передаётся как JSON-строки внутри JSON, с экранированием.

**Время и токены уходят на ответ.**

- 92% ответа ревьюера — строки покрытия по 1,5–8,7 КБ каждая. В ревью автотестов каждая пара заново пересказывает дайджест файла и устройство хелперов.
- Всего в step5 ревьюеры написали 0,77 МБ JSON на 11 КБ теста.
- Скорость вывода 150–260 байт/с, отсюда 7–8 минут на часть.

**Состояние после волны D1–D8.** D7 добавил исходники provenance в локальные области ревью кейсов, поэтому текущий план ревью кейсов step5 — 3 части (388 КБ), ревью автотестов — 6 частей (1 061 КБ). D3 убрал взрыв проверок после правки: служебная правка — 0 частей, поведенческая — 1 часть.

**Квадратичность.** 1 + N + N(N−1)/2 областей. Каждая правка ревьюера сейчас добавляет ещё N(N−1)/2 частей по одной паре (до исправления D3).

**Группировка по требованиям не спасает.** В Petclinic 78 CREQ:

- 7 связаны со всеми 64 кейсами (общие ограничения);
- 71 связаны ровно с одним кейсом.

Кейсы взаимодействуют через общее состояние (БД), а не через общие требования.

**Ревью автотестов на больших проектах сейчас не запускается.** Сентябрьский класс Petclinic весил 250 016 байт (4288 строк). Если каждая область несёт весь файл, любая область больше бюджета части в 200 КБ, и это `REVIEW_CONTEXT_LIMIT`.

Оговорки:

- По одному запуску на сценарий.
- Инструкции сокращены, поэтому INFO-замечаний меньше, чем у полного SKILL. Одно старое INFO (TC-B1-006: «студент не возвращается» без проверки) новый ревьюер счёл допустимым.
- Запуски шли вне драйвера.
- Части были маленькие, 31–34 КБ. На частях около 180 КБ результат нужно проверить отдельно.

## 3. Решение

1. **Упаковка по содержимому, а не по областям.**
   - Часть — это набор кейсов целиком плюс общий контекст один раз. Ревьюер проверяет каждый кейс и все связи между кейсами части.
   - Если документ помещается в одну часть, всё ревью идёт одной частью.
   - Если не помещается, кейсы делятся на стабильные блоки (по порядку документа), и каждая часть — пара блоков. Любая пара кейсов всё равно встречается вместе хотя бы в одной части, так что гарантия «проверены все пары» сохраняется, но частей C(b,2) вместо N²/2.
2. **Компактная проекция для ревью.**
   - Детерминированный текст с ID, привязанный к дайджесту канона: примерно в 1,9 раза меньше JSON, без экранирования и без ссылок-заглушек.
   - Правки адресуются ID и путём поля из закрытого словаря. Драйвер переводит их в JSON pointer и сверяет `before`.
   - Контракт явно разрешает эту проекцию как вход модели. Тест проверяет, что каждое смысловое поле канона видно в проекции.
3. **Короткое покрытие с проверяемыми ссылками.**
   - Строка покрытия: статус, до 3 ссылок (ID или строка файла) и до 200 символов. Схема задаёт пределы длины.
   - Драйвер проверяет, что каждая ссылка существует во входе части. Это защита от «одобрил не глядя», которую абзацы прозы дать не могут.
   - Подробности пишутся только в находках; INFO-находок не больше 5.
4. **Ревью автотестов без пар.**
   - Область кейса — кейс плюс срез его метода (по `generated_symbols`) и хелперы, которые он вызывает.
   - Общий код (поля, аннотации, хелперы, настройка) — одна область SUPPORT.
   - Взаимодействие тестов проверяется через общий код и состояние (SUPPORT и CROSS), а не через пары методов.
5. **Детерминированный линтер до модели.** Он ищет:
   - JSON или статус в тексте ожидания, который не совпадает с литералом проверки;
   - литерал в `.isEqualTo(...)`, который не совпадает с ожидаемым значением кейса;
   - требование без кейса;
   - одинаковый вызов с разными ожиданиями;
   - проверки абсолютного количества или полного списка ресурса, который меняют другие кейсы (класс ошибки ownerCount из сентября).

   Результат попадает в конверт как список подозрений, которые ревьюер должен рассмотреть.
6. **Пачки частей.** `next` отдаёт все готовые независимые части сразу, и оркестратор запускает субагентов параллельно. Отправка ответов по-прежнему последовательная, под замком.
7. **Кэш и инкрементальность.**
   - Результат части привязан к дайджесту её входа.
   - При r2, правке или повторном прогоне после изменения спецификации перепроверяются только части с изменёнными кейсами.
   - Правка служебного поля не требует перепроверки.

Исправления D2, D3, D4 и D8 остаются в силе: адресация проверок по `case_id` из D2 переиспользуется, а D3 после этапа R1 становится частным случаем.

## 4. Оценка для Petclinic (64 кейса, 290 шагов, 671 проверка)

Расчёт на реальных размерах: проекция 313 КБ (в среднем 5 КБ на кейс), CREQ 21 КБ, SREQ 18 КБ, возможности 90 КБ, класс тестов 250 КБ (хелперы около 34 КБ, около 3,4 КБ на метод). Бюджет части 200 КБ, из них 20 КБ резерв под ответ.

| | Сейчас | После |
| --- | --- | --- |
| Ревью кейсов | около 300 частей (симуляция на коде `review_parts.py`, ревью 5 октября), около 49 МБ входа | 11 частей с гарантией всех пар: 5 блоков → 10 пар блоков, плюс 1 часть исходника и возможностей. Или 5 частей, если линтер подтвердил независимость кейсов |
| Ревью автотестов | не запускается: файл больше бюджета части | 5 частей |
| Одна правка ревьюера | +2016 частей | 1–4 части; служебное поле — 0 |
| Время | сутки и больше | 1–2 ч подряд, около 20–30 мин при 4 параллельных субагентах (4–7 мин на часть) |

Для step5 после изменений: ревью кейсов — 1 часть, ревью автотестов — 1 часть, около 8 минут вместо около 70.

## 5. Риски и проверка

- **Внимание на больших частях.** Нужен eval с 10–15 внесёнными дефектами разных классов на Petclinic. Сравнить находимость старой и новой схем на одних входах; критерий — не хуже.
- **Правки по ID.** Нужен закрытый словарь полей, однозначный перевод в pointer и сверка `before`. Иначе — переработка, как сейчас.
- **Режим без пар между блоками** выключен по умолчанию. Включается только при подтверждении независимости линтером или явным флагом.
- **Изоляция ревьюера** не меняется: каждая часть — свежий контекст.

Задание для сессии Claude Code с реестром рисков и протоколом eval: `docs/review/2026-10-07-review-scaling-prompt.md`; прототипы эксперимента: `docs/review/2026-10-06-review-scaling-prototype/`.


- **R1. Ревью кейсов.** Проекция, упаковка по кейсам, короткое покрытие с проверкой ссылок. Приёмка: фикстуры step5 дают 1 часть; на внесённых дефектах 6 из 6.
- **R2. Ревью автотестов.** Срезы методов, SUPPORT, без пар; детерминированная сверка литералов в коде.
- **R3. Масштаб.** Линтер межкейсовых проверок, блоки и пары блоков для больших документов, пачки параллельных частей.
- **R4. Кэш и проверка.** Кэш по дайджестам и инкрементальное ревью r2 и правок; затем живой прогон Petclinic с независимой спецификацией и внесённым дефектом.
