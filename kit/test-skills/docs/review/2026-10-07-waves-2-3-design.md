# Волны 2 и 3: сила тестов и живой набор — план (2026-10-07)

В этом плане две волны, они идут друг за другом:

- **Волна 2 — сила тестов и честное ревью.** Мутационное тестирование, разбор выживших мутантов, отчёт для аналитиков, изоляция ревьюера процессом драйвера (A2) и запуск без оркестратора.
- **Волна 3 — живой набор и поддержка тестов.** Набор кейсов и тестов живёт в проекте и обновляется по изменениям требований и кода: идентичность требований, манифест, миграция, анализ влияния, обновление и ремонт, карантин, контроль силы тестов, ручные правки, итог для PR.

Порядок:

1. Волна 2 → гейт → отчёт.
2. Живой прогон Petclinic (приёмка волны 2) — отдельной сессией по инструкции, которую сессия разработки пишет после гейта. Прогон идёт параллельно с началом волны 3.
3. Волна 3 → гейт → отчёт. Находки живого прогона исправляются до гейта волны 3.

Общий план развития — Claude Doc «План развития test-skills», снимок в проекте `claude/development-plan-2026-10-07.md`. Задание для сессии Claude Code — `docs/review/2026-10-07-waves-2-3-prompt.md`.

## 2. Волна 2: сила тестов и честное ревью

### 2.1. Мутационное тестирование (M)

- **Где в жизненном цикле.** Новый этап `MUTATION` после `EXECUTION_TRACE` и до `RETAIN_OR_CLEANUP_DECISION`: файлы тестов ещё в проекте даже при FAIL.
  - Этап запускается, только если исполнение полное и достоверное (verification PASS или FAIL).
  - Мутации идут только на прошедших методах. Упавшие исключаются: `--skipFailingTests`, при необходимости `--includedTestMethods`.
- **Отдельная ось.** Результат мутаций не меняет `verification` и `accepted`. В волне 2 это только отчёт; порог для `accepted` — позже, параметром профиля.
- **Java — PIT из командной строки** (`org.pitest.mutationtest.commandline.MutationCoverageReport`). Плагин Maven без правки `pom.xml` не подключает `pitest-junit5-plugin`. Запуск из командной строки берёт плагин с classpath самого PIT, как требует README плагина.
  - Версии PIT и `pitest-junit5-plugin` и их SHA-256 закреплены в пакете. Если дайджест не совпал, мутации получают `NOT_RUNNABLE`, а verification не меняется.
  - Jar разрешаются инструментами проекта (Maven или Gradle) в локальный репозиторий и только по явному согласию: `.skillsrc` `mutation.enabled: true` плюс отметка в run-scoped authorization. Это меняет §1 п. 5 контракта пилота: разрешается загрузка закреплённых версий инструмента мутаций по согласию.
  - `junit-platform-launcher` той же версии, что JUnit Platform проекта, добавляется в classpath PIT. Плагины Maven и Gradle делают это сами, запуск из командной строки — нет.
  - Classpath проекта. Maven — `dependency:build-classpath` в файл каталога прогона. Gradle — init script из каталога прогона, без правки `build.gradle`. В PIT classpath передаётся файлом (`--classPathFile`): на Windows длинная командная строка не пройдёт.
  - `--targetTests` — только сгенерированные классы. `--targetClasses` — пакеты классов из provenance возможностей.
  - Отчёт (`--outputFormats XML`, `--fullMutationMatrix`) пишется в каталог прогона. Файлы проекта не меняются: инвентарь до и после этапа совпадает.
  - Ограничения времени: `--threads`, `--timeoutConst`, набор мутаторов DEFAULTS, общий таймаут этапа.
  - **Совместимость с JUnit проекта проверяется первой** (W2-Р15): PIT должен найти и запустить сгенерированные тесты step5 и Petclinic (JUnit 6). Если плагин не работает с JUnit 6, мутации на таком проекте получают `NOT_RUNNABLE` с понятной причиной.
- **Метрики.**
  - Доля = убитые / (убитые + выжившие) среди мутантов, покрытых сгенерированными тестами. NO_COVERAGE, TIMED_OUT и MEMORY_ERROR считаются отдельно.
  - По кейсу — через связи автоматизации: `implementation_relations` (символ → кейс) и `generated_symbols` (символ → метод), плюс `killingTests`/`succeedingTests` полной матрицы. По требованию — через связи кейс → CREQ → SREQ.
  - Итог — квитанция мутаций, отчёт в проекциях и поле `test_strength` в результате и в сводке драйвера.
- **`.skillsrc`** получает необязательные разделы `mutation` и `review_runner` (2.4). Это минорная версия схемы `.skillsrc`; существующие файлы остаются валидными.
- **Python в волне 2 не делаем.** mutmut 3 работает только там, где есть `fork` (на Windows — только в WSL), и держит мутанты в каталоге `mutants/` внутри проекта, а mutmut 2 правит исходники на месте. В отчёт волны — короткий разбор вариантов, совместимых с контрактом.

### 2.2. Разбор выживших мутантов (T)

- Выжившие группируются по методу и строке. Группы сверх предела за прогон (параметр, по умолчанию 30) идут в отчёт таблицей без разбора.
- Новая задача модели `mutation-triage`. Вход компактный:
  - текст требований и проекции связанных кейсов;
  - исходная и мутированная строка с соседним кодом;
  - срез метода теста (`tools/code_slices.py`).
- По каждой группе модель выбирает одно решение и даёт ссылки на якоря входа:
  - `TEST_GAP` — требование задаёт это поведение, а проверки не хватает; нужно предложение: какой шаг или ожидание добавить и в какой кейс;
  - `SPEC_GAP` — требование это поведение не задаёт; нужен вопрос аналитику;
  - `EQUIVALENT` — наблюдаемое поведение не меняется; нужно обоснование;
  - `OUT_OF_SCOPE` — код вне фичи.
- Драйвер проверяет ссылки так же, как в compact-v1.
- **В волне 2 кейсы не меняются.**
  - `TEST_GAP` сохраняются как предложения усиления; их берёт режим обновления волны 3.
  - `SPEC_GAP` уходят в отчёт для аналитиков.
  - Это отличие от плана развития, где выжившие сразу шли генератору. Частичное обновление кейсов и тестов появится только в волне 3, а повторять его в волне 2 дорого.
- Ожидание не подгоняется под код: если требование молчит, это вопрос, а не новое ожидание.

### 2.3. Отчёт для аналитиков (Q)

- Источники:
  - структурированные пробелы context-marker — новое необязательное поле `requirement_gaps` (требование или ключ, место в источнике, чего не хватает, какие проверки блокирует, вопрос); старый текст `warnings` по-прежнему читается;

  - `SPEC_GAP` из разбора мутантов.
- Сборка детерминированная: `analyst-report.json` и `analyst-report.md` в пакете проекций попытки. Дубли склеиваются по требованию и нормализованному вопросу. У каждого пункта есть источник и ссылка.
- В `openspec/` пакет сам ничего не пишет. Комментарий к change — отдельной командой экспорта.

### 2.4. Изоляция ревьюера процессом драйвера (A2) и запуск без оркестратора

- **Два способа включения:**
  - опция начала прогона `next … --review-runner process` — части ревью драйвер запускает сам, остальные задачи `llm` по-прежнему получает оркестратор;
  - новая команда `run --runner process` — раннер получает все задачи `llm` (ниже, «Запуск без оркестратора»).
- **Пресеты пакета:**
  - `claude` — `claude -p --output-format json`, по возможности `--json-schema` со схемой ответа, без инструментов записи и Bash;
  - `codex` — `codex exec --skip-git-repo-check --sandbox read-only --ephemeral --json --output-schema` (вне репозитория git `codex exec` без `--skip-git-repo-check` не запускается).
- **Настройки.** `.skillsrc` (`review_runner`) выбирает только пресет, модель по ролям, `max_parallel` и `timeout_seconds`. Свой шаблон команды задаётся только флагом запуска: файл проекта не должен запускать произвольные команды.
- **Окружение процесса.**
  - Рабочий каталог — временный каталог вне проекта, чтобы не подхватить `CLAUDE.md` проекта.
  - `--bare` у Claude Code требует API-ключа и не работает со входом по подписке, поэтому по умолчанию не включается. Без него процесс читает пользовательские настройки `~/.claude` (CLAUDE.md, хуки, плагины); доказательство это отмечает.
- **Как идёт часть ревью.**
  - Каждая часть — новый процесс без истории. Вход части (SKILL роли, конверт, схема ответа) драйвер передаёт в stdin.
  - Ответ берётся из вывода CLI (stdout или файл последнего сообщения). Файл ответа пишет драйвер: у ревьюера нет права записи.
  - Проверка та же, что у `submit`. При сбое транспорта или неверном формате — до 3 попыток (B10), при лимите частоты — пауза. Всё пишется в `driver-log.jsonl`.
  - `next` не ждёт модель: запускает процессы в фоне (до `max_parallel`), возвращает новое действие `wait` и при следующем вызове собирает готовые ответы. Обрыв оркестратора не теряет и не дублирует части.
- **Доказательство на каждую часть:**
  - дайджест команды без секретов, имя и версия CLI;
  - модель — из вывода CLI, если он её сообщает (Claude Code); у Codex события `--json` модель не называют, поэтому она берётся из параметра запуска с пометкой;
  - время начала и конца, код выхода;
  - ID сессии: `session_id` у Claude Code, `thread_id` из события `thread.started` у Codex; ID разных частей различны;
  - дайджест stdout и токены.
- **Уровень доказательства** — новое поле `isolation_evidence: DRIVER_PROCESS | HOST_DECLARED | NONE` рядом с осью `review_independence`.
  - По умолчанию принятие не меняется.
  - Флаг `--require-driver-isolation` (для CI) не принимает `HOST_DECLARED`; причина — `REVIEW_ISOLATION_UNVERIFIED`.
- **Запуск без оркестратора** (минимальный): новая команда `python -m tools.pipeline_driver run --runner process` отдаёт раннеру все задачи `llm`, а не только ревью.
  - Ответы на `ask_user` берутся из флагов или файла ответов. Если ответа нет, прогон останавливается с кодом 3, как сейчас при ожидании человека.
  - Артефакты те же, что у прогона с оркестратором.
  - Если ответ роли не помещается в вывод процесса, задача завершается отказом транспорта с понятной причиной.
  - Это основа запуска из CI в волне 3.
- По умолчанию раннер выключен, поведение драйвера прежнее.

## 3. Волна 3: живой набор и поддержка тестов

### 3.1. Идентичность требований (I)

- **Ключ требования:**
  - OpenSpec — capability и имя requirement; переименования из `RENAMED Requirements` сканер уже разбирает;
  - Markdown — явный ID в начале раздела, иначе путь файла и цепочка заголовков. Явные ID — встроенные (`REQ-`, `AC-` и другие) плюс шаблон из `.skillsrc` `requirements.id_pattern`, например `[OPVX]\d\d\.` для Petclinic.
- Шаблон из `.skillsrc` режет документ так же, как встроенные ID: у Petclinic будет 29 SREQ вместо 7 — 26 требований с ID и три раздела без ID («Назначение и границы», «Данные», «Условия работы над тестами»). Без шаблона разбиение прежнее.
- Новое поле — хеш текста самого требования (NFC, схлопнутые пробелы). Поле `digest` (хеш файла) остаётся для совместимости.
- Формат `SREQ-NNNN` не меняется: манифест связывает по ключам, а не по номерам. Старые прогоны читаются как раньше.
- Связь ключа с кейсами: ключ → SREQ → CREQ (`source_to_canonical_mappings`) → кейсы. Если раздел без ID крупный, анализ влияния шире, но без пропусков.

### 3.2. Набор в проекте и манифест (S)

- Каталог набора — `.skillsrc` `suite.path`, по умолчанию `test-cases/`. В нём канонический JSON, Markdown, HTML, CSV и манифест. Тесты остаются в каталоге тестов модуля.
- Манифест:
  - версия формата и версия пакета;
  - по каждому кейсу: ключи и хеши требований, метод теста и хеш его среза, ключ Zephyr, статус (`ACTIVE`, `QUARANTINED`, `RETIRED`), причина и ссылка карантина, последний зелёный прогон, доля убитых мутантов;
  - снимок поверхности кода (эндпоинты и поля) на момент обновления;
  - дайджесты, по которым видны ручные правки.
- Набор пишется только по run-scoped authorization, как сейчас тесты. Первый набор создаёт обычный `local-pilot-v1` с флагом `--suite`.

### 3.3. Миграция (G)

Если версия формата в манифесте старше пакета, набор сначала переводится в новый формат детерминированными мигрантами. Результат проверяется схемами, сводка идёт в описание PR. Без миграции остальные шаги не запускаются.

### 3.4. Анализ влияния и поверхность кода (D)

- Вход: текущий скан спецификации, манифест, по желанию JUnit-отчёт обычного CI проекта и git-диапазон.
- Выход:
  - требования добавлены, изменены, удалены или переименованы — по ключам;
  - затронутые кейсы;
  - упавшие и сломанные тесты;
  - новые эндпоинты и поля в коде без требования.
- Поверхность кода извлекается кодом: аннотации Spring MVC, маршруты Flask и FastAPI. Она сравнивается со снимком в манифесте и с эндпоинтами, которые называют требования. Новое без требования — вопрос в отчёт для аналитиков; кейсы не меняются.
- `python -m tools.suite status|impact|migrate` работает без модели. CI проекта может вызвать его, чтобы понять, нужна ли модель вообще.

### 3.5. Обновление и ремонт (U)

- **Обновление** — новый режим генератора по образцу доработки D4.
  - Вход: затронутые кейсы, старый и новый текст требований, предложения усиления `TEST_GAP` из волны 2.
  - Выход: изменённые кейсы с теми же ID, новые кейсы, предложения к выводу.
  - Дальше:
    - ревью только изменённого — перенос и кэш compact-v1;
    - автоматизация только изменённых кейсов, методы заменяются по срезам `tools/code_slices.py`;
    - статическое ревью изменённых срезов;
    - запуск всего набора.
- **Ремонт.** Тест не компилируется или падает его собственный код, а кейс и требования не менялись. Тогда по тому же кейсу заново пишутся только методы и общий код (SUPPORT), на которые указывает ошибка.
  - Ожидания не меняются. Это проверяют сверка литералов кодом (R2) и доля убитых мутантов по кейсу, которая не должна упасть.
  - Одна попытка, как r2 после `GENERATED_TEST_INVALID`.

### 3.6. Разбор падений и карантин (F)

- **Классификация:**
  - ошибка компиляции или кода теста — ремонт;
  - падение на проверке:
    - требование менялось — обновление;
    - не менялись ни требование, ни тест — поведение изменилось без спецификации: карантин, вопрос аналитику, черновик баг-репорта из кейса;
  - результат меняется между повторами — нестабильность или окружение: карантин с пометкой.
- **Карантин — на уровне теста, а не файла.** Пакет правит собственный файл:
  - JUnit 5 — `@Disabled` с причиной;
  - pytest — `xfail(strict=True)` с причиной.
- Если метод правил человек, карантин не вносится, а предлагается в PR.
- Карантинные тесты при разборе запускаются явно (для JUnit 5 — через `junit.jupiter.conditions.deactivate`). Так видно, когда дефект исправлен.
- **Новая политика диспозиций:** прошедшие тесты сохраняются, упавшие уходят в карантин. В `suite-update-v1` это поведение по умолчанию. В `local-pilot-v1` политика сначала включается флагом, а поведением по умолчанию становится после гейта, отдельным коммитом.

### 3.7. Контроль силы тестов во времени (K)

Доля убитых мутантов из волны 2 считается регулярно: по расписанию или при PR, который меняет код под тестами. История PIT для пересчёта (`--historyInputLocation`, `--historyOutputLocation`) лежит в служебном каталоге вне набора; в манифест идут только доли по кейсам и требованиям. Падение доли — сигнал пересмотреть тесты, даже если всё зелёное.

### 3.8. Ручные правки (H)

Кейс или метод, у которого дайджест не совпадает с манифестом, считается отредактированным человеком. Пакет его не перезаписывает: изменение уходит отдельным предложением в описание PR. Ослабление проверки человеком видно по падению доли мутантов и тоже попадает в PR.

### 3.9. Профиль `suite-update-v1` и итог (R)

- Шаги профиля:
  1. миграция;
  2. анализ влияния;
  3. обновление и ремонт;
  4. ревью;
  5. автоматизация изменённого;
  6. статическое ревью;
  7. запуск всего набора;
  8. разбор падений и карантин;
  9. мутации;
  10. манифест;
  11. итог.
- Запуск — через драйвер с этим профилем: с оркестратором или из CI через запуск без оркестратора (волна 2).
- **Итог по умолчанию — без коммитов.** Пакет пишет изменения в рабочее дерево, а также `pr-description.md` и patch:
  - diff кейсов в человеческом виде и diff тестов;
  - карантин и вопросы аналитикам;
  - предложения по ручным правкам.
- Коммит, ветку и PR делает человек или CI проекта. Другой вариант — отдельная команда с явным подтверждением.

## 4. Поправки к контракту пилота

Замороженный контракт (`docs/superpowers/specs/2026-08-26-portable-testing-skills-frozen-pilot-contract.md`) не допускает части того, что строят волны. Поправки оформляются так же, как erratum от 2026-09-01: отдельный документ в `docs/superpowers/specs/` и `contracts/pipeline.json`. Каждая новая возможность включается только опцией.

| Пункт | Сейчас | Поправка | Волна |
| --- | --- | --- | --- |
| §1 п. 2 | Пакет сам модель не вызывает | Драйвер может запускать процесс CLI модели (раннер процессов, `run`); учётные данные остаются у CLI | 2 |
| §1 п. 5 | Никаких установок зависимостей | Разрешена загрузка закреплённых по SHA-256 jar PIT в локальный репозиторий сборщика, только по согласию | 2 |
| §17 | Жизненный цикл строго фиксирован | Этап `MUTATION` между трассой исполнения и решением о сохранении, только при включённых мутациях | 2 |
| §17 п. 2 | После FAIL каждый файл — `CLEANED` | Политика «карантин»: прошедшие тесты сохраняются, упавшие помечаются | 3 |
| §25 | Нельзя менять существующие тесты и чинить тест после падения | Можно менять только тесты, которыми владеет пакет и чей дайджест совпадает с манифестом: обновление, ремонт, карантин. Ремонт — только в `suite-update-v1`, одна попытка, через ревью, ожидания не меняются | 3 |

Остаётся в силе: пакет не создаёт копий проекта, worktree и виртуальных окружений, не меняет код продукта, зависимости проекта, сборку и секреты, не трогает чужие и отредактированные людьми файлы, не создаёт коммитов, push, PR и задач CI.

Эти поправки — часть плана. Запуская задание, пользователь их принимает.

## 5. Решения по умолчанию, которые можно поменять

- Пакет не делает коммитов и PR: пишет изменения, описание PR и patch.
- Загрузка закреплённых версий PIT — только по согласию в `.skillsrc` и в разрешении прогона.
- Мутации и раннер процессов по умолчанию выключены. Карантин вместо очистки становится поведением `local-pilot-v1` по умолчанию только после гейта волны 3.
- Модели по ролям — минимальные по E5 (Sonnet), эталон — Fable.
- Снимать ли с релиза статус `implemented_unverified`, решает пользователь после живого прогона.

## 6. Отличия от плана развития

- Выжившие мутанты в волне 2 не уходят генератору: волна 2 их разбирает и копит предложения, а применяет их режим обновления волны 3.
- Python-мутации отложены: mutmut не работает на Windows без WSL.
- Живой прогон Petclinic идёт отдельной сессией по инструкции сессии разработки.
- Для волны 3 выбран итог без коммитов — это решение по умолчанию, его можно поменять до старта волны.
- Волны требуют поправок к контракту пилота (раздел 4).

## 7. Вне этих волн

Волна 4 (слабые модели, разделение кейса и автоматизации), волна 5 (тест-дизайн, Schemathesis и Pact), поля Zephyr в `.skillsrc`, возврат результатов в Zephyr, E2E и UI, `company_runner.py`, упрощение ядра.
