Полное ревью лежит в `docs/review/2026-10-05-pipeline-review.md`. Прочитай его целиком до начала работы. В нём есть:

3. Не добавляй зависимости и не меняй `requirements*.txt` без разрешения. Пакет ничего не устанавливает в целевой проект.
4. Для каждого бага сначала напиши регрессионный тест, который падает на текущем коде, затем исправь, затем прогони адресные тесты. Никаких исправлений «вслепую».
5. Ложное срабатывание ревью не «чини»: отметь его в плане с доказательством (команда и вывод) и иди дальше.
6. Сохрани смысл существующих контрактов, кроме случаев из раздела «Зафиксированные решения». Любое изменение семантики вноси в `contracts/pipeline.json` и схемы. Затем перегенерируй `CONTRACTS.md`/`PIPELINE.md` и обнови README/USAGE/HOW-IT-WORKS.
7. Состояние релиза остаётся `implemented_unverified`, ready tuple — `null`.
8. Не трогай `.tools/`, `.runtime/` и прочие каталоги вне `D:\AI-Projects\test-skills`, кроме запуска оттуда интерпретатора, JDK и Maven.

## Зафиксированные решения (не переспрашивай пользователя)

1. **B1/B2 — блокировка.**
   - Межпроцессная блокировка run: файл `.pilot-runs/<run_id>/.lock`, `msvcrt.locking` на Windows, `fcntl.flock` на POSIX.
   - Все писатели держат блокировку. Читатели (`status`, `derive_state`) никогда не удаляют pending-маркеры. Восстановление маркеров — только под блокировкой.
   - Писатель, вышедший через `_PublicationUnknown`, убирает свой маркер.
   - Добавь fsync каталогов на POSIX и повтор `os.replace` при `PermissionError` на Windows (ограниченный, с паузой).
2. **B3 — дрейф после запуска.**
   - Проверка дрейфа после запуска сравнивает только входы baseline (изменённые или удалённые). Новые файлы дрейфом не считаются.
   - Инвентарь уважает `.gitignore`: используй `git ls-files -co --exclude-standard`, если это git-репозиторий.
   - По умолчанию исключаются `.gradle`, `.kotlin`, `.idea`, `.vscode`, `coverage*`, `*.log`.
   - Уточни фиксированные имена `build`/`generated`/`coverage`, чтобы не выбрасывать исходные пакеты с такими именами (M-пункт).
3. **B4 — шлюз компиляции и сбора.**
   - После материализации и до запуска выполняется шлюз: pytest `--collect-only` по выбранным nodeid, Maven `test-compile`, Gradle `testClasses`.
   - Провал шлюза → `verification=NOT_RUNNABLE`, reason `GENERATED_TEST_INVALID`. Неизменённые pipeline-owned файлы очищаются, вывод сохраняется в run root.
   - Ревизия автоматизации r2 разрешена, если бюджет r1+r2 не исчерпан.
   - Ошибка компиляции или импорта, проскочившая в основной запуск, тоже даёт `NOT_RUNNABLE`, а не `UNKNOWN`.
   - Падение продуктовой проверки остаётся `FAIL` без регенерации.
4. **B5 — команды запуска.**
   - **Gradle:** запуск из корня с `settings.gradle(.kts)`, задача `:<path>:test --tests <FQN>`, `--no-daemon`.
   - **Maven:** запуск из корня реактора: `-pl <module> -am -Dtest=... -Dsurefire.failIfNoSpecifiedTests=false -B -ntp`. Без `-Pdefault`, если профиль не объявлен в `.skillsrc`.
   - Корень сборки — новое необязательное поле `.skillsrc`; схема версионируется аддитивно.
5. **B6 — сборка батчей.**
   - При сборке capabilities сортируются по code point.
   - Одинаковый `capability_id` с совпадающей семантикой и разным текстом provenance сливается (provenance объединяется). Различие в семантике — явный конфликт с указанием обоих батчей.
   - Сборка и валидаторы возвращают все диагностики с JSON-pointer, а не только первый код.
6. **B7 — блокеры.** Blocker блокирует только свой кейс. Автоматизация генерируется для остальных, заблокированные кейсы получают диспозиции. `BLOCKED` — только если автоматизировать нечего. Правила acceptance не меняются: при блокерах `accepted=false`.
7. **B8 — Zephyr CSV.**
   - Новый профиль по умолчанию `zephyr-scale-step-row-24-v5` содержит только человеческие поля: действие с разрешённым URL, `test_data`, текст ожиданий.
   - v4 остаётся как opt-in для совместимости.
8. **B9 — секреты.**
   - По имени файла исключаются только явные секреты: `.env*`, `*.pem/.key/.p12/.pfx/.kdbx`, `id_*`, каталоги `secrets/` и `credentials/`. Эвристику по словам в имени (`password`, `token`, `private` и т. п.) для исходников и документов убери.
   - По содержимому срабатывают только высокоуверенные сигнатуры и присваивания строкового литерала длиной не меньше 16 символов. Вызовы функций и идентификаторы не срабатывают.
   - В документах и спецификациях совпавшие строки маскируются (`[REDACTED:<rule>]`) с квитанцией, а не исключают файл. Маскированный документ не делает execution `NOT_RUNNABLE`.
9. **B10 — повтор частей ревью.**
   - Часть ревью без валидной оценки можно переоткрыть новым invocation: до 3 попыток, каждая записывается в журнал.
   - `transport_attempts` — до 3.
   - Причина блокировки части различает `TRANSPORT` и `CONTENT`. Транспортный сбой не превращается в `REWORK`.
10. **B11 — обнаружение модулей.**
    - Python-пакеты без `src/` распознаются.
    - Модули Maven с `packaging=pom` пропускаются как неисполняемые.
    - `requirements.txt` без Python-исходников рядом не создаёт модуль.
    - Go распознаётся как неисполняемый язык без `needs_source`.
    - `init_skillsrc` принимает ответ на вопрос об исходниках и записывает `.skillsrc`.
11. **B12 — reason phrase.** Своя таблица HTTP reason phrase. Для 413, 416 и 422 принимаются и формулировки RFC 9110, и старые. Никакой зависимости от `http.HTTPStatus`.
12. **Exit-коды.**
    - `cases-only-v1` с FATAL, `FINALIZATION_INVALID`, невалидным trace или `operational_reliable=false` даёт exit 2.
    - Валидный терминальный cases-only по-прежнему даёт exit 1 и `accepted=false`. Смысл профиля не меняется.
    - Неиспользуемый параметр `controller_error` приведи к контракту.
13. **Остановка процессов.**
    - Windows: процесс создаётся приостановленным, назначается в Job Object с `KILL_ON_JOB_CLOSE`, затем возобновляется. При таймауте — `TerminateJobObject` и ожидание, proof вида `WINDOWS_JOB_TERMINATED`.
    - POSIX: proof выдаётся только после проверки, что в группе нет живых процессов.
    - После `UNKNOWN` с валидным proof разрешена дочерняя попытка.
14. **Ошибки запуска процесса.** `OSError` при запуске → `NOT_RUNNABLE`, reason `LAUNCH_FAILED`. Ненулевой exit при полностью зелёном отчёте и сбой сохранения артефактов получают отдельные reason-коды, а не общий `JUNIT_INVALID`.
15. **pytest.**
    - Явно выбранный nodeid, который собрал 0 тестов из-за `addopts`, `-m` или `PYTEST_ADDOPTS`, даёт `NOT_RUNNABLE`, reason `TESTS_DESELECTED`. Это не `FAIL`, и очистка как при `FAIL` не выполняется.
    - Nodeid сопоставляется с учётом фактического rootdir pytest.
16. **Окружение тестового процесса.**
    - Имена и дайджесты значений переменных, влияющих на запуск, фиксируются в execution request: `PYTEST_ADDOPTS`, `PYTEST_PLUGINS`, `MAVEN_OPTS`, `MAVEN_ARGS`, `JAVA_TOOL_OPTIONS`, `_JAVA_OPTIONS`, `GRADLE_OPTS`, `JAVA_HOME`.
    - Сами значения не логируются, `PATH` не вырезается.
    - Хвост вывода хранится до 64 КиБ. Декодирование: UTF-8, затем кодировка консоли Windows.
17. **`.skillsrc`.** Хранит логические имена (`mvnw`, `gradlew`, `python` из venv модуля), а не пути конкретной ОС. Путь разрешается при запуске. Старые файлы читаются как раньше.
18. **OpenSpec.**
    - Ищется в любом каталоге проекта (`**/openspec/specs`).
    - Заголовки `Requirement:` и дельт разбираются без учёта регистра и пробелов, BOM допускается.
    - `SREQ`-ID назначаются в порядке документа. Обнови контракт context-marker под фактическую сортировку.
19. **Обычный Markdown.** Заголовок без текста требования (только подзаголовки, глоссарий, оглавление) не становится требованием, которое надо покрывать кейсом.
20. **Файл больше лимита контекста.** Пропускается с явным gap в квитанции, скан не падает целиком. Лимиты настраиваются в `.skillsrc`.

Если для пункта нужного решения здесь нет, выбери минимальное исправление, совместимое с документацией, и запиши решение в план одной строкой.
