# Переносимый пайплайн тестирования

Сценарий выступления на 20 минут для смешанной аудитории. Слайды редактируются в PowerPoint. Данные пилота исторические, новый полный прогон для презентации не выполнялся.

## 1. От требований к проверяемому результату (0:40)

Я покажу набор скиллов, который помогает пройти путь от документа требований до тест-кейсов, независимого ревью и запуска автотестов в самом проекте. Скилл здесь означает инструкцию для модели с определённой задачей и форматом результата. Рядом находятся скрипты, которые проверяют артефакты и выполняют разрешённые операции. Главное обещание этой системы: результат можно проверить по сохранённым данным. Сегодня разберём устройство, реальный пример на Spring Petclinic и то, что ещё нужно подтвердить перед широким применением. Текущий статус пакета: пилот, implemented_unverified.

Источники: README.md, HOW-IT-WORKS.md, release/manifest.json. Снимок 07.09.2026.

## 2. Что получает команда (1:15)

Начинаем с задачи команды. Требование нужно превратить в проверяемый сценарий, затем решить, можно ли его автоматизировать, написать тест и объяснить результат. При ручном переходе между этими шагами легко потерять условие, придумать лишнюю проверку или принять зелёный отчёт без связи с задачей. Пайплайн делает эти переходы явными. Есть два профиля. cases-only-v1 заканчивается проверенными тест-кейсами: код проекта не запускается. Это самостоятельный результат для ручного тестирования и обсуждения требований. local-pilot-v1 продолжает путь до автотестов и запуска. Для него нужно разрешение на выполнение в выбранном проекте. HTML и Markdown удобны человеку, JSON хранит смысл сценариев, CSV служит выгрузкой. Команда выбирает объём работы под задачу. Качество исходных требований по-прежнему важно: если поведение не определено, модель не должна молча придумывать продуктовую спецификацию.

Источники: README.md: два профиля, canonical JSON; USAGE.md.

## 3. Почему стоит попробовать (1:00)

Почему имеет смысл попробовать именно такой подход? Первое преимущество — проверка содержания до исполнения. Мы можем остановить ошибочный сценарий до того, как он станет кодом. Второе — возможность разобрать результат: есть конкретные файлы, версия и связь с требованием. Третье — работа рядом с существующим проектом через его обычные тестовые средства. Эти свойства особенно полезны, когда команда регулярно переводит требования в набор проверок и хочет сократить ручное связывание документов. Это инженерные основания для пилота, а не доказанный процент экономии. Для одноразовой маленькой проверки стоимость всего процесса может оказаться выше пользы. Если нет ясных требований или рабочего окружения, сначала нужно подготовить их. Решение об использовании принимаем по качеству и цене результата в собственной команде.

Источники: README.md; USAGE.md; contracts/pipeline.json. Оценка применимости является предложением, не результатом сравнительного исследования.

## 4. Разделение ролей (1:40)

Здесь полезно разделить содержание и выполнение. Orchestrate координирует этапы и продолжение работы. Context Marker формирует контекст с происхождением требований и ограничениями. TC Generator проектирует сценарии. TC Reviewer получает отдельный свежий вызов для проверки: это независимость вызова и роли, а не гарантия, что другая модель никогда не повторит ошибку. TC to Autotest переводит принятые сценарии в код. Autotest Reviewer делает отдельную статическую проверку кода до запуска. Совместимая CLI управляет вызовами модели. Python-инструменты проверяют структуры, фиксируют файлы, их контрольные суммы и результаты, затем вызывают штатный тестовый инструмент проекта. Поэтому скрипты не заменяют продуктовую оценку модели, а модель не заменяет механические проверки. Если возникает замечание, процесс должен сохранить его и предусмотренное контрактом продолжение. Наличие шести ролей само по себе не доказывает качество: доказательства появляются на выходах этих ролей и в реальном исполнении.

Источники: skills/*/SKILL.md; contracts/pipeline.json: stage_registry и reviewer policy.

## 5. Структура пакета (1:10)

В корне README даёт общую картину, USAGE объясняет запуск, HOW-IT-WORKS описывает поток. В skills лежат шесть ролевых инструкций и их справочные материалы. В contracts находится machine-readable pipeline.json: согласованные правила процесса. Schemas задают допустимые структуры документов и отчётов. Tools — обычные Python-модули для инвентаризации, проверки, сохранения артефактов, запуска тестов и финализации. Tests проверяют реализацию самого пакета. Evals описывает квалификационные сценарии, а release хранит манифест состава и подтверждённый статус. Наличие этих папок не означает, что квалификация уже пройдена. Docs содержит эту презентацию, заметки и краткое основание результатов. Это объясняет, почему переносимым элементом является весь пакет: отдельный файл инструкции без контрактов и инструментов не воспроизводит тот же процесс.

Источники: Фактическое дерево переносимого пакета; README.md; RELEASE.md; release/manifest.json.

## 6. Что остаётся после запуска (1:05)

Главный результат системы можно представить как цепочку документов. Сначала есть требование и его источник. Затем тест-кейс: что подготовить, что сделать, какие данные использовать, что увидеть. После автоматизации появляется конкретный файл и метод. Наконец, отчёт выполнения привязывается к тому, что действительно проверяли. Это помогает отвечать на обычные вопросы ревью: почему существует этот тест, какая проверка подтверждает требование, что именно упало. Canonical JSON является единственным источником смысла тест-кейсов. Человек читает HTML, а экспорт строится из той же модели. Контрольные суммы и записи журнала связывают проверенные и выполненные файлы. Это снижает риск случайно принять отчёт от другой версии теста. Но сама связь не делает слабое требование сильным и не доказывает полноту всей предметной области. Смысл кейсов нужно оценивать отдельно от технической целостности файлов.

Источники: README.md; CONTRACTS.md; tools/pilot_state.py; schemas/canonical-test-document.schema.json.

## 7. Границы выполнения (1:00)

В полном профиле инструменты запускают только согласованные цели. Исполнителю передаются типизированные параметры и выбранный адаптер, а не произвольная строка shell от модели. Пакет работает в подготовленном проекте: не устанавливает автоматически JDK или зависимости и сам не создаёт песочницу. Исходники приложения, существующие тесты и конфигурация не становятся свободным полем для исправлений ради зелёного результата. Для новых файлов учитываются принадлежность и содержимое. При FAIL правила позволяют убрать только собственные неизменённые сгенерированные файлы, сохранив доказательства в артефактах. При неопределённом результате действует другое правило: неизвестность нельзя использовать как основание для очистки. Для рабочего применения команда должна заранее решить, в какой подготовленной копии проекта это запускается и какие данные разрешены. Ограничения пайплайна не равны изоляции среды.

Источники: README.md: Execution и generated files, границы; contracts/pipeline.json; tools/execution_adapters.py.

## 8. Как попробовать в проекте (1:10)

Сначала выбираем одну понятную фичу и документируем ожидаемое поведение. В проекте уже должны работать обычные тестовые средства и зависимости. Затем копируем пакет целиком: одних SKILL.md недостаточно, потому что они ссылаются на схемы, контракты и инструменты. Типичное место: .tools/test-skills. Через совместимую CLI явно просим выполнить skills/orchestrate/SKILL.md из скопированного пакета для нашего документа требований. Указываем проект и модуль. Для первого знакомства можно выбрать cases-only-v1. Для полного прохода указываем local-pilot-v1 и разрешение выполнить выбранные проверенные цели в рамках текущего запуска. Совместимая CLI должна уметь читать инструкции и артефакты, сохранять результаты, выполнять отдельный вызов ревьюера и продолжать незавершённую попытку по сохранённому состоянию. Переносимость пакета означает такой способ подключения. Поддержку каждой конкретной CLI и платформы ещё нужно подтверждать испытаниями.

Источники: USAGE.md; README.md: точка входа и профили; tools/compatibility_contract.py.

## 9. Результат большого пилота (1:30)

Теперь о фактическом результате. В большом пилоте проверяли жизненный цикл владельца, питомца и визита в Spring Petclinic. Среда: Windows, Java 17, Maven и H2. Было 64 тест-кейса с 301 шагом. Сгенерированный Java-класс содержал 64 тестовых метода. Ревью тест-кейсов и автоматизации завершилось принятием, после чего был выполнен один Maven-запуск. JUnit зафиксировал 64 теста: 63 прошли, один упал, ошибок выполнения и пропусков не было. Полный связный сценарий жизненного цикла также прошёл. Время JUnit-набора около 35 секунд, нативного процесса около 70 секунд. Это время исполнения тестов, а не всего пайплайна с генерацией и ревью. Мы не заявляем экономию труда или ускорение всего процесса: для этого нужен отдельный сравнительный замер. Пилот выполнен на замороженной более ранней версии пакета. Последующие изменения инструкций не получили здесь задним числом статус проверенных этим прогоном.

## 10. Один найденный дефект (1:50)

Разберём упавший тест как пример полезного результата. Требование V05 запрещает сохранение визита с пустой датой. В сценарии используется существующий питомец, в поле даты передаётся пустая строка, описание равно «Первичный осмотр». Ожидание состоит из наблюдаемого поведения формы и отсутствия новой записи. Фактически приложение перенаправило запрос, не вернуло ошибку даты и сохранило визит с null в поле даты. Это проверялось через MockMvc и независимое чтение базы, а не через придуманное описание интерфейса. Чтение базы выполнялось до итогового объединения assertions. Поэтому у нас есть несколько согласованных наблюдений одной проблемы. Приложение в рамках прогона не исправляли, тест не ослабляли. Финальный FAIL сохранил найденное нарушение требования. На выступлении можно остановиться и разобрать вопрос: является ли здесь красный итог плохим результатом работы инструмента? Для тестирования обнаруженный и воспроизводимый дефект как раз полезен. Но решение о приоритете исправления и само исправление остаются задачей команды.

Источники: docs/pilot-evidence.md; TC-B1-056 / V05 / case056. Архив reviewed Java source, строки 3611–3622; независимый v05-runtime-defect.json.

## 11. От сценария к автотесту (1:20)

Этот пример показывает, зачем нам промежуточный тест-кейс. До написания Java-кода можно обсудить правило: действительно ли пустая дата недопустима, что считается ошибкой и что происходит с данными. Затем автоматизация должна сохранить именно этот смысл. В нашем примере проверяется не только статус HTTP-ответа. Проверяется ошибка конкретного поля и отсутствие записи в базе. Один технический сигнал вроде «ответ получен» был бы слишком слабым доказательством. Связь проходит через требование V05, кейс TC-B1-056 и метод case056. Для ручного тестировщика важны исходные условия и ожидаемый результат, для разработчика важен исполняемый запрос и способ проверки данных. Это разные представления одной проверки. Не каждый сценарий обязательно переводится в автотест: ограничения среды, доступные интерфейсы и необходимость ручного наблюдения должны быть отражены в покрытии. Показанный пример использует серверные тестовые средства проекта и не является доказательством проверки поведения в реальном браузере.

Источники: docs/pilot-evidence.md; schemas/canonical-test-document.schema.json; skills/tc-to-autotest/references/automation-output-contract.md.

## 12. Как читать итог (1:25)

Одна зелёная или красная лампочка смешала бы разные вопросы. Закончил ли инструмент работу? Что показали проверки? Какая доля согласованных кейсов автоматизирована? Можно ли принять итог по правилам? В большом прогоне lifecycle равен TERMINAL, completion равен COMPLETE. Это говорит о завершённости попытки. Verification равен FAIL из-за нарушения требования. Coverage равен FULL в рамках canonical-набора. Это не обещание, что проверены все мыслимые сценарии приложения. accepted равен false, а финализация валидна: пайплайн корректно сохранил отрицательный результат. Если тесты нельзя запустить, нужен NOT_RUNNABLE. Если надёжных данных недостаточно, нужен UNKNOWN. Эти ситуации нельзя выдавать за PASS. Для профиля только с кейсами исполнение вообще неприменимо. Читателю отчёта важно видеть причину и доказательства, чтобы понимать следующий шаг: исправлять продукт, окружение, входные данные или сам процесс.

Источники: README.md: результат; schemas/terminal-result.schema.json; docs/pilot-evidence.md.

## 13. Что уже сделано (1:10)

Здесь три разных уровня готовности. На уровне реализации собран переносимый пакет: ролевые скиллы, два профиля, закрытые форматы артефактов, процесс ревью, адаптеры pytest, Maven и Gradle, трассировка и финализация. На уровне наблюдаемого результата есть конкретный большой Java-пилот: 64 метода выполнились, нарушение V05 сохранилось в итоговом отчёте. На уровне последующих улучшений исправлен медленный поиск Java-методов на большом классе и уточнены требования к читаемости тест-кейсов. Для последних инструкций есть небольшая выборка из пяти кейсов, а не полный повтор той же фичи. При подготовке публикации отдельно проверена целостность пакета и прошли 24 связанных теста. Эти утверждения нельзя склеивать в «всё проверено везде»: объём доказательств у каждого уровня свой.

Источники: docs/pilot-evidence.md; release/manifest.json; contracts/pipeline.json; текущие skills и tools.

## 14. Что ещё нужно подтвердить (1:25)

Один большой пилот подтверждает конкретный путь на конкретном проекте и окружении. Он не заменяет квалификационную кампанию. В release manifest текущего пакета остаются implemented_unverified и ready_tuple=null. Это честное описание стадии. Есть несколько направлений следующей проверки. Во-первых, повторяемость на задачах разного типа. Во-вторых, переносимость на выбранные CLI и платформы. В-третьих, читаемость: сможет ли тестировщик, который не участвовал в генерации, выполнить сценарий без расшифровки внутренних терминов? После пилота инструкции по читаемости уточнялись и проверялись на небольшой выборке из пяти сценариев, но это не полный повтор большого прогона. Наконец, стоимость: сколько времени и денег стоит получить пригодный результат, сколько исправляет человек. Пока нет контролируемого сравнения, нельзя обещать процент экономии. XML-экспорт для Zephyr также не стоит представлять как подтверждённую интеграцию с реальным рабочим tenant: статус observed/unverified сохраняется.

Источники: release/manifest.json; README.md: Zephyr; docs/pilot-evidence.md: границы свидетельств. Локальный отчёт PILOT-RESULTS-REVIEW-2026-09-07.md, выборка пяти сценариев.

## 15. Предложение команде (1:00)

Предложение для команды: выбрать одну небольшую, но содержательную фичу, для которой есть понятные требования и рабочее тестовое окружение. До запуска договориться, что считается пригодным результатом. Например, кейсы понятны человеку, ключевые условия не потеряны, автотесты реализуют заявленные проверки, результат воспроизводится штатными средствами проекта. Замерить фактическое время, стоимость и ручные доработки. Отдельно разобрать найденные дефекты и ложные срабатывания. Это позволит обсуждать полезность на материале нашей команды, а не только на демонстрационном проекте. Предлагаемый следующий пилот является планом, а не уже выполненной работой.

Источники: Предложение по следующему применению на основе результатов пилота. Не является измеренным результатом.
