# Трасса: как пользоваться

Пошаговая инструкция. Что это за пакет и что он запускает — в [README.md](README.md).

В примерах проект лежит в `<проект>` (полный путь), документ требований — `docs/feature.md` (путь от корня
проекта), пакет — в `<проект>/.tools/test-skills`.

## 1. Что подготовить

- **Рабочую папку проекта** с исходниками и один документ требований к функции. Опишите, что функция
  делает, какие данные принимает и что ожидается при верном и при ошибочном вводе. Документ — в UTF-8.
- **Программу с доступом к модели**, открытую в папке проекта. Она должна уметь читать и писать файлы
  и выполнять команды. Лучше, если умеет запускать проверяющего в отдельном контексте; если нет — ревью
  идёт в той же сессии.
- **Python 3.11–3.13.**

## 2. Подключить пакет (один раз)

Пакет приходит папкой. Положите её в проект как `.tools/test-skills` — должен существовать файл
`.tools/test-skills/skills/orchestrate/SKILL.md`.

Ставить ничего не нужно: пакету достаточно Python 3.11–3.13 и его стандартной библиотеки, сторонние
пакеты и виртуальное окружение не требуются.

Ниже `<python пакета>` — команда вашего Python 3.11–3.13: `python` (Windows `py -3.11` тоже подойдёт) или
`python3` (Linux). Если `python` не находится, укажите полный путь к установленному Python 3.11+.

**Git проекта.** Пакет и результаты прогонов — не часть проекта:

- Допишите в `.gitignore` проекта три строки: `.tools/`, `.pilot-runs/`, `.skillsrc*` (последняя — настройки модулей,
  которые пакет создаёт при первом запуске, на каждой машине свои).
- Если пакет всё же попадает в git, положите в папку пакета (`.tools/test-skills/`) файл `.gitattributes` с одной
  строкой `* -text`. Иначе git на Windows заменит переносы строк (LF на CRLF), и `ready` остановится: проверка пакета
  сверяет файлы байт в байт и скажет, что изменены переносы строк.

**Документ в многомодульном проекте.** Документ требований может лежать в любой папке проекта, например в `docs/`
корня репозитория, — указывайте путь от корня проекта; модуль для него выбирается отдельно через `--module`.
Документ вне выбранного модуля читается только как документ задачи и в код модуля не попадает. ID модуля — путь его
папки от корня проекта: `api`, `services/core`; для корня проекта — `root`. Имена с точкой или не из латиницы
получают вид `root--<hex>`; `ready` без `--module` перечисляет ID всех модулей. Старая запись `root--617069` (hex
имени папки) ещё принимается, с предупреждением `MODULE_ID_LEGACY` и новым ID.

## 3. Проверить готовность

Одна команда показывает все проблемы сразу и к каждой — команду исправления. Терминал — в папке пакета
(`.tools/test-skills`). Профиль `cases-only-v1` указывайте всегда. Команда только читает проект и ничего в нём не запускает:

```text
<python пакета> -m tools.ready --project <проект> --docs docs/feature.md --profile cases-only-v1
```

Ещё флаги: `--docs` можно повторить для нескольких документов; `--docs файл.md#Раздел` берёт из Markdown-файла только один раздел
(заголовок и всё до следующего заголовка того же или более высокого уровня; нет такого заголовка — `TASK_DOC_SECTION_MISSING` с перечнем
заголовков файла); `--module <ID>` выбирает модуль, если их
несколько; `--target <путь>` заранее показывает, каким будет суженный контекст.

Как читать результат:

- `СТОП` нужно исправить — команда исправления напечатана рядом. Затем запустите
  проверку снова. Код выхода 0 — кейсы можно начинать.
- Выгрузку кейсов из Zephyr в `--docs` не подавайте — для неё есть `--cases` и `--reference` (раздел 6).

## 4. Дать модели запрос

Вставьте текст в программу с моделью. Замените `<проект>` и `docs/feature.md` на свои.

```text
Выполни .tools/test-skills/skills/orchestrate/SKILL.md.
Проект: <проект>.
Требования: docs/feature.md, путь от корня проекта.
Профиль: cases-only-v1 (ready и scan — с --profile cases-only-v1).
Инструменты пакета запускай командами python -m tools.… через Python
3.11–3.13; функции пакета не импортируй.

В конце кратко объясни результат ревью, перечисли пробелы и дай полные
пути к HTML, Markdown и JSON выбранной проверяющим редакции, а также
к отчёту ревью и папке запуска. Если редакция не принята или файл
не создан, прямо укажи это; черновик пометь как черновик.
```

Создаются кейсы и проводится их ревью. Автотесты не создаются, код проекта не запускается.

Первый запуск определит настройки проекта и при необходимости создаст `.skillsrc`. Если модулей несколько
или настройки неоднозначны, модель спросит вас. Одна попытка — один модуль.

**Пауза после разметки.** Если в требованиях нашлись пробелы (нет наблюдаемого результата, канала или доступа), модель остановится
и покажет их списком (`SCOPE_PENDING`). Ответьте одним из двух: «исключи `<номера SREQ…>`, потому что …» — для этих требований кейсы
не пишутся, причина попадёт в отчёт — или «продолжай как есть». Ваше решение Трасса записывает в прогон (`scope-decision.json`), без него
кейсы не пишутся. Другое решение позже — новый прогон. Черновик вопросов к аналитику уже лежит в `questions-for-analyst.md`.

## 5. Где результаты

Всё лежит в `<проект>/.pilot-runs/<run_id>/`; готовые кейсы и ревью — в подпапке `published/`. `run_id` — идентификатор прогона;
последняя строка вывода scan — `run_id: <id>`, полный путь модель называет в ответе. Файлы появляются по мере прохождения этапов.

| Файл | Зачем |
| --- | --- |
| `published/<документ>.r<ревизия>.html` | читать кейсы в браузере |
| `published/<документ>.r<ревизия>.md` | те же кейсы в редакторе или на GitHub |
| `published/<документ>.r<ревизия>.json` | исходный документ со связями с требованиями |
| `published/<документ>.r<ревизия>.zephyr-scale.csv` | импорт кейсов в Zephyr Scale (только у принятого набора) |
| `published/<документ>.r<ревизия>.REJECTED.html`, `.md` | набор отклонён ревьюером: кейсы и блокирующие замечания в шапке; CSV нет, не импортировать |
| `published/<документ>.r<ревизия>.UNREVIEWED.html`, `.md` | прогон закрыт без вердикта ревьюера: кейсы без проверки, CSV нет, не импортировать |
| `questions-for-analyst.md` | вопросы к требованиям |
| отчёт ревью | приняты ли кейсы и что исправить |
| `terminal-results/<attempt_id>.json` | итоговый статус закрытой попытки |

Как понимать итог (`accepted`, `verification`) — в [README.md](README.md#чем-всё-закончилось).

## 6. Кейсы из Zephyr

**Сравнить с вашими кейсами.** Добавьте модели в запрос: «эталонные кейсы — `cases/zephyr.csv`»; scan получит
`--reference cases/zephyr.csv`. Кейсы пишутся по документам, эталон получает только ревьюер (как подсказку), а отчёт прогона
показывает дубли, новые кейсы и пробелы относительно эталона.

**Кейсы и документы вместе.** Если есть и CSV, и документ требований, дайте оба: «Кейсы: `cases/zephyr.csv`,
требования: `docs/feature.md`» (scan с `--cases` и `--docs`). Модель свяжет кейсы с требованиями; требование
без кейса в CSV — пробел: кейс для него не пишется, его называют отчёт и `questions-for-analyst.md`.

CSV проверяется до создания прогона. Частые отказы: `IMPORT_CSV_SECRET` — в ячейке пароль или учётные данные
в адресе (отказ называет строку и колонку, значение не печатает; замените значение плейсхолдером `<…>`, например `<пароль>`);
`ZEPHYR_CSV_NOT_CSV` — файл не CSV; `ZEPHYR_CSV_COLUMNS` — незнакомые колонки.

**CSV для импорта по вашему шаблону.** Положите в проект CSV-выгрузку Zephyr с заглушками, где заполнены
обязательные поля вашего проекта, и укажите путь в `.skillsrc`:
`"projection": {"zephyr": {"template": "zephyr/stubs.csv"}}`. После закрытия попытки:

```text
<python пакета> -m tools.zephyr_template_export --project <проект> --run <run_id> --cases <путь к …zephyr-scale.csv>
```

Рядом появится `<документ>.r<ревизия>.zephyr-import.csv` — значения из шаблона, разделитель как в шаблоне.

## 7. Продолжить после перерыва

Длинный прогон можно продолжить в чистой сессии. Когда модель попросит, выполните `/clear` (или откройте
новую сессию) и напишите:

```text
продолжай test-skills <run_id>
```

Модель выполнит `run_pipeline status`, прочитает поле `next_step` и продолжит с первого незавершённого шага.
Посмотреть состояние самому:

```text
<python пакета> -m tools.run_pipeline status --project <проект> --run <run_id>
```

Если `status` показывает `drift` — файлы проекта изменились после scan: верните их или начните новый
прогон командой из `drift.fix`.

Ревью кейсов модель проводит двумя командами: `review-open` (кандидат, пакет и запрос проверяющего записываются до его вызова; файлов в `published/` пока нет) и
`review-select --verdict <ответ>` (ответ записывается, ревизия выбирается). `review-select --dry-run` проверяет ответ и ничего не
пишет — журнал и файлы прогона остаются как были.

### Ревью в свежей сессии

Ревью кейсов надёжнее, когда его проводит сессия, которая не видела генерацию. `review-open` печатает инструкцию (`for_human`):

1. Откройте новую сессию GigaCode или выполните `/clear` в рабочей.
2. Вставьте в неё: «проведи ревью test-skills `<run_id>`». Модель прочтёт вид кейсов из папки прогона (`review-views/`) и запишет свой
   ответ в файл `<run>/tmp/reviewer-answer.json` — путь она назовёт.
3. Вернитесь в рабочую сессию и выполните `review-select --verdict <этот файл>` (команда напечатана целиком).

Две вещи показывают, насколько ревью удалось. В вид кейсов код вставляет от нуля до трёх контрольных ошибок (по размеру набора) (в сам набор кейсов они не попадают):
отчёт `report.md` пишет, сколько из них ревьюер заметил; «ревью слабое: пропущено N из M» — повод перечитать набор самому, а
«ревью ненадёжно (`REVIEW_UNRELIABLE`)» (не замечена ни одна) значит, что вердикту ревью доверять нельзя. Контрольное слово — строка в задаче генератора:
ревьюер называет её в ответе, если она есть в его сессии. Названное слово значит, что сессия не свежая; не названное — признак
свежей сессии, не доказательство. Контрольные ошибки — сигнал качества ревью, не защита.

## 8. Частые остановки и что делать

Каждая остановка — JSON с кодом (`reason` или `code`) и подсказкой `fix`. Начинайте с `fix`.

| Код | Что случилось | Что делать |
| --- | --- | --- |
| `SCAN_RUN_IN_PROGRESS` | для того же запроса уже есть незакрытый прогон | продолжить его (`status`), закрыть (`finish`) или осознанно начать второй — scan с `--new-run` |
| `RUN_LEFT` | прогон оставлен до ревью кейсов, шаги модели в нём не идут | выполнить команду из `next_step` — обычный scan того же запроса начнёт новый |
| `DOCS_ENCODING` | документ требований не в UTF-8 | сохранить документ в UTF-8 и повторить scan |
| `DOCS_ZEPHYR_CSV` | в `--docs` подана выгрузка кейсов | подать её через `--reference` или `--cases` |
| `STEP_OVER_BUDGET` | вход шага модели больше бюджета | не стоп: шаг идёт; в следующий раз сузьте контекст (`--target` или пути модуля) |
| `STEP_INPUT_UNRESOLVED` | вход шага не найден в журнале | не стоп: модель сообщит одной строкой |
| `STEP_OUTPUT_LARGE` | ответ модели крупный | только замер, ничего делать не нужно |
| `SCOPE_PENDING` | после разметки остались пробелы, кейсы ещё не пишутся | ответить, исключать ли требования (с причиной) или продолжать как есть (раздел 4) |
| `OUTPUT_DIR_OUTSIDE_RUN` | каталог для готовых кейсов не `<run>/published` прогона | модель берёт `<run>/published` |
| `INPUT_OUTSIDE_PROJECT` | входной файл вне проекта, через ссылку или junction, путь с `..` или UNC | модель кладёт свой файл в `<run>/tmp/` и подаёт его путь |
| `COMMAND_NOT_PRINTABLE` | в пути проекта, документа или модуля, в заголовке раздела `--docs файл#Раздел` есть символ, который командная строка прочтёт по-своему (`$ % ! ^ " “ ” ' & \| < > ;` и др.; тире, `« »`, `№` и `?` можно); прогон не создан | переименовать папку или файл без этих символов и повторить scan; для `--docs файл#Раздел` — раздел без этих символов в заголовке или документ целиком |
| `MODEL_OUTPUT_TRUNCATED` | ответ модели оборван, JSON не закрыт | попросить модель выдать ответ короче или по частям и сохранить заново; шаг не засчитан, пока файл не разбирается |
| `TASK_DOC_OUTSIDE_CONTEXT` | документ из `--docs` лежит вне проекта или опись его не берёт (секрет, `node_modules`, `build`, бинарный файл); причина названа в остановке | положить документ внутрь проекта, вне исключённых папок, текстом без секретов; документ вне выбранного модуля, но внутри проекта, допустим |
| `MODULE_UNKNOWN` | `--module` указан не по id модуля из `.skillsrc` | `--module` — id модуля или путь его папки от корня проекта (`api`, `services/core`), для корня `root`; для папки с кириллицей или пробелом id — `root--<hex>` (его печатает остановка и `init_skillsrc`); старая запись вида `root--617069` ещё принимается (с предупреждением `MODULE_ID_LEGACY`); список id печатается в остановке |
| `SKILLSRC_UNREADABLE` | `.skillsrc` — каталог, junction, ссылка или не читается; прогон не создан | убрать с этим именем всё, кроме обычного файла в проекте, и повторить scan; нужен новый файл — `init_skillsrc --project <проект> --write` |
| `invalid_json`, `invalid_shape`, `schema_invalid` | чужой `.skillsrc`: пуст, не JSON, дубль ключа, лишний ключ; остановка называет ключ или строку; прогон не создан | исправить файл по названному ключу или переименовать его в `.skillsrc.bak` и создать новый: `init_skillsrc --project <проект> --write` (значения `limits`, `review` перенести из `.bak`) |
| `EXECUTION_COORDINATES` | `--run` или `--project` не указывают на один и тот же существующий прогон | подать точный `run_id` (32 символа) из `.pilot-runs` того же проекта; если проект перенесён в другую папку, `status` и `report` работают и там (с предупреждением `PROJECT_MOVED`), а `finish` — только в папке, где создан прогон |
| `FINISH_FACT_UNDETERMINED` | `finish` не может назвать итог: ревью ещё не закрыто | выполнить шаг из `fix` (`review-select` после ответа проверяющего, `finish --abandon` с причиной, если повтор стадии исчерпан) |
| `ZEPHYR_CSV_COLUMNS` | в CSV нет колонок шаблона Zephyr Scale или есть лишние | выгрузить кейсы из Zephyr Scale в CSV по шаблону, лишние колонки убрать |
| `FRESH_CONTEXT_REQUIRED` | модель открыла ревью, не сказав, свежий ли контекст у ревьюера | модель повторяет `review-open` с `--fresh-context yes` (отдельный проверяющий) или вы разрешаете ревью в той же сессии: `scan --accept-self-review` либо `review: {"self": true}` в `.skillsrc` |
| `REVIEW_ALREADY_OPEN` | ревью уже открыто другим проверяющим | повторить `review-open` с теми же `--invocation-id` и `--model-id` или идти дальше: `review-select --verdict <файл>` |
| `REVIEWER_RESPONSE_MISSING` | ответ проверяющего ещё не записан | `review-select --verdict <файл ответа>`; проверяющего ещё не вызывали — `review-open` |
| `REVIEW_CANARY_ONLY_VERDICT`, `REVIEW_ONLY_CANARY_FIXES` | вердикт ревью держится на контрольных ошибках, которые код вставил в вид ревьюера | проверяющий оставляет их находками `INFO` и даёт вердикт по остальному; затем `review-select` ещё раз |
| `REVIEW_CANARY_MISMATCH` | файлы пакета ревью не совпали с журналом | модель повторяет `review-open`, своих файлов не подставляет |
| `INTERNAL` | неожиданная ошибка пакета | передать разработчикам вывод команды |

**Закрыть цепочку, которая дальше не пойдёт.** Если остановка сама называет команду
`finish --abandon <причина>`, выполните её как есть:

```text
<python пакета> -m tools.run_pipeline finish --project <проект> --run <run_id> --abandon <причина>
```

Причины: `LEFT_BEFORE_REVIEW` (прогон застрял до ревью кейсов), `STAGE_RETRY_EXHAUSTED`, `ASSEMBLY_INVALID`. Без такой подсказки `--abandon` не нужен: обычный
`finish` закрывает попытку без исполнения, а уже закрытую — повторно без изменений.

После вердикта «ТРЕБУЕТ ДОРАБОТКИ» `finish` и `status` печатают `next_run` —
команду следующего захода. Её запускаете вы или модель по вашему слову.

## Памятка: модель запуталась

Если модель потеряла нить, повторяет шаги или предлагает странное:

1. Попросите выполнить `status` (команда из раздела 7) и сделать то, что написано в поле `next_step`. Больше ничего не придумывать.
2. Если `status` называет остановку — прочитайте `fix` и выполните его (раздел 8).
3. Если цепочка дальше не пойдёт, а остановка сама предлагает `finish --abandon <причина>` — выполните эту команду как есть.
4. Начинайте новый прогон (`scan` с `--new-run`) только когда прежний закрыт или вам нужен второй, независимый.
   Незакрытый прогон того же запроса с `--new-run` не заменяется — он останется в `.pilot-runs`.

## 9. Отчёт прогона

```text
<python пакета> -m tools.run_pipeline report --project <проект> --run <run_id>
```

Пишет в папку прогона `report.md`, `report.json` и `questions-for-analyst.md`. В отчёте — шаги со временем,
длительность и размер входа каждого вызова модели против бюджета шага, коды остановок, числа и окружение. Там же: фазы по времени, состав входа по видам, отказы команд (по командам,
кодам и пачкам), канон в числах и размер рабочей папки `tmp/` с командой её удаления — отчёт сам ничего не
удаляет. Кода проекта, текста требований, кейсов и ответов модели в нём нет. Что можно
выносить за пределы рабочей среды — решают правила вашей компании.

Если ревью приняло кейсы с замечаниями, в `report.md` есть раздел «Замечания ревью», а текст
замечаний — в `questions-for-analyst.md`.
