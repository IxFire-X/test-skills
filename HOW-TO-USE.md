# Трасса: как пользоваться

Пошаговая инструкция. Что это за пакет и что он запускает — в [README.md](README.md).

В примерах проект лежит в `<проект>` (полный путь), документ требований — `docs/feature.md` (путь от корня
проекта), пакет — в `<проект>/.tools/test-skills`.

## 1. Что подготовить

- **Рабочую папку проекта** с исходниками и один документ требований к функции. Опишите, что функция
  делает, какие данные принимает и что ожидается при верном и при ошибочном вводе. Документ — в UTF-8.
- **Программу с доступом к модели**, открытую в папке проекта. Она должна уметь читать и писать файлы
  и выполнять команды. Лучше, если умеет запускать проверяющего в отдельном контексте; если нет — ревью
  идёт в той же сессии.
- **Python 3.11–3.13.**

## 2. Подключить пакет (один раз)

Пакет приходит папкой. Положите её в проект как `.tools/test-skills` — должен существовать файл
`.tools/test-skills/skills/orchestrate/SKILL.md`.

Ставить ничего не нужно: пакету достаточно Python 3.11–3.13 и его стандартной библиотеки, сторонние
пакеты и виртуальное окружение не требуются.

Ниже `<python пакета>` — команда вашего Python 3.11–3.13: `python` (Windows `py -3.11` тоже подойдёт) или
`python3` (Linux). Если `python` не находится, укажите полный путь к установленному Python 3.11+.

Проверьте, что пакет цел. Терминал — в папке пакета (`.tools/test-skills`):

```text
<python пакета> -m tools.doctor --root .
```

Команда сверяет файлы пакета с `release/manifest.json` и проверяет версию Python; ничего не запускает и не пишет. В ответе `"status": "PASS"` — можно идти дальше; `"qualification": {"state": "implemented_unverified"}` при `PASS` — норма (пакет цел, проверка на связке моделей не заявлена), делать ничего не нужно. `NOT_RUNNABLE` — смотрите `messages`: там названы лишний или недостающий файл и изменённые переносы строк (CRLF) и сказано, что делать; обычно достаточно заново скопировать поставку. Версия Python ниже 3.11 видна в поле `python`.

**Git проекта.** Пакет и результаты прогонов — не часть проекта:

- Допишите в `.gitignore` проекта три строки: `.tools/`, `.pilot-runs/`, `.skillsrc*` (последняя — настройки модулей,
  которые пакет создаёт при первом запуске, на каждой машине свои).
- Если пакет всё же попадает в git, положите в папку пакета (`.tools/test-skills/`) файл `.gitattributes` с одной
  строкой `* -text`. Иначе git на Windows заменит переносы строк (LF на CRLF), и `ready` остановится: проверка пакета
  сверяет файлы байт в байт и скажет, что изменены переносы строк.

**Документ в многомодульном проекте.** Документ требований может лежать в любой папке проекта, например в `docs/`
корня репозитория, — указывайте путь от корня проекта; модуль для него выбирается отдельно через `--module`.
Документ вне выбранного модуля читается только как документ задачи и в код модуля не попадает. ID модуля — путь его
папки от корня проекта: `api`, `services/core`; для корня проекта — `root`. Имена с точкой или не из латиницы
получают вид `root--<hex>`; `ready` без `--module` перечисляет ID всех модулей. Старая запись `root--617069` (hex
имени папки) ещё принимается, с предупреждением `MODULE_ID_LEGACY` и новым ID.

## 3. Проверить готовность

Одна команда показывает все проблемы сразу и к каждой — команду исправления. Терминал — в папке пакета
(`.tools/test-skills`). Чтобы получить кейсы без автотестов, указывайте профиль `cases-only-v1`: он подходит для любой поставки. Если в папке пакета есть файл `HOW-TO-USE-MODE-B.md`, в вашей поставке есть и режим автотестов (режим Б): начните с этого файла; если файла нет, поставка — только для кейсов. Команда только читает проект и ничего в нём не запускает:

```text
<python пакета> -m tools.ready --project <проект> --docs docs/feature.md --profile cases-only-v1
```

Ещё флаги: `--docs` можно повторить для нескольких документов; `--docs файл.md#Раздел` берёт из Markdown-файла только один раздел
(заголовок и всё до следующего заголовка того же или более высокого уровня; нет такого заголовка — `TASK_DOC_SECTION_MISSING` с перечнем
заголовков файла; несколько разделов одного файла — несколько `--docs`, остальной документ модель читает как контекст); `--module <ID>` выбирает модуль, если их
несколько; `--target <путь>` сужает контекст: `ready` показывает, каким он будет, а `scan` с тем же `--target` его строит (готовую команду `scan` с `--target` `ready` печатает сам); шаблоны, которые код из `--target` называет по имени, подтягиваются сами (`ready` пишет, какие).

Как читать результат:

- `СТОП` нужно исправить — команда исправления напечатана рядом. Затем запустите
  проверку снова. Код выхода 0 — кейсы можно начинать.
- Выгрузку кейсов из Zephyr в `--docs` не подавайте — для неё есть `--cases` и `--reference` (раздел 6).
- `ВНИМАНИЕ` с прогонами по разделам: в документе много нумерованных утверждений (`1.1.1.`, `D01.`). Свыше ≈ 37 ревью такого объёма на прошлых
  прогонах проверяло слабее, свыше ≈ 59 оно не помещается в окно модели — `submit plan` остановит прогон до генерации (`PLAN_REVIEW_TOO_LARGE`).
  Строка уже называет прогоны: `--docs "файл.md#Раздел"` (в одном прогоне — несколько разделов). Просите одним запросом: «документ большой, веди по разделам
  из ready»: модель проведёт прогоны по очереди и соберёт один CSV (раздел 5).

### Требования в OpenSpec

Требования лежат в `openspec/specs/<область>/spec.md`, живые изменения — в `openspec/changes/<имя>/`, архив — в
`openspec/changes/archive/`. Что взять в прогон, выбирает `--docs`: файл `spec.md` или папка — `openspec/specs` (все области),
`openspec/specs/<область>`, `openspec/changes/<имя>` (его дельты и `proposal`/`design`/`tasks`), `openspec/changes/archive/<имя>` (все
его дельты; требований они не дают — архивное изменение называют только вместе с `--cases`, раздел 6). Папки вне `openspec/` не раскрываются — назовите файлы. Требования прогона — только названные `spec.md`; остальные области
модель видит как контекст, и **полнота неназванных областей не проверяется** — назовите всё, что должно попасть в кейсы.
Без «Код: <папка>» модель читает как контекст весь проект, и любой файл в нём тоже: например, старые кейсы в `docs/*.csv` идут во вход
как обычный текст, не как эталон, и вход шага растёт. Чтобы так не было, назовите код («Код: src/main») или на время прогона уберите
такой файл из проекта.

Вся спецификация без изменений:

```text
<python пакета> -m tools.ready --project <проект> --docs openspec/specs --profile cases-only-v1
```

Одно изменение — достаточно назвать его папку. Кейсы пишутся только по требованиям изменения (ADDED, MODIFIED, RENAMED); `spec.md`
областей, которые оно меняет, — база для сравнения и контекст, кейсов по ним нет. `proposal.md`, `design.md`, `tasks.md` модель читает как
контекст, требований из них нет. Называйте папку изменения целиком: дельты только части его областей — остановка до модели.

```text
<python пакета> -m tools.ready --project <проект> --docs openspec/changes/add-search --profile cases-only-v1
```

ready и scan напишут объём строкой «Объём OpenSpec: только изменение add-search; …», а требования базы, которые изменение не меняет, но
может задеть, — строкой «Проверьте регресс: …». Нужна полная регрессия области — добавьте её `spec.md`, как подсказывает строка: тогда
кейсы пишутся по всей области вместе с изменением:

```text
<python пакета> -m tools.ready --project <проект> --docs openspec/specs/owners --docs openspec/changes/add-search --profile cases-only-v1
```

Только по изменению идёт прогон, где в `--docs` одни файлы OpenSpec и нет `--cases`. С `--cases` (раздел 6) или вместе с обычным
документом `spec.md` области изменения называть обязательно, иначе остановка до модели.

Другие живые изменения и неназванный архив в модель не идут: scan называет их одной строкой в `warnings`. Файлы двух изменений в
одном запросе, а также два живых изменения в проекте без `--docs` — остановка `OPENSPEC_SOURCE_CONFLICT`: повторите `scan` с `--docs`
одного изменения (`--new-run` не нужен).

Изменение, уже вписанное в `spec.md` (то же требование с тем же текстом; тексты сравниваются по словам, переносы строк и пробелы не важны), — не остановка: `scan` напишет
строку «уже вписано» с числом, а требования возьмутся из изменения. Расхождение — другой текст у того же требования в ADDED, имя в MODIFIED, которого нет в `spec.md`. Если `spec.md` области назван — это
остановка на `scan`, до шага модели: агент покажет, где расхождение, и спросит автора изменения. В прогоне только по изменению такое
требование не берётся, а прогон идёт дальше: строка «Не применено: …» назовёт его с файлом, строкой и причиной, строка «Объём неполный: …» —
сколько взято, вопрос к нему попадёт в `questions-for-analyst.md`, а итог прогона получит оговорку. Не взялось ни одно требование
или изменение только удаляет требования — остановка. Повтор требования — остановка всегда. REMOVED, чьего имени в `spec.md` нет (уже удалено или имя не
совпало), не остановка и не «уже вписано»: `scan` называет его отдельной строкой с файлом, строкой и ближайшими именами — сверьте имя у автора изменения.

**Когда запускать.** Только кейсы — как только изменение согласовано, пока оно лежит в `openspec/changes/<имя>/`, даже до кода; хватит
`--docs openspec/changes/<имя>`: кейсы будут
готовы к концу разработки, а вопросы к аналитику (`questions-for-analyst.md`) появятся, пока требования дёшево править. С автотестами
(режим Б) — когда код изменения уже в ветке задачи, но PR ещё не влит: автотестам нужен реализованный код, а упавшие тесты — находки до
слияния. После слияния изменение уходит в архив: кейсы на регресс берите по всей спецификации — `--docs openspec/specs` (слитое изменение
уже в ней). Одно архивное изменение требований не даёт (прогон только с `--docs openspec/changes/archive/<имя>` получит 0 требований); его
называют вместе с `--cases` — когда нужно обновить старые кейсы под это изменение (раздел 6). Работаете в ветке задачи — проверьте
`.gitignore` (раздел 2), чтобы `.tools/`, `.pilot-runs/` и `.skillsrc*` не попали в PR.

## Когда запускать

1. Предложение изменения на ревью — запрос 1: только проверка готовности, секунды, модель кейсы не пишет и прогон не создаётся.
2. Дельта изменения согласована — запрос 2: кейсы по изменению и их ревью; код можно не ждать.
3. Код готов — запрос 3: автотесты по вашим кейсам, если в поставке есть режим автотестов (см. начало раздела 3).
4. Изменение ушло в архив — запрос 4: ваши кейсы из выгрузки Zephyr сверяются с обновлённой спецификацией.

## 4. Дать модели запрос

Откройте программу с моделью в папке проекта и вставьте один из запросов. Вместо `<имя>` — имя папки изменения в `openspec/changes/`.

Запрос 1 — проверить изменение:

```text
Выполни .tools/test-skills/skills/orchestrate/SKILL.md.
Проверь изменение OpenSpec <имя>: только ready, кейсы не пиши.
```

Запрос 2 — тест-кейсы:

```text
Выполни .tools/test-skills/skills/orchestrate/SKILL.md.
Напиши тест-кейсы по изменению OpenSpec <имя>. Код (по желанию): <папка>
```

Запрос 4 — обновить кейсы после архива:

```text
Выполни .tools/test-skills/skills/orchestrate/SKILL.md.
Изменение OpenSpec <имя> в архиве: обнови кейсы из <выгрузка Zephyr .csv>.
```

Обычный документ вместо изменения — «по документу <путь от корня проекта>», например: «Напиши тест-кейсы по документу docs/feature.md.» Несколько модулей — допишите строку «Модуль: <id модуля>». Какие пути изменения агент возьмёт в `--docs`, профиль и что он скажет в конце — его забота; пути те же, что `ready` из раздела 3.

С запросами 2 и 4 создаются кейсы и проводится их ревью; автотесты не создаются, код проекта не запускается.

Если `scan` отказал до модели (например `OPENSPEC_SOURCE_CONFLICT` или `DOCS_ENCODING`), в `.pilot-runs` остаётся папка прогона, но повтору она не мешает: исправьте и повторите `scan` — с теми же или другими `--docs`, `--new-run` не нужен. `--new-run` нужен, только когда незакрытый прогон того же запроса уже дошёл до модели (`SCAN_RUN_IN_PROGRESS`), а вам нужен второй, независимый.

Прогон агент ведёт сам, в основной сессии: не поручайте его субагенту — у субагента защита от зацикливания обрывает длинный прогон (`LOOP_DETECTED`). Самого субагента не продолжить, но прогон цел: напишите основному агенту «продолжай test-skills <run_id>». Тяжёлый прогон — в отдельной сессии; другую работу в ней не ведите.

Первый запуск определит настройки проекта и при необходимости создаст `.skillsrc`. Если модулей несколько
или настройки неоднозначны, модель спросит вас. Одна попытка — один модуль.

**Общая среда.** Если кейсы проходят в общей среде (там есть записи других людей и демо-данные), впишите у модуля в `.skillsrc`
`"shared_data": true`: тогда кейсы создают свои записи с меткой прогона, удаляют их последним шагом «Уборка» и чужие не трогают. Пока
ключа нет, `ready` напоминает об этом строкой.

Файл в папке проекта, который не обычный файл (например файл с именем `nul`), пакет пропускает: он называется в списке исключённых файлов вывода `scan`, а в кейсы и во вход модели не попадает.

**Пауза после разметки.** Если в требованиях нашлись пробелы (нет наблюдаемого результата, канала или доступа), модель остановится
и покажет их списком (`SCOPE_PENDING`). Ответьте одним из двух: «исключи `<номера SREQ…>`, потому что …» — для этих требований кейсы
не пишутся, причина попадёт в отчёт — или «продолжай как есть». Ваше решение Трасса записывает в прогон (`scope-decision.json`), без него
кейсы не пишутся. Другое решение позже — новый прогон. Черновик вопросов к аналитику уже лежит в `questions-for-analyst.md`. Расхождения кода и требования (замечание одной фразой) паузу не вызывают: ищите их в конце прогона в `questions-for-analyst.md`, раздел «Прочее».

**Метки неясности в тексте требования.** Требование со словами «требует уточнения», «нужно уточнить», «открытый вопрос», «под вопросом», «TBD» или «TBC» остаётся без кейса (ожидаемый результат не задан): в отчёте — строка «без кейсов», в `questions-for-analyst.md` — вопрос. Требование с пометкой «неподтверждённое условие» или «документация не задаёт…» кейс получает: поведение задано, неясна деталь, в файле вопросов — вопрос. Если на требование есть кейс в вашем CSV (`--cases`), оно остаётся с кейсом.

## 5. Где результаты

Всё лежит в `<проект>/.pilot-runs/<run_id>/`; готовые кейсы и ревью — в подпапке `published/`. `run_id` — идентификатор прогона;
последняя строка вывода scan — `run_id: <id>`, полный путь модель называет в ответе. Файлы появляются по мере прохождения этапов.

| Файл | Зачем |
| --- | --- |
| `published/<документ>.r<ревизия>.html` | читать кейсы в браузере |
| `published/<документ>.r<ревизия>.md` | те же кейсы в редакторе или на GitHub |
| `published/<документ>.r<ревизия>.json` | исходный документ со связями с требованиями |
| `published/<документ>.r<ревизия>.zephyr-scale.csv` | импорт кейсов в Zephyr Scale (только у принятого набора) |
| `published/<документ>.r<ревизия>.REJECTED.html`, `.md` | набор отклонён ревьюером: кейсы и блокирующие замечания в шапке; CSV нет, не импортировать |
| `published/<документ>.r<ревизия>.UNREVIEWED.html`, `.md` | прогон закрыт без вердикта ревьюера: кейсы без проверки, CSV нет, не импортировать |
| `questions-for-analyst.md` | вопросы к требованиям |
| `assembled/sections-<…>.zephyr-scale.csv`, `….summary.json` | один CSV из прогонов по разделам документа (`python -m tools.assemble_sections --project <проект> --doc <документ> --write`; без `--write` — какие разделы пройдены) и сводка: числа, коды, повторы названий, без текстов |
| отчёт ревью | приняты ли кейсы и что исправить |
| `terminal-results/<attempt_id>.json` | итоговый статус закрытой попытки |

Как понимать итог (`accepted`, `verification`) — в [README.md](README.md#чем-всё-закончилось).

## 6. Кейсы из Zephyr

**Сравнить с вашими кейсами.** Добавьте модели в запрос: «эталонные кейсы — `cases/zephyr.csv`»; scan получит
`--reference cases/zephyr.csv`. Кейсы пишутся по документам, эталон получает только ревьюер (как подсказку), а отчёт прогона
показывает дубли, новые кейсы и пробелы относительно эталона.

**Кейсы в стиле вашей команды.** Положите до трёх своих кейсов — экспорт Zephyr в CSV — и укажите путь в `.skillsrc`:
`"style": {"samples": "cases/style.csv"}`. Модель возьмёт из них форму: как вы называете кейсы, пишете шаги, данные и
ожидания. Факты из образцов она не берёт; если значение из образца всё же попало в кейс, ревьюер увидит это подсказкой.
Берите кейсы на другие требования, чем у прогона.

**Кейсы и документы вместе.** Если есть и CSV, и документ требований, дайте оба: «Кейсы: `cases/zephyr.csv`,
требования: `docs/feature.md`» (scan с `--cases` и `--docs`; `ready` принимает тот же `--cases` и проверяет CSV до прогона). Модель свяжет кейсы с требованиями; требование
без кейса в CSV остаётся требованием: под него пишутся новые кейсы рядом с вашими (ваши не меняются), Key у новых пуст —
при загрузке в Zephyr они создадутся, а не обновят старые; такое требование называют отчёт и `questions-for-analyst.md`.

**Обновить кейсы под изменившуюся фичу.** С теми же `--cases` и `--docs` модель судит каждый старый кейс: «подходит» (остаётся как есть),
«переписать» (текст приводится к требованию; Key, приоритет, папка, метки и место прежние — в Zephyr кейс обновится, а не создастся) или
«устарел» (требование удалено: кейс не удаляется, отчёт его называет, в выгрузке для Zephyr у него метка `устарел` в колонке Labels; снять её — вручную). По OpenSpec судятся кейсы, связанные с изменёнными
требованиями; без изменения OpenSpec — все. «Устарел» бывает только когда изменение OpenSpec удаляет (REMOVED) требование: в обычном документе кейс удалённого требования попадает «вне документов». Живое изменение: `--cases cases/zephyr.csv --docs openspec/specs --docs openspec/changes/<имя>`.
Архив: `--cases cases/zephyr.csv --docs openspec/specs --docs openspec/changes/archive/<дата-имя>` — изменение называют папкой
(или файлами всех его дельт `…/specs/<область>/spec.md`; `proposal.md` не годится); `spec.md` областей изменения называть обязательно.
Назовите все области, где у вас есть кейсы (`openspec/specs` — вся спецификация), — иначе их кейсы попадут «вне документов». Отчёт называет номера строк CSV по шести группам:
«без изменений» (кейс оставлен как есть, в том числе тот, что не судился), «проверить вручную» (кейс подходит, но модель назвала сомнение — решите сами),
«переписаны», «устарели», «вне документов» (кейс не связан ни с одним требованием названных документов, например его область не названа в `--docs`) и
«требования без кейса в CSV» (под них пишутся новые кейсы). «Было → стало» и причины — в разделе «Проверьте» файла `questions-for-analyst.md`;
он есть, когда нашлись такие кейсы, и кончается строкой о кейсах, оставленных как есть.

**Кейс из CSV, который ревью отклонило.** Он не пропадает: в выгрузку для Zephyr он попадает таким, каким был в CSV (после принятых кейсов), а отчёт
и раздел «Проверьте» называют его по Key и строке CSV с замечанием ревьюера. Требование, которое добавило изменение (ADDED), не связывают ни с каким старым кейсом: под него пишутся новые кейсы. Если отклонён весь набор, файла выгрузки нет.

CSV проверяется до создания прогона. Частые отказы: `IMPORT_CSV_SECRET` — в ячейке пароль или учётные данные
в адресе (отказ называет строку и колонку, значение не печатает; замените значение плейсхолдером `<…>`, например `<пароль>`);
`ZEPHYR_CSV_NOT_CSV` — файл не CSV; `ZEPHYR_CSV_COLUMNS` — незнакомые колонки.

**CSV для импорта по вашему шаблону.** Положите в проект CSV-выгрузку Zephyr с заглушками, где заполнены
обязательные поля вашего проекта, и укажите путь в `.skillsrc`:
`"projection": {"zephyr": {"template": "zephyr/stubs.csv"}}`. После закрытия попытки:

```text
<python пакета> -m tools.zephyr_template_export --project <проект> --run <run_id> --cases <путь к …zephyr-scale.csv>
```

Рядом появится `<документ>.r<ревизия>.zephyr-import.csv` — значения из шаблона, разделитель как в шаблоне.

## 7. Продолжить после перерыва

Длинный прогон можно продолжить в чистой сессии. Когда модель попросит, выполните `/clear` (или откройте
новую сессию) и напишите:

```text
продолжай test-skills <run_id>
```

Модель выполнит `run_pipeline status`, прочитает поля `state` и `next` и продолжит с первого незавершённого шага.
Посмотреть состояние самому:

```text
<python пакета> -m tools.run_pipeline status --project <проект> --run <run_id>
```

Если `status` показывает `drift` — файлы проекта изменились после scan: верните их или начните новый
прогон командой из `drift.fix`.

Новый прогон по тем же требованиям берёт готовое от прошлого прогона. Разметка берётся и при тестах, которые прошлый прогон записал в проект,
и при каталогах сборки (например `build`, `target`). План, пачки и ревью берутся, только если с прошлого прогона в проекте не появилось ни файлов
(в том числе записанных тестов), ни каталогов сборки; иначе они делаются заново, а причину называет `scan` (строка `cases.reason`; если изменились
файлы проекта, в строке «входы иные» стоит их список). В этой строке названо, что именно иное: «inventory» (файлы проекта; в строке `ready` про пропущенные файлы `CONTEXT_OWN_TEST` — тесты, записанные прошлым прогоном: моделям они не передаются), «requirements», «.skillsrc», «профиль» (прошлый прогон начат с другим профилем, чем этот), «модуль». Разметка берётся и из прогона, где ревью отклонило кейсы или принято не всё (план, пачки и ревью из него не берутся, причина — в `cases.reason`); если замечания ревью были к самим требованиям, разметку лучше сделать заново (`prepare` без `--reuse-from`). Автотесты, если прошлый прогон уже записал тесты в проект, пишутся заново: их пути заняты.

Ревью кейсов модель проводит тем же циклом, что и остальные стадии: `prepare --stage tc-reviewer:canonical` (кандидат, пакет и запрос проверяющего записываются до его вызова; файлов в `published/` пока нет), ответ проверяющего — в файл `incoming/tc-reviewer-canonical.json` прогона, затем `submit --stage tc-reviewer:canonical` (ответ записывается, ревизия выбирается). `submit --dry-run` проверяет ответ и ничего не
пишет — журнал и файлы прогона остаются как были.

### Ревью в свежей сессии

Ревью кейсов надёжнее, когда его проводит сессия, которая не видела генерацию. `prepare` печатает инструкцию (`for_human`):

1. Откройте новую сессию агента или выполните `/clear` в рабочей.
2. Вставьте в неё: «проведи ревью test-skills `<run_id>`». Модель прочтёт вид кейсов из папки прогона (`review-views/`) и запишет свой
   ответ в файл `incoming/tc-reviewer-canonical.json` прогона — путь она назовёт.
3. Вернитесь в рабочую сессию и выполните `submit --stage tc-reviewer:canonical` (ответ уже лежит в слоте `incoming/`).

Две вещи показывают, насколько ревью удалось. В вид кейсов код вставляет от трёх до пятнадцати контрольных ошибок (по размеру набора; в очень малом наборе меньше) (в сам набор кейсов они не попадают):
отчёт `report.md` пишет, сколько из них ревьюер заметил; «ревью слабое: пропущено N из M» — повод перечитать набор самому, а
«ревью ненадёжно (`REVIEW_UNRELIABLE`)» (замечена меньше трети) значит, что вердикту ревью доверять нельзя. Контрольное слово — строка в задаче генератора:
ревьюер называет её в ответе, если она есть в его сессии. Названное слово значит, что сессия не свежая; не названное — признак
свежей сессии, не доказательство. Контрольные ошибки — сигнал качества ревью, не защита.

## 8. Частые остановки и что делать

Каждая остановка — JSON с кодом (`reason` или `code`) и подсказкой `fix`. Начинайте с `fix`.
У частых остановок и предупреждений есть ещё поле `human` — одна фраза для вас: что случилось и что сделать. Агент пересказывает её, а чинит по `fix`.

| Код | Что случилось | Что делать |
| --- | --- | --- |
| `SCAN_RUN_IN_PROGRESS` | для того же запроса уже есть незакрытый прогон | продолжить его (`status`), закрыть (`finish`) или осознанно начать второй — scan с `--new-run` |
| `RUN_LEFT` | прогон оставлен до ревью кейсов, шаги модели в нём не идут | выполнить обычный scan того же запроса — он начнёт новый прогон |
| `DOCS_ENCODING` | документ требований не в UTF-8 | сохранить документ в UTF-8 и повторить scan |
| `DOCS_ZEPHYR_CSV` | в `--docs` подана выгрузка кейсов | подать её через `--reference` или `--cases` |
| `OPENSPEC_SOURCE_CONFLICT` | в `--docs` файлы двух изменений OpenSpec, или `--docs` нет при двух живых изменениях, или `spec.md` области изменения не назван (или состав спецификации не сходится), или требование изменения расходится со `spec.md` (другой текст у ADDED, имя MODIFIED, которого там нет) | назвать в `--docs` папку одного изменения и `spec.md` его областей, повторить scan; расхождение — показать автору изменения, прогон после правки; если отказ пришёл после шага модели — `scan --new-run` |
| `NEED_DOCS_LIMIT` | документы `--docs` (файлы папок и названные файлы) больше 256 КиБ каждый или 1 МиБ все вместе | назвать меньше областей, повторить scan |
| `PLAN_REVIEW_TOO_LARGE` | по числу номеров ревью набора не поместится в окно модели; прогон остановлен до генерации | вести документ по разделам из `fix` (раздел 3, `ВНИМАНИЕ`); этот прогон дальше не вести |
| `STEP_OVER_BUDGET` | вход шага модели больше бюджета | не стоп: шаг идёт; в следующий раз сузьте контекст (`--target` или пути модуля) |
| `STEP_INPUT_UNRESOLVED` | вход шага не найден в журнале | не стоп: модель сообщит одной строкой |
| `MODEL_STAGE_ARTIFACT_INVALID` | ответ модели не прошёл схему стадии | поправить поля из `diagnostics` и подать ответ единственным повтором стадии (`--transport-attempts 2`) |
| `BATCH_SEMANTIC_CONFLICT` | кейсы пачки не прошли проверку формата | исправить все строки `diagnostics` за один заход (у каждой свой путь и `fix`) и подать фрагмент единственным повтором стадии |
| `SEMANTIC_PARAM_GROUP_MISMATCH` | кейс группы `param_group` отличается от первого кейса группы не только вариантом | выровнять кейс по первому кейсу группы (путь первого расхождения — в `diagnostics`): различаться могут название, цель и значение варианта, а операции, виды входов, ожидания и число шагов должны совпасть |
| `STEP_OUTPUT_LARGE` | ответ модели крупный | только замер, ничего делать не нужно |
| `SCOPE_PENDING` | после разметки остались пробелы, кейсы ещё не пишутся | ответить, исключать ли требования (с причиной) или продолжать как есть (раздел 4) |
| `OUTPUT_DIR_OUTSIDE_RUN` | каталог готовых кейсов прогона `<run>/published` подменён ссылкой или ведёт за пределы прогона | выполнить `fix` из остановки; ссылок вместо каталога `published` не делать |
| `INPUT_OUTSIDE_PROJECT` | входной файл вне проекта, через ссылку или junction, путь с `..` или UNC | модель кладёт свой файл в `<run>/tmp/` и подаёт его путь |
| `COMMAND_NOT_PRINTABLE` | в пути проекта, документа или модуля, в заголовке раздела `--docs файл#Раздел` есть символ, который командная строка прочтёт по-своему (`$ % ! ^ " “ ” ' & \| < > ;` и др.; тире, `« »`, `№` и `?` можно); прогон не создан | переименовать папку или файл без этих символов и повторить scan; для `--docs файл#Раздел` — раздел без этих символов в заголовке или документ целиком |
| `MODEL_OUTPUT_TRUNCATED` | ответ модели оборван, JSON не закрыт | попросить модель выдать ответ короче или по частям и сохранить заново; шаг не засчитан, пока файл не разбирается |
| `TASK_DOC_OUTSIDE_CONTEXT` | документ из `--docs` лежит вне проекта или опись его не берёт (секрет, `node_modules`, `build`, бинарный файл); причина названа в остановке | положить документ внутрь проекта, вне исключённых папок, текстом без секретов; документ вне выбранного модуля, но внутри проекта, допустим |
| `MODULE_UNKNOWN` | `--module` указан не по id модуля из `.skillsrc` | `--module` — id модуля или путь его папки от корня проекта (`api`, `services/core`), для корня `root`; для папки с кириллицей или пробелом id — `root--<hex>` (его печатает остановка и `init_skillsrc`); старая запись вида `root--617069` ещё принимается (с предупреждением `MODULE_ID_LEGACY`); список id печатается в остановке |
| `SKILLSRC_UNREADABLE` | `.skillsrc` — каталог, junction, ссылка или не читается; прогон не создан | убрать с этим именем всё, кроме обычного файла в проекте, и повторить scan; нужен новый файл — `init_skillsrc --project <проект> --write` |
| `invalid_json`, `invalid_shape`, `schema_invalid` | чужой `.skillsrc`: пуст, не JSON, дубль ключа, лишний ключ; остановка называет ключ или строку; прогон не создан | исправить файл по названному ключу или переименовать его в `.skillsrc.bak` и создать новый: `init_skillsrc --project <проект> --write` (значения `limits`, `review` перенести из `.bak`) |
| `EXECUTION_COORDINATES` | `--run` или `--project` не указывают на один и тот же существующий прогон | подать точный `run_id` (32 символа) из `.pilot-runs` того же проекта; если проект перенесён в другую папку, `status` и `report` работают и там (с предупреждением `PROJECT_MOVED`), а `finish` — только в папке, где создан прогон |
| `FINISH_FACT_UNDETERMINED` | `finish` не может назвать итог: ревью ещё не закрыто | выполнить шаг из `fix` (`submit --stage tc-reviewer:canonical` после ответа проверяющего, `finish --abandon` с причиной, если повтор стадии исчерпан) |
| `ZEPHYR_CSV_COLUMNS` | в CSV нет колонок шаблона Zephyr Scale или есть лишние | выгрузить кейсы из Zephyr Scale в CSV по шаблону, лишние колонки убрать |
| `FRESH_CONTEXT_REQUIRED` | модель открыла ревью, не сказав, свежий ли контекст у ревьюера | модель повторяет `prepare --stage tc-reviewer:canonical` с `--fresh-context yes` (отдельный проверяющий) или вы разрешаете ревью в той же сессии: модель повторяет `prepare` с `--fresh-context no --accept-self-review` (или `scan --accept-self-review`), либо `review: {"self": true}` в `.skillsrc` |
| `REVIEW_ALREADY_OPEN` | ревью уже открыто другим проверяющим | повторить `prepare` с теми же `--invocation-id` и `--fresh-context` или идти дальше: ответ в слот и `submit` |
| `REVIEWER_RESPONSE_MISSING` | ответ проверяющего ещё не записан | ответ проверяющего в слот `incoming/tc-reviewer-canonical.json` и `submit`; проверяющего ещё не вызывали — `prepare` |
| `REVIEW_ONLY_CANARY_FIXES` | правки ревью держатся на контрольных ошибках, которые код вставил в вид ревьюера | проверяющий оставляет их находками `INFO` и даёт вердикт по остальному; затем `submit` ещё раз |
| `REVIEW_CANARY_MISMATCH` | файлы пакета ревью не совпали с журналом | модель повторяет `prepare`, своих файлов не подставляет |
| `INTERNAL` | неожиданная ошибка пакета | передать разработчикам вывод команды |

**Брошенный прогон и `scan`.** Обычный `scan` сам смотрит незакрытые прогоны того же запроса. Если прошлый прогон оставлен до ревью кейсов, оборван на самом `scan` или файлы проекта изменились после его `scan` (дрейф), `scan` не останавливается: он начинает новый прогон и называет прошлый в поле `abandoned_runs` с причиной в скобках. Прошлый прогон остаётся в `.pilot-runs`, ничего не удаляется. С флагом `--new-run` эта проверка не делается.

**Закрыть цепочку, которая дальше не пойдёт.** Если остановка сама называет команду
`finish --abandon <причина>`, выполните её как есть:

```text
<python пакета> -m tools.run_pipeline finish --project <проект> --run <run_id> --abandon <причина>
```

Причины: `LEFT_BEFORE_REVIEW` (прогон застрял до ревью кейсов), `STAGE_RETRY_EXHAUSTED`, `ASSEMBLY_INVALID`. Без такой подсказки `--abandon` не нужен: обычный
`finish` закрывает попытку без исполнения, а уже закрытую — повторно без изменений.

После вердикта «ТРЕБУЕТ ДОРАБОТКИ» `finish` и `status` печатают `next_run` —
команду следующего захода. Её запускаете вы или модель по вашему слову.

## Памятка: модель запуталась

Если модель потеряла нить, повторяет шаги или предлагает странное:

1. Попросите выполнить `status` (команда из раздела 7) и сделать то, что называют поля `state` и `next`. Больше ничего не придумывать.
2. Если `status` называет остановку — прочитайте `fix` и выполните его (раздел 8).
3. Если цепочка дальше не пойдёт, а остановка сама предлагает `finish --abandon <причина>` — выполните эту команду как есть.
4. Начинайте новый прогон (`scan` с `--new-run`) только когда прежний закрыт или вам нужен второй, независимый.
   Незакрытый прогон того же запроса с `--new-run` не заменяется — он останется в `.pilot-runs`.

## 9. Отчёт прогона

```text
<python пакета> -m tools.run_pipeline report --project <проект> --run <run_id>
```

Пишет в папку прогона `report.md`, `report.json` и `questions-for-analyst.md`. В отчёте — шаги со временем,
длительность и размер входа каждого вызова модели против бюджета шага, коды остановок, числа и окружение. Там же: фазы по времени, состав входа по видам, отказы команд (по командам,
кодам и пачкам), канон в числах и размер рабочей папки `tmp/` с командой её удаления — отчёт сам ничего не
удаляет. Кода проекта, текста требований и ответов модели в нём нет; из кейсов — только строка предусловия, если её подготовка не удалась. Что можно
выносить за пределы рабочей среды — решают правила вашей компании.

Если ревью приняло кейсы с замечаниями, в `report.md` есть раздел «Замечания ревью», а текст
замечаний — в `questions-for-analyst.md`.
