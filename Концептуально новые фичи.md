## Концептуально новые фичи для Test Orchestration Skills

Я глубоко изучил архитектуру проекта: это мультиагентный пайплайн из 6 скиллов (`context-marker → tc-generator → tc-reviewer → tc-to-autotest → autotest-reviewer`, координируется Оркестратором). Всё общение — через строгую систему XML-контрактов (`CONTRACTS.md`), статус-маркеров (`ПРИНЯТО / AUTO_FIX_APPLIED / ТРЕБУЕТ ДОРАБОТКИ`) и Progressive Disclosure (L1→L2 диспетчеризация).

Текущий пайплайн покрывает путь: **сырая аналитика → ручные ТК → валидация ТК → автотесты → валидация автотестов**. Это линейный «генеративный» конвейер. Ниже — идеи, которые расширяют экосистему в **новых направлениях**, не пересекаясь с существующими скиллами.

---

## 🆕 Новые скиллы (8 концепций)

### 1. `impact-analyzer` — Анализ влияния изменений (Impact Analysis)

**Проблема:** разработчик меняет 3 строки в сервисе — какие тесты перезапускать? Сейчас система только генерирует тесты, но не умеет отвечать на вопрос «что затронуто?».

**Суть скилла:**
- Принимает `<source_code_diff>` (git diff) и `<automation_matrix>` (traceability ТК→метод)
- Строит граф зависимостей: `файл → класс → метод → ТК-N → автотест`
- Возвращает `<impact_report>`: ранжированный список тестов, которые **необходимо** перезапустить
- Поддерживает `selective-regression` — минимальный набор тестов для проверки изменений

**Контракт входа:** `<source_code_diff>` + `<automation_matrix>` + (опц.) `<source_tree>`
**Контракт выхода:** `<impact_report>` с секциями `must-run`, `should-run`, `safe-to-skip`

---

### 2. `tc-prioritizer` — Приоритизация тест-кейсов

**Проблема:** сгенерировано 50+ ТК — с чего начать тестирование при ограниченном времени?

**Суть скилла:**
- Принимает `<test_cases>` + `<analytics_documentation>` (с приоритетами AC)
- Ранжирует ТК по 4 осям: **бизнес-критичность**, **риск отказа**, **сложность**, **новизна функциональности**
- Возвращает `<priority_matrix>` с весами: `P0 (must-test)`, `P1 (should-test)`, `P2 (nice-to-have)`
- Интегрируется с риск-матрицей проекта (вероятность × последствия)

**Контракт выхода:** `<priority_matrix>` — сортированный список `ТК-N` с приоритетами и обоснованием

---

### 3. `test-data-fabricator` — Генератор тестовых данных

**Проблема:** автотесты сгенерированы, но используют хардкод-значения (`"test@example.com"`, `amount=100`). Нужны реалистичные, граничные и случайные данные.

**Суть скилла:**
- Принимает DTO-классы (`<source_code>`) или OpenAPI-схемы
- Генерирует: **эквивалентные классы**, **граничные значения**, **случайные валидные**, **случайные невалидные**, **SQL-фикстуры**
- Поддерживает форматы: JSON-пейлоады, SQL `INSERT`, Testcontainers-инициализацию, Faker-библиотеки
- Учитывает доменные правила из `<analytics_documentation>` (например, `currency ∈ {RUB, USD, EUR}`)

**Контракт выхода:** `<test_data_suite>` с секциями `valid_equivalence`, `boundary_values`, `invalid_inputs`, `sql_fixtures`

---

### 4. `contract-tester` — Генератор контрактных тестов (Pact-стиль)

**Проблема:** в микросервисной архитектуре автотесты проверяют свой сервис, но не контракты между сервисами.

**Суть скилла:**
- Принимает OpenAPI / AsyncAPI спецификации (`<openapi_spec>`, `<asyncapi_spec>`)
- Генерирует **Consumer-Driven Contract тесты** в стиле Pact:
  - Для REST: валидация request/response схем, статус-кодов, хедеров
  - Для AsyncAPI: валидация событий (публикация/потребление), схемы сообщений
- Возвращает готовые тест-классы (Pact-JVM / Pact-Python) + `<contract_test_matrix>`

**Контракт выхода:** `<contract_test_suite>` + `<contract_test_matrix>` — traceability `эндпоинт → контрактный тест`

---

### 5. `observability-tester` — Генератор тестов наблюдаемости

**Проблема:** автотесты проверяют бизнес-логику, но не проверяют, что система **логирует**, **метрики** собираются, **трейсы** записываются. После деплоя в продакшн это становится критичным.

**Суть скилла:**
- Принимает `<analytics_documentation>` (где описаны ожидаемые события) и `<source_code>` (где @Slf4j, micrometer, OpenTelemetry)
- Генерирует тесты, проверяющие:
  - **Логирование:** при ошибке — ERROR с correlationId; при успехе — INFO с duration
  - **Метрики:** counter увеличился; timer записал duration; gauge в диапазоне
  - **Трейсы:** span создан; traceId проброшен между сервисами
- Интегрируется с Testcontainers (лог-контейнер) + InMemory-метрики

**Контракт выхода:** `<observability_test_suite>` + `<observability_coverage_report>`

---

### 6. `gherkin-exporter` — Экспорт ТК в Gherkin-формат (.feature)

**Проблема:** ручные ТК лежат в Zephyr Markdown, но команда хочет BDD (Cucumber/Behave/SpecFlow).

**Суть скилла:**
- Принимает `<test_cases>` (Zephyr Markdown)
- Конвертирует каждый `ТК-N` в Gherkin-сценарий:
  - Название ТК → `Scenario:`
  - Предусловия → `Given`
  - Шаги → `When`, `Then`
  - Граничные значения → `Scenario Outline` + `Examples`
- Группирует по фичам → отдельные `.feature` файлы
- Добавляет теги: `@positive`, `@negative`, `@boundary`, `@security`, `@P0` (из приоритизатора)

**Контракт выхода:** `<gherkin_suite>` + `.feature` файлы + `<feature_matrix>` (traceability `ТК-N → .feature:NN`)

---

### 7. `flakiness-detector` — Детектор нестабильных тестов

**Проблема:** автотесты написаны, но некоторые «мигают» (pass/fail без изменений кода). Flaky tests — главная боль CI/CD.

**Суть скилла:**
- Принимает `<test_run_history>` (результаты N последовательных прогонов) и `<autotest_code>`
- Анализирует паттерны нестабильности:
  - **Order-dependent:** тест зависит от порядка выполнения
  - **Time-dependent:** завязан на системное время / таймауты
  - **Data-dependent:** зависит от состояния БД / shared-фикстур
  - **Network-dependent:** зависит от внешнего сервиса (WireMock не настроен)
- Возвращает `<flakiness_report>` с классификацией причин и автофиксами (`AUTO_FIX_APPLIED`)

**Контракт выхода:** `<flakiness_report>` + `<review_verdict>` + (опц.) `<corrected_autotest_code>`

---

### 8. `test-estimator` — Оценка трудозатрат на тестирование

**Проблема:** менеджер спрашивает: «сколько времени займёт тестирование этой фичи?» Ответа нет.

**Суть скилла:**
- Принимает `<test_cases>` + `<project_context>` (стек, размер команды, исторические данные)
- Оценивает:
  - **Ручное тестирование:** время на прогон каждого ТК × сложность
  - **Автоматизация:** время на написание/поддержку автотестов (по историческим данным из `<automation_matrix>`)
  - **Общее время цикла:** генерация → валидация → автоматизация → ревью → прогон
- Возвращает `<estimation_report>` с breakdown по этапам и уровнем уверенности

**Контракт выхода:** `<estimation_report>` с секциями `manual_effort_hours`, `automation_effort_hours`, `total_cycle_hours`, `confidence_level`

## 🏗️ Инфраструктурные фичи (не скиллы, а новые возможности)

### A. Режим «Diff-пайплайн» (Incremental Pipeline)

Сейчас пайплайн всегда запускается **с нуля** для фичи. А если аналитика изменилась на 10%? Зачем перегенерировать всё?

**Идея:** Оркестратор получает на вход не только `<analytics_documentation>`, но и **предыдущий `<orchestration_result>`** с артефактами. Сравнивает `source_hash` каждого тега с предыдущим запуском. Если аналитика не изменилась → скилл пропускается. Если изменилась частично → скилл запускается в diff-режиме (как сейчас `tc-to-autotest` с `automation_matrix`).

**Новый контракт:**
```xml
<orchestration_request>
  <goal>...</goal>
  <previous_run_id>UUID предыдущего запуска</previous_run_id>  <!-- NEW -->
  <baseline_artifacts>                                           <!-- NEW -->
    <analytics_documentation source_hash="abc123">...</analytics_documentation>
    <automation_matrix source_hash="def456">...</automation_matrix>
  </baseline_artifacts>
</orchestration_request>
```

---

### B. Кросс-пайплайн (Cross-Pipeline Traceability)

Сейчас `test-pipeline` — единственный пайплайн. Но что если у вас несколько смежных сервисов?

**Идея:** Оркестратор поддерживает **межсервисную трассировку**: если сервис A вызывает сервис B (по OpenAPI), то при изменении контракта B — Оркестратор предлагает запустить пайплайн для A.

**Механизм:** Deep Scan парсит `openapi.yaml` на предмет `$ref`-зависимостей и строит **сервисный граф**. При изменении спецификации — автоматический `impact-report` по downstream-сервисам.

---

### C. Плагин-архитектура для языков/фреймворков

Сейчас поддержка языков (Java/Python/Go/TypeScript) захардкожена в `tc-to-autotest` и `.skillsrc`. Добавление нового языка (например, Kotlin + Kotest) требует правки скилла.

**Идея:** вынести генерацию кода в **шаблоны** (`templates/` директория уже есть!) и сделать их подключаемыми. `.skillsrc` получает секцию:
```yaml
templates:
  autotest: "templates/junit5-restassured"
  dto: "templates/java-lombok-dto"
```
Любой желающий может добавить `templates/kotlin-kotest/` — и система подхватит без изменения скиллов.

## 🧭 Направление 1: SDD (Specification-Driven Development) — углубление

Сейчас SDD в проекте на уровне `methodology: sdd` + ссылки на `openapi.yaml`. Но сама спецификация используется только как **источник контекста** для генерации ТК. Это уровень ~20% от того, что можно выжать из SDD-подхода. Вот куда можно расширить:

---

### 1. `spec-validator` — Валидатор спецификаций перед пайплайном

**Проблема:** пайплайн запускается, генерирует 50 ТК, а потом оказывается, что в OpenAPI пропущен обязательный `error.response.schema` или `nullable: true` на обязательном поле. Вся генерация — в мусор.

**Суть скилла:**
- Принимает `<openapi_spec>` + `<asyncapi_spec>` (до пайплайна, ещё до `context-marker`)
- Валидирует по **Spectral-правилам** (встроенный каталог правил: OWASP, Zalando, Google API Design Guide)
- Проверяет **полноту**: каждый эндпоинт имеет схему ответа, error-модели, примеры
- Проверяет **согласованность**: DTO в коде ↔ schema в OpenAPI (через сопоставление Java-классов и `$ref`)
- Проверяет **SDD-разрыв**: эндпоинт есть в коде, но отсутствует в OpenAPI → `spec_gap`
- Возвращает `<spec_validation_report>` с вердиктом: `SPEC_READY` / `SPEC_NEEDS_FIX` / `SPEC_INCOMPLETE`

**Контракт входа:** `<openapi_spec>` + `<asyncapi_spec>` + (опц.) `<source_tree>`
**Контракт выхода:** `<spec_validation_report>` с секциями `schema_errors`, `completeness_gaps`, `code_spec_divergence`

**Ключевая фишка:** блокирует пайплайн до исправления спецификации. В SDD спецификация — источник правды. Если она невалидна — всё остальное теряет смысл.

---

### 2. `spec-coverage-analyzer` — Покрытие спецификации тестами

**Проблема:** сгенерировали ТК и автотесты. Какие эндпоинты / статус-коды / сценарии НЕ покрыты?

**Суть скилла:**
- Принимает `<openapi_spec>` + `<test_cases>` + `<automation_matrix>`
- Строит **матрицу покрытия** на уровне:
  - `Operation × Status Code` (GET /users → 200 ✅, 404 ❌, 500 ❌)
  - `Schema Property × Boundary` (поле `amount` → min ✅, max ✅, null ❌)
  - `Security Scheme` (OAuth2 → token expired ❌)
- Подсвечивает **spec-coverage-gaps**: что спецификация описывает, но тестами не покрыто
- Для AsyncAPI: события, которые не тестируются (event published, но consumer не проверен)

**Контракт выхода:** `<spec_coverage_report>` с heatmap-матрицей и разделом `uncovered_risk` (ранжированный по критичности)

---

### 3. `breaking-change-detector` — Детектор ломающих изменений в спецификации

**Проблема:** команда меняет поле с `int → string` в OpenAPI. Пайплайн перегенерит тесты, но **никто не скажет**, что это ломающее изменение для 3 downstream-сервисов.

**Суть скилла:**
- Принимает `<openapi_spec>` (новая) + `<baseline_openapi_spec>` (старая) + `<service_graph>` (граф зависимостей между сервисами)
- Детектирует по OpenAPI Diff (аналог `openapi-diff`):
  - **Breaking:** удалён эндпоинт, изменён тип поля, удалён enum-вариант, изменён `required → optional`
  - **Non-breaking:** добавлен эндпоинт, добавлено опциональное поле, добавлен enum-вариант
- Строит **карту поражённых потребителей** через граф зависимостей
- Возвращает `<breaking_change_report>` с уровнями `CRITICAL` / `WARNING` / `INFO`

**Контракт выхода:** `<breaking_change_report>` с traceability `изменение → поражённые сервисы → рекомендуемое действие`

---

### 4. `spec-to-tc-direct` — Прямая трансляция OpenAPI → ТК (без аналитики)

**Проблема:** у команды есть только OpenAPI и исходный код, нет текстовой аналитики (`docs/requirements/`). Сейчас `tc-generator` в этом случае переходит в ручной режим и задаёт вопросы. А хочется автоматического режима.

**Суть скилла:**
- Это **альтернативный вход** в пайплайн (не замена `tc-generator`, а препроцессор перед ним)
- Принимает `<openapi_spec>` — и генерирует `<analytics_documentation>` автоматически:
  - Из `operation.description` → описание фичи
  - Из `requestBody.schema.required` → AC (обязательные поля)
  - Из `responses.*.schema` → ожидаемые результаты
  - Из `enum` значений → граничные условия
  - Из `security` → security-тесты (401, 403)
- Затем передаёт сгенерированную аналитику в `tc-generator`

**Контракт выхода:** `<analytics_documentation>` — полноценная аналитика, синтезированная из OpenAPI

---

### 5. `bpmn-scenario-extractor` — Извлечение тестовых сценариев из BPMN-схем

**Проблема:** SDD-проекты часто содержат BPMN-схемы в `docs/domain/`, описывающие бизнес-процессы. Сейчас они НЕ используются тестовым пайплайном вообще.

**Суть скилла:**
- Принимает BPMN-файлы (XML) из `docs/domain/`
- Извлекает из диаграммы:
  - **Все возможные пути** через process flow (happy path + альтернативные ветки + исключения)
  - **Граничные события** (таймеры, ошибки, отмена)
  - **Состояния ожидания** (user tasks, receive tasks)
- Генерирует `<analytics_documentation>` и предварительные `<generated_test_cases>` с привязкой к элементам BPMN

**Контракт выхода:** `<bpmn_scenario_analysis>` + `<generated_test_cases>` с traceability `ТК-N → BPMN Element ID`

---

### 6. `adr-compliance-checker` — Проверка соответствия Architecture Decision Records

**Проблема:** команда приняла ADR-003 «Все ошибки должны возвращать ProblemDetail (RFC 7807)». А тесты проверяют это?

**Суть скилла:**
- Принимает ADR-документы из `docs/architecture/` (Markdown)
- Извлекает **проверяемые утверждения** из ADR (через LLM-разбор)
- Сопоставляет с `<automation_matrix>` + `<test_cases>`: проверяет, покрыто ли каждое архитектурное решение тестами
- Возвращает `<adr_compliance_gap>` — список ADR-требований без тестового покрытия

**Контракт выхода:** `<adr_compliance_report>` — traceability `ADR-N → требование → ТК-N (или GAP)`

## 🧠 Направление 2: Память / Statefulness

Сейчас система **полностью амнезична** между запусками. Единственное, что сохраняется — `<automation_matrix>` и `<orchestration_result>`. Но нет накопления знаний, обучения на ошибках, истории.

---

### 7. `project-memory-bank` — Банк памяти проекта

**Идея:** ввести новый артефакт — **`.memory-bank/`** директорию — которая живёт рядом со скиллами и накапливает знания между запусками.

**Структура:**
```
.memory-bank/
├── project-context.md        # Актуальный <project_context> (обновляется после каждого Deep Scan)
├── decisions-log.md          # Журнал решений: когда пользователь выбрал "analytics_wins" при конфликте
├── learned-rules.json        # Правила, выученные из паттернов отказов (см. rejection-pattern-learner)
├── style-profile.json        # Стилистический профиль проекта (см. style-drift-detector)
└── domain-dictionary.json    # Словарь сущностей и бизнес-правил (см. domain-dictionary-builder)
```

**Суть механики:**
- После каждого запуска пайплайна Оркестратор обновляет `project-context.md` результатами Deep Scan.
- Каждое решение пользователя при конфликте (`ask_user` из `.skillsrc` §`resolution`) фиксируется в `decisions-log.md` с меткой времени и контекстом — это позволяет со временем автоматически предлагать то же решение без повторного вопроса.
- `.memory-bank/` — единственный артефакт, переживающий между запусками; все остальные контракты (`<generated_test_cases>`, `<automation_matrix>` и т.д.) остаются per-run.

**Контракт входа:** `<orchestration_result>` предыдущего запуска (опц.) + Deep Scan текущего запуска
**Контракт выхода:** обновлённые файлы `.memory-bank/*.json` / `*.md`

## 🧬 Направление 3: Самообучение и адаптация скиллов


Идея в том, чтобы система **эволюционировала внутри конкретного проекта** — как иммунная система, которая со временем лучше распознаёт «своё» и «чужое». Сейчас скиллы статичны: загрузил SKILL.md → получил результат. А если бы они накапливали опыт?

---

### 1. `rejection-pattern-learner` — Обучение на паттернах отказов

**Механика:** каждый раз, когда ревьюер возвращает `ТРЕБУЕТ ДОРАБОТКИ`, система не просто пишет `<review_comments>`, а **классифицирует ошибку** в паттерн:

```
Отказ #1: "ТК-7 не содержит проверку на null для поля amount" 
  → паттерн: "boundary:null-missing:monetary-field"
Отказ #2: "ТК-12 не содержит проверку на null для поля currency"
  → паттерн: "boundary:null-missing:enum-field"
Отказ #3: "ТК-15 не содержит проверку на null для поля recipientId"  
  → паттерн: "boundary:null-missing:uuid-field"
```

После 3 отказов одного класса — система **выучивает правило**: «в этом проекте ВСЕ поля должны иметь null-проверку». И **автоматически инжектирует** это правило в `tc-generator` при следующем запуске:

```xml
<learned_rules>
  <rule id="auto-001" source="rejection_pattern" confidence="0.95">
    Все поля DTO должны иметь тест на null-значение
  </rule>
</learned_rules>
```

**Файл:** `.memory-bank/learned-rules.json` — накапливается между запусками.

---

### 2. `style-drift-detector` — Подстройка под стиль проекта

**Проблема:** в проекте используют `@ParameterizedTest` + `@CsvSource`, а скилл генерирует отдельные `@Test` методы. Или в проекте assert'ы через BDD (`then().assertThat()`), а скилл использует `assertEquals()`.

**Механика:** скилл анализирует **существующие тесты** в проекте и извлекает **стилистический профиль**:

```json
{
  "style_profile": {
    "assertion_library": "assertj",
    "assertion_style": "bdd_chain",        // then().assertThat() vs assertEquals()
    "test_structure": "parameterized",      // @ParameterizedTest vs @Test
    "naming_convention": "should_when_given",  // shouldCreate_whenValidInput_given...
    "mock_style": "mockito_strict",         // @Mock vs @MockBean vs mock()
    "grouping": "nested",                   // @Nested vs flat
    "setup_style": "before_each",           // @BeforeEach vs constructor injection
    "wiremock_style": "json_mapping",       // stubs через JSON-файлы vs inline
    "soft_assertions": true                 // SoftAssertions vs hard assert
  }
}
```

При следующей генерации `tc-to-autotest` получает `<style_profile>` и генерирует код, **неотличимый** от написанного командой.

**Файл:** `.memory-bank/style-profile.json` — обновляется при каждом Deep Scan.

---

### 3. `domain-dictionary-builder` — Автословарь предметной области

**Идея:** LLM не знает вашего домена. Но после нескольких запусков пайплайна она может выучить:

- **Бизнес-сущности:** `Subscription`, `Renewal`, `BillingCycle`, `PricePlan` — и их связи
- **Бизнес-правила:** «подписка продлевается за 3 дня до окончания», «после 3 неудачных попыток — блокировка»
- **Терминологию:** команда говорит «пролонгация», а не «продление»
- **Граничные значения:** `amount ∈ [100, 1_000_000]`, `period ∈ {MONTHLY, QUARTERLY, YEARLY}`

**Механика:** после каждого прогона пайплайна извлекаются ключевые сущности и правила из `<analytics_documentation>`, `<source_code>`, `<test_cases>`. Строится **доменный граф**:

```json
{
  "domain_dictionary": {
    "entities": {
      "Subscription": {
        "fields": ["id", "userId", "planId", "status", "expiresAt", "autoRenew"],
        "lifecycle": ["ACTIVE", "EXPIRING", "EXPIRED", "CANCELLED", "SUSPENDED"],
        "relationships": { "belongs_to": "User", "has": "PricePlan" }
      }
    },
    "rules": [
      { "text": "автопродление за 3 дня до expiresAt", "confidence": 0.98, "source": "analytics_docs" },
      { "text": "3 неудачных платежа → SUSPENDED", "confidence": 0.95, "source": "code+test_cases" }
    ],
    "terminology": {
      "пролонгация": "renewal",
      "подписчик": "subscriber"
    }
  }
}
```

При генерации новых ТК — скилл использует терминологию команды и учитывает известные бизнес-правила, даже если они не упомянуты явно в новой аналитике.

---

### 4. `confidence-calibrator` — Калибровка уверенности автофиксов

**Проблема:** автофикс (`AUTO_FIX_APPLIED`) может быть ошибочным. Но сейчас система не различает «уверенный автофикс» (исправляли 100 раз, всегда правильно) и «рискованный» (новый паттерн, впервые).

**Механика:** для каждого типа автофикса ведётся статистика:

```json
{
  "auto_fix_stats": {
    "add_missing_null_check": { "applied": 47, "accepted": 47, "rejected_later": 0, "confidence": 1.0 },
    "rename_tc_to_match_numbering": { "applied": 12, "accepted": 11, "rejected_later": 1, "confidence": 0.92 },
    "split_parameterized_test": { "applied": 3, "accepted": 2, "rejected_later": 1, "confidence": 0.67 }
  }
}
```

При `confidence < 0.8` → автофикс применяется, но с пометкой `⚠️ LOW_CONFIDENCE` — ревьюер должен проверить особенно внимательно.

При `confidence < 0.5` → автофикс **не применяется**, вместо этого возвращается `ТРЕБУЕТ ДОРАБОТКИ` с подробной подсказкой.

---

### 5. `evolutionary-prompt-tuner` — Эволюционная оптимизация промптов

**Бредовая, но рабочая идея:** сами SKILL.md — это промпты. Почему бы не оптимизировать их A/B-тестированием?

**Механика:** 
- Для каждого скилла поддерживается **базовый SKILL.md** и **N экспериментальных вариантов** (отличаются формулировками, порядком инструкций, примерами)
- При каждом запуске скилла — случайно выбирается один из вариантов
- Результат оценивается через ревьюера (вердикт `ПРИНЯТО` = success, `ТРЕБУЕТ ДОРАБОТКИ` = failure)
- После 10+ запусков — вариант с лучшим acceptance rate становится новым базовым

**Файл:** `.memory-bank/prompt-variants/tc-generator/variant-3.md` — мутировавшие версии промптов.

Это буквально **эволюция скиллов под конкретный проект**: через 50 запусков пайплайна SKILL.md адаптируется под то, что лучше работает именно в этом проекте.

## 🔌 Направление 4: Zero-Friction Onboarding (plug-and-play)

Идея: закинул папку `test-orchestration-skills/` в любой проект — и **всё заработало без единой правки конфигурации**.

---

### 6. `project-fingerprinter` — Снятие отпечатка проекта

**Идея:** не спрашивать пользователя о стеке, а **узнавать проект в лицо**.

**Механика:** Deep Scan (уже есть) дополняется **fingerprinting** — снятием уникального «отпечатка» проекта:

```
Fingerprint: spring-boot-3.2-junit5-restassured-wiremock-postgresql-maven-lombok-sdd
              ↓
Сравнение с базой известных fingerprint'ов:
  ✅ 94% совпадение с "типовой Spring Boot микросервис"
  → Загружаю преднастроенный профиль: spring-boot-microservice-profile.json
  → Содержит: naming conventions, mock-стратегию, паттерны assert'ов, 
     типовые DTO-шаблоны, тестовую конфигурацию Testcontainers
```

**Файл:** `shared/fingerprints/spring-boot-microservice-profile.json` — библиотека профилей для типовых проектов. Пополняется сообществом.

---

### 7. `gradual-trust-escalator` — Постепенное наращивание доверия

**Идея:** новый проект → скиллы работают в **advisory mode**: не пишут код, а предлагают, что бы они сделали. Пользователь говорит «да, делай» или «нет, не так». Система **запоминает границы доверия**.

```
День 1: "Я предлагаю сгенерировать ТК-1...ТК-5 для TransferService. Показать?"  → advisory
День 3: "Сгенерировал ТК-1...ТК-5. Показываю перед валидацией."                 → semi-auto
День 7: "Сгенерировал и отвалидировал ТК-1...ТК-5. Все ПРИНЯТО. Иду дальше."    → auto
День 30: полный auto по всем этапам, кроме security-тестов (пользователь отметил "всегда спрашивать")
```

**Файл:** `.memory-bank/trust-boundaries.json` — карта решений, которые пользователь разрешил автоматизировать.

---

### 8. `self-healing-configurator` — Самовосстанавливающаяся конфигурация

**Идея:** если `.skillsrc` говорит `test.framework: junit5`, а в проекте все тесты — `pytest` → система **сама находит и исправляет расхождение**.

**Механика:**
```
1. Deep Scan обнаружил: 42 тестовых файла в src/test/** → все pytest
2. .skillsrc говорит: test.framework: junit5
3. Расхождение: 100% → ERROR
4. Авто-диагностика:
   "Обнаружен pytest (42 тестовых файла), но .skillsrc указывает junit5.
    Вероятно, .skillsrc устарел или скопирован из другого проекта.
    Автоисправить на pytest? [Y/n]"
5. Если Y → обновить .skillsrc + продолжить пайплайн
```

Это убирает главную боль: «я скопировал скиллы из проекта A в проект B, и всё сломалось».

---

### 9. `plugin-discovery-protocol` — Автообнаружение плагинов

**Идея:** любой разработчик может написать скилл, положить в папку — и система **сама его обнаружит и зарегистрирует**.

**Механика:**
```
test-orchestration-skills/
├── .skillsrc
├── plugins/                              ← НОВАЯ ДИРЕКТОРИЯ
│   ├── my-custom-reviewer/
│   │   ├── SKILL.md                      ← стандартный формат SKILL.md
│   │   └── plugin.json                   ← метаданные: имя, теги, контракты
│   └── team-specific-fixtures/
│       ├── SKILL.md
│       └── plugin.json
```

**plugin.json:**
```json
{
  "name": "my-custom-reviewer",
  "version": "1.0",
  "description": "Проверяет, что все ТК содержат correlationId",
  "tags": ["@review", "@custom", "@correlation"],
  "input_contract": "markdown:generated_test_cases",
  "output_contract": "xml:validation_report",
  "pipeline_hook": "after:tc-reviewer",     // где вставить в пайплайн
  "priority": "append"                       // append | replace | before
}
```

Оркестратор при старте сканирует `plugins/` и автоматически встраивает их в пайплайн. **Никакой правки .skillsrc или PIPELINE.md.**

---

### 10. `skeleton-scaffolder` — Генератор скиллов под проект

**Идея:** а что если скиллы не копировать из репозитория, а **генерировать под конкретный проект**?

**Механика:** одноразовый запуск:

```
> orchestrate scaffold --from-scratch

Что делает:
1. Deep Scan проекта (язык, фреймворк, тесты, API, БД)
2. Генерирует ПЕРСОНАЛИЗИРОВАННЫЕ SKILL.md под каждый компонент:
   - tc-generator: с упоминанием КОНКРЕТНЫХ DTO, контроллеров, эндпоинтов
   - tc-to-autotest: с шаблонами тестов на основе СУЩЕСТВУЮЩИХ тестов в проекте
   - autotest-reviewer: с правилами, специфичными для стека (Spring Boot + JUnit5)
3. Генерирует .skillsrc с заполненными путями
4. Генерирует .memory-bank/ с начальным project_context
5. Выводит: "Скиллы готовы. Скажи 'создай тест-кейсы для X' чтобы начать."
```

Результат: скиллы, которые выглядят так, как будто их **писали разработчики этого конкретного проекта**, а не абстрактный AI.
