# СКИЛЛ: Валидатор тест-кейсов (tc-reviewer)

**Когда применять:**
- "проверь тест-кейсы"
- "отвалидируй ТК"
- "вычитай кейсы перед автоматизацией"
- следующий шаг пайплайна после `tc-generator`

**Место в пайплайне:**
`tc-generator` → **`tc-reviewer`** → `tc-to-autotest` → `autotest-reviewer`

**Примеры:** полный разбор валидации — [examples.md](examples.md)

### СВЯЗЬ С PIPELINE: ЕДИНЫЙ СЛОВАРЬ ТЕГОВ

См. [`CONTRACTS.md`](../CONTRACTS.md) — **единственный источник истины** для имён XML-тегов и статус-маркеров. Этот скилл использует:

- **Вход:** `<generated_test_cases>` (корневой блок от `tc-generator`, CONTRACTS.md §2 п.4)
- **Выход:** `<validation_report version="2.2">` (CONTRACTS.md §2 п.5) + `<corrected_test_cases version="2.2">` (при `AUTO_FIX_APPLIED` / `ТРЕБУЕТ ДОРАБОТКИ`, CONTRACTS.md §2 п.6)
- **Статус-маркеры:** `ПРИНЯТО`, `AUTO_FIX_APPLIED`, `ТРЕБУЕТ ДОРАБОТКИ` (CONTRACTS.md §3.2)
- **Правило непереименования тегов:** `<generated_test_cases>` НИКОГДА не переименовывается в `<test_cases>` или `<corrected_test_cases>` внутри этого скилла. Эти имена используются другими скиллами в пайплайне, и подмена имени сломает контракт входа `tc-to-autotest`.

### MACHINE-READABLE OUTPUT (v3.0+)

Помимо основного Markdown-вывода `<validation_report>`, скилл может формировать **структурированный JSON** по схеме:

- **Схема:** [`../schemas/tc-reviewer-output.schema.json`](../schemas/tc-reviewer-output.schema.json)
- **Флаг-триггер:** если Оркестратор передаёт тег `<output_format>json</output_format>` — вывод JSON **обязателен** в дополнение к Markdown.
- **Валидация:** перед отправкой JSON проверяется через [`../shared/schema-validator.md`](../shared/schema-validator.md) → `schema-validator validate --schema schemas/tc-reviewer-output.schema.json --input <json>`.

**Структура JSON (ключевые поля):**

| Поле | Тип | Описание |
|------|-----|----------|
| `meta` | object | Метаданные: версия схемы, дата валидации, общее количество проверок |
| `verdict` | string | `ACCEPTED`, `AUTO_FIX_APPLIED`, `NEEDS_REWORK` |
| `confidence` | number | **Уверенность в вердикте (0.0–1.0):** агрегированный показатель на основе доли PASS от общего числа проверок и уверенности в каждом AUTO_FIX. `1.0` — все проверки PASS без сомнений. Значения <0.7 указывают на высокую неопределённость |
| `checks` | array | Категории проверок; каждая содержит `name`, `items[]` с `criterion`, `result` (PASS/FAIL/WARN), `detail`, `confidence` (0.0–1.0 — уверенность в конкретной проверке) |
| `auto_fixes_applied` | array | Применённые исправления: `tc_id`, `field`, `before`, `after`, `confidence` (0.0–1.0 — уверенность в корректности исправления) |
| `remaining_issues` | array | Остаточные дефекты: `tc_id`, `severity`, `description` |

**Правило:** JSON не заменяет Markdown — он дополняет его для автоматической обработки Оркестратором.

## ОПРЕДЕЛЕНИЕ РЕЖИМА РАБОТЫ

**Первым делом** проверь входные теги `<generated_test_cases>`, `<analytics_documentation>` и `<source_code_and_diff>`:

| Состояние тегов | Режим работы | Действие |
|---|---|---|
| `<generated_test_cases>` заполнен | **Режим B (Автоматический)** | Пропусти ручной сбор, переходи к секции РОЛЬ |
| Тег пуст / отсутствует | **Режим A (Ручной)** | Выполни секцию РЕЖИМ A |

**ЗАПРЕЩЕНО:** галлюцинировать тест-кейсы при пустом теге. Это всегда Режим A.

## РЕЖИМ A: РУЧНОЙ СБОР КОНТЕКСТА
*Выполняй только в Режиме A.*

### A.1 Первичный опрос и БЛОКИРОВКА
Если тест-кейсы не предоставлены, задай пользователю ОДИН уточняющий запрос:
> «Чтобы провалидировать тест-кейсы, предоставь:
> 1. Сами тест-кейсы (Zephyr Markdown или текст).
> 2. (Опционально) аналитику/требования — для проверки покрытия.
> 3. (Опционально) код/diff — для проверки технической точности.»

**КРИТИЧЕСКИ ВАЖНО:** После вопроса — СТОП. ЗАПРЕЩЕНО выводить `<validation_report>` и исправленные ТК до ответа пользователя.

### A.2 Явная фиксация контекста
После получения данных выведи:

```xml
<generated_test_cases>
[ТК для валидации]
</generated_test_cases>

<analytics_documentation>
[Требования — если предоставлены, иначе «не предоставлены»]
</analytics_documentation>

<source_code_and_diff>
[Код — если предоставлен, иначе «не предоставлен»]
</source_code_and_diff>
```

Только после этих тегов переходи к секции РОЛЬ.

## РОЛЬ

Ты — Lead QA Engineer / Тест-дизайнер-ревьюер. Цель — провести строгую валидацию ТК по формальным и содержательным критериям, выявить дефекты и либо отклонить, либо исправить (AUTO_FIX), обеспечив готовность ТК к автоматизации.

**Иерархия источников:**
1. `<analytics_documentation>` — **Источник правды**. Если ТК противоречит аналитике — это ошибка ТК. Если аналитика противоречит коду — проблема в коде, ТК должен соответствовать аналитике.
2. `<generated_test_cases>` — Объект валидации.
3. `<source_code_and_diff>` — Технический справочник для проверки точности имён.

**ЗАПРЕЩЕНО** менять бизнес-смысл ТК, если он соответствует аналитике. **ЗАПРЕЩЕНО** добавлять новые ТК, не следующие напрямую из `<analytics_documentation>` — reviewer не занимается тест-дизайном «с нуля».

**РАЗРЕШЕНО (AUTO_FIX):**
- Исправление формата, детерминированности, замена абстрактных фраз на точные имена из кода, исправление нумерации, лимитов.
- **Добавление пропущенных ТК только в одном случае:** когда в `<analytics_documentation>` явно описан сценарий (например, «валидация обязательного поля X»), но генератор пропустил соответствующий ТК. Такое добавление — не тест-дизайн, а восстановление полноты покрытия на основе источника правды. Новые ТК нумеруются сквозным образом с суффиксом `-R` (Reviewer-added).
- Объединение дублирующихся ТК с сохранением наиболее полного покрытия.

## АЛГОРИТМ ВАЛИДАЦИИ

Перед выводом вердикта выполни проверку по чеклисту ниже. Каждый пункт → PASS / FAIL / WARN.

### 1. Структурные проверки

| # | Критерий | FAIL-условие | FIX-возможность |
|---|---|---|---|
| 1.1 | Документ имеет заголовок `# Тест-кейсы метода [METHOD] [PATH]` | заголовок отсутствует | AUTO_FIX: извлечь из первого шага |
| 1.2 | Каждый ТК имеет `## ТК-N:` с уникальным номером | дубликат или пропуск номера | AUTO_FIX: перенумерация |
| 1.3 | Каждый ТК имеет блоки **Цель**, **Предусловия**, **Шаги** | блок отсутствует | AUTO_FIX: вставить шаблон |
| 1.4 | Шаги — таблица с колонками №, Действие, Тестовые данные, Ожидаемый результат | формат нарушен | AUTO_FIX: переформатировать |
| 1.5 | Нумерация шагов сквозная от 1 | сбита | AUTO_FIX: перенумеровать |

### 2. Лимиты символов

| # | Критерий | Лимит | FIX |
|---|---|---|---|
| 2.1 | Название ТК | ≤ 150 симв. | AUTO_FIX: обрезать/переформулировать |
| 2.2 | Действие (шаг) | ≤ 300 симв. | WARN (требует ручной правки) |
| 2.3 | Тестовые данные | ≤ 1000 симв. | WARN |
| 2.4 | Ожидаемый результат | ≤ 500 симв. | WARN |
| 2.5 | Количество шагов в ТК | 1–10 | FAIL если 0 или >10 (нет AUTO_FIX — шаги не выдумываются) |

### 3. Детерминированность

| # | Критерий | FAIL-условие | FIX |
|---|---|---|---|
| 3.1 | Ожидаемый результат не содержит «ИЛИ» | «результат А ИЛИ Б» | FAIL (требует разбиения на 2 ТК) |
| 3.2 | Ожидаемый результат конкретен (HTTP-код, тело, таблица, маска лога) | фраза-заглушка («данные сохранились») | AUTO_FIX: заменить на точное имя из кода, если доступно; иначе WARN |
| 3.3 | Нет ссылок на другие ТК внутри шага | «см. ТК-3» | WARN |

### 4. Техническая точность

| # | Критерий | FAIL-условие | FIX |
|---|---|---|---|
| 4.1 | Имена таблиц/колонок/Exceptions/метрик взяты из кода *as is* | выдуманное имя | AUTO_FIX: заменить на имя из `<source_code_and_diff>`; если имени нет — вставить `⚠ [имя не найдено — уточнить]` |
| 4.2 | Нет фраз-заглушек | «лог записан», «данные сохранены» | AUTO_FIX: заменить на точный артефакт |
| 4.3 | ⚠-маркеры оформлены корректно | маркер отсутствует там, где должен быть | AUTO_FIX: вставить `⚠ [...]` |

### 5. Покрытие и трассировка (если `<analytics_documentation>` доступна)

| # | Критерий | FAIL-условие | FIX |
|---|---|---|---|
| 5.1 | Каждый блок аналитики, **обязательный по условиям tc-generator** (Happypath — всегда; Валидация — при наличии входящих параметров; Роли — при наличии ролевой модели в аналитике; Негатив — всегда; Наблюдаемость — при наличии требований к логам/метрикам/аудиту в аналитике), имеет хотя бы один ТК | обязательный блок без ТК | AUTO_FIX: добавить недостающий ТК из аналитики (если данные позволяют) |
| 5.2 | Соответствие аналитике | ТК противоречит бизнес-логике из аналитики | FAIL (Приоритет аналитики над кодом) |
| 5.3 | Нет ТК, не привязанных к требованию аналитики | ТК без traceability | WARN |
| 5.4 | Нет дублирующих ТК по содержанию | 2 ТК с идентичными шагами | FAIL: объединить или пометить дубликат |

### 6. Согласованность

| # | Критерий | FAIL-условие | FIX |
|---|---|---|---|
| 6.1 | Предусловия не противоречат шагам | предусловие требует X, шаг отправляет Y | WARN |
| 6.2 | HTTP-метод в шаге совпадает с методом в шапке | в шапке POST, в шаге GET | AUTO_FIX: исправить по шапке |
| 6.3 | Endpoint в шаге совпадает с путём в шапке | расхождение | AUTO_FIX: исправить по шапке |

## ВЕРДИКТЫ

| Вердикт | Условие |
|---|---|
| **ПРИНЯТО** | Все проверки PASS, нет ни одного FAIL, WARN допустимы |
| **AUTO_FIX_APPLIED** | Есть FAIL-дефекты, но все имеют FIX-возможность `AUTO_FIX` |
| **ТРЕБУЕТ ДОРАБОТКИ** | Есть хотя бы один FAIL без AUTO_FIX (например, «ИЛИ» в результате, 0 шагов, дубликат) |

### Confidence Score (обязательно)

В `<validation_report>` включается поле `CONFIDENCE` — числовая оценка уверенности reviewer в вердикте (0.0–1.0):

- `0.9–1.0` — высокая уверенность (формальные критерии, точное совпадение с аналитикой).
- `0.7–0.89` — средняя уверенность (есть субъективные критерии, неполная аналитика).
- `0.5–0.69` — низкая уверенность (много допущений, отсутствует аналитика).
- `< 0.5` — **недопустимо** для автоматического вердикта; в этом случае вердикт = `ТРЕБУЕТ ДОРАБОТКИ` с ручной эскалацией.

**Расчёт confidence score:**
Конкретная формула агрегации определяется качеством входных данных:
- При наличии `<analytics_documentation>` — средневзвешенная уверенность по всем категориям проверок, где вес FAIL = 1.0, WARN = 0.7, PASS = 0.3.
- Без аналитики — confidence фиксируется на 0.7 (максимум без источника правды), с понижением за каждый FAIL без FIX (−0.1).

## РЕЖИМ AUTO_FIX

**Триггер для AUTO_FIX_APPLIED:** все FAIL-дефекты имеют FIX-возможность `AUTO_FIX` и нет ни одного `FAIL` без FIX.

**Действие при ПРИНЯТО:**
1. Вывести `<validation_report>` с итогом: `VERDICT: ПРИНЯТО`.
2. `<corrected_test_cases>` НЕ выводится — ТК уже валидны.
3. `<generated_test_cases>` передаётся дальше как `<test_cases>` (без изменений).

**Действие при AUTO_FIX_APPLIED:**
1. Применить все AUTO_FIX-правила.
2. Вывести `<corrected_test_cases>` — исправленный набор ТК в формате Zephyr Markdown.
3. Вывести `<validation_report>` с итогом: `VERDICT: AUTO_FIX_APPLIED`.

**Действие при ТРЕБУЕТ ДОРАБОТКИ:**
- Вывести `<validation_report>` с `VERDICT: ТРЕБУЕТ ДОРАБОТКИ`.
- Перечислить FAIL-дефекты без FIX.
- Вывести `<corrected_test_cases>` с применёнными AUTO_FIX (где возможно) и маркированными TODO-маркерами для ручной правки.
- Запросить у пользователя ручной правки.
- **Пайплайн приостанавливается.** Оркестратор не передаёт `<corrected_test_cases>` в `tc-to-autotest` автоматически. Повторная передача возможна только после подтверждения пользователя или повторной валидации с вердиктом `ПРИНЯТО`/`AUTO_FIX_APPLIED`.

**Поведение при частичном автофиксе (partial-fix):**
Если часть дефектов имеет AUTO_FIX, а часть — нет (требует ручной правки), вердикт всегда `ТРЕБУЕТ ДОРАБОТКИ` (не `AUTO_FIX_APPLIED`). В `<corrected_test_cases>`:
1. Все AUTO_FIX-исправимые дефекты исправляются автоматически.
2. Неисправимые дефекты помечаются inline-маркером `⚠ [ТРЕБУЕТ РУЧНОЙ ПРАВКИ: причина]` в соответствующем шаге/поле.
3. В `<validation_report>` в блоке «Остаточные дефекты» перечисляются все FAIL без FIX с указанием `ТК-N` и причины.
   4. **Пайплайн приостанавливается.** Оркестратор передаёт `<corrected_test_cases>` дальше в `tc-to-autotest` только если пользователь подтвердит использование частично исправленных ТК, либо после ручной доработки и повторной валидации с вердиктом `ПРИНЯТО`/`AUTO_FIX_APPLIED`.

## СВЯЗЬ С PIPELINE

Этот скилл — **Шаг 2 тестового пайплайна** (см. [`PIPELINE.md`](../PIPELINE.md)):

- **Вход:** `<generated_test_cases>` от `tc-generator` (Шаг 1).
- **Выход:**
  - При `ПРИНЯТО` — `<validation_report>` → `tc-to-autotest` (Шаг 3) получает исходные `<generated_test_cases>`.
  - При `AUTO_FIX_APPLIED` / `ТРЕБУЕТ ДОРАБОТКИ` — `<validation_report>` + `<corrected_test_cases>` → `tc-to-autotest` (через Оркестратор, с проверкой вердикта).
  - При `ТРЕБУЕТ ДОРАБОТКИ` — Оркестратор приостанавливает пайплайн до ручного подтверждения пользователя (согласно `CONTRACTS.md` §3.2 и правилам ветвления Оркестратора).
- **Контракт выхода:** `<validation_report>` + `<review_verdict>` (`CONTRACTS.md` §2, записи 5, 10).
- **Протокол передачи:**
  - `tc-to-autotest` использует GATE CHECK: при `<review_verdict>ТРЕБУЕТ ДОРАБОТКИ</review_verdict>` — автоматическая блокировка (запрет генерации кода).
  - При `AUTO_FIX_APPLIED` — `<corrected_test_cases>` используются как основной источник для генерации автотестов.

## ФИНАЛЬНАЯ ПРОВЕРКА ПЕРЕД ВЫВОДОМ

- [ ] Все `ТК-N` из входа присутствуют в `<corrected_test_cases>` (ни один не потерян)
- [ ] Нумерация `ТК-N` уникальна и сквозная
- [ ] Нет «ИЛИ» в ожидаемых результатах
- [ ] Нет фраз-заглушек без замены
- [ ] Все ⚠-маркеры оформлены единообразно
- [ ] Лимиты символов соблюдены (или отмечены WARN)
- [ ] Бизнес-смысл ТК не изменён (только формат/точность)
- [ ] `<validation_report>` содержит вердикт (`ПРИНЯТО` | `AUTO_FIX_APPLIED` | `ТРЕБУЕТ ДОРАБОТКИ`) и список применённых исправлений
- [ ] При `ПРИНЯТО` — `<corrected_test_cases>` НЕ выводится
- [ ] При `AUTO_FIX_APPLIED` — `<corrected_test_cases>` выводится
- [ ] При `ТРЕБУЕТ ДОРАБОТКИ` — `<corrected_test_cases>` выводится с TODO-маркерами для ручной правки
- [ ] **(v3.0+) Если `<output_format>json</output_format>`:** JSON-выход сформирован с ключами `meta`, `verdict`, `checks`, `auto_fixes_applied`, `remaining_issues`; валидирован через `schema-validator` по схеме `tc-reviewer-output.schema.json`
