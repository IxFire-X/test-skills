## Исходные требования

- SREQ-0015: 1.4.4. Любая операция чтения, обновления и удаления по идентификатору, которого нет в системе, возвращает 404 с телом `ProblemDetail`, и это не изменяет данные других записей.
- SREQ-0017: 2.1.2. Значение firstName длиной 30 символов (30 букв A) принимается, длиной 31 символ отклоняется ответом 400. Значения длины 1 («A») принимаются.
- SREQ-0018: 2.1.3. firstName состоит из одного, двух или трёх слов из букв (в том числе нелатинских), разделённых одним пробелом, апострофом или дефисом. Принимаются: Irina, Anna-Maria, Jean Paul, O'Neil, Élodie, Иван. Отклоняются ответом 400: Anna1, «Anna  Maria» (два пробела подряд), «␣Anna» (пробел в начале), Anna- (разделитель в конце), A-B-C-D (четыре слова), Anna. (точка в конце).
- SREQ-0023: 2.1.8. telephone принимает значения длиной от 1 до 20 символов: строка из 20 цифр 1 принимается, из 21 цифры — отклоняется ответом 400.
- SREQ-0024: 2.1.9. telephone содержит только цифры. Значение 0123456789 принимается, возвращается без изменений, начальный ноль сохраняется. Значения +71234567890, 123-456, «123 456» и 12345A7890 отклоняются ответом 400 без создания записи.
- SREQ-0030: 2.2.6. Запрос `POST /owners` с телом, не являющимся корректным JSON (например, `{"firstName": `), возвращает 400 с телом `ProblemDetail`. Неподтверждённое условие: контракт описывает 400 как «Bad request» без перечня причин.
- SREQ-0034: 2.3.4. Идентификатор 0 лежит в допустимых границах контракта: запрос `GET /owners/0` возвращает 404 (владельца с таким id нет) или 200 (если он есть), но не 400.
- SREQ-0053: 2.7.2. Повторное `DELETE` того же идентификатора, а также `DELETE` несуществующего идентификатора возвращает 404 с `ProblemDetail`.
- SREQ-0058: 3.1.4. Поле birthDate в схеме снабжено проверкой возраста питомца (`PetAgeValidation`). Неподтверждённое условие: содержание проверки в контракте не описано; ожидаем, что дата рождения позже D (в будущем) отклоняется ответом 400, а дата D принимается.
- SREQ-0059: 3.2.1. `POST /owners/{ownerId}/pets` с телом `PetFields` (name Rex, birthDate 2019-04-10, type — объект «dog» из справочника) возвращает 201 и `Pet`, в котором name, birthDate и type совпадают с отправленными значениями.
- SREQ-0072: 4.1.2. date имеет формат `ГГГГ-ММ-ДД`: значения `2024-02-01` и `2024-02-29` (2024 — високосный год) принимаются, значения `01.02.2024`, `2024-02-30` и `not-a-date` отклоняются ответом 400.
- SREQ-0076: 4.2.3. После создания `GET /owners/{ownerId}/pets/{petId}` содержит новый визит в массиве `visits` ровно один раз; у других питомцев визиты не добавились.
- SREQ-0083: 4.3.5. `GET /visits/{visitId}` возвращает 200 и `Visit` существующего визита; для несуществующего — 404, для нечислового значения (`abc`) — 400, оба с `ProblemDetail`.
- SREQ-0103: 7.1.1. `GET /specialties` возвращает 200 и массив `Specialty`; у каждого элемента есть целочисленный `id` и непустой name.
- SREQ-0111: 8.1.3. name обязателен и ограничен длиной: отсутствие, `null` и пустая строка отклоняются ответом 400 с `ProblemDetail`; строка из 80 букв принимается, из 81 — отклоняется ответом 400.
- SREQ-0115: 9.1.1. `POST /users` с телом `{"username": "qa.user1", "password": "Secret-123", "enabled": true, "roles": [{"name": "OWNER_ADMIN"}]}` возвращает 200 (не 201) и тело `User`, в котором username, enabled и roles совпадают с отправленными.
