## Исходные требования

- SREQ-0001: 1.1.1. Все операции предметной области доступны по префиксу `/petclinic/api` на порту 9966; запрос по пути контракта без этого префикса операцией API не обслуживается. Неподтверждённое условие: контракт задаёт префикс только в адресе сервера и не описывает ответ на запрос без него; ожидаем 404.
- SREQ-0012: 1.4.1. Операции создания возвращают разные коды успеха. `POST /owners`, `POST /owners/{ownerId}/pets` и `POST /owners/{ownerId}/pets/{petId}/visits` — 201. `POST /pettypes`, `POST /specialties`, `POST /vets`, `POST /visits` и `POST /users` — 200 (так описано в контракте; тест не должен «исправлять» ожидание на 201).
- SREQ-0013: 1.4.2. Операции удаления `DELETE` по адресам `/owners/{ownerId}`, `/pets/{petId}`, `/visits/{visitId}`, `/vets/{vetId}`, `/specialties/{specialtyId}` и `/pettypes/{petTypeId}` возвращают при успехе 200 и в теле — удалённую запись в том виде, в каком её вернуло бы чтение.
- SREQ-0014: 1.4.3. Операция `PUT /owners/{ownerId}/pets/{petId}` при успехе возвращает 204 без тела, тогда как остальные операции обновления (`PUT /owners/{ownerId}`, `/pets/{petId}`, `/visits/{visitId}`, `/vets/{vetId}`, `/specialties/{specialtyId}`, `/pettypes/{petTypeId}`) возвращают 200 и обновлённую запись.
- SREQ-0015: 1.4.4. Любая операция чтения, обновления и удаления по идентификатору, которого нет в системе, возвращает 404 с телом `ProblemDetail`, и это не изменяет данные других записей.
- SREQ-0016: 2.1.1. Каждое из пяти полей `OwnerFields` обязательно. Если поле отсутствует в теле, равно `null` или равно пустой строке, а остальные четыре поля корректны, `POST /owners` возвращает 400 с телом `ProblemDetail`, и новый владелец не создаётся.
- SREQ-0017: 2.1.2. Значение firstName длиной 30 символов (30 букв A) принимается, длиной 31 символ отклоняется ответом 400. Значения длины 1 («A») принимаются.
- SREQ-0018: 2.1.3. firstName состоит из одного, двух или трёх слов из букв (в том числе нелатинских), разделённых одним пробелом, апострофом или дефисом. Принимаются: Irina, Anna-Maria, Jean Paul, O'Neil, Élodie, Иван. Отклоняются ответом 400: Anna1, «Anna  Maria» (два пробела подряд), «␣Anna» (пробел в начале), Anna- (разделитель в конце), A-B-C-D (четыре слова), Anna. (точка в конце).
- SREQ-0019: 2.1.4. lastName подчиняется тому же правилу, что firstName, но допускает ровно одну точку в конце. Принимаются: BigdocOne, Smith Jr., O'Brien, De-La Cruz. Отклоняются ответом 400: Smith2, «Smith..» (две точки), «.Smith» (точка в начале), «Smith. Jr» (точка в середине).
- SREQ-0044: 2.5.5. Параметр `size` принимает значения от 1 до 100: `size=1` и `size=100` принимаются (200), `size=0` и `size=101` отклоняются ответом 400 с `ProblemDetail`.
- SREQ-0045: 2.5.6. Параметр `page` принимает значения от 0: `page=0` принимается, `page=-1` отклоняется ответом 400.
- SREQ-0055: 3.1.1. Поля name, birthDate и type обязательны. Если любое из них отсутствует или равно `null`, а остальные корректны, `POST /owners/{ownerId}/pets` возвращает 400 с `ProblemDetail`, и питомец не создаётся.
- SREQ-0062: 3.2.4. `type` с идентификатором, отсутствующим в справочнике, отклоняется ответом 4хх с `ProblemDetail`; питомец не создаётся, справочник типов не пополняется. Неподтверждённое условие: контракт не задаёт, будет это 400 или 404 (описан и тот и другой для этой операции).
- SREQ-0064: 3.3.1. `GET /owners/{ownerId}/pets/{petId}` для питомца этого владельца возвращает 200 и `Pet` с полями name, birthDate, type, id, ownerId, visits.
- SREQ-0072: 4.1.2. date имеет формат `ГГГГ-ММ-ДД`: значения `2024-02-01` и `2024-02-29` (2024 — високосный год) принимаются, значения `01.02.2024`, `2024-02-30` и `not-a-date` отклоняются ответом 400.
- SREQ-0077: 4.2.4. `POST` для питомца, не принадлежащего указанному владельцу, и для несуществующего `petId` возвращает 404 «Pet not found for this owner» с `ProblemDetail`; визит не создаётся.
- SREQ-0082: 4.3.4. `POST /visits` с `petId`, которого нет в системе, возвращает ответ 4хх (400 или 404) и не создаёт визит. Неподтверждённое условие: контракт описывает для этой операции 400 и 404 без пояснений.
- SREQ-0086: 4.3.8. `DELETE /visits/{visitId}` возвращает 200 и тело `Visit` удалённого визита; последующий `GET /visits/{visitId}` возвращает 404, а из массива `visits` питомца визит исчез. Повторное `DELETE` возвращает 404.
- SREQ-0088: 5.1.2. `GET /v2/pets` возвращает 200 и объект `PetPage` с полями `content` (массив `Pet`), `page`, `size`, `totalElements`, `totalPages`. Без параметров `page` = 0 и `size` = 20.
- SREQ-0090: 5.1.4. Границы параметров те же, что у постраничного списка владельцев: `size` от 1 до 100 (значения 0 и 101 дают 400), `page` от 0 (значение -1 даёт 400), нечисловые значения дают 400 с `ProblemDetail`.
- SREQ-0093: 5.2.3. `PUT /pets/{petId}` с некорректным телом (name из 31 символа или отсутствующий type) возвращает 400, данные питомца не меняются; для несуществующего `petId` возвращается 404.
- SREQ-0096: 6.1.1. `GET /vets` возвращает 200 и массив `Vet`; у каждого элемента есть `id`, firstName, lastName и массив specialties (возможно пустой), каждый элемент которого содержит `id` и name.
- SREQ-0098: 6.1.3. Поля firstName, lastName и specialties обязательны: отсутствие любого из них или `null` отклоняется ответом 400 с `ProblemDetail`, ветеринар не создаётся. Для firstName и lastName действуют те же шаблоны и границы длины 30 символов, что и для владельца (требования 2.1.2–2.1.5): строка из 31 буквы отклоняется ответом 400.
- SREQ-0100: 6.1.5. `GET /vets/{vetId}` возвращает 200 и `Vet` существующего ветеринара; для несуществующего — 404, для нечислового идентификатора — 400, оба с `ProblemDetail`.
- SREQ-0105: 7.1.3. name обязателен и ограничен длиной: отсутствие, `null` и пустая строка отклоняются ответом 400 с `ProblemDetail`; строка из 80 букв принимается, из 81 — отклоняется ответом 400. Справочник после отказа не меняется.

- SREQ-0128: 11.1.4. Неподтверждённое условие: код отказа 403 в контракте не описан; допустимо 401, если авторизация реализована иначе.
