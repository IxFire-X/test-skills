Смысл операций, входов и выходов шага проверяешь ты: та ли capability и тот ли action, те ли метод, путь и значения, что в действии, данных и требовании. Длинный литерал урезан с пометкой «…(+N симв.)» — полное значение в JSON кандидата у того же шага.

## Исходные требования

- SREQ-0003: 1.1.3. Идентификаторы в пути (`ownerId`, `petId`, `visitId`, `vetId`, `specialtyId`, `petTypeId`) — целые числа типа int32 с минимумом 0 (`minimum: 0` в контракте). Идентификатор из букв (например, `abc`) отклоняется ответом 400 с телом `ProblemDetail`.
- SREQ-0008: 1.2.3. После изменения данных (создание, обновление, удаление записи) значение `ETag` для списка этой же сущности меняется, и `GET` с прежним `ETag` возвращает 200 с актуальным телом, а не 304. Неподтверждённое условие: способ вычисления `ETag` в контракте не описан.
- SREQ-0014: 1.4.3. Операция `PUT /owners/{ownerId}/pets/{petId}` при успехе возвращает 204 без тела, тогда как остальные операции обновления (`PUT /owners/{ownerId}`, `/pets/{petId}`, `/visits/{visitId}`, `/vets/{vetId}`, `/specialties/{specialtyId}`, `/pettypes/{petTypeId}`) возвращают 200 и обновлённую запись.
- SREQ-0015: 1.4.4. Любая операция чтения, обновления и удаления по идентификатору, которого нет в системе, возвращает 404 с телом `ProblemDetail`, и это не изменяет данные других записей.
- SREQ-0016: 2.1.1. Каждое из пяти полей `OwnerFields` обязательно. Если поле отсутствует в теле, равно `null` или равно пустой строке, а остальные четыре поля корректны, `POST /owners` возвращает 400 с телом `ProblemDetail`, и новый владелец не создаётся.
- SREQ-0020: 2.1.5. lastName длиной 30 символов принимается, 31 символ отклоняется ответом 400.
- SREQ-0028: 2.2.4. Два запроса `POST /owners` с одинаковым телом создают двух владельцев с разными `id`. Неподтверждённое условие: контракт не запрещает дубликаты; проверка уникальности по сочетанию полей не требуется.
- SREQ-0029: 2.2.5. При ответе 400 на создание тело содержит `ProblemDetail`; число владельцев в `GET /owners` не меняется.
- SREQ-0031: 2.3.1. `GET /owners/{ownerId}` для существующего владельца возвращает 200 и `Owner` со всеми пятью полями, `id` и массивом `pets`.
- SREQ-0054: 2.7.3. После удаления владельца с питомцами его питомцы и их визиты недоступны: `GET /pets/{petId}` для бывшего питомца возвращает 404. Неподтверждённое условие: контракт не описывает каскадное удаление; принято ожидание, что осиротевших питомцев в системе не остаётся.
- SREQ-0057: 3.1.3. birthDate имеет формат `ГГГГ-ММ-ДД`. Значения `not-a-date`, `2020-13-01` и `2020-02-30` отклоняются ответом 400 без создания питомца; корректная прошлая дата 2020-01-02 принимается и возвращается без сдвига на день.
- SREQ-0062: 3.2.4. `type` с идентификатором, отсутствующим в справочнике, отклоняется ответом 4хх с `ProblemDetail`; питомец не создаётся, справочник типов не пополняется. Неподтверждённое условие: контракт не задаёт, будет это 400 или 404 (описан и тот и другой для этой операции).
- SREQ-0063: 3.2.5. `POST /owners/{ownerId}/pets` для несуществующего владельца возвращает 404 с `ProblemDetail` и не создаёт питомца ни у одного владельца.
- SREQ-0064: 3.3.1. `GET /owners/{ownerId}/pets/{petId}` для питомца этого владельца возвращает 200 и `Pet` с полями name, birthDate, type, id, ownerId, visits.
- SREQ-0066: 3.3.3. Нечисловой `petId` (например, `abc`) возвращает 400 с `ProblemDetail`.
- SREQ-0072: 4.1.2. date имеет формат `ГГГГ-ММ-ДД`: значения `2024-02-01` и `2024-02-29` (2024 — високосный год) принимаются, значения `01.02.2024`, `2024-02-30` и `not-a-date` отклоняются ответом 400.
- SREQ-0073: 4.1.3. Если date в запросе отсутствует, визит создаётся с датой, равной текущей дате сервера D (по Javadoc модели: «Creates a new instance of Visit for the current date»). Неподтверждённое условие: контракт поле date не требует и значение по умолчанию не называет.
- SREQ-0080: 4.3.2. `POST /visits` с телом `Visit` (description «checkup», date 2024-03-05, `petId` существующего питомца) возвращает 200 (не 201) и созданный `Visit` с выданным `id`; `petId` в ответе совпадает с переданным.
- SREQ-0082: 4.3.4. `POST /visits` с `petId`, которого нет в системе, возвращает ответ 4хх (400 или 404) и не создаёт визит. Неподтверждённое условие: контракт описывает для этой операции 400 и 404 без пояснений.
- SREQ-0088: 5.1.2. `GET /v2/pets` возвращает 200 и объект `PetPage` с полями `content` (массив `Pet`), `page`, `size`, `totalElements`, `totalPages`. Без параметров `page` = 0 и `size` = 20.
- SREQ-0090: 5.1.4. Границы параметров те же, что у постраничного списка владельцев: `size` от 1 до 100 (значения 0 и 101 дают 400), `page` от 0 (значение -1 даёт 400), нечисловые значения дают 400 с `ProblemDetail`.
- SREQ-0097: 6.1.2. `POST /vets` с телом из firstName Olga, lastName Testvet и specialties из двух объектов (radiology и surgery, взятых из справочника) возвращает 200 и `Vet` с выданным `id` и теми же специальностями; повторное чтение возвращает те же значения.
- SREQ-0098: 6.1.3. Поля firstName, lastName и specialties обязательны: отсутствие любого из них или `null` отклоняется ответом 400 с `ProblemDetail`, ветеринар не создаётся. Для firstName и lastName действуют те же шаблоны и границы длины 30 символов, что и для владельца (требования 2.1.2–2.1.5): строка из 31 буквы отклоняется ответом 400.
- SREQ-0099: 6.1.4. Пустой массив specialties принимается: ветеринар без специальностей создаётся, ответ содержит `specialties: []`. Неподтверждённое условие: контракт требует наличия поля, но не требует непустого массива.
- SREQ-0100: 6.1.5. `GET /vets/{vetId}` возвращает 200 и `Vet` существующего ветеринара; для несуществующего — 404, для нечислового идентификатора — 400, оба с `ProblemDetail`.
- SREQ-0106: 7.1.4. `GET /specialties/{specialtyId}` возвращает 200 и `Specialty`; для несуществующего идентификатора — 404, для нечислового — 400, оба с `ProblemDetail`.
- SREQ-0108: 7.1.6. `DELETE /specialties/{specialtyId}` возвращает 200 и тело `Specialty` удалённой специальности; последующий `GET` возвращает 404, повторное `DELETE` — тоже 404. Неподтверждённое условие: контракт не описывает поведение при удалении специальности, назначенной ветеринару.
- SREQ-0110: 8.1.2. `POST /pettypes` с телом `{"name": "hamster-test"}` возвращает 200 (не 201) и `PetType` с выданным `id` и тем же name; созданный тип присутствует в `GET /pettypes` ровно один раз и может быть использован в поле type питомца.
- SREQ-0111: 8.1.3. name обязателен и ограничен длиной: отсутствие, `null` и пустая строка отклоняются ответом 400 с `ProblemDetail`; строка из 80 букв принимается, из 81 — отклоняется ответом 400.
- SREQ-0113: 8.1.5. `PUT /pettypes/{petTypeId}` с телом `{"id": <тот же id>, "name": "hamster-updated"}` возвращает 200 и обновлённый `PetType`; питомцы этого типа при последующем чтении возвращают новое название типа. Для несуществующего идентификатора — 404.
- SREQ-0114: 8.1.6. `DELETE /pettypes/{petTypeId}` возвращает 200 и тело `PetType` удалённого типа; последующий `GET` возвращает 404, повторное `DELETE` — 404. Неподтверждённое условие: контракт не описывает удаление типа, у которого есть питомцы.
- SREQ-0118: 9.1.4. Имя роли ограничено длиной 80 символов, пустое имя роли отклоняется ответом 400. По readme существуют роли `OWNER_ADMIN`, `VET_ADMIN` и `ADMIN`. Неподтверждённое условие: контракт не запрещает другие имена ролей, значение вне этого перечня должно приниматься или отклоняться — решение аналитика.
- SREQ-0120: 10.1.1. Ответ об ошибке содержит все шесть обязательных полей: type, title, status, detail, timestamp и schemaValidationErrors; поле status равно HTTP-коду ответа, а detail непустое.
- SREQ-0122: 10.1.3. Поле timestamp — дата и время в формате ISO 8601 (пример контракта: `2024-11-23T13:59:21.3820407Z`); значение не отличается от текущего времени сервера более чем на минуту.
- SREQ-0126: 11.1.2. При включённой аутентификации запрос без заголовка `Authorization` или с неверным паролем отклоняется ответом 401; запрос `admin`/`admin` выполняется для операций всех разделов этого документа.
