# Руководство по эксплуатации: Скиллы тестирования + Оркестратор

> **Версия:** 1.1 (2026-07-07)  
> **Аудитория:** инженер / QA / разработчик, который хочет запускать пайплайн и отдельные скиллы **промптами**, без чтения SKILL.md  
> **Связанные документы:** `Instruction.md` (общая настройка), `CONTRACTS.md` (канон тегов), `PIPELINE.md` (схема), `.skillsrc` (манифест)

---

## 1. Что это за система (30 секунд)

У вас есть **4 скилла тестирования** + **1 скилл разметки контекста** + **1 Оркестратор**:

```
context-marker       tc-generator  ──→  tc-reviewer  ──→  tc-to-autotest  ──→  autotest-reviewer
(разметка .md)       (ручные ТК)       (валидация ТК)     (автотесты)          (валидация автотестов)
```

- **Каждый скилл можно запустить отдельно** (одним промптом)
- **context-marker** размечает сырые `.md`-файлы в XML-теги (нужен, если аналитика без тегов)
- **Оркестратор** запускает всю цепочку автоматически (одним промптом) — включая вызов context-marker при необходимости
- **Оркестратор Lite** (SKILL-LITE.md) — облегчённая версия для моделей 7B–13B (DeepSeek, Qwen, Llama)

## 2. Быстрый старт (3 команды)

### 2.1 Полный пайплайн (4 этапа, одной фразой)

```
Создай тест-кейсы и автотесты для TransferService
```

Оркестратор сам:
- Выполнит **Deep Scan** проекта (определит стек, методологию)
- **Если аналитика в сыром `.md`** → вызовет `context-marker` для разметки в `<analytics_documentation>`
- Выполнит **Contract Check** (проверит совместимость контрактов между скиллами)
- Запустит `tc-generator → tc-reviewer → tc-to-autotest → autotest-reviewer`
- Сгенерирует отчёт `docs/to_do/orchestration-report-<TIMESTAMP>.md`

### 2.2 Только ручные тест-кейсы (1 скилл)

```
Сгенерируй тест-кейсы для TransferService
```

Загрузите `Ручные тест-кейсы/SKILL.md`, передайте `<analytics_documentation>` + `<source_code_and_diff>`.

### 2.3 Только автотесты из готовых ТК

```
Напиши автоматизированные тесты
```

Загрузите `Автоматизированные кейсы на основе тест-кейсов/SKILL.md`, передайте `<test_cases>`.

## 3. Каталог промптов (все сценарии)

### 3.1 Полный пайплайн — через Оркестратор

**Что сказать LLM (любая из фраз):**

| # | Промпт | Что произойдёт |
|---|--------|----------------|
| 1 | `Создай тест-кейсы и автотесты для <фича>` | Запуск test-pipeline |
| 2 | `Запусти тестовый пайплайн` | Запуск test-pipeline |
| 3 | `Полный цикл тестирования` | Запуск test-pipeline |
| 4 | `Проверь качество` | Запуск test-pipeline |
| 5 | `Сделай все проверки` | Запуск test-pipeline |
| 6 | `Прогони пайплайн` | Запуск test-pipeline |

**Обязательно передать:** `<analytics_documentation>` + `<source_code_and_diff>` (в том же диалоге).

**Дополнительные параметры (опционально):**
```xml
<goal>Создай тест-кейсы и автотесты для TransferService</goal>
<pipeline>test-pipeline</pipeline>
<max_iterations>5</max_iterations>
<strict_mode>true</strict_mode>
<context>Проект: subscription-renewal-service, Java 17, Spring Boot 3.2</context>
```

### 3.2 Quickstart / Инициализация проекта

**Что сказать:**
```
Инициализируй проект
```
или
```
Quickstart
```

**Что делает Оркестратор:**
1. Запускает **Deep Scan** всего проекта (код, build-файлы, документация, OpenAPI-спецификации)
2. Сравнивает с `.skillsrc` (если есть) и сливает данные по стратегии `skillsrc_vs_scan`
3. Если `.skillsrc` нет — предлагает создать автоматически
4. Выводит чек-лист:
   ```
   ✅ Java 17, Spring Boot 3.2
   ✅ Maven, JUnit 5, PostgreSQL
   🧪 12 автотестов
   📋 0 тест-кейсов

   Доступные команды:
   - 'создай тест-кейсы'
   - 'сгенерируй автотесты'
   - 'запусти тестовый пайплайн'
   ```

**Зачем:** после Quickstart Оркестратор «знает» ваш стек и не переспрашивает язык/фреймворк/тестовые инструменты.

### 3.3 Отдельный скилл — генерация ручных ТК (tc-generator)

**Что сказать:**
```
Сгенерируй тест-кейсы
```
(или: `напиши ручные тест-кейсы`, `создай ТК`, `покрой тестами`, `нужны тест-кейсы для`, `составь тест-кейсы`)

**Что передать (вместе с SKILL.md):**
```xml
<analytics_documentation>
## Фича: Создание заявки на перевод
### Acceptance Criteria
- AC-1: Заявка создаётся с обязательными полями: amount, currency, recipientId
...

### API
POST /api/v1/transfers
Request: { amount: BigDecimal, currency: String, recipientId: UUID }
Response: { transferId: UUID, status: String, createdAt: ISO8601 }
</analytics_documentation>

<source_code_and_diff>
## TransferController.java
@PostMapping("/transfers")
public ResponseEntity<TransferResponse> createTransfer(@RequestBody TransferRequest request) { ... }
</source_code_and_diff>
```

**Что получить на выходе:** `<generated_test_cases>` — Zephyr Markdown с ТК-N.

### 3.4 Отдельный скилл — валидация ТК (tc-reviewer)

**Что сказать:**
```
Проверь тест-кейсы
```
(или: `отревьюй ТК`, `валидируй тест-кейсы`, `проверь качество ТК`, `сделай ревью тест-кейсов`)

**Что передать (вместе с SKILL.md):**
```xml
<generated_test_cases>
... (результат tc-generator)
</generated_test_cases>

<analytics_documentation>
... (та же аналитика для сверки)
</analytics_documentation>

<source_code_and_diff>
... (тот же diff для проверки технической точности)
</source_code_and_diff>
```

**Что получить:** `<validation_report>` + `<review_verdict>` (одно из `ПРИНЯТО` / `AUTO_FIX_APPLIED` / `ТРЕБУЕТ ДОРАБОТКИ`).

### 3.5 Отдельный скилл — генерация автотестов (tc-to-autotest)

**Что сказать:**
```
Сгенерируй автотесты
```
(или: `напиши автоматизированные тесты`, `преврати ТК в код`, `автоматизируй тест-кейсы`)

**Что передать (вместе с SKILL.md):**
```xml
<!-- ВАРИАНТ А: ТК приняты ревьюером -->
<test_cases>
... (исходные <generated_test_cases>, ПЕРЕИМЕНОВАННЫЕ в <test_cases> после вердикта ПРИНЯТО)
</test_cases>

<!-- ВАРИАНТ Б: ревьюер применил автофикс -->
<corrected_test_cases>
... (результат tc-reviewer при AUTO_FIX_APPLIED / ТРЕБУЕТ ДОРАБОТКИ)
</corrected_test_cases>

<!-- ОПЦИОНАЛЬНО: для итеративной регенерации -->
<existing_project_context>
... (архитектурный шаблон проекта)
</existing_project_context>

<!-- ОПЦИОНАЛЬНО: предыдущая матрица для diff -->
<automation_matrix>
... (старая матрица ТК-N → java-метод)
</automation_matrix>
```

**Что получить:** Java-файлы (DTO + тест-класс) + `<automation_matrix>` + `<automation_analysis>` + (при diff) `<conflict_resolution>`.

### 3.6 Отдельный скилл — валидация автотестов (autotest-reviewer)

**Что сказать:**
```
Проверь автотесты
```
(или: `отревьюй код тестов`, `валидируй автотесты`, `проверь качество автотестов`, `сделай ревью кода тестов`)

**Что передать (вместе с SKILL.md):**
```xml
<test_cases>
... (утверждённые ТК)
</test_cases>

<automation_matrix>
... (матрица от tc-to-autotest)
</automation_matrix>

<autotest_code>
... (Java-код автотестов, сгенерированный tc-to-autotest)
</autotest_code>
```

**Что получить:** `<autotest_review>` + `<review_verdict>` + `<review_comments>` (если есть ошибки) + (при `AUTO_FIX_APPLIED`) `<corrected_autotest_code>`.

### 3.7 Частичный пайплайн (2–3 скилла без Оркестратора)

**Сценарий А: генерация + валидация ТК (без автотестов)**
```
Шаг 1: "Сгенерируй тест-кейсы"   → tc-generator   → <generated_test_cases>
Шаг 2: "Проверь тест-кейсы"       → tc-reviewer    → <validation_report> + вердикт
```

**Сценарий Б: только автотесты из готовых ТК + их валидация**
```
Шаг 1: "Сгенерируй автотесты"     → tc-to-autotest → <automation_matrix> + Java-файлы
Шаг 2: "Проверь автотесты"        → autotest-reviewer → <autotest_review> + вердикт
```

### 3.8 Разметка сырого контекста (context-marker)

**Что сказать:**
```
Разметь контекст для пайплайна
```
(или: `разметь аналитику`, `оберни требования в XML`, `подготовь контекст`)

**Что передать (вместе с SKILL.md):**
```xml
<raw_content>
# Функциональные требования: Продление подписки

## AC-1: Успешное автоматическое продление
При наступлении даты окончания подписки...

## AC-2: Ручное продление
Пользователь может продлить подписку вручную...
</raw_content>

<!-- Опционально: -->
<file_path>docs/requirements/renewal.md</file_path>
```

**Что получить:** `<analytics_documentation>...</analytics_documentation>` (размеченный XML) или `<source_code_and_diff>...</source_code_and_diff>` / `<test_cases>...</test_cases>` в зависимости от автоопределённого типа контента.

**Когда использовать:**
- Если у вас SDD-проект с аналитикой в сырых `.md`-файлах без XML-тегов
- Перед передачей данных в `tc-generator` для автоматического режима
- Для batch-разметки всей директории `docs/requirements/` за один вызов

> **Примечание:** при запуске через Оркестратор (`Создай тест-кейсы...`) context-marker вызывается автоматически для SDD-проектов. Ручной вызов нужен только если вы запускаете скиллы по отдельности.

### 3.9 Итеративная регенерация автотестов (diff-режим)

**Ситуация:** ТК изменились, нужно обновить существующие автотесты без переписывания всех методов с нуля.

**Что передать в `tc-to-autotest`:**
```xml
<test_cases>
... (обновлённые ТК)
</test_cases>

<automation_matrix>
... (старая матрица от предыдущего запуска!
     Скилл сделает diff: сохранит методы для неизменных ТК,
     удалит для удалённых, добавит для новых)
</automation_matrix>
```

**Что получить:**
- `<conflict_resolution>` — отчёт о diff'е: `removed`, `added`, `renamed`, `merged`
- Обновлённые Java-файлы (старые методы сохранены, новые добавлены)

**Когда использовать:**
- После обновления ТК в ответ на изменившиеся требования
- После исправления ТК ревьюером (`AUTO_FIX_APPLIED` / `ТРЕБУЕТ ДОРАБОТКИ`)

### 3.10 Оркестратор Lite (для слабых моделей 7B–13B)

Если вы используете DeepSeek, Qwen, Llama (7B–13B) или другую модель с ограниченным контекстом, загружайте **`Оркестратор/SKILL-LITE.md`** (~260 строк) вместо полного `SKILL.md`.

Промпты — **те же** (см. §3.1). Отличие: убраны Deep Scan, Zero-Config и Quickstart. Только диспетчеризация: выбор пайплайна, управление итерациями, изоляция контекста, обработка ошибок.

## 5. Как читать результаты

### 5.1 Вердикты ревьюеров

| Вердикт | Означает | Что делать дальше |
|---------|----------|-------------------|
| `ПРИНЯТО` | Всё OK, ошибок нет | Передайте артефакт следующему скиллу |
| `AUTO_FIX_APPLIED` | Скилл сам всё исправил | Используйте `<corrected_*>` (не исходный артефакт) |
| `ТРЕБУЕТ ДОРАБОТКИ` | Критические ошибки, автофикс невозможен | Прочитайте `<review_comments>`, исправьте вручную ИЛИ передайте комментарии обратно в генератор |

### 5.2 Статус оркестратора (в `<orchestration_result>`)

| Статус | Означает |
|--------|----------|
| `completed` | Пайплайн выполнен полностью, финальный артефакт готов |
| `partial` | Выполнен, но есть предупреждения (был `AUTO_FIX_APPLIED`) |
| `failed` | Критическая ошибка, пайплайн остановлен |
| `retry` | Исчерпан `max_iterations`, нужно вмешательство |

### 5.3 Отчёт оркестратора

Файл: `docs/to_do/orchestration-report-<TIMESTAMP>.md`

Структура:
- **Contract Check** — результаты проверки контрактов (PASS / FAIL по каждой паре скиллов)
- **Цель** — что было запрошено
- **Выполнение** — пошаговый лог (скилл → статус → выход)
- **Предупреждения** — что пошло не так
- **Рекомендации** — что делать при `failed` / `retry`

## 6. Как «стегать» проект: подготовка входных данных

Качество результата **прямо пропорционально** качеству входных данных.

### 6.1 Минимальный набор (запустится, но с вопросами)

```
Без всего — просто промпт.
Скилл перейдёт в ручной режим и задаст уточняющие вопросы.
```

### 6.2 Хороший набор (рекомендуемый)

```
✅ .skillsrc в корне проекта (см. инструкцию ниже)
✅ <analytics_documentation> — описание фичи, AC, API-контракты
   (если аналитика в сыром .md → используйте context-marker для разметки)
✅ <source_code_and_diff> — релевантный код и diff из PR
```

### 6.3 Идеальный набор (максимальная точность)

```
✅ .skillsrc (заполненный манифест)
✅ <analytics_documentation> — полная аналитика (размеченная через context-marker):
   - Acceptance Criteria (с номерами AC-N)
   - API-контракты (Swagger / OpenAPI)
   - Доменные правила (валидация, границы, типы)
✅ <source_code_and_diff>:
   - Контроллеры, сервисы, DTO
   - SQL-миграции
   - Diff из PR (git diff origin/main...HEAD)
✅ <existing_project_context>
   - Структура пакетов
   - Существующие тесты (чтобы не дублировать)
```

### 6.4 Шаблон `.skillsrc` для нового проекта

Создайте файл `.skillsrc` в корне проекта (см. пример в `test-orchestration-skills/.skillsrc`).  
**Или скажите:** `Инициализируй проект` — Оркестратор создаст `.skillsrc` автоматически.

## 7. Как передавать контекст между ручными шагами (правило переименования)

> **Критически важное правило**, без которого `tc-to-autotest` выдаст ошибку контракта.

На границе `tc-reviewer → tc-to-autotest` действует правило:

| Вердикт ревьюера | Что передавать в `tc-to-autotest` |
|------------------|-----------------------------------|
| `ПРИНЯТО` | `<generated_test_cases>` **переименовать** в `<test_cases>` |
| `AUTO_FIX_APPLIED` | `<corrected_test_cases>` как есть (без переименования) |
| `ТРЕБУЕТ ДОРАБОТКИ` | `<corrected_test_cases>` как есть (после доработки) |

**Запрещено** передавать `<generated_test_cases>` напрямую в `tc-to-autotest` — это вызовет ошибку контракта (скилл ожидает `<test_cases>` или `<corrected_test_cases>`).

Оркестратор делает это переименование автоматически. При ручном запуске — вы сами должны переименовать тег.

## 8. Обработка ошибок: что говорить LLM

### 8.1 Пайплайн остановился с `failed`

1. Откройте отчёт `docs/to_do/orchestration-report-*.md`
2. Прочитайте секцию «Рекомендации»
3. Скажите Оркестратору:
   ```
   Перезапусти пайплайн с теми же входными, но с max_iterations=5
   ```

### 8.2 Ревьюер отклонил ТК (`ТРЕБУЕТ ДОРАБОТКИ`)

1. Прочитайте `<review_comments>` — там список дефектов по severity
2. **Вариант А:** исправьте ТК руками и передайте в `tc-to-autotest`:
   ```
   Сгенерируй автотесты
   <corrected_test_cases>... (исправленные вручную ТК) </corrected_test_cases>
   ```
3. **Вариант Б:** верните `<review_comments>` + исходные данные обратно в `tc-generator` (через Оркестратор):
   ```
   Перегенерируй тест-кейсы с учётом замечаний ревьюера
   <review_comments>... </review_comments>
   <analytics_documentation>... </analytics_documentation>
   <source_code_and_diff>... </source_code_and_diff>
   ```

### 8.3 Ревьюер отклонил автотесты (`ТРЕБУЕТ ДОРАБОТКИ`)

1. Прочитайте `<review_comments>`
2. Передайте замечания обратно в `tc-to-autotest`:
   ```
   Перегенерируй автотесты с учётом замечаний
   <test_cases>... </test_cases>
   <automation_matrix>... (старая матрица для diff-режима) </automation_matrix>
   <review_comments>... </review_comments>
   ```

### 8.4 Исчерпан лимит итераций (`status = retry`)

```
Увеличь max_iterations до <N> и перезапусти
```

## 9. Интеграция в CI/CD (GitHub Actions)

### 9.1 Запуск пайплайна на каждый PR

```yaml
# .github/workflows/skills-test-pipeline.yml
name: Skills — Test Pipeline
on:
  pull_request:
    types: [opened, synchronize, reopened]
    paths:
      - 'src/**'
      - 'docs/analytics/**'
jobs:
  test-pipeline:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - name: Prepare Context
        run: |
          find docs/analytics -name '*.md' -exec cat {} + > /tmp/analytics.md
          git diff origin/${{ github.base_ref }}...HEAD -- src/ > /tmp/diff.patch
      - name: Run Test Pipeline
        env:
          AI_API_KEY: ${{ secrets.AI_API_KEY }}
        run: |
          {{YOUR_AI_CLI}} run \
            --skill-file "Оркестратор/SKILL.md" \
            --input-tag analytics_documentation "$(cat /tmp/analytics.md)" \
            --input-tag source_code_and_diff "$(cat /tmp/diff.patch)" \
            --pipeline test-pipeline \
            --output-dir "outputs/${{ github.run_id }}"
      - name: Upload Report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: orchestration-report-${{ github.run_id }}
          path: outputs/${{ github.run_id }}/
          retention-days: 30
```

### 9.2 Проверка статуса в PR

```bash
STATUS=$(grep -oP '<status>\K[^<]+' outputs/${{ github.run_id }}/orchestration-report-*.md)

case "$STATUS" in
  "completed") echo "✅ Всё успешно" ;;
  "partial")   echo "⚠️  Есть предупреждения" ;;
  "failed"|"retry") echo "❌ Ошибка"; exit 1 ;;
esac
```

## 11. Частые вопросы

**Можно ли использовать скиллы без `.skillsrc`?**  
Да. Скажите `Инициализируй проект` — Оркестратор запустит Zero-Config (автообнаружение стека) и предложит создать `.skillsrc`. 80% проектов запускаются без ручной настройки.

**Можно ли пропустить `tc-reviewer`?**  
Можно, но не рекомендуется. Невалидированные ТК могут содержать ошибки, которые перейдут в автотесты. Быстрее исправить ТК, чем потом переписывать код автотестов.

**Какой минимальный промпт для запуска?**  
`Создай тест-кейсы и автотесты` + аналитика в том же диалоге. Оркестратор сам определит пайплайн и при необходимости вызовет `context-marker` для разметки сырых `.md`-файлов.

**Как запустить то же самое на Python / Go / TypeScript?**  
Скиллы автоопределяют язык из `.skillsrc` или Deep Scan. Если `.skillsrc` говорит `language: python`, автотесты будут на Python (pytest). Стек не нужно указывать в промпте каждый раз.

**Что делать, если аналитика в сыром `.md` без XML-тегов?**  
Используйте `context-marker`: скажите «Разметь контекст для пайплайна» и передайте `.md`-файл. Скилл автоопределит тип контента и обернёт в правильный XML-тег. Или просто запустите пайплайн через Оркестратор — он вызовет `context-marker` автоматически для SDD-проектов.

**Где смотреть примеры промптов с живыми входными данными?**  
В файлах `examples.md` каждого скилла. Например: `Оркестратор/examples.md`, `Ручные тест-кейсы/examples.md`.

**Что делать с `<review_comments>` при `ТРЕБУЕТ ДОРАБОТКИ`?**  
Не исправляйте руками — передайте `<review_comments>` + исходные `<test_cases>` обратно в генератор. Скилл сделает точечный diff, а не перепишет всё с нуля.
