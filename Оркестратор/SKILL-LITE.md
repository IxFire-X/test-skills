# SKILL: Оркестратор Lite (v2.0-lite)

> **Целевые модели:** Qwen, DeepSeek, Llama 7B–13B, и любые модели с эффективным контекстом < 32K токенов.
> **Полная версия:** [`SKILL.md`](SKILL.md) — Deep Scan, Zero-Config, Quickstart, полный Contract Check, детальные Fallback-стратегии, подробные примеры. Используйте полную версию с Claude/GPT-4o.

**Назначение:** Координирует цепочки скиллов (Sub-Agent диспетчеризация), контроль итераций, изоляция контекста и обработка ошибок. Принимает `<goal>` и строит план выполнения.

---

## Контракт входа

| Тег | Обязательность | Описание |
|---|---|---|
| `<goal>` | ✅ | Цель в свободной форме (например, "создать тест-кейсы для TransferService") |
| `<pipeline>` | ❌ | Имя пайплайна (по умолчанию: `test-pipeline`) |
| `<max_iterations>` | ❌ | Лимит итераций (по умолчанию: `3`) |
| `<strict_mode>` | ❌ | `true` / `false` (по умолчанию: `false`) |
| `<context>` | ❌ | Дополнительный контекст проекта |

## Контракт выхода

```xml
<orchestration_result version="2.0">
  <execution_id>UUID — уникальный идентификатор запуска</execution_id>
  <status>completed | partial | failed | retry</status>
  <pipeline_name>test-pipeline</pipeline_name>
  <iterations>N</iterations>
  <steps>
    <step>
      <name>название шага</name>
      <skill>использованный скилл</skill>
      <status>успех/ошибка</status>
      <output>путь к результату</output>
      <retries>количество retry</retries>
    </step>
  </steps>
  <final_result>путь к финальному результату</final_result>
  <warnings>список предупреждений</warnings>
</orchestration_result>
```

## Поддерживаемый пайплайн

### test-pipeline (5 этапов)

```
context-marker → tc-generator → tc-reviewer → tc-to-autotest → autotest-reviewer
```

> **Примечание:** `context-marker` (Разметка контекста) — опциональный препроцессор. Вызывается автоматически при обнаружении сырых `.md`-файлов без XML-разметки (SDD-проекты). Если аналитика уже в XML-тегах — этап пропускается.

| Этап | Скилл | Вход | Выход |
|---|---|---|---|
| 0* | `context-marker` | сырые `.md`-файлы | `<analytics_documentation>` + `<source_code_and_diff>` |
| 1 | `tc-generator` | `<analytics_documentation>` + `<source_code_and_diff>` | `<generated_test_cases>` |
| 2 | `tc-reviewer` | `<generated_test_cases>` | `<validation_report>` + вердикт + (опц.) `<corrected_test_cases>` |
| 3 | `tc-to-autotest` | `<test_cases>` или `<corrected_test_cases>` | `<automation_matrix>` + `<automation_analysis>` + файлы |
| 4 | `autotest-reviewer` | `<test_cases>` + `<automation_matrix>` + код | `<autotest_review>` + `<review_verdict>` |

## Progressive Disclosure (L1→L2)

**Критический механизм экономии токенов.** Оркестратор не загружает все SKILL.md сразу:

1. **L1:** Читает `.skillsrc` → секцию `skills_registry` (только `name` + `description` + `tags` + `input_contract` / `output_contract`)
2. **Сопоставляет** `<goal>` с `description` + `tags` → отбирает подходящий скилл
3. Если неоднозначность — вывести список кандидатов, запросить уточнение
4. **L2:** Загружает полный `SKILL.md` только отобранного скилла

Это даёт экономию 40–60% токенов на этапе диспетчеризации.

## Алгоритм выполнения

### Шаг 0: Приём цели и выбор пайплайна

1. Извлечь `<goal>`.
2. Сопоставить с триггерами скиллов в `.skillsrc` → выбрать пайплайн.
3. Если цель не распознана → задать уточняющий вопрос.

### Шаг 1: Подготовка контекста + базовый Contract Check

1. Прочитать `.skillsrc` → `project`, `paths`, `test`, `methodology`.
2. Собрать входные данные: `<analytics_documentation>`, `<source_code_and_diff>`, `<project_context>`.
3. Если данных нет → задать уточняющие вопросы или перейти в ручной режим.
4. **Базовый Contract Check:** проверить соответствие имён корневых блоков и статус-маркеров по `CONTRACTS.md` §2/§3. При несоответствии → `status = failed`, `contract_mismatch`. (Полный Contract Check с алгоритмом блокировки — в [`SKILL.md`](SKILL.md).)

### Шаг 2: Инициализация пайплайна

1. Установить `execution_id` (UUID), `iteration = 1`, `max_iterations` (по умолчанию 3).
2. Инициализировать `step_results = []`, `warnings = []`.
3. Зафиксировать результат базового Contract Check.

### Шаг 3: Последовательный запуск скиллов

**Для каждого этапа пайплайна:**

1. **Изолировать контекст:** передать ТОЛЬКО входной тег текущего этапа + `.skillsrc` + `<analytics_documentation>` (источник правды).
2. **Запустить скилл** — дождаться результата.
3. **Проверить вердикт** (см. «Таблицу решений» ниже).
4. **Сохранить** результат в `step_results[i]`.
5. **Передать** выходной тег как вход следующего этапа (с учётом правил переименования, см. `CONTRACTS.md` §2.3).

### Шаг 4: Обработка ошибок и Retry

При сбое — см. «Fallback-таблицу». Максимум 2 попытки retry на шаг.

### Шаг 5: Проверка max_iterations

Если `iteration > max_iterations` → `status = retry`, запросить вмешательство пользователя.

### Шаг 6: Генерация отчёта

Записать `docs/to_do/orchestration-report-<TIMESTAMP>.md` со структурой:
- Статус и сводка
- Результат Contract Check
- Результаты каждого шага
- Предупреждения
- Рекомендации (при `failed` / `retry`)

## Таблица решений (реакция на вердикты)

| Вердикт | Реакция |
|---|---|
| `ПРИНЯТО` | **Продолжить** к следующему шагу. Использовать исходный артефакт. |
| `AUTO_FIX_APPLIED` | **Продолжить.** Использовать `<corrected_*>` вместо исходного. В отчёте указать `auto_fix: true`. |
| `ТРЕБУЕТ ДОРАБОТКИ` | **Приостановить.** Вывести `<review_comments>`. Ждать подтверждения пользователя. **Запрещено** автоматически перезапускать тот же скилл на тех же данных. |
| `failed` | **Остановить** пайплайн. `status = failed`. Эскалация пользователю. |
| Любой другой / отсутствует | **Блокировать.** `status = failed`, эскалация. |

### Правило приоритета `<analytics_documentation>`

На протяжении всего пайплайна `<analytics_documentation>` — **источник правды**. При расхождениях:
- **Аналитика > Тест-кейсы** → ТК ошибочны, вернуть на `tc-generator`/`tc-reviewer`.
- **Аналитика > Автотесты** → код ошибочен, вернуть на `tc-to-autotest`.

Оркестратор обязан явно передавать этот приоритет следующему скиллу через пометку в контексте.

## Fallback-таблица (A–J)

> Коды синхронизированы с полной версией [`SKILL.md`](SKILL.md). Детальные prose-описания — в полной версии.

| Код | Ситуация | Реакция |
|---|---|---|
| A | Шаг не вернул ожидаемый корневой блок | Retry шага (до 2 раз). Если не помогло → `status = failed`, эскалация. |
| B | Неизвестный status-маркер (не из `CONTRACTS.md` §3) | **Остановить** пайплайн. Вывести `unknown_status: <mark>`. Эскалация. |
| C | Конфликт версий скилла | Вывести предупреждение `version_mismatch`. Продолжить, если `strict_mode = false`; иначе — стоп. |
| D | Циклическая зависимость | Прервать. `status = failed`. Вывести `cycle_detected`. |
| E | Артефакт не найден | Если вход пользователя → `failed` + запросить. Если результат шага → retry шага. |
| F | Пользователь отменил | **Graceful stop**: сохранить `partial_results` в отчёт. |
| G | Таймаут шага | Retry (1 раз). Затем — `status = failed` + эскалация. |
| H | Несовместимый артефакт (не проходит базовую валидацию) | Стратегия **A** (retry). Затем — `status = failed`. |
| I | Переполнение контекста | Сократить через `<context_summary>` (внешний шаг суммаризации). |
| J | Расхождение в `<automation_matrix>` | Если `strict_mode = true` → стоп. Иначе — продолжить, зафиксировать в отчёте. |

### Правила retry (декларативные)

- Retry только для **транзитных** сбоев (A, G, H, I). Для **логических** (B, D, J в strict-режиме) — retry запрещён.
- Между retry — задержка 5–10 секунд.
- Каждый retry логируется: `step_results[i].retries`.

## Контракт передачи контекста между шагами

**Правило изоляции:** каждый скилл получает ТОЛЬКО:
- Свой входной тег (из контракта входа скилла)
- `.skillsrc` (манифест проекта)
- `<analytics_documentation>` (источник правды — сохраняется на всём протяжении пайплайна)

### Обязательные выходные теги по скиллам

| Скилл | Выходной корневой блок | Принимающий скилл |
|---|---|---|
| `context-marker` | `<analytics_documentation>` + `<source_code_and_diff>` | `tc-generator` |
| `tc-generator` | `<generated_test_cases>` | `tc-reviewer` |
| `tc-reviewer` | `<validation_report>` + (при AUTO_FIX_APPLIED / ТРЕБУЕТ ДОРАБОТКИ) `<corrected_test_cases>` | `tc-to-autotest` |
| `tc-to-autotest` | `<automation_analysis>` + `<automation_matrix>` + файлы | `autotest-reviewer` |
| `autotest-reviewer` | `<autotest_review>` + `<review_verdict>` + (опц.) `<review_comments>` + (при AUTO_FIX_APPLIED) `<corrected_autotest_code>` | (завершение) |

**Правило переименования (`CONTRACTS.md` §2.3):**
- `tc-reviewer` вернул `ПРИНЯТО` → `<generated_test_cases>` переименовать в `<test_cases>` перед передачей в `tc-to-autotest`
- `tc-reviewer` вернул `AUTO_FIX_APPLIED` / `ТРЕБУЕТ ДОРАБОТКИ` → передавать `<corrected_test_cases>` как есть

**Запрещено:** передавать скиллу контекст предыдущих шагов (протоколы, логи, промежуточные результаты других скиллов). Внутренние рассуждения (`<thought>`, `<analysis>`, `<draft>`, `<notes>`) **не передаются**.

## Изоляция контекста

Каждый вызов скилла — изолированная Sub-Agent сессия:
- Скилл не видит историю предыдущих шагов
- Скилл не видит логи оркестратора
- Скилл получает ТОЛЬКО входной тег + `.skillsrc` + `<analytics_documentation>`

Это предотвращает:
- Confabulation на основе чужих результатов
- Разрастание контекста (экономия токенов)
- Каскадные ошибки

> Формальный протокол делегирования и сжатия — в [`shared/sub-agent-compaction.md`](../shared/sub-agent-compaction.md).

## Ограничения (Scope)

**НЕ входит в scope:**
- Выполнение бизнес-логики (только координация)
- Изменение исходного кода
- Принятие бизнес-решений
- Работа без подключённых скиллов

## Зависимости

- `context-marker` — разметка сырых `.md`-файлов аналитики в XML-теги (опциональный препроцессор, вызывается автоматически для SDD-проектов)
- `tc-generator` — генерация тест-кейсов
- `tc-reviewer` — валидация тест-кейсов
- `tc-to-autotest` — генерация автотестов
- `autotest-reviewer` — валидация автотестов
