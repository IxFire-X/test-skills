## Дефекты и что сделать

Порядок выполнения: D1 → D2 → D3 → D6 → D5 → D4 → D7. Каждый пункт начинай с падающего теста, по возможности на настоящих ответах ревьюеров из фикстур, потом исправляй.

### D1. Финализация отклонённого или незавершённого ревью падает
Прогон `d1834358`: агрегат `blocked=true`, `pre_verdict_abort=true`, verdict null. `closure/…/finalization_receipt.json` записан с `valid: true`, но terminal result не опубликован. Драйвер вернул `DRIVER_FAILURE` (`pipeline_driver.py`, обработчик `except (ValueError, OSError, KeyError, TypeError)` в `main`), попытка осталась не терминальной, причина есть только в stdout.
Нужно: любой исход ревью (REJECTED, blocked, abort, UNCHECKED) даёт опубликованный terminal result с понятным `reason_code`; повторный `next` на таком прогоне не падает. Найди точное место исключения: воспроизведи на фикстуре `d1834358`.

### D2. required_checks и UNCHECKED
- Ревьюер обязан адресовать `required_checks` по `scope_id`, но видит только области своей части. В `d1834358` ревьюер хотел проверить TC-B1-001/002, а назвал области своей части, и в проверочную часть попали TC-B1-003/004/007/008. Ревьюер ответил UNCHECKED.
- `review_parts.aggregate_review_parts` не снимает ранний UNCHECKED, даже когда следующая часть ответила на тот же вопрос (`CROSS_CHECK_RESOLVED` в части 4). Агрегат остаётся blocked навсегда.

Нужно:
- `required_checks` адресуются по `case_id` / `requirement_id` (допустимо вместе со `scope_id`), а драйвер сам подбирает области с этими кейсами.
- Поздняя проверочная часть со статусом CHECKED на тот же вопрос закрывает исходный UNCHECKED; связь между ними фиксируется в агрегате.
- UNCHECKED из-за неполного конверта — повод переспросить ревьюера с правильным конвертом, а не повод для REWORK.
- Схемы ответа ревьюера и SKILL обновить согласованно.

### D3. Взрыв проверок после правки ревьюера
`review_parts._required_checks`: для каждого набора правок проверка создаётся на каждую cross-область плана. Если правка к области не относится, срабатывает `related = proposed`, и `_check_part` кладёт каждую проверку в отдельную часть. Итог: 1 правка → 66 частей по 4–5 минут.
Нужно:
- Правки служебных полей, которые не влияют на поведение и оракул (как минимум `management.*`), не требуют перекрёстной перепроверки.
- Для остальных правок — только области, где есть затронутые кейсы или требования (по `related_ids` и pointer).
- Проверки упаковываются в части по байтовому бюджету (`input_byte_budget`), а не по одной.
- Регрессия на фикстуре `3e852e76`: правка `management.components` даёт 0 дополнительных частей. Синтетическая поведенческая правка одного кейса из 12 даёт не больше 11 областей, упакованных в минимальное число частей.

### D6. Лог драйвера и причины простоя
На прогоне `9340016c` между запросом и ответом части ревью прошло 74 минуты — кончился лимит сессии, потом ещё 16 минут после переподключения. Журнал фиксирует только запрос и ответ модели, поэтому ожидание неотличимо от работы.
Нужно: `.driver/driver-log.jsonl` с записями о каждом `next`, `submit`, повторной выдаче открытой задачи (с прошедшим временем), `--failed` с причиной и о любом исключении драйвера (код, сообщение, traceback). Схему событий журнала не меняй. Лог служебный и в дайджесты не входит.

### D5. Ранний стоп на `.skillsrc`
Драйвер останавливается на `.skillsrc` без вопроса, и такой прогон нельзя продолжить, поэтому оркестратор обходит драйвер вручную. Нужно: вопрос уходит задачей `ask_user`, после ответа прогон продолжается тем же `run_id`.

### D4. Цикл доработки внутри драйвера
Сейчас REJECTED сразу даёт терминальный REWORK, и доработку оператор делает вне пайплайна, перезапуская всё. Нужно:
- REJECTED → задача генератору: canonical r1 + находки уровня BLOCKING/WARNING (без INFO) + список затронутых кейсов. Генератор возвращает только изменённые кейсы, а не весь документ.
- Каноническая ревизия r2 с `parent_sha256` от r1, новая сессия ревью для r2 (контракт разрешает одну сессию на ветку или ревизию).
- Ревью r2 инкрементальное: только изменённые кейсы и их cross-области. Покрытие остальных переносится из r1 по совпадению дайджестов входов, с записью в агрегате, что перенесено.
- Не больше одной доработки: после r2 — терминальный REWORK.
- UNCHECKED из-за конверта генератору не отдаётся (см. D2).
- Обнови контракт, схемы, SKILL генератора и `CONTRACTS.md` (он генерируется из `contracts/pipeline.json`).

### D7. Контекст и конверты
- Context-marker выдал в источники `mvnw`, `mvnw.cmd`, `.mvn/wrapper/*`, `run-tests.ps1`, `.gitattributes`. Исключи обёртки сборки и скрипты запуска из контекста генератора и ревьюеров.
- Ревьюер кейсов не видит исходников, на которые ссылается provenance capability (`CAPABILITY_PROVENANCE_NOT_VERIFIABLE_IN_ENVELOPE`). Добавь в конверт эти файлы в пределах бюджета.
- Конверты частей статического ревью не несут глобальных привязок, которых требует шаг 1 SKILL ревьюера (`REVIEW_PART_GLOBAL_BINDINGS_NOT_IN_ENVELOPE`). Либо добавь их, либо измени SKILL так, чтобы части без них не считались неполными.
