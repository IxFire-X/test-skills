  (`gradle-wrapper:selected-symbols-v1`, `gradlew.bat`), `mutation: {enabled: true, threads: 4}`.

Прогон A1 — полный `local-pilot-v1`:

```text
python -m tools.pipeline_driver next --project <проект> --profile local-pilot-v1 --docs docs/realworld-api-spec.md
  --subject "RealWorld (Conduit) API" --model-id claude-sonnet-5-5 --host-cli "Claude Code" --host-cli-version <версия>
  --reviewer-isolation fresh --mutation --analyst-report --suite --max-tasks 4
```

Это первый живой прогон Gradle-пути (адаптер, мутации через init script) — каждое отличие от Maven записать.
Цель — фактическое покрытие условий спецификации, без квоты на число кейсов и без сокращения до happy path.
Расхождение реализации со спецификацией — не повод ослабить проверку: FAIL и карантин с вопросом аналитику.

После конца — сопоставление с эталоном: `coverage-oracle.json` (`id`, `hurl_file`, `request`, `expectation`,
`case_ids`, `assertion_ids`, `method`, `result` PASS/FAIL/NOT_COVERED, доказательство); отдельно — проверки пакета
сверх эталона.

Прогон A2 — `suite-update-v1` на том же проекте, каждый пункт — новый прогон профиля:

1. изменить одно требование в спецификации и реализовать его — обновляются только затронутые кейсы и методы;
2. изменить поведение без требования — карантин с вопросом и черновиком баг-репорта;
3. добавить эндпоинт без требования — вопрос аналитику, кейсы не меняются;
4. ослабить проверку руками (`isEqualTo` → `isNotNull`) и запустить с `--mutation` — падение доли в описании PR,
   метод не тронут;
5. `python -m tools.suite impact --project <проект> --junit <отчёт тестов проекта>` — без модели;
6. дефекты 3 и 4 ревью вживую: прогон набора без JDK в `PATH` и ошибка компиляции в общем коде теста — честная
   остановка, не ложный зелёный и не карантин всего файла.

Для каждого — `pr-description.md`, `suite.patch`, `suite-update-result.json`, части и байты ревью, токены.

- найденные в живых прогонах дефекты пакета — с коммитами и тестами;
- рекомендация по карантину как политике по умолчанию — по данным прогонов (решает пользователь).

## 4. Решения пользователя — не принимай их сам

Запиши каждое как вопрос в разделе «Решения пользователя» плана и продолжай то, что не заблокировано:

- оставить карантин политикой `local-pilot-v1` по умолчанию или вернуть очистку — после живых прогонов;
- переписывать ли историю git ради личных адресов почты и трейлеров `Co-Authored-By` (раздел 1 ревью): это
  force-push, только по явному решению и силами пользователя;
- менять ли CI workflow (JDK в GitHub Actions), если правила репозитория этого не разрешают сессии;
- снятие `implemented_unverified`; порог доли убитых мутантов для `accepted`; коммиты и PR силами пакета.
