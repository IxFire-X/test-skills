# Ревью пайплайна test-skills

Дата: 2026-10-05 · Автор запроса: Babijon · Живая версия документа: https://claude.ai/code/artifact/7bb5a941-961b-4529-be09-ec20df11df54

Ревью относится к рабочему дереву `D:\AI-Projects\test-skills` на 2026-10-05 (HEAD `455ef01` + незакоммиченный WIP bounded-review, Task 6). Номера строк указаны по этому состоянию; после правок сверяйтесь по именам функций.

## Итог

Целостность артефактов в пайплайне продумана, но задачу «подключил к любому SDD-проекту → получил читаемые тест-кейсы → получил по ним автотесты» он в текущем виде не решает. Он слишком тяжёлый, не масштабируется по объёму и жёстко привязан к узкому набору стеков, формату и языку. Сам пакет честно помечен как `implemented_unverified`. В текущем рабочем дереве (незавершённая миграция на ревью по частям) на Linux падают 11 из 446 тестов.

Пять главных проблем:

1. **Процессом управляет LLM, а гарантии самоотчётные.** Минимальный прогон требует от модели-оркестратора 18–40 точных вызовов инструментов, на 64 кейса — порядка 1 800, и примерно 30 путей и дайджестов, которые она держит в памяти. «Изоляцию ревьюера», «независимость батчей» и даже разрешение на запуск кода подтверждает JSON, который пишет сам вызывающий.
2. **Человеческие кейсы и модель автоматизации слиты в один canonical JSON.** На 220 символов человеческого текста шага приходится около 2,3 КБ машинной модели (примерно 10×). Русский язык зашит константой `ru-RU`.
3. **У автотестов нет цикла «скомпилировал → исправил».** Ошибка компиляции или импорта даёт терминальный `UNKNOWN`: файл остаётся в проекте, дочерняя попытка запрещена.
4. **Нет масштабирования ни на генерации, ни на ревью.** Генерация по умолчанию идёт одним батчем на всю спецификацию. Ревью перебирает все пары кейсов: 64 кейса дают около 2 000 cross-проверок, примерно 300 вызовов ревьюера и около 49 МБ входа.
5. **Ядро состояния хрупкое и медленное.** Чтение `status` может безвозвратно испортить журнал. Каждое событие перечитывает весь журнал. `exec` на тривиальном проекте идёт около 70 с при 0,5 с работы самого pytest. Полный тест-сьют на Windows занимает 1 ч 44 мин.

Всего найдено 8 архитектурных проблем, 12 багов высокой критичности и 38 средних и низких. Дальше они описаны с файлами, строками и сценариями воспроизведения.

## Архитектурные ошибки

Главная ошибка — роли распределены наоборот. Последовательностью шагов управляет LLM, а детерминированный код только проверяет её задним числом. При этом проверяет целостность файлов, а не то, что шаг действительно выполнен.

**A1. LLM в роли контроллера.** Порядок шагов, передача путей и дайджестов описаны прозой в `skills/orchestrate/SKILL.md` (347 строк плотного RU/EN-жаргона). Для контекста, генерации, сборки, материализации и финализации нет готовых команд вида python -m tools.…, поэтому модель-оркестратор пишет для них ad-hoc Python к внутренним функциям. В итоге у LLM не минимум функций, а больше, чем нужно: она ведёт порядок шагов и носит пути между вызовами. Артефакты неизменяемы, так что любая ошибка порядка закрывает попытку. Нужен драйвер `next`: код сам решает следующий шаг и выдаёт модели только «сгенерируй X из входа Y, ответ положи сюда». Тогда у модели остаются две команды — next и submit — и сама генерация содержимого.

**A2. «Гарантии» на самоотчёте.**

- Изоляция ревьюера: `evidence_digest` — хеш остальных полей той же записи (`pilot_state.py:3475–3478`), а `fresh_context: true` пишет оркестратор. Тесты строят такую «verified»-изоляцию в три строки (`tests/helpers.py:103–106`). Оценку ревьюера (`submit-part`) тоже передаёт оркестратор, и ничто не связывает её с реальным ответом модели.
- Разбиение на батчи включается флагом `independence_proven: true` от вызывающего (`batch_assembly.py:89`).
- `run_pipeline scan` по умолчанию сам создаёт run с `execution_requested: true` (`run_pipeline.py:276`, дефолт `--profile local-pilot-v1`). «Явное разрешение пользователя» на деле сводится к дефолту флага.

SHA-256, readback и append-only защищают от порчи файлов, но не от главного риска: модель пропустила или выдумала шаг. В вашем эксперименте с `codex exec --ephemeral` настоящие thread ID собирал внешний скрипт, а не пайплайн.

**A3. Кейсы и автоматизация слиты в одну модель.** Каждый неручной шаг обязан сразу иметь operation, типизированные inputs/outputs, assertions на каждое ожидание и capabilities с provenance. Человеческий текст валидируется против этих привязок. Следствия:

- генератор кейсов вынужден заранее проектировать автоматизацию;
- поддерживаются только два вида операций: `http` (только JSON) и `project_action`;
- единственный путь к «просто человеческим кейсам» — пометить всё `manual_only`, и тогда автотестов будет 0.

Для вашей цели нужны два слоя. Первый — лёгкий кейс: цель, предусловия, шаги, ожидаемое, ссылки на требования. Второй — спецификация автоматизации, которая строится на этапе автотестов.

**A4. Нет обратной связи от компилятора и раннера.** Статическое ревью идёт до первой компиляции, дальше есть ровно один запуск. Правило «не исправлять тест после FAIL» верно для падения продуктовой проверки. Но оно смешано с ошибками самого теста: компиляция, импорт, фикстуры, конфигурация. Рабочая практика для LLM-тестов такая: сгенерировать → скомпилировать или собрать → запустить → классифицировать падение → ограниченно исправлять только ошибки теста.

**A5. Объём не масштабируется ни на входе, ни на выходе.**

- **Генерация.** `plan_batches` по умолчанию создаёт один батч (`batch_assembly.py:112–135`). Для объёма Petclinic это один вызов модели, который должен выдать 0,3–0,6 МБ JSON с дайджестами.
- **Ревью.** Проверяются все пары кейсов (`review_parts.py:349–357`, в коде прямо написано «quadratic pairs»). Каждая локальная область тащит все контекстные файлы целиком. Одно исправление добавляет ещё по проверке на каждую пару.

Ваш план bounded-review ставит цель «задачи больше примерно 260 тыс. токенов», но эта схема её не достигает:

| Кейсов / шагов | Cross-проверок | Вызовов ревьюера | Вход ревьюеров |
| --- | --- | --- | --- |
| 16 / 80 | 120 | 20 | 3,3 МБ |
| 32 / 150 | 496 | 76 | 12,5 МБ |
| 64 / 300 | 2 016 | 297 | 49 МБ |
| 64 / 300 + одно исправление | 2 016 + 2 016 | около 2 300 | около 100 МБ |

Симуляция на реальном `review_parts.py`: бюджет части 200 КБ, контекст 20 КБ. Уникального контента в снимке из 64 кейсов всего 125 КБ, то есть ревьюеры получают его около 356 раз.

**A6. Сложность несоразмерна задаче.**

- В `tools/` 24 тыс. строк Python: из них 10,4 тыс. занимают состояние, квитанции, трассировка, финализация и релиз, и только 4,5 тыс. — сама модель кейсов и проекции.
- 47 JSON-схем, 56 типов артефактов, 21 тип событий.
- Примерно 110 тыс. символов инструкций в SKILL и references, 446 тестов (11,6 тыс. строк).
- `pilot_state.py` — 5 476 строк, 151 функция, 70 локальных импортов из-за циклических зависимостей.
- `contracts/pipeline.json` кодом не читается: профили, события и приоритет exit-кодов продублированы строками в `pilot_state.py` и `contract_check.py`.

**A7. Режим «только кейсы» не может завершиться успехом.** `cases-only-v1` — один из двух ваших основных сценариев. Он всегда даёт `accepted=false` и exit 1 (`pilot_state.py:3941–3943`, `5467–5468`), даже при FATAL или `FINALIZATION_INVALID`, тогда как в local-pilot такие случаи дают exit 2. CI не отличит успешные кейсы от сломанного прогона, а 11 предикатов acceptance для cases-only в контракте никогда не срабатывают.

**A8. Пакет нельзя настроить под проект.** `release/manifest.json` хеширует каждый байт `skills/`, `tools/`, `contracts/`, `schemas/` и `evals/`. Добавленный skill, правка формулировки или CRLF дают `doctor = NOT_RUNNABLE`. Переносимому пакету нужны точки расширения вне подписанного ядра: стиль кейсов, язык, адаптеры, форматы экспорта.

## Баги высокой критичности

Двенадцать багов ниже либо ломают прогон безвозвратно, либо дают неверный результат на обычных проектах. Одиннадцать из них подтверждены запуском на копии пакета, исключение отмечено.

**B1. Чтение статуса удаляет чужое событие** (`pilot_state.py:582–617`, `922–932`). `_events()` считает любой pending-маркер остатком сбоя и удаляет его вместе с файлом события, а межпроцессной блокировки нет. Если `run_pipeline status` (SKILL сам просит его опрашивать) попадёт между записью события и заменой `events.jsonl`, журнал навсегда становится невалидным. Подтверждено запуском.

**B2. Второй писатель оставляет маркер и ломает run** (`pilot_state.py:909–957`). Писатель с устаревшим состоянием выходит через `_PublicationUnknown`, не удалив свой pending-маркер. Следующее чтение видит несовпадение дайджеста, и run больше не читается. Подтверждено запуском.

**B3. Побочные файлы сборки превращают PASS в UNKNOWN** (`run_pipeline.py:938–943`, `run_tests.py:1478–1484`, `project_inventory.py:35–38`). После запуска всё дерево сравнивается с baseline, а инвентарь игнорирует `.gitignore`. `coverage.xml` из conftest, файлы `.gradle/*` после первого запуска Gradle, логи и `.idea/workspace.xml` дают `BASELINE_DRIFT` → `UNKNOWN`, сгенерированные файлы остаются в проекте. Подтверждено запуском (pytest + coverage.xml, реальный Gradle).

**B4. Некомпилируемый тест остаётся в проекте навсегда** (`run_tests.py:1476–1495`, `pilot_state.py:1212–1213`). Ошибка компиляции или импорта даёт `UNKNOWN`, `UNKNOWN` запрещает cleanup, а дочерняя попытка требует `PROCESS_STOPPED`, которого нет. В Java файл в `src/test/java` ломает все последующие `mvn test` и сборки пользователя, а новый run не может занять тот же путь. Подтверждено запуском (ImportError в pytest).

**B5. Многомодульные сборки запускаются неверно** (`execution_adapters.py:156–160`, `init_skillsrc.py:133–163`).

- **Gradle:** `gradlew test --tests X` из корня мультипроекта запускает тесты всех подпроектов. Те, где теста нет, падают с «No tests found», exit 1 превращает PASS в `UNKNOWN`. Подтверждено на Gradle 8.14.3.
- **Maven:** подмодуль без своего `mvnw` запускается системным `mvn` без реактора, и соседние модули берутся из `~/.m2`: их нет или они устарели. Вывод по коду, запуском не проверялось.

**B6. Два валидных фрагмента не собираются в документ** (`batch_assembly.py:299, 314`). Capabilities склеиваются в порядке батчей, а валидатор требует порядок по code point. `CAP-z-payment` в первом батче и `CAP-a-refund` во втором дают `CANONICAL_CAPABILITY_ORDER`. Общая capability должна совпадать побайтно в независимых вызовах модели, иначе `BATCH_ID_CONFLICT`. Подтверждено запуском.

**B7. Один blocker убивает всю автоматизацию** (`automation_validation.py:323–330`). Если в любом шаге документа есть blocker, артефакт обязан быть `BLOCKED` с нулём файлов. Из 64 кейсов с одним неизвестным полем получится 0 автотестов. Подтверждено запуском.

**B8. Zephyr CSV выгружает машинную модель вместо человеческого текста** (`test_case_projections.py:385–406`, `583–585`). Профиль по умолчанию v4 пишет в Test Data «`HTTP: POST /owners/{ownerId}/pets; базовый URL: environment:BASE_URL`», в Expected — «`Проверка: http_status equals 201`». Человеческое поле `test_data` в CSV не попадает. Это противоречит собственным human scenario rules. Подтверждено запуском.

**B9. Эвристика секретов скрывает обычный код и спеки** (`project_inventory.py:47–49`, `275`, `525–549`). По имени целиком исключаются `password_reset.py`, `token_utils.py`, `private_messages.py`, `docs/password-reset.md`, `api-key-rotation.md`. По содержимому — строки `password = request.form.get("password")` и `token = client.post("/login")`. Модель не видит спецификации аутентификации, а local-pilot закрывается `NOT_RUNNABLE/BASELINE_INCOMPLETE`. Подтверждено запуском.

**B10. Сбой одного вызова ревьюера обрывает всё ревью** (`pilot_state.py:3683`, `3731`). `open-part` не даёт переоткрыть часть, `transport_attempts` разрешён только 1. Честный путь — `block-part`, и тогда ревью заканчивается `ABORTED/REWORK`: сетевой таймаут записан как дефект содержания. При примерно 300 частях и 1% сбоев до конца дойдёт около 5% ревью. Подтверждено симуляцией.

**B11. Автообнаружение модулей не справляется с обычными структурами** (`discover_project.py:128–134`, `173`, `init_skillsrc.py:657–666`).

- Python без `src/` (стиль Django), Go и Maven с POM-only модулем `bom/` получают `needs_source`.
- Лишний `docs/requirements.txt` становится вторым модулем.
- `init` всегда возвращает `needs_input`, даже когда передан единственный предложенный ответ, и `.skillsrc` приходится писать руками.

Подтверждено запуском.

**B12. Результат валидации зависит от версии Python** (`canonical_document.py:209`). Текст статуса сверяется с `HTTPStatus.phrase`, а фразы изменились в 3.13: 422 — «Unprocessable Entity» на 3.11/3.12 и «Unprocessable Content» на 3.13. То же с 413 и 416. Один и тот же документ валиден на одном интерпретаторе и отклоняется на другом, включая `--verify-only`. Подтверждено запуском на трёх версиях.

## Баги средней и низкой критичности

По отдельности эти баги прогон не ломают, но часто дают `UNKNOWN` или вводящую в заблуждение диагностику. Сгруппированы по областям.

**Ядро состояния (`pilot_state.py`)**

- Попытка не возвращается в `ACTIVE` после `WAITING_FOR_MODEL` (711–722): `status` показывает «ждёт» у работающей попытки.
- Прерванный Ctrl-C `create_attempt` (1240–1253) оставляет незафиксированный файл попытки, после чего падают все чтения.
- Дедупликация событий игнорирует позицию (825–826, 889): повторный `INVENTORY_READY` возвращает старое событие, второй законный `WAITING_FOR_MODEL` проглатывается.
- Нет fsync каталогов: после отключения питания четырёхшаговый коммит может рассинхронизироваться.
- Windows: замена журнала падает при любом открытом дескрипторе (антивирус, параллельный `status`) без повтора. Временный путь внутри проекта доходит до 207 символов, поэтому проект глубже примерно 51 символа превышает MAX\_PATH без LongPathsEnabled.
- `_validate_authorization` (272) на отсутствующий ключ бросает `KeyError` вместо `ValueError`. Конфликт содержимого сообщается как «unsafe path» (183–184).
- При наличии `.git` и отсутствии `git` в PATH `create_run` падает с `FileNotFoundError`. Вызов git (4627) идёт без таймаута и с `-c safe.directory=<project>`, то есть отключает защиту git от чужих репозиториев (CVE-2022-24765).
- При повторном чтении terminal-result, closure и disposition схемой не проверяются (198–204 против 146–157).

**Исполнение (`run_tests.py`, `execution_adapters.py`)**

- Вложенный pytest-модуль с конфигом в родительском `pyproject.toml` даёт другой classname, и PASS становится `UNKNOWN` (751–757).
- `addopts = -m smoke` или `PYTEST_ADDOPTS` дают корректному тесту `FAIL/NO_TESTS_COLLECTED`, и файл удаляется. В Maven/Gradle тот же случай даёт `UNKNOWN`.
- На POSIX доказательство остановки ложное для Gradle daemon: он делает `setsid` и продолжает сборку. На Windows доказательство не выдаётся вообще (558–577, 662–666).
- `OSError` при запуске процесса классифицируется как `UNKNOWN`, а не `NOT_RUNNABLE` (549–552). Пример: `.skillsrc` с Linux-путём `mvnw` на Windows даёт WinError 193.
- Исключения при сохранении артефактов после запуска не перехватываются (1521–1525). Результат теряется, следующий `exec` пишет `EXECUTION_RESULT_LOST`.
- Ненулевой exit при полностью зелёном отчёте даёт `UNKNOWN` с меткой `JUNIT_INVALID`, а `JUNIT_MISSING` недостижим. Ошибку компиляции, coverage-gate и отсутствие отчёта не различить.
- Хранятся только последние 2 000 байт stdout+stderr в UTF-8 (534). На Windows вывод в cp1251/cp866 превращается в «�», а хвост вывода Maven занят служебным текстом.
- Тестовый процесс наследует весь `os.environ` (542): `PYTEST_ADDOPTS`, `MAVEN_OPTS`, `JAVA_TOOL_OPTIONS`, API-ключи. Это не входит в baseline, а ключи доступны коду, написанному LLM.
- Maven всегда вызывается с `-Pdefault` (в Maven 4 отсутствующий профиль — ошибка) и без `-B -ntp`.
- `python -m tools.run_tests` расходует единственный запуск попытки, но не публикует receipt.
- `company_runner.py`: статусы сопоставлены иначе, чем в валидаторе, имена профилей ему неизвестны. Модуль никуда не подключён и не покрыт тестами, фактически мёртвый код.

**Модель кейсов и проекции**

- Blocker на `/inputs` допускается только при несвязанном path-плейсхолдере (`canonical_document.py:455–496`). Неизвестное поле тела POST заблокировать нельзя, модели приходится удалять проверки.
- Литерал никогда не совместим с именованным типом: `LocalDate` и `"2024-01-01"` дают `SEMANTIC_CAPABILITY_TYPE_MISMATCH` (448–449, 609).
- При сборке возвращается только первый код ошибки без пути (`batch_assembly.py:321–323`), а фрагмент неизменяем: модели нечего исправлять.
- Регулярки в assertions не разбираются при валидации (612–613). `\d+` принимается, но падает в `portable-regex-v1`; `^…$` там литералы; `[А-Я]` — ошибка.
- HTTP-шаг без тела требует буквально «Тело запроса отсутствует.» (144). Нелитеральные path-параметры остаются в HTML как `{ownerId}`, и ручному тестировщику нечего ввести.
- Markdown-проекция: в code fence попадает JSON только последнего ожидания, `1.` и `---` не экранируются. U+2028 в строке JSON ломает ячейку HTML.
- XML-экспорт: `sha256` без префикса `sha256:`. Управляющие символы проходят валидацию и падают только на экспорте.

**Спецификации и контекст (`build_context.py`, `project_inventory.py`)**

- OpenSpec распознаётся только в корневом `openspec/`. В `svc/openspec/` дельты не применяются: REMOVED выживает, требование дублируется, из одного требования получается 9 строк.
- `###Requirement:` без пробела склеивается с предыдущим требованием. `## Added Requirements` или BOM дают ложную ошибку «no delta operation».
- `SREQ`-ID назначаются по сортировке текста, а не по порядку документа, поэтому новый раздел перенумеровывает всё после него.
- В обычном Markdown каждый заголовок, включая «# Владельцы» и «Глоссарий», становится требованием, которое нужно покрыть кейсом.
- Один файл больше 256 КБ (например, `openapi.json` на 379 КБ) даёт `CONTEXT_SELECTION_INVALID` для всего скана без деталей, даже в cases-only.
- Фиксированные имена `build`, `generated`, `coverage` выбрасывают из контекста настоящие пакеты с такими именами.

**Конфигурация и инструменты**

- `.skillsrc` привязан к ОС (`.venv/bin/python` или `Scripts/python.exe`, абсолютный путь `mvn`): закоммиченный на Linux ломает Windows. Для Python-модуля нужен `.venv` именно в корне модуля.
- Создание `.skillsrc` — проверка и `os.replace` без эксклюзивного создания (`init_skillsrc.py:419–441`). Логика слияния и миграции v2 недостижима.
- `orchestrate_test_case_revision` скрывает сообщения argparse: любая ошибка флага превращается в «Orchestration failed.».
- `ci_gate` без pytest возвращает 1 вместо 2, а его дочерние процессы запускаются без таймаута.
- `scan_project._java_imported_sources` обходит весь репозиторий на каждый импорт и минует фильтр секретов. В пайплайне он не используется.
- Тест `test_run_and_module_reparse_components_never_escape` читает вывод `cmd.exe mklink` как UTF-8 и на русской Windows даёт `UnicodeDecodeError` (видно в вашем логе `reliability-full-20261005-r2`).

## Что сделано хорошо

Идеи качества тестов в пакете сильные, и их стоит сохранить при любой переделке.

- **Требование главнее текущего поведения кода.** Дефект приложения остаётся FAIL, а не подгоняется под зелёный отчёт. На Petclinic так нашли настоящий дефект V05 (визит с пустой датой сохраняется).
- **Явные пробелы вместо выдумок.** Неопределённый ожидаемый результат становится вопросом к человеку, а не придуманным 403.
- **Правила ревью автотестов.** Запрещены тавтологические проверки, мок тестируемого субъекта, skip/xfail и sleep. Ревьюер отвечает на три вопроса о границе приложения, реальных компонентах и наблюдаемом результате.
- **Безопасная работа с проектом.** Существующие файлы не трогаются. Cleanup удаляет только побайтно неизменённые собственные файлы. Запуск идёт через закрытые адаптеры без shell-строк и только для отревьюенных тестов.
- **Независимые оси результата.** Completion, verification и coverage не смешиваются в один статус: `COMPLETE + FAIL` честно различает «процесс завершён» и «продукт не прошёл».
- **Атомарная публикация и append-only история.** Для аудита это правильная модель, ей не хватает только блокировки и кэша.
- **Экранирование.** HTML экранируется полностью, CSV защищён от формул (`=+-@`).
- **Честность статуса.** `implemented_unverified` и границы пилота описаны прямо. Контрольные ревью на живой модели с дефектным и исправленным наборами дали одинаковый вердикт в обоих повторах — хорошая методика.

## Рекомендации и план исправлений

Сначала стоит закрыть блокеры в текущем коде, затем перестроить архитектуру вокруг детерминированного драйвера и двух слоёв артефактов.

Целевая архитектура (схема из живого документа в текстовом виде):

```text
Детерминированный драйвер на Python — сам выбирает следующий шаг, хранит журнал, проверяет ответы LLM по схемам
│
├── Слой 1 · Тест-кейсы, без запуска кода
│     Адаптеры спецификаций (OpenSpec, Markdown, Gherkin, OpenAPI)
│       → Нормализованные требования (стабильные ID, источник, группы по фиче)
│       → LLM: генерация кейсов (по группам требований; язык — параметр)
│       → LLM: ревью кейсов (по группам; полноту покрытия считает код) ──┐ принятые кейсы
│       → Экспорт кейсов (Markdown, HTML, CSV, плагины TMS)               │
│                                                                         ▼
└── Слой 2 · Автотесты по принятым кейсам
      LLM: код автотестов (pytest, JUnit, Jest… через адаптеры)  ◄──┐
        → Шлюз компиляции (test-compile, --collect-only)            │ ≤ 2 исправления,
        → Запуск отобранных тестов (закрытый адаптер)               │ только ошибки теста
        → Классификация падений: ошибка теста → исправление ────────┘
                                 дефект → FAIL, среда → UNKNOWN
        → Отчёт и трассировка (требование → кейс → тест → итог)
```

Последовательность шагов, журнал и проверки живут в коде, а модель получает одну задачу за раз. Кейсы — самостоятельный результат первого слоя. Автотесты строятся по принятым кейсам и проходят компиляцию до запуска. Пунктир — ограниченный цикл исправления только для ошибок самого теста; дефект продукта идёт в отчёт как FAIL.

### Первая очередь: блокеры

1. Межпроцессная блокировка run, чтение без побочных эффектов, журнал через `O_APPEND` с кэшем состояния (B1, B2, производительность).
2. Шлюз компиляции или сбора до запуска. Ошибки самого теста → `NOT_RUNNABLE/REWORK` с очисткой и правом на r2 (B4, A4).
3. Проверка дрейфа после запуска — только по входам baseline; учитывать `.gitignore`, исключить `.gradle`, coverage, файлы IDE (B3).
4. Секреты искать по содержимому и маскировать, а не исключать файлы по имени (B9).
5. Запуск: Gradle `:path:test`, Maven `-pl <module> -am` из корня реактора, pytest `--rootdir` (B5).
6. Сортировка capabilities при сборке, все диагностики с путями, инструмент `normalize` для дайджестов и порядка (B6).
7. Blocker блокирует кейс, а не весь документ (B7).
8. Собственная таблица HTTP reason phrase вместо `HTTPStatus` (B12).
9. CSV v4 — только человеческие поля (B8).
10. Синхронизировать HOW-IT-WORKS и USAGE с ревью по частям, дочинить тесты Task 6.

### Вторая очередь: архитектура

11. Драйвер `python -m tools.pipeline next --run <id>` возвращает JSON-задачу: `llm` (skill, вход, путь ответа), `ask_user` или `done`. Модель больше не держит в голове 30 путей (A1).
12. Разделить canonical на лёгкий кейс (цель, предусловия, шаги, ожидаемое, требования; язык — параметр) и спецификацию автоматизации, которую строит `tc-to-autotest` (A3).
13. Генерация по группам требований по умолчанию; группа — capability OpenSpec или раздел документа (A5).
14. Ревью по группам: cross-проверки только между кейсами с общими требованиями или операциями, входы без дублей, матрицу покрытия считает код (A5).
