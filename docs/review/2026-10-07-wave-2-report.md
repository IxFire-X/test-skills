## Решение гейта

**Гейт пройден.** Пройдены W2-Р1–Р3, Р5, Р7–Р9, Р11, Р13–Р15; по Р4, Р6, Р10 и Р12 цифры в пределах
порогов (таблица ниже).

Две оговорки, обе из-за того, что CLI модели на машине не залогинен, а пользователь решил обойтись
без него («сделай тут просто»):

- **Р10.** Живой прогон step5 сделан силами сессии: все роли — свежие субагенты Sonnet. Процессы
  драйвера (`--review-runner process`, `run --runner process`) проверены фальшивым CLI, а не
  настоящим `claude -p`.
- **Р12.** Процесс против субагента замерен в сессии: субагент получал ровно stdin раннера. Цена
  системного промпта настоящего CLI не измерена.

Обе оговорки снимает живой прогон Petclinic по инструкции
`docs/review/2026-10-07-petclinic-live-run.md`: там части ревью — процессы драйвера, у каждой
квитанция с токенами, ожидается `isolation_evidence: DRIVER_PROCESS`.

Поведение по умолчанию не менялось: мутации, раннер процессов, отчёт для аналитиков и
`--require-driver-isolation` включаются только опциями. Статус `implemented_unverified` сохраняется,
порог доли убитых мутантов для `accepted` не введён — это решения пользователя.

## Что сделано

**Поправки к контракту** (`docs/superpowers/specs/2026-10-07-pilot-contract-amendments.md`, раздел
`contract_amendments` контракта): A1 — §1 п. 2, драйвер может запускать процесс CLI модели;
A2 — §1 п. 5, закреплённые по SHA-256 jar PIT разрешаются Maven проекта по согласию; A3 — §17,
необязательный этап `MUTATION` между трассой исполнения и решением о сохранении. Всё — опциями;
в силе остаются запреты на копии проекта, правку кода продукта, зависимостей, сборки и секретов,
чужих и отредактированных людьми файлов, коммиты, push, PR и задачи CI. Замороженные реестры
контракта не тронуты: новое — в `optional_lifecycle_stages`, `optional_result_axes`,
`optional_skills`, `optional_stage_registry`, `optional_schema_registry`,
`optional_artifact_registry`, `mutation_tooling`, `model_runner`; `contract_check` сверяет их
точно и проверяет, что `MUTATION` стоит между двумя соседними замороженными стадиями.

**M. Мутации** (`tools/mutation.py`, `tools/mutation_tools.json`, `tools/strength_report.py`).
- Включение: `.skillsrc` `mutation.enabled: true` (схема `.skillsrc` 5.1.0; файлы 5.0.0 валидны)
  **и** `next --mutation` (`mutation_requested` в разрешении прогона, только `local-pilot-v1`).
- PIT 1.30.0 + `pitest-junit5-plugin` 1.2.3 из командной строки. Замыкание (15 jar) Maven проекта
  разрешает по временному POM в каталоге прогона (`maven-dependency-plugin:3.8.1`); SHA-256 каждого
  jar сверяется с пином (SHA-1 пинов сверены с Maven Central); лишний jar → `MUTATION_TOOL_UNPINNED`,
  подменённый → `MUTATION_TOOL_DIGEST_MISMATCH`. `junit-platform-launcher` — версии Platform проекта.
- Classpath проекта — `dependency:build-classpath` (`-pl` для реактора; Gradle — init script из
  каталога прогона) в файл, `--classPathFile`; `--targetTests` — классы сгенерированных символов;
  `--targetClasses` — пакеты файлов продукта из provenance возможностей (или `mutation.target_classes`);
  упавшие методы исключены (`--skipFailingTests` + `--includedTestMethods` прошедших); XML с полной
  матрицей, `DEFAULTS`, UTF-8, потоки и общий таймаут из `.skillsrc`.
- Этап — в `finalize_durable_execution_attempt` после пары трассы, до решения о диспозициях; после
  решения квитанция только читается. Дайджест всего дерева проекта (кроме `.pilot-runs`, `.git`) до и
  после; изменение → `MUTATION_PROJECT_CHANGED`. Любая остановка — статус квитанции с причиной.
- Итог: квитанция `mutation-receipt` (счётчики без дробей, XML — в `artifacts/` прогона), ось
  `test_strength` в терминальном результате и сводке драйвера, `test-strength.json`/`.md` рядом с
  проекциями. Атрибуция — метод (дескриптор JUnit Platform) → символ → кейс → CREQ → SREQ.

**T. Разбор выживших** (`skills/mutation-triage`, `tools/mutation_triage.py`, `tools/pipeline_driver_strength.py`).
Группы по методу и строке продукта, первые 30 (`triage_limit`) — задачам `mutation-triage` после
терминального результата (журнал попытки после `EXECUTION_STARTED` событий модели не принимает, а на
результат попытки разбор не влияет). Вход — строки продукта с соседями из маскированного контекста
попытки, мутации, кейсы в виде для автотестов, CREQ/SREQ с текстом, срезы методов теста; ответ — одно
решение на группу со ссылками на якоря задачи; драйвер проверяет: все группы по порядку, ссылки —
якоря задачи, своя строка группы, кейс/шаг/требование группы. `TEST_GAP` → `proposals.json`,
`SPEC_GAP` → отчёт для аналитиков; кейсы и тесты не меняются.

**Q. Отчёт для аналитиков** (`tools/analyst_report.py`, `tools/pipeline_driver_analyst.py`).
Опция `next --analyst-report`. Источники: `requirement_gaps` у context-marker (5.1.0) и старый текст
`warnings`, `analyst_question` у находок compact (ответ 2.1.0 — только с вопросом), `SPEC_GAP`
разбора. Склейка по SREQ (CREQ приводится к SREQ) и нормализованному вопросу; у пункта — все
источники; детерминированные `analyst-report.json`/`.md`; `python -m tools.analyst_report export`
печатает комментарий для change OpenSpec (в `openspec/` пакет не пишет).

**A2. Ревью процессами драйвера** (`tools/model_runner.py`, `tools/pipeline_driver_runner.py`).
`next … --review-runner process`: граница части объявляет `isolation_evidence: DRIVER_PROCESS` и
раннер, процесс CLI запускается отсоединённым (оболочка с замком, атомарный `result.json`, временный
cwd вне проекта, вход целиком в stdin, `--tools ""` у `claude`, `--sandbox read-only` у `codex`),
`next` сразу возвращает `wait`, следующий `next` собирает. Ответ проверяется как при `submit`;
квитанция процесса части (`review-part-process-*`): дайджест команды без секретов, CLI, модель из
вывода CLI, время, код выхода, сессия, дайджест stdout, токены, `user_settings_loaded`. Сбой —
новый процесс, до трёх, затем `REVIEW_TRANSPORT_FAILED`; 429 — пауза. `isolation_evidence`
(`DRIVER_PROCESS`/`HOST_DECLARED`/`NONE`) выводится из долговременных квитанций, не заявляется;
`--require-driver-isolation` → `REVIEW_ISOLATION_UNVERIFIED`. `.skillsrc` `review_runner` выбирает
только пресет, модели по ролям, `max_parallel`, `timeout_seconds`; свой шаблон — только флагом.

**Без оркестратора** (`tools/pipeline_driver_run.py`): `python -m tools.pipeline_driver run --runner process`
— все задачи модели раннеру, ответы на `ask_user` из `--answer`/`--answers`, без ответа — код 3;
отклонённый ответ — новый процесс с ошибками (до 3), неуместившийся ответ — `RUNNER_TASK_FAILED`
с причиной.

**Найденный попутно дефект.** Граница части, которую журнал ревьюера заблокировал после третьего
сбоя, не проходила проверку при чтении, и финализация такой попытки падала («undeclared or blocked
review part»). Исправлено и закрыто тестом (`test_three_failures_block_the_part_as_transport`).

## Процессы против субагентов (W2-Р12)

`claude.exe` desktop-приложения вне своей сессии отвечает «Not logged in», других учётных данных CLI на
машине нет; пользователь решил обойтись без внешнего CLI и замерить в сессии. Процесс имитирован свежим
субагентом Sonnet: он получает ровно тот stdin, который собрал бы раннер (`tools.model_runner.compose_input`:
производственный SKILL, инструкции задачи, схема ответа, часть), читает его, пишет JSON и не проверяет себя;
ответ проверяет производственный валидатор (`run_eval.py check`), как это делает драйвер. Рядом — режим
субагента волны 1: SKILL, вход и схема по путям из `tasks.json`, до трёх самопроверок. Части — из
производственного планировщика (`compact-v1`), по одному прогону на ячейку.

| Конверт | Режим | Вход | Токены | Время | Попытки | Заложенные дефекты |
| --- | --- | --- | --- | --- | --- | --- |
| E1 step5, ревью кейсов | процесс | stdin 69 001 байт | 84 370 | 68,5 с | 1 | 6/6 (5 BLOCKING, 1 WARNING) |
| E1 step5, ревью кейсов | субагент | 3 файла | 85 698 | 75,6 с | 1 (1 самопроверка) | 6/6 (5 BLOCKING, 1 WARNING) |
| E3 step5, ревью автотестов | процесс | stdin 64 151 байт | 83 897 | 73,4 с | 1 | 6/6 (6 BLOCKING) |
| E3 step5, ревью автотестов | субагент | 3 файла | 83 096 | 69,2 с | 1 (1 самопроверка) | 6/6 (6 BLOCKING) |

Разница токенов между режимами — не больше 1,6 %, времени — в пределах разброса одного прогона; качество
одинаковое, совпадает с волной 1 (E5: 81 и 83 тыс. токенов, 0,8 мин). Процесс не дороже субагента по форме
входа. Оговорка: оба режима несут одну и ту же обвязку субагента, а у настоящего `claude -p --tools ""` свой
системный промпт и пользовательские настройки (`user_settings_loaded`) — их цену покажут квитанции
`review-part-process-*` живого прогона Petclinic. У E1-процесса чтение вернуло 815 строк из 992, агент
дочитал вторым вызовом; настоящий процесс получает stdin целиком. Данные:

## Разбор вариантов Python-мутаций

Граница контракта: этап не меняет файлов проекта (дайджест дерева до = после), не создаёт копий проекта, worktree и venv, работает на Windows без WSL, запускает только прошедшие сгенерированные тесты и даёт полную матрицу «мутант → тест».

| Вариант | Как мутирует | Совместим с контрактом | Почему |
| --- | --- | --- | --- |
| mutmut 3 | копия исходников в `mutants/` внутри проекта, запуск через `fork` | нет | каталог в проекте меняет инвентарь; `fork` нет на Windows (только WSL) |
| mutmut 2 | правит исходный файл на месте и возвращает | нет | меняет код продукта; при обрыве процесса файл остаётся мутированным |
| cosmic-ray | локальный исполнитель правит файлы на месте, распределённый — работает в клонах | нет | правка на месте или копия проекта |
| mutatest | пишет мутированный байткод в `__pycache__` | возможно, с оговорками | при `PYTHONPYCACHEPREFIX` кэш уходит в каталог прогона и дерево проекта не меняется; проект давно не обновлялся, поддержку Python 3.12 и pytest 8 нужно проверить |
| свой импорт-хук | мутирует AST в памяти загрузчиком модулей (`sys.meta_path`) и гоняет pytest в отдельном процессе на мутант; `sys.dont_write_bytecode` | да | файлы не пишутся, Windows поддерживается, матрицу даёт сам раннер (`--junitxml` на мутант); объём работ — свой набор мутаторов и таймауты |

Предложение на волну 4+: импорт-хук пакета с закреплённым набором мутаторов (границы сравнений, отрицание условий, возвраты, удаление вызовов) и тем же контрактом квитанции; mutatest с `PYTHONPYCACHEPREFIX` — запасной вариант после проверки на Python 3.12.
