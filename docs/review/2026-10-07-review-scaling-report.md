## Что сделано

**R1. Ревью кейсов compact-v1.**
- Режим выбирается параметром `--review-mode` и записывается в `config.json` и snapshot ревью. Читатели берут правила из замороженного плана (`tools/review_modes.py`).
- Проекция канона (`tools/review_projection.py`) — детерминированный текст. Каждый ID канона — ровно один якорь `[ID]`. Продолжение текстового поля пишется с префиксом `| `, поэтому документ не может подделать якорь. Проекция привязана к дайджесту канона и лежит в snapshot. Контракт (`reviewer_session_contract.modes`) разрешает её как вход модели, HTML, Markdown и CSV по-прежнему не входы.
- Упаковка (`tools/review_compact.py`): документ помещается целиком — одна часть; иначе блоки с границей по хешу `case_id` или по пределу размера, а части — пары блоков. У кейса одна домашняя область `local-<case>`, в каждой части есть `cross`. Исходник (документы дословно с номерами строк, SREQ → CREQ, возможности, файлы проекта) идёт в первую часть, иначе — в свои части, при необходимости по строкам. Кейс больше части — явная заблокированная часть.
- Ответ — схема `review-part-output-compact` 2.0.0:
  - строка покрытия: 1–3 ссылки на якоря части, заметка до 200 символов;
  - находки: до 600 символов, INFO не больше 5;
  - правки по `target_id` и полю из закрытого словаря;
  - решение по каждому подозрению линтера.
  
  Драйвер проверяет ссылки, подозрения, ID и правки до записи и возвращает `status: rejected` с кодом.
- Правка переводится в один JSON pointer со сверкой `before`. `management.*` не перепроверяется, остальное — только в частях с исправленным кейсом. При доработке область переносится по отпечатку проекции кейса и политике ревью: роль, дайджесты SKILL и инструкций, модель, режим.

**R2. Ревью автотестов compact-v1.**
- Срезы методов по `generated_symbols` (`tools/code_slices.py`). Java разбирает собственный лексер: строки, символы, text blocks, комментарии, аннотации, вложенные классы, лямбды. Python — через `ast`. Сохраняются номера строк, хелперы находятся транзитивно.
- Общий код файла — область SUPPORT с таблицей общего состояния. Парных областей нет.
- Сверки кодом до модели: ID проверок, литералы с учётом констант и оператор целиком, метод, путь и тело запроса.
- Если срез не удался, идёт весь файл или часть блокируется.

**R3. Масштаб.**
- Линтер подозрений (`tools/review_lint.py`), 5 правил. ID подозрения устойчив к правкам других кейсов.
- Пачки `next --max-tasks K`: команды драйвера выполняются под замком run, выдача пишется в `driver-log.jsonl`, SKILL orchestrate описывает работу с пачками.
- Порог SELF (D8) для compact-v1 считается как входы плюс резерв ответа на часть.

**R4.** Eval E1–E4 и гейт. Документация: `HOW-IT-WORKS.md`, `USAGE.md`, SKILL обоих ревьюеров и orchestrate, `CONTRACTS.md`, `PIPELINE.md`. E5 отложен.

### Р7: локальность как стоимость доработки

- **Формулировка (ваше решение).** Жёсткие свойства со 100 %: каждая пара кейсов покрыта, у кейса одна домашняя часть, ни одна часть не больше бюджета, план детерминирован. Локальность блоков — не порог, а замер стоимости доработки.
- **Почему не порог.** Пусть блок [a, b] заполнен так: a = 0,1 предела, b = 0,9 предела. Вставим между ними кейс x = 0,95 предела. Любое допустимое разбиение теперь даёт три блока [a][x][b], обратное удаление x снова сливает их в один. При кейсах размером до предела блока условие «≤ 2 блока» не выполняется ни при каком правиле разбиения, кроме «каждый кейс — свой блок».
- **Цена строгой локальности** (замер на `content_blocks`):
  - только границы по хешу: 1,9 % нарушений, но блоков в 2,95 раза больше минимума, то есть частей примерно в 9 раз больше;
  - выбранная настройка (MIN_FILL 0,85): около 40 % нарушений, Petclinic укладывается в 11 частей;
  - при MIN_FILL 0,75 — уже 16 частей.
- **Стоимость доработки r2 на Petclinic.** Скрипт `evals/review-scaling/r2_cost.py`: правит на месте ожидания случайных кейсов и строит план r2 с переносом проверенного в r1, 30 испытаний на сценарий, результат `results/2026-10-07/r2-cost.json`. План r1 — 11 частей, 1,85 МБ входа.

  | Правка | Частей r2: медиана (мин–макс) | Байт входа r2: медиана (макс) | Новых блоков: медиана (макс) |
  | --- | --- | --- | --- |
  | 1 кейс, текст ±5 % | 4 (4–4) | 668 056 (682 119) | 0 (0) |
  | 1 кейс, текст ±30 % | 4 (4–9) | 672 349 (1 512 474) | 0 (3) |
  | 3 кейса, текст ±30 % | 9 (7–15) | 1 510 638 (2 172 636) | 0 (4) |

- **Что это значит.**
  - Обычно правка одного кейса пересылает 4 части из 11: пары его блока с остальными четырьмя блоками.
  - Если правка сдвинула границу блоков, r2 перестраивает соседние блоки, и частей становится до 9.
  - Худший случай при трёх правках — 15 частей, больше, чем в r1: план r2 разложился на 6 блоков вместо 5.
  - Качество не страдает. Области кейсов переносятся по отпечатку кейса и от границ блоков не зависят; заново проверяются cross-области изменившихся пар блоков и области исправленных кейсов.

### Р14: ревью автотестов Petclinic в 6 частях

Было 11 частей при пороге 6. Две причины и два исправления (`tools/review_compact_automation.py`, `tools/review_projection.py`):

1. **Ошибка упаковки.** Части набираются жадно по порядку кейсов. Пробная часть считалась так, будто в ней отвечают все области SUPPORT: с полными возможностями (38 КБ). На деле они есть только в первой части. Поэтому части 2–11 закрывались на 125–141 КБ из примерно 180 КБ. Теперь закрытая часть забирает свои области SUPPORT, и следующие пробные части считаются без них. Только это дало 11 → 8 частей.
2. **Вид кейса для автотестов** (`automation_case_text`). Ревьюеру автотестов кейс теперь приходит плотнее; якоря и все привязки те же, что в проекции (это проверяет тест):
   - выходы шага — одной строкой `out:`, для результата проекта с тем же именем — `имя:тип`;
   - Test Data, записанные JSON, идут одной строкой: убраны только пробелы между токенами, литералы не меняются;
   - Test Data шага с входами `[INPUT-…]` опускаются: код реализует входы, а сверку Test Data со входами делает ревью кейсов (правило линтера и ревьюер кейсов);
   - нет management, приоритета и категорий — это поля ревью кейсов.

   Кейсы Petclinic в этом виде занимают 403 КБ вместо 633 КБ.

**Запас.** Скрипт `evals/review-scaling/r14_margin.py` удлиняет ожидания случайных кейсов, пока частей не станет больше 6 (5 испытаний).
- При упаковке по порядку документа проекция кейсов могла вырасти на 6,6–12,3 % (медиана 9,4 %).

- Пробная часть считается с заголовком не короче настоящего. Без этого часть 5 вышла на 3 байта больше предела.
- Больше упаковка не даст: общий код (30 КБ) нужен каждой части целиком, хелперы `request`/`seed`/`read` вызывают все кейсы. Дальше запас растёт только с бюджетом части.

### Находка: правило линтера `request-differs`

Код Haiku вызывает MockMvc через `get()/post()/put()`, а не через общий хелпер `exchange(метод, путь, …)`. На нём правило дало 15 ложных подозрений из 46 (33 %; порог Р10 — 30 %). Остальные 31 — верные `assert-id-missing`. Fable все 15 правильно отклонил, находками они не стали. Правило было рассчитано на метод и путь в аргументах общего хелпера. На наборах основного eval ложных 0 %, поэтому на решение гейта это не влияло.

**Исправлено** (`tools/review_lint.py`):
- Метод запроса теперь находится не только как литерал `"GET"`, но и как `HttpMethod.GET` / `RequestMethod.GET` или как вызов билдера с литералом пути или URL: `get("/student")`, `client.post("/…")`. Вызов `map.get("key")` за GET не считается.
- Поле тела больше не путается с `MockMvcRequestBuilders.put("/путь")`.

На классе Haiku (он стал фикстурой `tests/fixtures/review-scaling/automation-mockmvc-builders.json.gz`) теперь 0 `request-differs` и 31 верное `assert-id-missing`. Подмена метода (`get` → `post`) и пути (`/students/10` → `/students/11`) по-прежнему ловятся, это проверяет тест. Подозрений на наборах eval столько же, сколько было: E3 — 6, E4 — 3, чистые классы — 0.
