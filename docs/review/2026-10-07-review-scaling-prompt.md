## 3. Что строим

Новый режим ревью `compact-v1` появляется рядом с текущим режимом (`pairs`, legacy).

- Режим выбирается параметром прогона (`--review-mode`) и записывается в `config.json` и snapshot ревью.
- По умолчанию остаётся текущий режим, пока не пройден гейт (раздел 6).
- Legacy-режим не удаляй: на нём проигрываются фикстуры и делается сравнение.
- Остаётся одна логическая сессия ревьюера на ключ ревью, и каждая часть — свежий контекст.

### R1. Ревью кейсов в compact-v1

1. **Проекция для ревью** (`tools/review_projection.py`).
   - Детерминированный текст с якорями ID: исходные требования SREQ дословно, CREQ со связью SREQ → CREQ, возможности, кейсы. У кейса — заголовок, приоритет, категории, CREQ, цель, предусловия, поля управления и шаги (действие, данные, вызов возможности со входами, выходы, ожидания, проверки вида `ASSERT-…: actual operator expected`).
   - Проекция привязана к дайджесту канона и хранится в snapshot.
   - Контракт явно разрешает именно эту проекцию как вход модели. HTML, Markdown и CSV по-прежнему не входы.
2. **Упаковка по кейсам.**
   - Кейсы делятся на блоки с границами по содержимому: граница ставится по хешу `case_id` или по пределу размера. Тогда вставка или удаление одного кейса меняет не больше двух блоков.
   - Если общий контекст и все кейсы помещаются в одну часть, всё ревью идёт одной частью.
   - Иначе каждая часть — пара блоков, всего b·(b−1)/2 частей.
   - У каждого кейса одна «домашняя» часть, где отвечается его локальная область. В каждой части есть область `cross` по её блокам.
   - Исходник (SREQ ↔ CREQ) и полные описания возможностей идут в первую часть, если помещаются, иначе отдельной частью.
   - Общий контекст каждой части: индекс всех кейсов (ID, заголовок, CREQ), тексты CREQ, сигнатуры возможностей и подозрения линтера для кейсов этой части.
   - Кейс больше части — явная заблокированная часть с `REVIEW_CONTEXT_LIMIT`. Молча не обрезать.
3. **Ответ ревьюера.** Пределы задаются схемой и валидатором; ссылки и подозрения проверяет драйвер при `submit`.
   - `coverage` — строка на каждую назначенную область: `status`; `refs` — от 1 до 3 якорей из этой части, для области кейса хотя бы один якорь этого кейса; `note` — до 200 символов.
   - `findings` — `severity`, `code`, `related_ids`, `message` до 600 символов. INFO — не больше 5 на часть.
   - `corrections` — `target_id`, `field` из закрытого словаря, `before`, `after`, `why`.
   - `lint_dispositions` — на каждое подозрение линтера в части: `confirmed` или `rejected` с короткой причиной.
   - `required_checks` — как в D2, адресуются по `case_ids` и `requirement_ids`.
4. **Правки.**
   - Каждое поле словаря однозначно переводится в JSON pointer, `before` сверяется, дальше работает существующий `apply_review_corrections`.
   - `management.*` перепроверки не требует (как в D3).
   - Остальные правки перепроверяются только областями исправленного кейса в частях, где он есть.
5. **Инкрементальность** — перенос из D4 в compact-v1.
   - Область кейса переносится, если отпечаток её проекции совпал и на кейс нет BLOCKING.
   - Часть, где перенесены все области, не выдаётся.
   - Частично перенесённая часть выдаётся с полным контекстом, но отвечать нужно только по неперенесённым областям.

### R2. Ревью автотестов в compact-v1

1. **Срезы по `generated_symbols`.**
   - Срез — метод кейса плюс хелперы, которые он вызывает (транзитивно, в пределах файла).
   - Java: разбор с учётом строк, символьных литералов, text blocks, комментариев, аннотаций, вложенных классов и лямбд. Python: модуль `ast`.
   - Срезы сохраняют номера строк исходного файла, поэтому якоря вида `L123` проверяются по диапазонам срезов части.
   - Остальной общий код (поля, аннотации класса, `@BeforeEach` и фикстуры, хелперы) — одна область SUPPORT.
2. **Таблица общего состояния** строится кодом: статические и общие изменяемые поля и методы, которые их пишут и читают. Таблица кладётся в SUPPORT.
3. **Сверки кодом до модели.**
   - Каждая ASSERT кейса есть в коде с тем же ID.
   - Для простых операторов литерал в коде совпадает с ожидаемым значением кейса.
   - Метод, путь и тело запроса совпадают со входами шага.

   Результат — подозрения в конверте, а не автоматический отказ.
4. **Парных областей нет.** В каждой части есть CROSS по SUPPORT и методам этой части.
5. **Если срез не удался**, весь файл идёт в часть, когда помещается. Иначе — явная заблокированная часть с причиной. Без молчаливой обрезки.

### R3. Масштаб

1. **Линтер** (`tools/review_lint.py`) выдаёт только подозрения. Он ищет:
   - JSON или статус в тексте ожидания, отличающийся от литерала проверки;
   - требование без кейса;
   - одинаковый вызов с разными ожиданиями;
   - проверку абсолютного количества или полного списка ресурса, который меняют другие кейсы;
   - проверку результата, которого нет у возможности.
2. **Пачки.**
   - `next --max-tasks K` отдаёт до K независимых задач частей. `submit` работает как раньше, под замком.
   - `driver-log.jsonl` записывает выдачу пачки.
   - SKILL orchestrate разрешает параллельных субагентов, по одному на часть.
3. **D8.** Порог предупреждения о размере контекста в режиме SELF пересчитать под compact-v1.

## 6. Гейт

compact-v1 становится режимом по умолчанию, только если выполнены оба условия:

- пройдены Р1, Р2, Р4, Р5, Р6, Р7, Р8, Р11, Р12 и Р13;
- по Р3, Р9, Р10 и Р14 в отчёте есть цифры, и пороги не нарушены.

Иначе режим остаётся доступным по флагу, а отчёт объясняет, что не прошло. Решение о переключении — отдельным коммитом.
