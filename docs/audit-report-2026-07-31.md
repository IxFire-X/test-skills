# Аудит мультиагентной системы «Скиллы для работы»

> **Дата первичного аудита:** 2026-07-31
> **Дата ревизии отчёта:** 2026-08-01
> **Объект:** папка `test-orchestration-skills/` (все файлы и подпапки)
> **Метод:** архитектурный ревью по 5 параметрам (баги, логическая полнота, функциональность, передовые технологии, межкомпонентное взаимодействие), оценка 1–10, сравнение с мировыми практиками 2025–2026 (Anthropic Agent Skills, OpenAI, DeepSeek/Qwen, Google Gemini, Z.ai, MCP).
> **Статус:** после первичного аудита выполнена независимая проверка исходников и доказательных отчётов. Функциональные файлы системы в рамках этой ревизии не исправлялись; изменены только `ROADMAP.md` и настоящий отчёт.

## А. Общее резюме

### Что хорошо

1. **Progressive Disclosure (L1→L2) реализован в `.skillsrc`** — прямой канон Anthropic Agent Skills: Оркестратор читает только реестр (name, description, tags), затем загружает полный SKILL.md выбранного скилла. Экономия токенов 40–60% заявлена и архитектурно обоснована.
2. **Execution Gate (`tools/run_tests.py`)** — детерминированный оракул `PASS/FAIL/NOT_RUNNABLE`. Принцип «честность > удобство» соблюдён: InvenTree не получил ложный `PASS`. При этом статусы нужно разделять: pytest реально запустился и вернул runner verdict `FAIL` (0 тестов, 74 collection errors), а orchestration report классифицировал внешний блокер как `BLOCKED (окружение)`. Это не `NOT_RUNNABLE`.
3. **Задекларированный канон контрактов `CONTRACTS.md` + JSON Schema (Draft 2020-12)** — машиночитаемые дубли выходов (`schemas/`) и Contract Check создают хорошую основу, но текущий чекер не является полноценным quality gate: он возвращает `passed` на известном drift и не проверяет `PIPELINE.md`/`.skillsrc` как единое целое.
4. **Контекстная инженерия:** sub-agent-compaction, изоляция контекста между шагами, lite-версия Оркестратора для моделей <32K токенов, sha256-идемпотентность — мировые практики 2025–2026 применены осознанно.
5. **Модульный дизайн «агенты как инструменты»:** 6 скиллов + 3 детерминированных Python-инструмента + шаблоны для 4 языков (Java, Python, TypeScript, Go) — хорошая основа масштабирования без монолита. Однако Execution Gate фактически реализован только для Java и Python; Go/TypeScript пока имеют шаблоны, но не рабочие ветки раннера.

### Что плохо (критично)

1. **Рассинхрон контрактов внутри канона:** `PIPELINE.md` разрешает то, что `CONTRACTS.md` запрещает (`<generated_test_cases>` → `tc-to-autotest`); диаграммы используют `<generated_tc>` вместо `<generated_test_cases>`; выход `<analysis>` объявлен в `PIPELINE.md`, но отсутствует в реестре `CONTRACTS.md §2`. **Канон перестал быть единственным источником истины.**
2. **Гигиена дистрибутива:** файл `nul` — артефакт bash-ошибки; вложенный `InvenTree-master/` является тестовым fixture примерно на 113 MB, а `docs/` не описана в структуре поставки. Это не функциональный дефект ядра, но нарушает границы release-пакета.
3. **Битые ссылки:** `BACKLOG.md` отсутствует, но упоминается в трёх основных руководствах и дополнительно в docstring/описании схемы. При этом `ROADMAP.md` уже объявлен единственным плановым документом.
4. **Противоречие версий:** `.skillsrc` заявляет `status_markers_version: "v1.2"`, `CONTRACTS.md` — «Версия канона: 1.0».

### Основные риски

- **R1 (критический):** рассинхрон контрактов приводит к `contract_mismatch` в рантайме или к генерации артефактов, не соответствующих канону; текущий Contract Check может ошибочно пропустить такой drift.
- **R2 (средний):** декларативность retry/timeout/idempotency — при ручном запуске скиллов эти механизмы не исполняются никем.
- **R3 (средний):** отсутствие machine-readable observability (JSON-логи, метрики) — невозможно анализировать историю запусков, стоимость, качество.
- **R4 (низкий):** нет явных границ «что скилл НЕ делает» — LLM может вызывать скилл вне его зоны ответственности.

### 1. `.skillsrc` (манифест проекта)

**Что проверял:** структуру манифеста, поддержку SDD (`methodology`, секция `sdd:`), реестр скиллов, контракты входа/выхода, стратегии разрешения конфликтов.

**Наблюдения:**
- Реестр содержит 6 скиллов + orchestrator-lite с полными метаданными (name, path, description, tags, triggers, input_contract, output_contract).
- Секция `sdd:` (openapi/asyncapi/domain/requirements/architecture) — задел под SDD-проекты, согласуется с приоритетом владельца.
- Стратегии разрешения конфликтов (`analytics_vs_code`, `status_conflict`, `skillsrc_vs_scan`) — зрелое решение, редкое в подобных системах.
- **Недостаток:** в описаниях скиллов нет явных границ «что скилл НЕ делает» и нет поля `request_user_clarification` (рекомендация Google Gemini).
- **Контрактный drift:** `tc-to-autotest` объявляет `validated_test_cases` и `autotest_files`, `autotest-reviewer` — только `autotest_files`, а `context-marker` — `tagged_content`; это не совпадает с каноном `<test_cases>`, `<corrected_test_cases>`, `<automation_matrix>`, `<analytics_documentation>` и `<source_code_and_diff>`.
- Файл содержит конкретный проект `subscription-renewal-service` и не отделён от шаблона манифеста (`.skillsrc.example`), поэтому копирование дистрибутива в новый проект может унаследовать чужой стек.
- **Рассинхрон версий:** `contracts.status_markers_version: "v1.2"` vs `CONTRACTS.md` «Версия канона: 1.0».

**Сравнение с эталоном:** `.skillsrc` — прямое воплощение L1-метаданных Anthropic Agent Skills + принципа «прогрессивного раскрытия». По полноте метаданных превосходит типовые реестры конкурирующих наборов скиллов.

**Оценки:**
- Отсутствие багов: **6** — рассинхрон версии, межшаговые имена контрактов и проектные значения в дистрибутивном манифесте.
- Логическая полнота: **9** — все скиллы описаны, триггеры и контракты на месте; нет только границ «не делать».
- Функциональность: **9** — Оркестратор корректно читает реестр и диспетчеризует.
- Передовые технологии: **9** — Progressive Disclosure, SDD-метаданные, конфликт-стратегии.
- Межкомпонентное взаимодействие: **6** — контракты указаны, но часть имён не совпадает с каноном и не проверяется машиной на уровне манифеста.

### 2. `CONTRACTS.md` (канон тегов и статусов)

**Что проверял:** реестр выходных тегов §2, правило переименования §2.3, статус-маркеры §3, граф передачи §4, исполнимый чеклист §5, retry/timeout §6.

**Наблюдения:**
- Единый реестр корневых блоков — сильная сторона; машиночитаемые дубли в `schemas/` — соответствие OpenAI/DeepSeek.
- Правило переименования `<generated_test_cases>` → `<test_cases>` — **уникальное и правильное решение**, устраняющее семантическую путаницу владения артефактом.
- **Расхождения:**
  - Диаграмма §4 использует `<generated_tc>`, а §2/§2.3 — `<generated_test_cases>` — один тег, два имени в «единственном каноне».
  - §3.3 объясняет `partial` через `partial-fixed`, который в §3.1 помечен @deprecated.
  - `<analysis>` (выход tc-generator в `PIPELINE.md`) отсутствует в реестре §2.
- §6 честно помечает retry/timeout/idempotency как «спецификацию поведения, а не гарантию исполнения» — правильная позиция, но риск R2 остаётся.
- `tools/contract_check.py` не следует канону как данным: он использует ручные константы и допускает `<analysis>`/`batch_marking_result`, которых нет в реестре §2. Запуск `python tools/contract_check.py --full` возвращает `status: passed`, хотя расхождения с `PIPELINE.md` и `.skillsrc` остаются.

**Сравнение с эталоном:** концепция «единственного источника истины» + JSON Schema Draft 2020-12 соответствует лучшим практикам OpenAI/DeepSeek. Исполнимый чеклист §5 — шаг к машинной проверке, но остаётся в Markdown.

**Оценки:**
- Отсутствие багов: **4** — внутренние противоречия (§4 `<generated_tc>`, §3.3 partial-fixed, отсутствие `<analysis>`) плюс разрыв между заявленным каноном и фактическим Contract Check.
- Логическая полнота: **7** — реестр покрывает текущий test-pipeline, но не покрывает SDD-расширения (S-1…S-7) и события.
- Функциональность: **7** — канон работает, но рассинхрон с `PIPELINE.md` ослабляет его.
- Передовые технологии: **6** — JSON Schema есть, но enforce-слой пока не проверяет канон и каждый переход достоверно.
- Межкомпонентное взаимодействие: **6** — граф передачи есть, но внутриканонные противоречия создают риск `contract_mismatch`.

### 3. `PIPELINE.md` (схема пайплайна)

**Что проверял:** 5 этапов + Execution Gate, контракты этапов, структуру папок, версионирование.

**Наблюдения:**
- Чёткая схема: context-marker → tc-generator → tc-reviewer → tc-to-autotest → autotest-reviewer → Execution Gate.
- Execution Gate описан правильно: финальный `ПРИНЯТО` невозможен без `PASS` от `run_tests.py`.
- **Критичные расхождения с `CONTRACTS.md`:**
  - Этап 3 разрешает передачу `<generated_test_cases>` напрямую в `tc-to-autotest`, хотя `CONTRACTS.md §2.3` это **запрещает**.
  - Этап 1 объявляет выход `<analysis>`, отсутствующий в реестре §2 `CONTRACTS.md`.
  - Диаграмма использует сокращения `<generated_tc>`, `<corrected_tc>`, `<analytics_doc>` — не канонические имена.
- Версионирование скиллов в таблице — хорошая практика.

**Сравнение с эталоном:** схема соответствует OpenAI Agents SDK (рутины: чёткая последовательность шагов с передачей управления). Но канон нарушен — это главный архитектурный дефект папки.

**Оценки:**
- Отсутствие багов: **4** — рассинхрон контрактов с каноном и разрешённый прямой переход к `tc-to-autotest`.
- Логическая полнота: **8** — все этапы и альтернативные сценарии (ПРИНЯТО/AUTO_FIX/ТРЕБУЕТ ДОРАБОТКИ) описаны.
- Функциональность: **6** — как руководство работает, но противоречия контрактов могут привести к неверным передачам данных при ручном запуске.
- Передовые технологии: **7** — Execution Gate — сильная практика.
- Межкомпонентное взаимодействие: **6** — из-за несогласованных имён тегов.

#### 18.1 `tools/run_tests.py` (Execution Gate)

**Оценки:**

## Г. Общие рекомендации по улучшению

> Рекомендации сформулированы **только для компонентов внутри папки**. Внесение правок — отдельный этап (см. `ROADMAP.md`, Шаг 7).

### Г-1. КРИТИЧНО — Синхронизировать канон контрактов
- **Что:** привести `PIPELINE.md` к `CONTRACTS.md §2.3` (запрет прямой передачи `<generated_test_cases>` в `tc-to-autotest`), заменить `<generated_tc>` на `<generated_test_cases>` в диаграммах, решить судьбу `<analysis>` (добавить в §2 или убрать из `PIPELINE.md`).
- **Почему:** рассинхрон канона — корневой риск R1; при ручном запуске пользователь может нарушить контракт незаметно.
- **Источник:** CONTRACTS.md §5 (исполнимый чеклист), ROADMAP Шаг 6.1/Шаг 7.

### Г-2. ВЫСОКО — Очистить границы release-дистрибутива
- **Что:** удалить `nul`; вынести `InvenTree-master/` как тестовый fixture за пределы release-пакета и описать назначение `docs/` либо также исключить её из дистрибутива.
- **Почему:** лишние артефакты и fixture в поставляемой папке размывают границы продукта и могут переноситься в целевые проекты. Это release-hygiene, а не дефект исполнения ядра.
- **Источник:** Anthropic Agent Skills — «навык должен быть автономным и не содержать лишнего».

### Г-3. ВЫСОКО — Убрать битые ссылки на `BACKLOG.md`
- **Что:** не создавать второй плановый документ; заменить ссылки в `Instruction.md`, `PIPELINE.md`, `USER-GUIDE.md`, docstring и schema description на `ROADMAP.md` либо удалить их.
- **Почему:** битые ссылки разрушают доверие к документации, а два плановых документа создали бы новый источник рассинхрона. План развития уже находится в `ROADMAP.md`.

### Г-4. ВЫСОКО — Согласовать версии статус-маркеров
- **Что:** `.skillsrc` (`v1.2`) и `CONTRACTS.md` («1.0») должны совпадать.
- **Почему:** расхождение версий — классический признак «двух источников правды»; Оркестратор при Contract Check может счесть это `contract_mismatch`.

### Г-5. ВЫСОКО — Добавить явные границы скиллов
- **Что:** в `.skillsrc` (описания) и в каждый SKILL.md добавить секцию «Что скилл НЕ делает» и «Когда задать уточняющий вопрос».
- **Почему:** Google Gemini Agent Designer — «устанавливай границы того, что скилл может и не может делать»; снижает риск нецелевого вызова LLM.

### Г-6. СРЕДНЕ — Проверить агрегацию тестов в `run_tests.py`
- **Что:** разобраться с расхождением `total=13` vs 24 (Maven); добавить unit-тесты на `tools/*.py`.
- **Почему:** оракул должен быть безупречен — если статистика врёт, доверие к `PASS/FAIL` подрывается.

### Г-7. СРЕДНЕ — Добавить machine-readable observability
- **Что:** JSON-логи каждого шага (время, токены, вердикты, стоимость) рядом с Markdown-отчётами; далее — OTLP.
- **Почему:** без метрик невозможно анализировать историю запусков и качество; требование production-агентов 2025–2026 (Anthropic/OpenAI).

### Г-8. НИЗКО — Исполнить retry/timeout/idempotency
- **Что:** перевести `CONTRACTS.md §6` из деклараций в исполняемый слой (`contract_check.py`/обёртка хоста) либо явно пометить как «поведение при ручном запуске».
- **Почему:** декларативные механизмы, которые никто не исполняет, создают ложное чувство надёжности (риск R2).

### Г-9. SDD-приоритет владельца (отдельный трек)
