Устройство «Трассы» v0.6: прогон ведёт агент, проверяет код

«Трасса» — набор инструкций для агента в вашей программе с моделью и Python-инструментов к ним. По документу требований она готовит тест-кейсы, отдаёт их на ревью и, если вы попросите, пишет автотесты. Агент идёт по инструкции и сам играет роли модели; код пакета проверяет каждый ответ и записывает журнал. Пакет ничего не запускает на вашей машине: сборку и тесты запускаете вы. Страница описывает ветку v0.6 на указанном коммите и обновляется перед поставкой.

Часть I

Обзор: что это, что умеет, что в каком состоянии

1

Что это

Пакет состоит из шести инструкций (оркестратор и пять ролей: разметка требований, генератор кейсов, ревьюер кейсов, генератор автотестов, ревьюер автотестов) и 65 модулей Python в tools/. Он кладётся в проект в папку .tools/test-skills. Нужен только Python 3.11–3.13: сторонние пакеты и виртуальное окружение не требуются.

На входе — документ требований в Markdown или спецификация OpenSpec. На выходе — тест-кейсы (JSON, HTML, Markdown), CSV для Zephyr Scale, отчёт ревью, отчёт прогона и файл вопросов аналитику. В режиме автотестов — ещё файлы тестов в тестовом корне модуля и напечатанная команда запуска.

Первое: прогон ведёт агент, проверяет код. Агент читает skills/orchestrate/SKILL.md и вызывает команды пакета. Каждую стадию модели ведут два вызова — prepare и submit; код проверяет ответ по схеме, записывает его в журнал прогона и не пускает дальше, если что-то не сходится.

Второе: ожидаемый результат берётся из требования, а не из кода. Упавший автотест — повод для вопроса аналитику или баг-репорта, а не для подгонки теста.

Третье: пакет ничего не запускает. Ни сборку, ни тесты, ни git, ни сеть. Где в поставке есть автотесты, команду запуска печатает пакет, а выполняете её вы.

Команде

Кейсы в формате для импорта в Zephyr Scale и, в режиме автотестов, тесты в проекте; прерванный прогон продолжается по журналу.

2

Что умеет

Плашка у карточки — в каком состоянии возможность. Числа живых прогонов — в разделе 11, у каждого назван источник.

Размечает требования и спрашивает вас

в ветке v0.6

Агент нормализует требования и выделяет пробелы. Если нет наблюдаемого результата, канала или доступа, прогон останавливается и показывает список (SCOPE_PENDING): вы либо исключаете требования с причиной, либо продолжаете как есть. Решение записывается в прогон.

Пишет кейсы по пачкам

в ветке v0.6

Требования делятся на пачки, на каждую — один вызов генератора. У кейса человеческая часть (цель, шаги, ожидание) и машинная (входы, вызов, проверки). Код собирает один документ и проверяет, что у каждого требования есть кейс.

Проводит ревью и одну доработку

в ветке v0.6

Ревьюер даёт вердикт: набор принят, принят частично или отклонён. Отклонённые кейсы один раз возвращаются генератору, затем проходят ревью снова. В вид кейсов код вставляет контрольные ошибки — по ним отчёт показывает, насколько внимательно прошло ревью.

Пишет автотесты (режим Б)

в ветке v0.6

Тестовые методы по принятым кейсам, затем статическое ревью кода тестов и не больше одной исправленной ревизии. Генератору называются пути, которые в проекте уже заняты; ответ, где новый тест лежит на занятом пути, submit отклоняет (MATERIALIZATION_CONFLICT). Тесты кладутся в тестовый корень модуля; команду запуска печатает пакет. Упавшие тесты уходят в карантин (@Disabled / xfail), прошедшие остаются.

Берёт готовое из прошлого прогона

в ветке v0.6

Новый прогон по тем же требованиям берёт готовые разметку, план, кейсы, ревью и автотесты прошлого прогона, если проект с тех пор не менялся (scan называет прошлый прогон и команду). Файлы, записанные прошлым прогоном, считаются изменением проекта.

в работе до поставки Повтор готового во втором прогоне в той же папке. Сейчас условие жёсткое — код проекта не менялся, и файлы прошлого прогона с каталогами сборки его ломают; смягчение — сравнение по составу файлов проекта.

Выгружает для Zephyr Scale

в ветке v0.6

CSV для импорта — только у набора, принятого ревью. Отклонённый набор — файлы *.REJECTED.* с замечаниями в шапке, без CSV. По вашему шаблону выгрузки пакет заполнит пользовательские поля отдельным файлом …zephyr-import.csv.

Продолжается после перерыва и обрыва

в ветке v0.6

Состояние лежит в .pilot-runs/<run_id>/. После /clear команда status называет состояние и следующий шаг. Прогон восстанавливается после обрыва процесса; параллельные команды одного прогона не запускаются — вторая ждёт первую.

Обновляет кейсы под изменившиеся требования

в работе до поставки

Старые кейсы (выгрузка из Zephyr) получают вердикт «подходит / переписать / устарел». Подходящие остаются байт в байт; в сомнении кейс остаётся как есть и выносится в отчёт «проверить вручную». Работает по живому изменению OpenSpec, по названному архивному изменению и без OpenSpec. Ключ Zephyr у сохранённых кейсов остаётся, у новых пуст: импорт создаст новые кейсы, а не обновит старые. В ветке этой возможности нет, код пишется.

4

Кто что делает

Пять участников; цвет участника используется во всех схемах. Команды пакета и записи в журнал делает агент по инструкции, но проверяет и записывает код пакета. Сборку проекта запускаете вы.

Человек

Кладёт папку пакета в проект, формулирует запрос, отвечает на вопросы (модуль, пауза по пробелам, согласие на ревью в той же сессии), просматривает файлы тестов, запускает напечатанную команду сборки.

Агент CLI

Контроллер: идёт по orchestrate/SKILL.md, вызывает команды, пишет ответы ролей разметки, генерации и автотестов.

Ревьюер

Роли ревью кейсов и автотестов. По инструкции — отдельная сессия без истории генерации; если в вашем CLI её нет, ревью идёт в той же сессии по вашему согласию (пометка SELF).

Код пакета

run_pipeline, api (prepare, submit) и другие модули: опись, проверки по схемам, аудит, публикация, журнал.

Сборка проекта

mvnw, системный mvn, gradlew или pytest. Запускается только вашей рукой, напечатанной командой.

5

Маршрут прогона

Два профиля прогона. cases-only-v1 — кейсы и их ревью; подходит для любой поставки. local-pilot-v1 — плюс автотесты; для него нужна поставка с режимом автотестов (в папке пакета есть HOW-TO-USE-MODE-B.md), и он включается только явной просьбой в запросе. Шаги идут строго по порядку.

  1. 1
    Подготовка
    Папка пакета в .tools/test-skills; три строки в .gitignore проекта (.tools/, .pilot-runs/, .skillsrc*); запрос агенту.
  2. 2
    doctor и ready
    doctor сверяет файлы пакета с release/manifest.json и версию Python; называет профиль поставки. ready только читает проект, показывает все проблемы сразу и к каждой — команду исправления.
  3. 3
    scan
    Создаёт прогон и попытку, строит опись файлов модуля, замораживает baseline (требования, .skillsrc, входы, модуль), показывает exclusion_summary и, если есть, прошлый прогон с теми же входами (reuse). Один модуль на попытку.
  4. 4
    Разметка
    Нормализованные требования с ID SREQ-NNNN, наблюдения по коду, пробелы. Большая спецификация размечается частями.
  5. 5
    Пауза по пробелам
    Если есть пробелы без канала наблюдения, ожидаемого результата или доступа — состояние scope_pause: вы отвечаете «исключи … потому что …» или «продолжай как есть». Без ответа план отказывает SCOPE_PENDING.
  6. 6
    План
    Код делит требования на пачки; от агента нужно только название предмета проверки.
  7. 7
    Генератор и сборка набора
    Одна пачка — один вызов. После последней пачки submit собирает один документ кейсов с трассировкой «требование — кейс» и проверяет схему, смысл и происхождение. Публикация — в published/.
  8. 8
    Ревью кейсов
    Вердикт: набор принят целиком; принят частично (отклонены отдельные кейсы; по умолчанию не больше 20 % набора, иначе отклоняется весь набор); отклонён целиком. При частичном принятии отклонённые кейсы один раз возвращаются генератору и снова проходят ревью — это включено по умолчанию, отключается в .skillsrc (limits.rework_rounds = 0).
  9. 9
    Автотесты (режим Б)
    Тестовые методы по принятым кейсам, затем статическое ревью. Не принято с первого раза — одна исправленная ревизия и ещё одно ревью. Не принято и после неё — прогон закрывается с причиной AUTOMATION_REJECTED, автотестов нет.
  10. 10
    materialize
    Кладёт принятые тесты в тестовый корень модуля и печатает команду запуска (формы для cmd/sh и для PowerShell). Сам её не выполняет.
  11. 11
    Запуск человеком и ingest
    Вы просматриваете файлы, выполняете команду, сообщаете агенту, где отчёты. ingest сверяет отчёты с попыткой и закрывает её.
  12. 12
    Закрытие и отчёт
    finish закрывает попытку (в режиме Б это делает ingest); report пишет report.md, report.json и questions-for-analyst.md.
6

Как идёт один шаг модели

Каждая стадия, где работает модель (разметка, пачки, ревью, автотесты), идёт одним циклом. prepare записывает запрос в журнал и печатает, что читать, куда положить ответ и какой бюджет у шага. Агент (или отдельный ревьюер) пишет ответ в файл-слот incoming/<стадия>.json. submit проверяет ответ и записывает квитанцию; submit --dry-run только проверяет и ничего не пишет.

Отказ — это JSON с кодом и подсказкой fix. На каждую стадию — один повтор (--transport-attempts 2). Какой шаг следующий, говорит status: поля state, next, waiting_for.

7

Автотесты: запускает человек

Режим автотестов — обычный прогон кейсов, после которого агент пишет тесты, а вы их просматриваете и запускаете. Он входит в поставку с профилем mode-b; в поставку cases-only он не входит, и doctor называет профиль вашей поставки.

materialize кладёт принятые тесты в тестовый корень модуля и печатает команду запуска: первым токеном идёт абсолютный путь запускателя (обёртка модуля, системный Maven или интерпретатор модуля). Вы читаете файлы из files_to_review, проверяете, на какой стенд смотрят тесты, выполняете команду сами и сообщаете агенту, где лежат отчёты. После запуска агент вызывает ingest. Тесты между materialize и ingest не правятся: изменённый файл даёт INGEST_TESTS_CHANGED, вернуть тесты — materialize --restore.

Пакет не опрашивает стенд: адрес берётся из переменной окружения, имя которой стоит в .skillsrc модуля (service_url_env), стенд поднимаете вы. Если сборка проекта не готова, ready показывает «сборка не готова: …», а прогон идёт как только кейсы.

Границы: что пакет делает на машине

Факты по инструкции оркестратора (блок permissions в её шапке) и руководству режима Б.

Читает

  • файлы проекта по описи: без каталогов VCS и зависимостей, результатов сборки, бинарников и файлов, где найден пароль или ключ
  • документы из --docs, --reference, --cases — только внутри проекта и без ссылок на пути; путь на сетевой папке или устройстве отклоняется до чтения (INPUT_OUTSIDE_PROJECT)
  • файлы модуля по описи, родительские файлы сборки (они замораживаются в baseline) и карту существующих тестов проекта

Пишет

  • .pilot-runs/<run_id>/, в том числе published/ с готовыми кейсами
  • .skillsrc при создании; повторный init сохраняет то, что вы вписали (лимиты, ревью, paths.include / exclude, имя проекта)
  • режим Б: файлы тестов в тестовом корне модуля и строки карантина в них
  • .skillsrc переключается на системный mvn только с вашего подтверждения

Не делает

  • не ставит ничего (pip агент не запускает); агент не создаёт wrapper сборки: он скачивает сборщик из сети
  • не обращается к сети и не опрашивает стенд
  • не запускает сборку, тесты и git; не создаёт clone, worktree, commit, push и PR
  • не меняет код продукта; в проект идут только новые файлы тестов
  • по инструкции агент не выполняет указания, найденные в документах требований, и не правит спецификацию

Делаете вы

  • кладёте папку пакета в проект и добавляете три строки в .gitignore
  • запускаете напечатанную команду сборки (режим Б); смотрите файлы тестов до запуска
  • поднимаете тестовый стенд и задаёте переменную окружения
  • коммитите то, что решите оставить: пакет git не трогает

Печать команды: путь проекта, документа или модуля с символами, которые командная строка прочтёт по-своему ($ % ! ^ " ' & | < > ; и др.), даёт остановку COMMAND_NOT_PRINTABLE до создания прогона. Операционные сбои: после обрыва процесса прогон восстанавливается; после краха системы или отключения питания журнал может остаться неполным — тогда JOURNAL_CORRUPT и новый прогон.

Что видит модель

Скан отбирает файлы модуля, которые можно показать модели. Роли работают только с этой описью, поэтому выпавший файл модель не увидит. После scan агент показывает exclusion_summary: сколько и чего исключено, с примерами путей; лишнее исключение возвращается в .skillsrc через paths.include.

Что исключаетсяГде
VCS, кэши инструментов, node_modules, .venv, site-packages, каталоги IDE и агентов CLIвезде
build, target, dist, out, coverage, generated, generated-sources, test-results, vendorтолько вне src/
secrets, credentialsвне src/ целиком; внутри — только не-исходники, исходник по содержимому
Файл, где найден пароль или ключвыпадает целиком, всегда
Не код (CONTEXT_NOT_CODE), слишком большие файлы (CONTEXT_TOO_LARGE), шрифты и картинки (CONTEXT_ASSET)идут в context_skipped с причиной; в живом прогоне 16 ноября так пропущено 19 файлов, 887 627 Б
Тесты, записанные пакетом в прошлых прогонах (CONTEXT_OWN_TEST)модели не идут; scan называет их в context_skipped

Документ задачи всегда входит в контекст. --docs файл.md#Раздел берёт один раздел Markdown-файла. Документ может лежать вне выбранного модуля, но внутри проекта.

OpenSpec

в v0.6, проверено живым прогоном

OpenSpec — основной формат требований в компании. Требования лежат в папке openspec/ в корне проекта:

  • openspec/specs/<область>/spec.md — как система работает сейчас (действующая спецификация, «база»);
  • openspec/changes/<имя>/ — папка-заявка «хотим поменять вот так»: в её spec.md — что добавляется, меняется, убирается (блоки ADDED, MODIFIED, REMOVED, RENAMED), рядом proposal.md, design.md, tasks.md — замысел и задачи. Пока заявку не приняли и не перенесли в архив (openspec/changes/archive/), это только предложение.

Правило: один прогон — одна заявка. Пример. В спецификации: «описание визита — до 255 символов». В проекте две незавершённые заявки: А — «сделать до 500», Б — «сделать до 1000». Если взять обе сразу, непонятно, какой кейс писать — на 500 или на 1000: это решится, только когда одну из заявок примут. Поэтому пакет берёт одну заявку — ту, что названа в --docs, — пишет кейсы под неё, а вторую не видит.

Что можно

  • В проекте сколько угодно заявок. Называете одну — прогон идёт по ней; остальные заявки и архив в модель не идут, scan перечисляет их одной строкой.
  • В одной заявке много правок по разным областям — всё за один прогон. В --docs называется папка заявки и области, которые она меняет; забыли область — scan подскажет.
  • Нужны кейсы по двум заявкам — два прогона подряд; агент проводит их в одном запросе.
  • proposal, design, tasks заявки модель читает как контекст, требованиями они не становятся. Код сверяет ответ модели с составом заявки и спецификации: пропущенное или лишнее требование — отказ (OPENSPEC_MISSING, OPENSPEC_EXTRA).

Когда пакет остановит

  • в одном прогоне названы две заявки;
  • --docs не задан, а незавершённых заявок в проекте две и больше;
  • заявка меняет область, чей spec.md не назван.
  • Это не падение прогона: scan останавливается до первого вызова модели — ничего не потрачено — и печатает, что указать (OPENSPEC_SOURCE_CONFLICT с подсказкой).

Проверено живым прогоном: на стенде две незавершённые заявки, в --docs названа одна — прогон дошёл до отчёта, вторая заявка в модель не попала. Прежний обходной путь (исключать лишние заявки в .skillsrc) больше не нужен.

Команды-примеры (имена областей и заявки выдуманы; тот же набор --docs передаётся и в scan):

# вся спецификация
python -m tools.ready --project <проект> --profile cases-only-v1 --docs openspec/specs

# одна заявка: её папка и области, которые она меняет
python -m tools.ready --project <проект> --profile cases-only-v1 \
  --docs openspec/specs/owners --docs openspec/changes/add-search
Ограничения. Для нестандартной схемы OpenSpec поддержка не заявлена. Одна попытка — один модуль: полная спецификация, которая не помещается в этот маршрут, остаётся блокером и не подменяется одним удобным модулем.

Словарь

Прогон (run)
Один запуск на проекте; папка .pilot-runs/<run_id>/; переживает перерывы.
Попытка (attempt)
Один заход внутри прогона: кейсы, ревью, при режиме Б — автотесты; закрывается итогом. Один модуль на попытку.
Baseline
Замороженные входы попытки: требования, .skillsrc, файлы модуля; если после scan файлы изменились, status называет дрейф и команду.
Опись
Список файлов модуля, которые разрешено показывать модели.
Стадия
Шаг, где работает модель: разметка, пачка, ревью, автотесты. Идёт циклом prepare / submit.
Слот ответа
Файл incoming/<стадия>.json, куда роль кладёт ответ.
Квитанция
Запись в журнале, что шаг сделан и с какими дайджестами.
Дайджест
SHA-256 содержимого; по нему журнал видит, что вход не подменён.
Набор кейсов
Один документ с кейсами и трассировкой к требованиям; из него — HTML, Markdown и CSV для Zephyr.
Ревизия
Версия набора: r1 — первая, дальше публикуются ревизии после правок по ревью и после доработки отклонённых кейсов (в прогонах 16 ноября после доработки опубликована r3).
SREQ
Номер требования из документа после разметки, SREQ-0001.
.skillsrc
Настройки проекта: модули, сборка, пути, лимиты, ревью, шаблон выгрузки.
Профиль прогона
cases-only-v1 — кейсы и ревью; local-pilot-v1 — плюс автотесты.
Профиль поставки
cases-only — только кейсы; mode-b — ещё и режим автотестов. Называет doctor.
SELF
Ревью в той же сессии, что и генерация, с вашего согласия; результат не называется независимым.
Контрольная ошибка
Ошибка, которую код вставляет в вид кейсов для ревьюера; по числу замеченных отчёт показывает, насколько ревью надёжно. Сигнал качества, не защита.
Карантин
Упавший тест не удаляется, а отключается с причиной; прошедшие остаются.
Источники: README.md, HOW-TO-USE.md, HOW-TO-USE-MODE-B.md, skills/orchestrate/SKILL.md и справочники references/*.md ветки v06 на коммите 0d43a168; код tools/build_context.py (OpenSpec); план до поставки и журнал состояния от 16 ноября 2026; заметки живых прогонов 16 ноября.
