## 2. Что в этом плане означает «автотест»

Автоматизация — способ выполнения проверки. Unit — уровень и область проверки: небольшая часть программы. Поэтому формально юнит-тест тоже может быть автотестом. Функциональное тестирование проверяет выполнение функциональных требований; end-to-end означает проверку процесса от начала до конца. Это разные признаки, а не взаимоисключающие названия. Источники: [ISTQB о test automation и system testing](https://api.glossary.istqb.org/storage/help/R0uz58NqLzUz48LVUuyGSF76NFj4LHQazSs0GlNS.pdf), [ISTQB о functional testing](https://glossary.istqb.org/en_US/term/functional-testing/3), [ISTQB об end-to-end testing](https://api.glossary.istqb.org/storage/help/zsbmVUA9KghcXUrcOoTUZMsGufs1tp2mZj3uQK10.pdf), [Martin Fowler о Unit Test](https://martinfowler.com/bliki/UnitTest.html).

Для данного продукта принимается следующее требование:

> Пайплайн создаёт функциональные автотесты приложения по принятым тест-кейсам. Тест выполняет заданные действия через согласованный интерфейс приложения и проверяет наблюдаемые ответы или состояние. Изолированная проверка внутреннего метода и проверка заглушки вместо целевого поведения не заменяют такой автотест. Длинная сквозная цепочка требуется только тогда, когда её требует сам тест-кейс.

Примеры нужного результата: проверка обязательного поля одним запросом; отказ роли в доступе; создание объекта и проверка сохранённых значений; многошаговый процесс с изменениями состояния. Длина сценария не определяет его качество и уровень.

Для описанного Java/backend проекта предпочтительна проверка работающего приложения через внешний API с существующими в проекте клиентом, конфигурацией и способом авторизации. Проверка через MockMvc с поднятыми внутри тестового процесса реальными компонентами приложения также принята пользователем. Конкретная граница фиксируется перед генерацией по запросу и конфигурации проекта; при равной доступности выбирается внешний API. Этот план не добавляет поддержку новых UI-стеков.

Название библиотеки не доказывает уровень теста. MockMvc проводит запрос через Spring MVC без работающего сервера; для принятия важны реальные компоненты и фактический путь проверки. Замоканное целевое поведение не принимается. Если пользователь явно потребовал внешний API для конкретного запуска, молчаливый переход на MockMvc не допускается. [Документация Spring](https://docs.spring.io/spring/reference/testing/mockmvc.html).

RestAssured, AssertJ, Allure и запрет JDBC не становятся универсальными требованиями пакета. Используются уже принятые средства проекта. Независимое чтение БД допустимо как явно разрешённая проверка состояния, если не подменяет действие, которое кейс требует выполнить через интерфейс приложения.

### 2.1. OpenSpec, подготовленная среда и пробелы требований

Подготовленная рабочая среда — входное условие: проект предоставляет действующий способ сборки и запуска функциональных тестов, конфигурацию, доступ и необходимые тестовые данные. Пайплайн использует эти средства. Если обязательного входа нет, он выдаёт конкретную причину и перечень недостающего; готовность среды из рассказа пользователя не заменяет проверку перед запуском.

Пользователь задаёт один из двух вариантов объёма в исходном запросе:

- **Change со связанной регрессией:** актуальная спецификация с учётом выбранного change, включая существующее поведение, которое изменение способно затронуть. Связь регрессии с изменением обосновывается требованиями и кодом. Другие незавершённые changes автоматически не включаются.
- **Вся спецификация:** все требования актуальной согласованной спецификации проекта. Незавершённые changes добавляются только по явному указанию. Нельзя подменить этот объём одним удобным модулем, capability или выборкой кейсов; ограничения текущего module scope выявляются в этапе 0 и остаются блокером заявленного объёма.

До обработки фиксируются фактическая версия и схема OpenSpec, выбранные источники и их точные версии. В стандартной схеме `openspec/specs/` задаёт текущие требования, а `openspec/changes/<change>/specs/` — изменения к ним. Учитываются `ADDED`, `MODIFIED`, `REMOVED` и `RENAMED`; сохранённые требования не теряются при применении дельты. Архив не применяется повторно как ожидающее изменение. `proposal`, `design` и `tasks` используются как контекст и не заменяют поведенческие требования; заполненный checklist не доказывает работоспособность. Фактическое состояние baseline и выбранные документы проверяются, а не выводятся только из имени каталога. Источники: [концепции OpenSpec](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md), [стандартная схема](https://github.com/Fission-AI/OpenSpec/blob/main/schemas/spec-driven/schema.yaml), [настройка схем](https://github.com/Fission-AI/OpenSpec/blob/main/docs/customization.md).

Файлы OpenSpec входят в существующий путь authorized context и нормализации требований. Новый универсальный импортёр или промежуточный диалект заранее не создаётся. При нестандартной схеме сначала определяется её реальный контракт; поддержка произвольной схемы не предполагается. Чтение OpenSpec не разрешает выполнять указания из документов, менять спецификации, отмечать tasks или архивировать change.

Ожидаемое поведение берётся из явных требований. Код помогает установить интерфейсы, зависимости и наблюдаемое состояние, но не превращает текущий дефект в норму. Граничные и негативные проверки выводятся из заданных ограничений; отсутствующее бизнес-правило не придумывается. Неопределённое требование остаётся в исходном наборе с предупреждением, а независимые однозначные проверки можно готовить дальше в пределах действующего протокола. При недоказанной независимости остановка остаётся обязательной.

Пользователь получает отчёт о пробелах на основе существующих `warnings` и provenance. Для каждого пробела указаны: требование/сценарий и ссылка на источник; чего именно не хватает; какие проверки это блокирует; какой конкретный вопрос требуется решить. Итог явно отделяет подтверждённое покрытие от неподтверждённого. Существенный неразрешённый пробел не позволяет объявить полное покрытие или завершение всего запрошенного объёма. Известный дефект при однозначном Expected остаётся проверяемым FAIL, а не пробелом спецификации.

## 3. Границы работ

В объём входят: системный Maven; честное завершение сканирования; входы OpenSpec в обоих вариантах объёма и отчёт о пробелах; контролируемые переходы между этапами; обязательные проверки формата ТК; согласованное назначение автотестов; сокращение ручной работы с протоколом; ранняя проверка вместимости и необходимые адресные исправления для Deepseek 0731 Flash; четыре итоговых запуска на одном подготовленном проекте с сопоставлением доступного baseline.

Не входят: второй реестр шагов; параллельные `compact` и legacy-пути; универсальный импортёр OpenSpec; универсальный раннер моделей; новая тестовая инфраструктура; runtime-сборка; рефакторинг `pilot_state.py`; удаление Zephyr или retained rerun; отдельный dev-режим, ослабляющий manifest; новые зависимости целевого проекта. Новый canonical-диалект, компилятор, сегментатор или ревью срезами заранее не проектируются. Если этап 0 докажет, что действующий протокол не позволяет обработать согласованный объём, выполняется минимальное необходимое изменение с сохранением полноты, независимости ревью и происхождения результатов; полный сценарий не исключается из приёмки ради сохранения упаковки протокола.

Сохраняются: независимое ревью, связи требований и проверок, точные байты принятой автоматизации, хэши и повторное чтение артефактов, журнал без переписывания истории, разрешение на запуск в рамках конкретного run, отказ при недоказанных условиях, запрет ремонта после runtime FAIL. `cases-only-v1` остаётся без выполнения проектного кода, с `accepted=false` и существующей exit-семантикой.

Не меняются приложение пользователя и его существующие тесты ради нужного результата. Покрытие требований не сокращается ради уменьшения ответа. Не добавляются минимальная длина кейса, обязательный CRUD-цикл или обязательная передача ID для каждого сценария.

Текущие изменения `README.md`, `USAGE.md`, `QUICKSTART.md` и `docs/research/` принадлежат существующей работе. При реализации их сохраняют; этот план не разрешает reset, массовое staging, commit, push или PR. Необратимые действия требуют отдельного подтверждения кодом по правилам пользователя.

### 3.1. Поддержка менее сильных моделей

Поддержка менее сильной модели реализуется в общем пути: по одному ясному заданию на вызов, обязательные входы конкретной роли, небольшой эталон и точная диагностика ошибки. Требования к покрытию, ожидаемым результатам и ревью остаются общими. Отдельный `compact`-диалект или legacy-путь для этого заранее не создаются.

Целевая модель — доступная пользователю Deepseek 0731 Flash во всех модельных ролях. Генерация и независимое ревью выполняются в отдельных контекстах. До первого прогона фиксируются точные CLI, идентификатор модели в рабочем хосте, настройки, доступные инструменты и объёмы обоих сценариев; пользовательское название не подменяется предположением о версии провайдера. Слабость следования инструкциям, малая вместимость контекста и малый лимит ответа проверяются отдельно. Если хост не сообщает точные токены, используется явно обозначенная оценка; оценку не представляют как измерение.

Контекст каждого вызова включает необходимые инструкции и доказательства; перед ним проверяется бюджет с учётом истории сессии и места на полный ответ. Генерация использует существующие независимые батчи, когда независимость подтверждена; код собирает общий canonical без потери требований и связей. Дробить связанные условия только ради размера или обрезать обязательные входы нельзя. Дополнительные вызовы в той же накопленной истории сами по себе не решают переполнение.

Вместимость полного сценария проверяется в этапе 0 до основной реализации, отдельно для нормализации требований, генерации и независимого ревью. Уменьшение генераторских батчей не гарантирует, что весь результат сможет проверить reviewer. Действующий контракт требует полного candidate в одной независимой reviewer-сессии и запрещает отдельные authoritative reviewers по батчам; несколько запросов доказательств в одной сессии не устраняют предел её контекста. Если этот протокол не позволяет обработать всю выбранную спецификацию, это блокер принятого требования. Выбирается минимальное решение для подтверждённого ограничения, при необходимости с точечным изменением контракта, без потери покрытия, связей между частями и независимого ревью. Успех на небольшом change или сильной модели не закрывает этот блокер.

Восстановление после ошибки использует существующий разрешённый бюджет: короткая диагностика с путём к полю, нарушенным правилом и требуемым исправлением. Повтор не разрешает менять уже принятый артефакт, пропускать ревью или чинить runtime FAIL. Замена любой роли более сильной моделью не допускается в итоговой приёмке. Диагностические эксперименты с другой моделью, если отдельно разрешены, не засчитываются как прохождение Deepseek.

| Генерация и сборка ТК | Все части запланированного набора, единый canonical | Нет потерянных частей; проходят схема, связи и обязательные правила человеческих полей |
| Ревью и публикация ТК | Вердикт независимого reviewer для точной версии | Требования сопоставлены с исходным запросом; выбранная версия и её происхождение проверены |
| Генерация и ревью автотестов | Исходники, связи с кейсами, принятое статическое ревью | Подтверждены нужная граница приложения, проверки фактического результата и точные байты |
| Материализация, запуск и завершение | Проверенные файлы, результаты именно этого запуска, согласованный итог | Запущены принятые тесты; отчёт и завершение привязаны к текущей попытке |

Для `cases-only` маршрут завершается публикацией ТК. Отсутствие инструмента исполнения не является основанием объявлять требования непрочитанными или запрещать подготовку ручных кейсов. Для `local-pilot` отсутствие необходимой среды даёт точную причину остановки, без выдуманного runtime-успеха.

Полный скан означает завершённый учёт файлов согласованной области с причинами исключений, затем содержательное чтение точек входа, проверяемой реализации, связанных компонентов и конфигурации. Чтение расширяется по обнаруженным зависимостям через действующий контроллер и правила актуальности снимка; модель не расширяет область самовольно. Не требуется читать каждый нерелевантный исходник, но непрочитанная необходимая зависимость не позволяет подтвердить завершённость анализа. Перечень файлов сам по себе не доказывает содержательного чтения.

Контроллер получает регламент оркестрации и формирует краткий план конкретного запуска: область, входы, маршрут, результат и условия остановки. Это позволяет обнаружить неверную постановку, но не доказывает внутреннее «понимание» модели. Проверка manifest доказывает целостность пакета, а не чтение моделью текста.

Запись о подготовленном контексте доказывает его состав. Утверждение «точные входы переданы модели без обрезки» допустимо только при подтверждении используемой CLI/хостом; при отсутствии такого подтверждения оно остаётся непроверенным. Самоотчёт модели не заменяет доказательство. Каждый результат всё равно проходит проверки перед принятием.

Переход проверяет сохранённые результаты и их связи с текущими входами. Изменение зависимого входа делает прежнее подтверждение непригодным; продолжение следует существующим правилам resume или новой попытки. Перепроверка не означает повторный полный скан и новый вызов reviewer после каждой команды.

## 5. Порядок реализации и приёмка этапов

Каждый этап — отдельное законченное изменение. Сначала используются существующие проверки. Новая автоматическая регрессия добавляется только для изменённого поведения, которое они не покрывают: максимум один основной путь и при необходимости один ключевой отказ на сфокусированное изменение. Указание тестового файла ниже не требует переписывать весь файл или запускать несвязанные наборы.

### Этап 0. Зафиксировать оба сценария и проверить вместимость до реализации

- [ ] На одном подготовленном проекте сохранить два исходных запроса: вся актуальная спецификация и выбранный change со связанной регрессией. Зафиксировать соответствующие версии требований, кода, конфигурации и тестовых данных, границу приложения, отсутствие wrapper при доступном Maven и полный объём каждого сценария. Отметить, какие материалы доступны только из рассказа пользователя.
- [ ] Проверить действительный контракт OpenSpec и соответствие всего объёма спецификации доступной области кода. Несколько модулей или неучтённые зависимости не разрешают молча сузить запрос; конкретное ограничение текущего маршрута фиксируется до обещания полноты.
- [ ] До изменения поведения зафиксировать доступный baseline на тех же задачах и Deepseek во всех ролях: точные CLI/модель/настройки, правильность формата, уровень тестов, ручные вмешательства, остановки, время, ошибки валидатора и разрешённые повторы. Токены — только если их показывает хост; иначе отдельно обозначенная оценка размера. Название из пересказа не подменяет точный идентификатор модели в доступном CLI.
- [ ] Для полной спецификации проверить обязательные входы каждой роли, размер ответа и полный пакет независимого ревью с учётом истории. Измеренный размер подготовленных пакетов отделить от оценки ещё не созданного результата; ранняя оценка не заменяет проверку фактических пакетов при исполнении. Установить, способен ли рабочий CLI предоставить отдельный контекст reviewer и необходимые инструменты.
- [ ] При подтверждённом ограничении выбрать и описать минимальное исправление на существующей границе, включая точные затронутые файлы, необходимое изменение контракта и адресную проверку. Сначала устранить ограничение для зависимых этапов; не откладывать его до итоговых запусков и не уменьшать объём спецификации. Уже достаточные инструкции и helpers оставить без изменений.
- [ ] Только после подтверждения ограничения вместимости рассмотреть следующие гипотезы наряду с уже доступными средствами; ни одна не считается заранее выбранной или доказанно достаточной:
  - **Вариант A: проекция с запросом фрагментов.** Рассмотреть компактное представление candidate, привязанное к его точной версии, исходные требования и матрицу «условие → кейс → проверка», с получением полного содержимого по ID. Проверить, как протокол обеспечивает рассмотрение всех необходимых частей и связей: доступность фрагмента по запросу не доказывает его проверки. Переиспользовать существующие receipts, digest binding и журнал evidence; получение кейса по ID и reviewer-проекция потребуют адресной реализации, если выбран этот вариант.
  - **Вариант B: ревью по частям с сохранением результатов.** Рассмотреть только при наличии у рабочего хоста подходящих средств управления контекстом. До выбора показать, как сохраняются точные исходные материалы, результаты проверок и условия, необходимые для проверки связей между частями. Сводка находок, матрица покрытия, одна сессия и один verdict сами по себе не доказывают полноту. Возможность освобождать контекст и соответствующий учёт бюджета проверяются на хосте; новые записи реестра и изменения протокола заранее не вводятся.
  - **Критерий выбора:** сохраняются независимое содержательное ревью всех необходимых частей и связей, происхождение результата и итоговый вердикт для точной версии; фактический бюджет вместе с историей и резервом ответа достаточен. Размер контекста — необходимое, но недостаточное условие. Автоматического перехода «A не помещается → B» нет. Выбрать минимальное достаточное изменение для измеренного ограничения, оформить необходимый erratum и проверить на полном реальном пакете. Если достаточность не подтверждена, блокер остаётся открытым; прохождение малого change его не закрывает.
- [ ] Выбрать короткий эталон ТК из разрешённых требований: цель, предусловия, конкретное действие/данные и наблюдаемый Expected. Не придумывать endpoint, код ответа или бизнес-правило рабочего проекта.

Приёмка: есть два воспроизводимых запроса, соответствующие исходные состояния и таблица ожидаемого результата. Ограничения области, модели, входа, выхода и полного ревью установлены настолько, насколько это подтверждают доступные артефакты; оценки явно помечены. Для подтверждённого блокера есть адресное решение и проверка, без объявления поддержки завершённой до реального прохождения. Если старый прогон или доступ к рабочему хосту отсутствует, это явно отмечается; baseline не реконструируется по памяти. Универсальный eval harness и матрица моделей не создаются.

## 6. Общая проверка при реализации

После каждой правки запускаются только относящиеся к ней существующие тесты и необходимые адресные регрессии. Новые framework, каталоги тестовой инфраструктуры, fuzz-корпуса, массовые snapshots и матрицы моделей не добавляются.

Формальные изменения frozen-контракта сначала отражаются в минимальном erratum и машинном контракте. Генерируемые документы и manifest обновляются штатными средствами, а не вручную. После изменения зарегистрированных байтов выполняются `tools.render_contract_docs`, `tools.release_manifest`, затем `tools.contract_check --root . --full`, `tools.render_contract_docs --root . --check` и `tools.doctor --root .`. Проверки целостности не объявляются доказательством качества тестов или релизной готовности. Чтобы не вводить последовательность вручную после каждой правки, допустим локальный скрипт-обёртка вне зарегистрированных файлов пакета: он запускает те же штатные команды в том же порядке и останавливается на первой ошибке. Он не создаёт отдельного режима и не ослабляет проверки manifest. Такая обёртка — необязательное удобство разработчика, не новая часть поставляемого runtime пайплайна.

Команды существующих модулей выполняются из корня пакета через выбранный Python. В текущей Windows-среде проверенный путь: `D:\AI-Projects\.runtime\test-skills-venv\Scripts\python.exe -X utf8 -m ...`. Доступность интерпретатора и зависимостей перепроверяется перед реализацией. Итоговая общая регрессия выполняется один раз после объединения принятых изменений; её повторяют только при новых правках или сбоях. `implemented_unverified` и `ready_tuple=null` сохраняются без отдельной квалификационной кампании.

В этапе 0 уточняются факты рабочего проекта, отсутствующие в текущем контексте: точный CLI/идентификатор Deepseek и доступные лимиты/инструменты/изоляция reviewer; версия и схема OpenSpec, полный набор спецификаций и выбранный change; соответствие требований модулям; существующий способ запуска функциональных тестов (включая Surefire/Failsafe); граница API/MockMvc, конфигурация, авторизация и восстановление тестовых данных. Если проект использует отдельный Maven integration-test lifecycle, нельзя считать адаптер `-Dtest ... test` достаточным: поддержку необходимого запуска нужно адресно добавить и проверить с точными reviewed targets и соответствующими отчётами, без произвольной shell-команды. Она становится частью этапа 2, если нужна пилотному проекту; одной заменой wrapper на `mvn` этот блокер не закрывается.

Эти сведения извлекаются из разрешённого проекта, когда он доступен. Если доступа нет, зависимая приёмка остаётся непроверенной; значения не изобретаются и секреты не запрашиваются для включения в документ.
