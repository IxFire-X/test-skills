Обзор: что это, что умеет, что получилось

Для тех, кто решает, пробовать ли пайплайн у себя. Техническое устройство — во второй части.

1

Что это

test-skills — это пакет из семи «скиллов» (инструкций для модели по ролям) и примерно семидесяти модулей Python, который кладётся в проект на Java…

Подробнее

test-skills — это пакет из семи «скиллов» (инструкций для модели по ролям) и примерно семидесяти модулей Python, который кладётся в проект на Java (Maven или Gradle, JUnit 5 и 6) или Python (pytest). На входе — спецификация в Markdown или OpenSpec и агентный CLI с ИИ-моделью. На выходе — тест-кейсы для людей, автотесты, прошедшие независимое ревью и запуск, измеренная сила тестов, список вопросов аналитикам и набор test-cases/ в проекте, который дальше живёт вместе с кодом.

Первый принцип: ИИ пишет тексты, обычная программа всё проверяет. ИИ-модель пишет только содержание: тест-кейсы, код тестов, замечания ревью. Всё, что можно проверить механически, делает обычная программа без ИИ (в пакете она называется драйвером): нумерует кейсы, связывает их с требованиями и тестами, сверяет каждую ссылку и каждое число в ответе модели с тем, что есть в документе на самом деле, запускает тесты, ведёт журнал. Если модель сослалась на несуществующий кейс или перепутала ожидаемое значение, программа отклоняет ответ и просит переделать. В файлы проекта модель не пишет вообще, это делает программа после проверки. Поэтому прерванный прогон продолжается с того места, где остановился: все промежуточные результаты лежат на диске, а не «в памяти» модели.

Второй принцип: ИИ видит код, но ожидаемый результат берёт из требования. Перед генерацией кейсов отдельный шаг — разметка контекста: ИИ смотрит в отобранные файлы проекта и записывает, какие ручки реально есть, как к приложению обращаются, какие у них параметры, а заодно где требования молчат. Поэтому генератор знает, что ручка существует и как её вызвать, но что должно произойти, берёт из спецификации. Код Petclinic сохраняет визит с явно пустой датой, а требование этого не допускает — кейс ожидает отказ, тест падает, и это реальный дефект V05. Роль, которая пишет автотесты, видит код по-настоящему (ей нужны имена классов и настройка окружения), но ожидания менять не может: каждая проверка несёт свой ID прямо в коде теста, и программа ещё до ревью сверяет значения в проверках теста (код ответа, число, строку) с ожиданием из кейса: в кейсе 400, а в тесте 404 — расхождение уходит ревьюеру как подозрение. Зелёный прогон при таком подходе что-то значит, а красный — повод для вопроса аналитику или баг-репорта, а не для подгонки теста.

Третий принцип: пакет ничего не ставит и не меняет в проекте, кроме тестов и набора. Сборка — штатная, своя для проекта; зависимости, конфигурация и код продукта не трогаются; коммит и pull request делает человек или CI проекта.

QA-инженеру

Аналитику

Список вопросов к спецификации с источником каждого: где требование молчит, где два кейса противоречат друг другу, где мутант выжил, потому что требование не задаёт поведение.

Команде

Что умеет

Восемь вещей, каждая проверена живым прогоном.

Подробнее

Восемь вещей, каждая проверена живым прогоном. Где написано «Petclinic», речь о прогоне 9 октября на Spring Petclinic по спецификации, написанной независимо от кода: 81 кейс, 1285 проверок.

Восемь возможностей — подробно, с проверкой на живых прогонах

Пишет кейсы по спецификации

Markdown или OpenSpec; код режет документ на исходные пункты, у каждого стабильный ключ и хеш текста; каждый пункт покрыт хотя бы одним кейсом. У кейса две стороны: человеческая (цель, шаги, ожидание словами) и машинная (входы, вызов, проверка «статус равен 400»). Экспорт в Zephyr, HTML и Markdown.

Проверено · Petclinic: 81 кейс, 349 шагов, 1285 проверок; step5: 20 кейсов.

Проверяет их независимым ревью

Кейсы читает другой ИИ, который не видел, как они писались: каждая часть документа уходит ему в чистом контексте. Перед ним программа сама помечает подозрительные места — число в проверке не совпадает с текстом ожидания, требование без кейса, два кейса с одинаковым вызовом и разными ожиданиями — и ревьюер обязан ответить на каждое. Его ответ тоже проверяется программой: ссылка на несуществующий кейс или чужой ID — ответ отклонён. Цена ревью растёт с объёмом текста, а не с квадратом числа кейсов.

Проверено · 28 из 28 внесённых дефектов найдены, на чистом документе 0 ложных BLOCKING; Petclinic: 41 + 8 частей, 0 BLOCKING.

Превращает принятые кейсы в автотесты

Один метод на кейс, ID проверки стоит прямо в коде (.as("ASSERT-…")), поэтому программа находит каждую проверку в коде и сверяет её значение с кейсом. Ревью кода смотрит метод теста с вызываемыми им вспомогательными функциями, а не весь файл.

Проверено · Petclinic: 81 метод, 1633 связи «проверка ↔ метод»; step5: 17 методов.

Запускает их штатной сборкой проекта

Maven Wrapper, Gradle Wrapper или pytest; только проверенные методы и только один раз; команда строится из типизированных полей, без строки shell. Исход по каждому методу: PASS, FAIL, UNKNOWN или NOT_RUNNABLE.

Проверено · Petclinic: 81 тест, 1 падение — дефект приложения V05; step5: 17 из 17.

Измеряет силу тестов

Зелёный прогон говорит только, что тесты согласны с текущим поведением кода. Чтобы узнать, ловят ли они баги, пакет запускает мутационное тестирование: инструмент PIT (стандартный для Java, работает на байткоде) по очереди вносит в код продукта мелкие искусственные дефекты — меняет «больше» на «больше или равно», убирает проверку, подменяет возвращаемое значение — и смотрит, упал ли хоть один тест. Упал — дефект «убит», тесты его заметили; не упал — проверка слабая, требование молчит или изменение ничего не меняет по смыслу. Код проекта при этом не трогается: PIT работает с копией в памяти. Инструмент подключается только по согласию, его файлы закреплены по контрольной сумме. Доля считается по кейсу и по требованию; выживших мутантов разбирает модель: пробел в тесте, пробел в требовании или эквивалент.

Проверено · Petclinic: 146 мутантов, 93 убито, test strength 73,8 %; граница длины имени убита. 100 % не цель: из 33 выживших 18 эквивалентны (код ничего не меняет по поведению), 5 — пробелы требований, настоящих слабых проверок 3, по ним есть предложения. Важнее абсолютного значения падение доли по кейсу после правок — это сигнал «тест ослаб».

Собирает вопросы аналитикам

Пробелы требований из разметки, находки ревьюеров о противоречиях и пробелы из разбора выживших сливаются в один отчёт с источником у каждого пункта. Есть экспорт комментария для change в OpenSpec.

Проверено · Petclinic: 47 вопросов; step5: 13.

Оставляет живой набор в проекте

test-cases/ с манифестом: ключи требований, дайджесты методов, статусы. Требование изменилось — переписываются только затронутые кейсы; код переименовали — метод чинится при тех же ожиданиях; поведение изменилось — тест уходит в карантин с вопросом, а не удаляется. Итог — предложение в PR. Без модели работают suite status и suite impact.

Проверено · шесть сценариев на step5; Petclinic: карантин V05 и манифест — да, обновление по изменённому требованию — остановилось на двух находках (раздел 16).

Воспроизводится и проверяется

Журнал событий с цепочкой хешей и квитанции на всё опубликованное; прогон прерывается и продолжается; ответы ролей переносятся в новый прогон и проверяются заново; записи живых прогонов становятся офлайн-тестами планировщика.

Проверено · прогон e доведён до конца на третьем клоне с переносом 52 ответов; 1094 автотеста пакета зелёные.

Модель и CLI. Оркестратором может быть любой агентный CLI, читающий инструкции и файлы (сейчас — Claude Code); режим run --runner process вообще обходится без оркестратора и запускает модель процессом на каждую задачу. Какая ИИ-модель стоит за CLI, пакету безразлично, но по замерам слабые модели роли не держат, поэтому новую модель сначала проверяют на записанных частях ревью, без живого прогона.

3

В чём хорош и в чём слаб

Обе колонки — из отчётов живых прогонов и независимого ревью, а не из описания замысла.

Подробнее

Обе колонки — из отчётов живых прогонов и независимого ревью, а не из описания замысла.

В чём хорош

  • Находит дефекты продукта, а не фиксирует его поведение.V05 в Petclinic пойман как упавший тест, потому что ожидание пришло из требования. Тест отключён одной строкой с причиной, 80 остальных остались зелёными, аналитику ушёл вопрос, команде — черновик баг-репорта.
  • Контроль у программы, не у модели.Каждая ссылка в ответе ревьюера, каждый ID и каждое значение проверяются программой; ответ с неизвестным ID отклоняется и переделывается. Журнал с цепочкой хешей не даёт подменить середину прогона незаметно.
  • Ревью масштабируется.Документ уходит ревьюеру компактным текстом с короткими ID, порциями по группам кейсов, а не по каждой паре, и ответ он даёт по ID, а не пересказом. На 64 кейсах Petclinic было 447 порций и 73 МБ входа, стало 11 и 1,85 МБ при той же находимости: 28 из 28 внесённых дефектов, 0 ложных блокировок на чистом документе.
  • Сила тестов измеряется, а не предполагается.73,8 % покрытых мутантов убиты; из 33 выживших 18 эквивалентны, 5 указывают на молчащее требование, 3 — на слабую проверку. Каждое решение привязано к кейсу и требованию.
  • Ничего не ломает в проекте.Ни зависимостей, ни конфигурации, ни кода продукта; коммит и PR — за человеком. Единственная установка — jar PIT по явному согласию, с проверкой SHA-256.
  • Проверяемость самого пакета.1094 автотеста; 17 из 17 дефектов независимого ревью исправлены за день, каждый с тестом, который падал до исправления; записи живых прогонов стали офлайн-фикстурами. Секретов и ключей в репозитории нет.

В чём пока слаб

  • Ревью большого документа дорого растёт.81 кейс даёт 38 частей по 115–175 КБ: частей столько, сколько пар блоков. На 150–300 кейсах это станет непомерным. Это дефект дизайна, исправление спроектировано и стоит первым в плане.
  • Первый прогон на новом проекте находит дефекты пакета.Petclinic понадобилось пять прогонов, чтобы дойти до конца: добавочные части ревью, часть на 577 КБ, блокировка файла на Windows, лимит командной строки cmd.exe. Каждый дефект стал тестом, но на следующем непохожем проекте будут свои.
  • Разбор выживших мутантов — половина цены прогона.2,07 из 3,84 млн токенов; разборщик не видит полного кода класса, поэтому решение «эквивалентен» опирается на знание вне входа.
  • Живой набор вживую не доведён.Обновление по изменённому требованию на Petclinic точно нашло затронутые кейсы и прошло ревью за 2 % байт полного, но остановилось: состояние прогона внутри дерева проекта валит проверку nohttp, а проверка ревьюера на неизменённые кейсы незакрываема.
  • Качество кейсов генератора — среднее.Скопированные действия между соседними кейсами, ожидания снимков шире проверок, порядок полей строже требования. Ревью ловит часть; независимая оценка кейсов по рубрике ещё не делалась.
  • Нужна достаточно сильная ИИ-модель и один оркестратор.Слабые модели по замерам не держат ни одну роль; автоматизация идёт одной задачей на весь документ (2,35 МБ); изоляция ревьюера без раннера процессов доказана только словами хоста. Статус пакета — implemented_unverified.

7

Цикл драйвера: next, submit и wait

Оркестратор не держит в голове последовательность шагов.

Подробнее

Оркестратор не держит в голове последовательность шагов. Он вызывает next, и драйвер сам проходит всё детерминированное, пока не упрётся в работу для модели или вопрос для человека. Тогда он отдаёт задачу: какой SKILL читать, какие файлы на входе, по какой схеме писать ответ и куда его положить. С --max-tasks K драйвер отдаёт пачку до K независимых частей ревью для параллельных субагентов.

Модель пишет ответ и вызывает submit. Драйвер проверяет его по схеме и смыслу: в ревью ещё и каждую ссылку на якорь, и ответ на каждое подозрение линтера. Если что-то не так, он возвращает ту же задачу со списком ошибок. Если всё хорошо, публикует результат, читает его обратно и выдаёт следующую задачу.

Если части ревью выполняет сам драйвер (--review-runner process), next не ждёт модель: запускает процессы в фоне, возвращает действие wait с числом секунд, а следующий next собирает готовые ответы. Команда run --runner process делает то же для всех задач модели и доводит прогон до итога без оркестратора; ответы на вопросы человеку берёт из --answer. Команда CLI задаётся шаблоном, поэтому вместо claude или codex может стоять любая обёртка, которая читает задачу со стандартного ввода и пишет ответ в файл.

Сколько это стоит по времени: на Petclinic (81 кейс, 41 часть ревью) next занимает в медиане 13 с, submit — 9 с; выбросы — открытие пачки частей (80 с), компиляция сгенерированного класса (80 с) и последняя подача, за которой идут запуск тестов и PIT (6 мин). До исправлений 8 октября те же команды держали оркестратора по 52–195 с: проверка плана ревью пересчитывалась на каждом вызове, теперь она кэшируется по дайджесту (47 частей: 33,6 с → 3,9 с).

Один документ — источник смысла

Всё, что пайплайн знает о кейсах, лежит в одном JSON: TCDOC-…r1.json.

Подробнее

Всё, что пайплайн знает о кейсах, лежит в одном JSON: TCDOC-…r1.json. Markdown, HTML и CSV для Zephyr строятся из него и обратно в работу не идут. Генератор автотестов тоже получает только этот JSON.

У каждого кейса две стороны. Человеческая: цель, предусловия, шаги, текст ожидания. Машинная: входы шага, вызываемая «возможность» и проверки вида «статус равен 400». Ревью следит, чтобы обе стороны говорили одно и то же.

С волны 3 у каждого исходного пункта есть ещё ключ и хеш собственного текста: в OpenSpec — capability и имя requirement, в Markdown — явный ID (встроенный REQ-7, AC-3 или шаблон проекта вроде [OPVX]\d\d\.), иначе путь файла и цепочка заголовков. Номер SREQ-NNNN остаётся позиционным, а набор связывает кейсы с требованиями по ключам, поэтому вставка раздела в середину документа чужие связи не рвёт.

Ревью по частям: compact-v1 волна 1

Раньше ревьюер получал область на каждую пару кейсов, и цена ревью росла с квадратом числа кейсов: 64 кейса Petclinic давали около 300 частей.

Подробнее

Раньше ревьюер получал область на каждую пару кейсов, и цена ревью росла с квадратом числа кейсов: 64 кейса Petclinic давали около 300 частей. Теперь цена растёт с объёмом содержимого.

Драйвер строит из канона проекцию: детерминированный текст, где у каждого ID ровно один якорь вида [TC-B1-006]. Кейсы делятся на блоки с границами по содержимому, и если всё помещается в одну часть, ревью идёт одной частью; иначе каждая часть — пара блоков, у каждого кейса одна «домашняя» часть. Ревью автотестов получает не весь файл, а срез метода с его хелперами; общий код, фикстуры и таблица общего состояния лежат в области SUPPORT.

До модели работает линтер: ищет литерал проверки, не совпадающий с текстом ожидания, требование без кейса, одинаковый вызов с разными ожиданиями, проверку количества при общем состоянии. Он выдаёт только подозрения, и ревьюер обязан ответить на каждое. Ответ короткий: строка покрытия на область с 1–3 ссылками на якоря, находки до 600 символов, правки по ID и полю из закрытого словаря. Драйвер проверяет каждую ссылку: несуществующий якорь или якорь чужого кейса — ответ отклонён.

Ревьюер может попросить дополнительную проверку (required_checks): например, сверить кейсы с исходным текстом требования, которого в его части не было. Живой Petclinic показал, как это выходит из-под контроля: 38 основных частей породили 58 добавочных, по одной за раз. С 8 октября действует политика merged-after-base-v1: добавочные части выдаются только после всех основных, сливаются по набору кейсов, пакуются в бюджет и уходят пачкой; их не больше четверти основных, сверх — REVIEW_CHECK_LIMIT и ревью неполное. Просьба «проверить все требования» не раскрывается во все кейсы: это предупреждение и вопрос аналитику. На тех же ответах добавочных частей стало 3 вместо 58.

Что осталось: частей столько, сколько пар блоков, поэтому 81 кейс даёт 9 блоков и 38 частей по 115–175 КБ — 6,2 МБ входа при документе в 1,9 МБ. Это дефект дизайна, а не реализации; исправление — cross-части только для кейсов с общим требованием, возможностью или эндпоинтом — записано в план.

Сила тестов: мутации, разбор выживших, вопросы аналитикам волна 2

Зелёный прогон говорит только одно: тесты совпадают с текущим поведением приложения.

Подробнее

Зелёный прогон говорит только одно: тесты совпадают с текущим поведением приложения. Чтобы узнать, ловят ли они баги, пакет по опции --mutation запускает PIT: вносит в код продукта мелкие дефекты (мутанты) и смотрит, падают ли тесты. Убитый мутант — тест заметил подделку; выживший — проверка слабая, или требование молчит, или мутант ничего не меняет.

Этап стоит между трассой исполнения и решением о судьбе файлов, когда тесты ещё в проекте, и работает даже после FAIL: мутируется только то, что проверяют прошедшие методы. Нужны два согласия — mutation.enabled: true в .skillsrc и флаг прогона. Независимое ревью 8 октября нашло 17 подтверждённых дефектов в коде волн 2 и 3 — все 17 исправлены в тот же день, каждый с тестом, который падал до исправления (docs/review/2026-10-08-review-fixes-report.md, +75 тестов). Пять живых прогонов Petclinic нашли ещё 9 дефектов пакета, тоже исправленных с фикстурами повтора. Ниже то, что остаётся открытым и что стоит знать, пользуясь схемами выше.

  1. 1
    Cross-части растут с квадратом числа блоков
    81 кейс — 9 блоков — 38 основных частей по 115–175 КБ. На документе в 150–300 кейсов ревью станет непомерно дорогим. Исправление спроектировано (cross только по общему требованию, возможности или эндпоинту), гейт — частей не больше 1,5 × число блоков на синтетике 150 кейсов.
  2. 2
    Состояние прогона внутри дерева проекта
    .pilot-runs/ лежит в проекте; вывод упавшей сборки в нём содержит строку с http-адресом и валит проверку nohttp самого Petclinic при любой следующей сборке. Это остановило первый живой suite-update-v1. Где хранить состояние — решение пользователя.
  3. 3
    Проверка ревьюера на неизменённые кейсы незакрываема в обновлении
    План ревью обновления содержит только изменённые кейсы; просьба свериться с неизменёнными оставляет область UNCHECKED, агрегат неполон, обновление не применяется. Нужна часть проверки с неизменёнными кейсами как контекстом.
  4. 4
    Разбор выживших дорог и слеп
    26 задач по одной группе — 2,07 млн токенов, больше половины прогона. Разборщик не видит полного кода мутируемого класса и вызывающего кода, поэтому решение EQUIVALENT опирается на знание вне входа.
  5. 5
    Сбой окружения выглядит как плохие тесты
    Падение фазы validate сборки (окружение, проверки проекта) классифицируется как GENERATED_TEST_INVALID с предложением перегенерировать тесты.
  6. 6
    Лимиты командной строки Windows
    Селекторы методов теперь группируются по классу (Класс#m1+m2, 2726 символов вместо 8414), но рост линейный: класс на 200+ методов снова упрётся в 8191 символ cmd.exe; Gradle на Windows — примерно на 90 методах.
  7. 7
    Изоляция ревьюера доказана только словами хоста
    Пока части ревью идут субагентами, уровень — HOST_DECLARED. DRIVER_PROCESS даёт только раннер процессов, и с настоящим CLI он ещё не прогонялся; против пользователя своей машины уровень в любом случае не сильнее HOST_DECLARED.
  8. 8
    Качество кейсов генератора
    Действие V06-03/04 скопировано из V06-01 (ревью поймало как WARNING), ожидания снимков шире проверок, порядок полей формы строже требования, изоляция только в предусловии. Отдельная оценка кейсов «извне» по рубрике ещё не делалась.
  9. 9
    Одна задача на весь документ
    Автоматизация идёт одной задачей модели на все 81 кейс (2,35 МБ входа), а обновление несёт весь документ набора ради двух кейсов. На больших проектах это упрётся в окно модели.
  10. 10
    Нужна достаточно сильная модель
    По E5 Haiku 4.5 не держит ни одну роль. Как поведут себя другие модели того же класса, не проверялось: бенчмарк на записанных частях ревью — следующий шаг перед переносом на другую инфраструктуру.

Ещё не сделано: RealWorld (Gradle) живьём; Python-мутации; Gradle и pytest в живом наборе проверены только механикой; сравнение с дешёвым эталоном (одна сессия пишет тесты по той же спецификации + PIT). Статус пакета по-прежнему implemented_unverified; снимать его — решение пользователя после живого Petclinic.

Часть ревью, которую драйвер создаёт по просьбе ревьюера (required_checks) после всех основных: слитая по набору кейсов, упакованная в бюджет, не больше четверти основных.
Фикстуры повтора
Записи живого прогона (снимок канона, ответы ролей), по которым планировщик и проверки драйвера гоняются офлайн, без модели. Каждый дефект живого прогона становится таким тестом.
Перенос ответов
Повтор прогона на новом клоне проекта с принятыми ответами прошлого прогона: задача сверяется с источником по файлу, схеме и входам, submit проверяет каждый ответ заново. Сейчас — скриптами оркестратора, в плане — в драйвере.
Срез, SUPPORT
Срез — метод кейса с хелперами, которые он вызывает. SUPPORT — общий код файла: фикстуры, хелперы, таблица общего состояния.
Линтер
Код, который до модели находит подозрительные места; ревьюер обязан ответить на каждое подозрение.
Раннер процессов
Опция, при которой драйвер сам запускает claude -p или codex exec на часть ревью или на любую задачу модели (run).
isolation_evidence
Насколько доказана изоляция ревьюера: процесс драйвера, слова хоста или ничего.
Мутант, test_strength
Мелкий дефект, внесённый PIT в код продукта. Доля убитых мутантов — ось итога, отдельная от verification и accepted.
Разбор выживших
Задача модели после итога: для каждой группы выживших мутантов решить TEST_GAP, SPEC_GAP, EQUIVALENT или OUT_OF_SCOPE.
Отчёт для аналитиков
Пробелы требований и вопросы ревьюеров и разбора, собранные в один документ с источниками.
Набор, манифест
Каталог test-cases/ в проекте с каноном, проекциями и манифестом: ключи, дайджесты, статусы, доли мутантов, снимок эндпоинтов.
Карантин
Пометка упавшего метода @Disabled или xfail(strict=True) с причиной вместо удаления файла; карантинные тесты запускаются явно, чтобы увидеть исправление.
Обновление, ремонт
Режимы генераторов в suite-update-v1: обновление переписывает кейсы вслед за требованием, ремонт чинит метод при неизменных кейсе и требовании, не меняя ожиданий.
Квитанция (receipt)
JSON с хешами опубликованного, по которому позже проверяют, что ничего не подменили.
Трасса
Связи требование → кейс → проверка → метод теста → результат запуска.
