# Переносимый пайплайн: что сделано и зачем применять

Пакет помогает пройти от документа требований до проверенных тест-кейсов и, при выборе полного профиля, до автотестов и их выполнения в проекте. Смысл результата можно проследить по связи «требование — кейс — метод теста — отчёт». Текущий статус — пилот: `implemented_unverified`, `ready_tuple=null`.

## Что реализовано

- Шесть скиллов: координация, подготовка контекста, генерация кейсов, их отдельное ревью, генерация автотестов и отдельное статическое ревью кода.
- Профиль `cases-only-v1` для документации тестирования и `local-pilot-v1` для продолжения до исполнения.
- Canonical JSON как источник смысла тест-кейсов. HTML и Markdown для чтения, CSV для выгрузки строятся из него. XML остаётся опциональным экспортом для Zephyr.
- Явные требования к совместимой CLI: чтение инструкций и артефактов, отдельный вызов ревьюера, сохранение результатов и продолжение работы по состоянию.
- Исполнение выбранных проверенных целей штатными pytest, Maven wrapper или Gradle wrapper проекта.
- Учёт собственных сгенерированных файлов, сохранение исходных отчётов, контрольных сумм, истории попытки и связей между артефактами.
- Раздельный итог: состояние процесса, результат проверок, покрытие и вычисленное принятие.

Модель выполняет содержательную работу через совместимую CLI. Python-инструменты проверяют форматы, целостность и допустимость операций. Они не являются отдельным универсальным сервисом управления LLM.

| `skills/autotest-reviewer/` | Статическое ревью автоматизации до запуска |

| `schemas/` | Форматы документов, результатов и свидетельств операций |

## Почему стоит попробовать

**Проверка до исполнения.** Отдельное ревью даёт возможность обнаружить слабый сценарий или несоответствие автоматизации до запуска. Отдельный вызов не устраняет все ошибки модели, но делает проверку явным этапом с собственным результатом.

**Разбираемый результат.** Команда может проверить, какое требование породило кейс, какой метод его реализовал и откуда взялся статус. Это полезно при разборе дефектов и повторном ревью.

**Работа средствами проекта.** Пакет подключается целиком в проект, а тесты выполняются через выбранный штатный инструмент. Для пилота не требуется внедрять отдельный удалённый runner. Рабочее окружение и совместимая CLI нужны заранее.

**Два масштаба применения.** Можно остановиться на качественных кейсах, если автоматизация не нужна, либо продолжить до проверяемого исполнения.

Это основания для практического испытания, а не доказательство превосходства над альтернативами. Экономия времени, денег и количества ошибок пока не измерена сравнительным экспериментом.

## Где польза наиболее вероятна

У команды регулярно появляются фичи с понятными требованиями. Есть подготовленный тестовый проект, а результаты нужно независимо ревьюить и связывать с требованиями. Особенно полезно, когда документация тестирования и код тестов должны сохранять один смысл.

Для единичной простой проверки весь процесс может стоить дороже ручного теста. Нечёткие требования, отсутствие исполняемого окружения или неподдерживаемый адаптер сначала требуют отдельной работы. Пакет не создаёт песочницу и не подменяет решение команды о корректности продукта.

## Что доказано на практике

В большом пилоте на Spring Petclinic выполнены 64 метода: 63 прошли, один выявил нарушение требования V05 о пустой дате визита. Финализация корректно сохранила `FAIL`, а не скрыла дефект за фактом завершения процесса. Подробности, контрольные суммы и границы свидетельств: [pilot-evidence.md](pilot-evidence.md).

После уточнения инструкций полный набор из 64 кейсов повторно сгенерирован и принят независимым ревью; автотесты повторно не запускались. Полная квалификация текущего пакета, переносимость во всех окружениях и реальный Zephyr XML import/re-export ещё не подтверждены.

## Как принять решение в команде

Выбрать одну репрезентативную фичу и до запуска согласовать критерии: понятность кейсов независимому QA, сохранение ключевых условий, соответствие кода кейсам и воспроизводимость результата. Записать фактические время, стоимость, ручные исправления и ложные срабатывания. По этим данным решить, где пайплайн полезен и что нужно поправить.
